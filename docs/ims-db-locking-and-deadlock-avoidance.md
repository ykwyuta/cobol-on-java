## 1. なぜ IMS DB を RDB 化するとロック競合が起きやすいのか？

メインフレームの IMS は、**IRLM (Internal Resource Lock Manager)** という専用の超高速ロックマネージャを備えており、「セグメントレベル」または「ブロックレベル」で非常に細かい粒度のラッチ/ロックを行います。

一方、汎用 RDB（PostgreSQL / Db2）上に [docs/ims-rdb-storage-engine-report.md](ims-rdb-storage-engine-report.md) の非正規化スキーマ（`IMS_SEGMENT_STORE`）を構築した場合、以下の理由で**ロック競合・デッドロックが発生しやすくなるリスク**があります。

1. **インデックスの局所集中（B-Tree ページのホットスポット）**:
   - すべてのセグメントが同一のテーブル `IMS_SEGMENT_STORE` に集約され、主キーが `(DBD_NAME, ROOT_KEY_RAW, HIERARCHY_PATH)` となるため、同一 DBD への並行 INSERT がインデックスの同一ページで競合しやすい。
2. **階層ツリー更新時のロック順序の不一致によるデッドロック**:
   - ジョブ A が「ルート取得 → 子 A 更新 → 子 B 更新」の順で処理している裏で、ジョブ B が「子 B 更新 → 子 A 更新」または「別のアプローチで木を探索」した場合に、RDB の行ロック同士が交差してデッドロック（SQLState 40P01 / 40001）が発生する。
3. **カスケード削除 (`DLET`) による広範な範囲ロック**:
   - `DLET` は親セグメントだけでなく配下の子孫すべて（`WHERE HIERARCHY_PATH LIKE '/parent/%'`）を削除するため、PostgreSQL の述語ロック（Predicate Lock）や Db2 の次キーロック（Next-Key Lock）が広範囲にかかり、無関係なトランザクションをブロックする。
4. **バッチ処理（大量件数更新）とオンライン処理の衝突**:
   - 数十万件の `ISRT` や `REPL` を行う夜間バッチが動いている最中に、MPP オンライン処理が同じ DBD にアクセスするとロック待ちタイムアウトが発生する。

## 2. ロック競合を回避するための 5 つの対策方式

本プロジェクトにおいて、COBOL のプログラム意味論（`CBLTDLI`）を壊さずに RDB 側のロック競合を最小化するための具体的な対策を以下に設計・提案します。

```
+-----------------------------------------------------------------------------------+
| IMS DB ロック競合回避アーキテクチャ                                               |
|                                                                                   |
|  [ 対策 1: ルートアンカーロック (Root-Level Coarse Locking) ]                    |
|    - 木構造の更新前に必ずルートキー（IMS_ROOT_INDEX）を行ロックし、順序を直列化   |
|                                                                                   |
|  [ 対策 2: MVCC (多版並行性制御) による「読み取りは書き込みをブロックしない」]    |
|    - GU/GN は FOR UPDATE をかけず Snapshot Read。GHU/GHN のみ意図ロックを予約    |
|                                                                                   |
|  [ 対策 3: 階層順序ソート (Ordered DML Buffer) ]                                 |
|    - トランザクション内の INSERT/UPDATE/DELETE を HIERARCHY_PATH 順にソート実行   |
|                                                                                   |
|  [ 対策 4: DBD 単位の物理テーブル分離 (Table-per-DBD Partitioning) ]             |
|    - 1つの巨大テーブルではなく、DBD ごとにテーブルを分離して競合ドメインを局所化 |
|                                                                                   |
|  [ 対策 5: PROCOPT (処理オプション) に基づく分離レベルの動的制御 ]               |
|    - 参照専用 (PROCOPT=G) は Read Committed / ロックフリーで実行                 |
+-----------------------------------------------------------------------------------+
```

---

### 対策 1: ルートアンカーロック（Root-Level Coarse Locking）
**【最も効果的なデッドロック防止策】**

階層型 DB において、木構造の内部（子セグメント、孫セグメント）で細かく行ロックを獲り合うと、ロック獲得順序の違いから容易にデッドロックが発生します。

これを防ぐため、**「あるルートキー（木全体）を更新するトランザクションは、まず最初にルートセグメント（または `IMS_ROOT_INDEX`）の該当 1 行を排他ロックする」** というルールをランタイム側で徹底します。

```sql
-- 子セグメントを更新・挿入・削除する前に、必ず木全体の代表行をロックする
SELECT ROOT_KEY_RAW 
  FROM IMS_ROOT_INDEX
 WHERE DBD_NAME = :dbd AND ROOT_KEY_RAW = :root_key
   FOR UPDATE;
```

- **効果**:
  - 同一のルートキー（例: 顧客 10001 の全データ）に対する複数プロセスの更新は、**入り口（ルート）で確実にキューイング（直列化）** されます。
  - 木の内部で子セグメント同士のロック順序が交差することが物理的に不可能になり、**同一ルート配下のデッドロックが原理的に 100% 撲滅** されます。
  - 異なるルートキー（顧客 10001 と 顧客 10002）は完全に独立して並行実行できるため、スループットを損ないません。

---

### 対策 2: MVCC（多版並行性制御）の徹底活用
PostgreSQL および Db2 は、MVCC（Multi-Version Concurrency Control）をサポートしています。

1. **通常の検索（`GU`, `GN`, `GNP`）は一切ロックを獲らない**:
   - `SELECT ...` を実行する際、`FOR UPDATE` や共有ロック（`LOCK IN SHARE MODE`）をかけず、スナップショット参照（Read Committed / Repeatable Read）とします。
   - **「参照処理（読込）は更新処理をブロックせず、更新処理も参照処理をブロックしない」** 状態を保ちます。
2. **保持付き検索（`GHU`, `GHN`, `GHNP`: Get Hold ...）の扱い**:
   - COBOL が `GHU`（更新前提の読込）を呼んだ場合のみ、対象行（またはルート行）に対して `FOR UPDATE` を発行します。
   - これにより、読込専用の大量参照バッチが更新トランザクションを巻き込んで待たせることがなくなります。

---

### 対策 3: DML 遅延バッファリングと辞書順ソート（Ordered Execution）
COBOL プログラムがループ内で複数の `ISRT`（挿入）や `REPL`（置換）を呼ぶ場合、都度 SQL を発行するのではなく、**コミット時（またはチェックポイント時）まで DML 操作を内部メモリにバッファリング** します。

そして、実際に RDB へ発行する直前に、DML を **`HIERARCHY_PATH ASC`（階層パスの辞書順）でソート** して順番に発行します。

```
[COBOL の呼出し順]         [ランタイムのソート後発行順]
  1. ISRT /001/02-005       --> 1. ISRT /001/01-001  (昇順)
  2. ISRT /001/01-001       --> 2. ISRT /001/02-005  (昇順)
  3. REPL /001/01-002       --> 3. REPL /001/01-002  (昇順)
```

- **効果**:
  - すべての並行トランザクションが、全く同一の物理的順序（昇順）で行ロックを獲得していくため、複数行更新時における循環待ちデッドロックが発生しなくなります。

---

### 対策 4: DBD 単位の物理テーブル分離（Table-per-DBD）
[docs/ims-rdb-storage-engine-report.md](ims-rdb-storage-engine-report.md) の基本設計では単一の `IMS_SEGMENT_STORE` を例示しましたが、本番運用や高負荷環境では **DBD ごとにテーブルを物理分割（またはパーティショニング）** します。

```sql
-- 顧客DB専用テーブル
CREATE TABLE IMS_SEG_CUSTDBD ( ... ) PARTITION BY HASH (ROOT_KEY_RAW);

-- 商品DB専用テーブル
CREATE TABLE IMS_SEG_ITEMDBD ( ... );
```

- **効果**:
  - `CUSTDBD` の大量更新と `ITEMDBD` の更新が、同一のインデックス木（B-Tree ページ）を取り合う競合（ラッチ競合）が完全にゼロになります。
  - さらに、PostgreSQL や Db2 のテーブルパーティショニング（ハッシュ分割）を併用することで、同一 DBD 内でも異なるルートキー同士の物理 I/O 競合を分散できます。

---

### 対策 5: PSB の `PROCOPT` に基づく接続・トランザクション最適化
メインフレームの PSB（プログラム仕様ブロック）には、各 DB に対してどのような意図でアクセスするかを表す **`PROCOPT` (Processing Option)** が明記されています。

| `PROCOPT` 指定 | 意味 | RDB 側での最適化アクション |
| :--- | :--- | :--- |
| **`G`** (Get) | 参照専用 (Read Only) | - JDBC 接続を `readOnly = true` に設定。<br>- トランザクション分離レベルを `READ COMMITTED` (MVCC) に固定し、一切のロックを抑止。<br>- 不要な Undo/Redo ログのオーバーヘッドを削減。 |
| **`I` / `R` / `D`** | 挿入 / 置換 / 削除 | - 通常の更新トランザクション。対策 1（ルートアンカーロック）を適用。 |
| **`E`** (Exclusive) | **排他実行** (他ジョブの同時実行を拒絶) | - 対象 DBD のテーブル全体に対して `LOCK TABLE ... IN EXCLUSIVE MODE` を獲得。<br>- 行ロックのオーバーヘッドを無くし、バッチ一括処理を最速で完走させる。 |

ランタイム起動時に PSB 定義を読み取り、`PROCOPT` に応じて JDBC の接続プロパティやロック獲得戦略を自動で切り替えます。

## 3. デッドロック発生時のフェイルセーフ設計

どれほど対策を施しても、予期せぬ競合により RDB 側でデッドロック検知（PostgreSQL: `40P01`, Db2: `-911 / SQLState 40001`）が発生する可能性はゼロにはできません。

メインフレームの IMS においても、競合時には **擬似 ABEND `U0777`（デッドロックによる強制終了と自動再試行）** が発生します。

### 3.1 `U0777` 擬似 ABEND と自動リトライ機構
1. **ランタイムでの捕捉**:
   - `cobol-ims` の JDBC アダプタが `SQLException` のエラーコード（`40001`, `-911` 等）を検知。
2. **自動リトライ（MPP オンラインの場合）**:
   - トランザクション開始時点（電文デキュー直後）までロールバックし、ランダムなバックオフ（指数待機）を挟んで、**最大 3 回まで同一メッセージの処理を自動再試行** する（メインフレーム IMS TM の標準挙動に準拠）。
3. **バッチジョブの場合**:
   - 自動リトライ不能な場合は、メインフレームと同一の **`ABEND U0777`** を発生させ、ジョブステップを安全に異常終了させる（[設計文書 90](design/90-job.md) の異常終了処理機構と連携）。

## 4. 推奨する実装構成まとめ

| 対策項目 | 推奨設定 / 実装方針 |
| :--- | :--- |
| **デッドロック防止の主軸** | **対策 1（ルートアンカーロック）**: ルートキー単位で直列化 |
| **検索スループット維持** | **対策 2（MVCC）**: 通常の `GU`/`GN` はノーロック検索 |
| **複数行更新の安全性** | **対策 3（DML 昇順ソート）**: `HIERARCHY_PATH ASC` で発行 |
| **負荷分散** | **対策 4（Table-per-DBD）**: DBD 単位で物理テーブルを分離 |
| **PSB 定義の活用** | **対策 5（PROCOPT 最適化）**: 参照専用 (`PROCOPT=G`) は `readOnly` 接続 |
| **例外時の救済** | **3.1（U0777 自動リトライ）**: デッドロック時はトランザクション再試行 |

この多層防御アプローチをとることで、メインフレームと同等以上の同時実行性能を保ちながら、RDB バックエンド特有のロック競合とデッドロックを確実に抑え込むことができます。
