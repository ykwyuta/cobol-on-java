## 1. はじめに：MFS と BMS の本質的な違い

CICS の画面制御である **BMS (Basic Mapping Support)** については、[ADR-0010](../decisions/0010-bms-thymeleaf-terminal-ui.md) において「中立な `BmsScreenModel` を構築し、Spring Boot (Thymeleaf + CSS Grid + 端末エミュレーション JS) でブラウザ上に 3270 画面を再現する」という方針が決定されている（**未実装**）。

MFS に対しても同様のアプローチを検討するが、そのためには BMS と MFS の設計思想の違いを認識する必要がある。

### 1.1 BMS と MFS の比較

| 観点 | CICS: BMS | IMS TM: MFS |
| :--- | :--- | :--- |
| **主な目的** | 画面のレイアウト定義と COBOL レコードの相互マッピング | 端末画面だけでなく、**「外部電文」と「COBOL 入出力領域」のデータフォーマッティング** |
| **定義の構造** | **1対1**<br>`DFHMSD` ⊃ `DFHMDI` ⊃ `DFHMDF` | **2層構造（メッセージ層とデバイス層の分離）**<br>- **MSG 側**: `MSG` / `LPAGE` / `MFLD`<br>- **DEV 側**: `DEV` / `DPAGE` / `DFLD` |
| **COBOL 側の記述** | `EXEC CICS SEND MAP(...)` / `RECEIVE MAP(...)` | **プログラム側に画面操作コマンドが一切現れない。**`CALL 'CBLTDLI' USING 'GU  ', IO-PCB, IN-BUFFER` を呼ぶだけ |
| **画面制御のトリガー** | COBOL が能動的に「このマップを表示する」と指示 | **IMS 制御領域（MFS エンジン）が背後で自動フォーマット** |
| **ページネーション** | アプリケーションが制御 | MFS 自身が**オペレータ論理ページング**を持ち、ページ送りを自動処理 |

## 2. BMS 類似方針を MFS に適用したアーキテクチャ

```
[ ブラウザ (3270 端末エミュレーション UI: CSS Grid + JS) ]
          |
          | (1) HTTP POST (入力フィールド値, AIDキー, カーソル位置)
          v
+-------------------------------------------------------------------------+
| `cobol-ims-mfs` (MFS 中立フォーマッタ層)                                |
|   1. 入力メッセージフォーマット (DIF/MID)                               |
|      - 入力値 (DFLD) を MFS ルールに従って MFLD へ転記                  |
|      - 充填 (FILL)、寄せ (JUST)、パディング                             |
|      - PFK= によるリテラル置換 (4.2 節)                                 |
|      - COBOL 用の生バイトバッファを生成                                 |
|   2. キューへの電文格納                                                 |
+-------------------------------------------------------------------------+
          |
          | (2) CALL 'CBLTDLI' (GU) でデキュー
          v
+-------------------------------------------------------------------------+
| COBOL 業務プログラム (MPP)                                              |
|   - プログラムは MFS や画面の存在を意識せず純粋な電文として処理         |
+-------------------------------------------------------------------------+
          |
          | (3) CALL 'CBLTDLI' (ISRT) でエンキュー
          v
+-------------------------------------------------------------------------+
| `cobol-ims-mfs`                                                         |
|   3. 出力メッセージフォーマット (DOF/MOD)                               |
|      - MFLD を 物理画面フィールド (DFLD) へ展開                         |
|      - 色・輝度・保護属性・カーソル初期位置の決定                       |
|      - 中立な `MfsScreenModel` の構築                                   |
+-------------------------------------------------------------------------+
          |
          | (4) Thymeleaf + CSS Grid で HTML レンダリング
          v
[ ブラウザ ]
```

## 3. BMS と共通化できる可能性がある部分

**以下は「共通化できるはずだ」という見込みであって、測った結果ではない。**BMS が実装され、MFS を実際に当ててみるまで、流用可能な範囲は分からない。

1. **共通端末 UI レイヤ（ブラウザ側）**:
   - **CSS Grid 固定セル配置**: 3270 の 24行×80桁（または 32×80、43×80）の固定グリッド描画。画面サイズの扱いは共通化できる見込み。
   - **JavaScript 端末ステートマシン**: カーソル移動、Tab/Backtab、Insert/Overwrite、MDT、PF/PA キー、Enter キーハンドリング。**ただし MFS 固有の機構（`PFK=` のリテラル置換など）は BMS に無いため、そのままでは足りない**（4.2 節）。
2. **中立画面モデルの共通化**:
   - 行・桁、属性（PROTECTED, NUMERIC, BRT, NORM, DRK）、色、下線、初期カーソル位置を保持する中立データ構造は、`BmsScreenModel` と `MfsScreenModel` で共通の基盤インタフェース（例: `TerminalScreenModel`）に統合できる見込み。
3. **Thymeleaf 共通テンプレート**: HTML レンダリング部分は共用できる見込み。

## 4. MFS 固有の難しさと追加で必要になる実装

### 4.1 MFS マクロ構文のパース（DIF / DOF / MID / MOD）

BMS が単一のマップ定義であるのに対し、MFS は**メッセージ定義（MID/MOD）**と**デバイス定義（DIF/DOF）**の 2 系統をパースする必要がある。

```assembler
* --- デバイス側定義 (DIF / DOF: 3270画面上の位置) ---
CUSTDEV  DEV   TYPE=(3270,2),FEAT=IGNORE
CUSTDPG  DPAGE
DF1      DFLD  'CUSTOMER ID:',POS=(3,5)
DF2      DFLD  POS=(3,20),LTH=8,ATTR=(NUM,PROT)

* --- メッセージ側定義 (MID / MOD: COBOLバッファ上の位置) ---
CUSTMID  MSG   TYPE=INPUT,SOR=(CUSTDEV,START)
CUSTSEG  SEG
MF1      MFLD  DF2,LTH=8               <-- 画面の DF2 を COBOL の先頭8バイトへマップ
         MSGEND
```

**対応**: MFS マクロのパーサを実装し、「画面上の `DFLD`」と「COBOL バッファ上の `MFLD`」の間の双方向バイトオフセット変換マップをビルド時に生成する。

### 4.2 MFS 固有機構【改訂で追加】

改訂前は「マクロのパース」「MOD 名の解決」「論理ページング」の 3 つだけを追加項目としていたが、他にもある。**これらが「BMS + パーサ」で済むという見立てを弱める。**

| 機構 | 内容 | BMS との差 |
| --- | --- | --- |
| **`PFK=` によるリテラル置換** | PF キーの押下で、あらかじめ定義したリテラルが電文へ挿入される | **BMS に無い。**サーバ側の入力構築規則が変わる |
| **`DPAGE` の `COND=`** | 入力内容によってデバイスページを選び分ける | BMS に無い |
| **`MFLD` のリテラル / システムリテラル** | 日付・時刻・LTERM 名等の自動埋め込み | BMS の初期値とは別機構 |
| **`FILL=` / `JUST=`** | 充填文字と寄せの規則 | 規則の定義が要る |
| **`EXIT=`** | フォーマット出口ルーチン | 対応不可。**L0** |
| **MFS バイパス** | MFS を通さない生の 3270 データストリーム | 別経路 |
| **DFS メッセージ** | システムメッセージの画面出力 | 別経路 |

マクロ要素ごとに対応・非対応の表を作り、**非対応は L0 として診断を出す**（要件 §4.1）。

### 4.3 画面遷移トリガー（MOD 名の解決）

CICS ではプログラムが `EXEC CICS SEND MAP('CUSTMAP')` と記述するため次画面が明白である。IMS TM では COBOL 側は `ISRT` で電文を吐き出すだけである。

- **画面決定の仕組み**: COBOL が `IO-PCB` の MOD 名領域（8バイト）に出力用の MOD 名をセットして `ISRT` を呼ぶ。または入力時の MID 定義に指定された既定の MOD が採用される。
- **対応**: ランタイム側で `IO-PCB` の MOD 名欄を監視し、指定された MFS 定義を動的にロードして画面を組み立てるディスパッチャが必要になる。

### 4.4 複数論理ページ（Logical Paging）

「プログラムが一度の `ISRT` で何ページ分もの明細データを出力し、MFS がそれを分割して端末へ送り、ユーザーがページをめくる」機能がある。

- **対応**: サーバ側セッションに「ページバッファ」を保持し、ページ送り操作を検知して切り替える状態管理が必要になる。
- **ページ送りのキー割り当ては未確認である。**改訂前は「PA2 キー（または `/FOR` コマンド）」と断定していたが出典が無い。公開仕様で確認する ([P-108](../decisions/provisional.md))。

## 5. 推奨されるロードマップと段階的アプローチ

| フェーズ | スコープ | 前提条件 | 実装内容 |
| :--- | :--- | :--- | :--- |
| **Phase 0**<br>(現状) | **MFS バイパス（電文直結）** | なし | MFS を通さない純粋な電文（MQ / REST 連携）のみを対象とする。COBOL プログラムは電文の直読み書きとして動作する（[ims-tm-rabbitmq-jms-proposal.md](ims-tm-rabbitmq-jms-proposal.md)）。 |
| **Phase 1** | **単一画面 MFS のエミュレーション** | **[AR-12](../reviews/2026-09-09-interop-adversarial-review.md) の BMS spike 合格。**BMS の端末 UI が実際に動いていること | - MFS 定義（MID/MOD/DIF/DOF）のパーサを実装<br>- 1画面・1ページの入出力マッピングを中立モデル経由でブラウザ表示<br>- **BMS からの流用可能範囲をここで測る** |
| **Phase 2**<br>(必要時) | **高度な MFS 機能の拡充** | Phase 1 完了 | - 複数論理ページング<br>- `PFK=`、`DPAGE COND=`、システムリテラル<br>- 属性の動的変更 |

**Phase 1 は Phase 0 の後ではなく、BMS が動いた後に始まる。**改訂前のロードマップはこの依存を「(BMS 連携後)」と括弧書きで示すのみだった。

## 6. まとめ

- **BMS 類似方針（中立モデル + Thymeleaf/CSS Grid/JS）の適用は合理的である。**方向性は妥当と考える。
- ただし**流用可能な範囲は測っていない。**流用元である BMS の実装が存在せず、方式も [AR-12](../reviews/2026-09-09-interop-adversarial-review.md) で未確定である。「100% 流用可能」という改訂前の記述は削除した ([P-108](../decisions/provisional.md))。
- **BMS と違って「COBOL 側には SEND MAP がなく、キュー電文の途中に MFS マッパーが透過的に割り込む」**というアーキテクチャ上の差があるため、バックエンド側では「電文（MFLD）⇔ 画面（DFLD）の自動フォーマット変換エンジン」を IMS TM 制御層に組み込む設計となる。
- **MFS 固有機構（`PFK=`、`DPAGE COND=`、`EXIT=`、MFS バイパス、DFS メッセージ）**は BMS に対応物が無く、「BMS + パーサ」で済むという見立てを弱める（4.2 節）。対応・非対応を要素ごとに表にし、非対応は L0 として診断する。
