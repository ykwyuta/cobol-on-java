## 1. 結論を先に

**手法の骨格は同じでよい。ただし部品が 2 つ足りない。そして 1 つだけ PL/I より恵まれている。**

| | PL/I で採った手法 | HLASM |
| :--- | :--- | :--- |
| 新モジュール 1 つをフロントエンドとして足す | ○ | **○ そのまま** |
| 生成クラスは `CobolProgram` ABI に着地する薄い殻 | ○ | **○ そのまま。むしろ HLASM のほうが必然** |
| 意味論はランタイムが持ち、生成コードは持たない | ○ | **○ そのまま** |
| `cobol-runtime` / `cobol-db2` / `cobol-ims` / `cobol-job` を再利用 | ○ | **△ 記憶域モデルだけ足りない** |
| 原文を歩く実行器で意味論を書く | ○ | **× 歩く対象が文ではなく機械の状態** |
| プリプロセッサは小さくて済む | ○ (63 行) | **× マクロ層それ自体が処理系** |
| `cobol-verify` で外から測る | ○ | **◎ PL/I より良い基準が既に配線されている** |

足りない 2 つは次のものである。

1. **レジスタと線形アドレス空間を持つ機械の層**。`Storage` / `DataView` の下に敷く必要がある
2. **マクロと条件付きアセンブリの処理系**。PL/I に対応物がなく、しかも切り落とせない

恵まれている 1 つは **Hercules** である。PL/I で最も弱かった「外の基準」(設計 26 §1: PL/I には CCVS85 相当が存在しない) が、HLASM では最も強い。命令単位のオラクルとして既にこのリポジトリに配線されている。

## 2. PL/I で実際に採った手法 (実装の実態)

先行する[検討レポート](pli-support-and-execution-requirements.md) §4 は「ANTLR4 で構文解析し、ASM で各 `PROCEDURE` を JVM メソッドへバイトコード生成する」と書いた。**実装はそうなっていない。**比較の基準を取り違えないため、実装の実態を先に確認する。

| 層 | 実装 | 行数 |
| :--- | :--- | ---: |
| プリプロセッサ | `PliPreprocessor` — `*PROCESS`, `%INCLUDE` のみ | 63 |
| 構文解析 | `PliSyntax` — 手書きの字句解析器＋再帰下降パーサ。ANTLR は使っていない | 890 |
| 意味実行 | `PliRuntime.Executor` — 構文木を歩く実行器 | 993 |
| クラス生成 | `PliClassGenerator` — ASM。**原文を定数に埋め、`PliRuntime.execute` を呼ぶだけの殻** | 119 |
| 入口・診断 | `Main`, `Diagnostic`, `IncludeResolver`, `PliCompiler` | 228 |
| 測定 | `cobol-verify/.../pli` — 5 状態で数える外部コーパス実行器 | 329 |

`PliClassGenerator` が生成するのは `initialStorage()` が長さ 0 の配列を返し、`run()` が原文と `ProgramContext` を `PliRuntime.execute` へ渡すだけのクラスである。これは `CobolProgram` の注記そのものである。

> **意味論はランタイムが持つ**ため、生成コードがやるのは記憶域の位置を決めて `Ops` を呼ぶことだけである。これにより、コード生成の誤りと意味論の誤りを切り分けられる。

つまり PL/I 対応の本体は次の一文に要約できる。

> **新しい言語のフロントエンドを 1 つ足し、意味論は既存ランタイムに委ね、生成クラスは既存 ABI に着地するだけの殻にする。測る道具は別モジュールに置き、数を門にしない。**

「PL/I と同じ手法で対応できるか」は、この一文が HLASM で成り立つかという問いである。

## 3. 同じ形で載る部分

### 3.1 固定形式の読み取りは既にある

HLASM の固定形式 (1〜71 桁が文、72 桁が空白でなければ継続、継続行は 16 桁から、73 桁以降は順序番号、1 桁の `*` が注記) は、**このリポジトリで既に 2 度実装されている**。

- `cobol-ims/.../gen/MacroReader` — DBDGEN / PSBGEN の原文を読む。継続、引用符内の空白、最上位のコンマによるオペランド分割まで持つ
- `cobol-cics/.../bms/BmsMacroReader` — BMS マクロ (`DFHMSD` 等) を読む

DBDGEN も BMS も**実体は HLASM のマクロ呼出し**である。ラベル / 命令 / オペランド欄の読み取りはこの 2 つの一般化で足りる。

### 3.2 薄い殻と `CobolProgram` ABI はそのまま使える

`run(Storage, ProgramContext, DataView[])` に着地させれば、プログラム解決 (決定 0001)、呼出し契約 (決定 0002)、実行単位とライフサイクル (決定 0003)、配備カタログ、JCL の `EXEC PGM=`、CICS / IMS の領域はすべて既存のものが動く。PL/I が `pli.generated.HELLO` として着地したのと同じ形で `hlasm.generated.XXX` が着地する。

### 3.3 十進演算・編集・EBCDIC・ファイル・SQL・DL/I は再利用できる

HLASM の `AP` / `SP` / `MP` / `DP` / `ZAP` / `CP` / `SRP` / `PACK` / `UNPK` / `ED` / `EDMK` / `MVO` / `TR` / `CLC` / `MVC` の意味論は、**COBOL の算術と編集のために既に実装され、Hercules で突き合わせ済みである** (`Decimal`, `PackedDecimal`, `EditMask`, 暫定判断 P-001 のゼロ結果の符号など)。COBOL の `COMPUTE` を支えている層が、そのまま命令 1 本の意味論として使える。

`DataSet` / `OpenMode`、`Db2RuntimeOps`、DL/I コアも同様である。PL/I が `PLITDLI` を `CBLTDLI` と同じ足し方で載せたのと同じく、`ASMTDLI` を足せばよい。

## 4. 同じ形では載らない部分

### 4.1 記憶域モデル — `Storage` / `DataView` では足りない

`Storage` は「プログラム 1 個のデータ領域を表す連続したバイト列」であり、`DataView` はその上の名前付き範囲である。COBOL も PL/I も**項目を名前で指す**ので、これで足りる。

HLASM は名前で指さない。**ベースレジスタ + 変位 (+ 指標)** で指す。

- `USING` / `DROP` は実行時の命令ではなく、**翻訳時に「どのレジスタが今どの位置を指しているか」を追う状態**である。命令のオペランドに書いた記号名は、この状態から `D(B)` へ解決される
- 実行時に存在するのは 16 本の汎用レジスタの値、条件コード、そして**番地の付いた連続した記憶域**だけである
- `DSECT` は記憶域を持たない型であり、`USING` で任意の番地に被せる。`LA` / `L` / `ST` はレジスタ上で番地そのものを計算する
- `A` / `V` 型の定数 (アドレス定数) は、**他の場所の番地を値として持つ**

したがって、`Storage` を置き換えるのではなく、**その下に 1 本の番地体系を敷く**必要がある。境界の設計が最初の難所になる。

- COBOL 側から `CALL` で渡された `DataView` が、この番地体系の中の範囲として見えること (R1 の parmlist が指すのはその番地である)
- 逆に、アセンブラ側が `GETMAIN` した領域を COBOL 側へ返せること
- 既存の COBOL / PL/I 側のコードは触らずに済む見込みだが、**確かめていない**

これは PL/I にはまったく無かった仕事である。PL/I の `POINTER` と `BASED` は「渡されたバッファの上の動的オフセットビュー」で足り、`DataView` の枠内に収まった。

### 4.2 マクロと条件付きアセンブリ — PL/I に対応物がない層

PL/I のプリプロセッサは 63 行で足りた。`*PROCESS` と `%INCLUDE` しか無かったからである。

HLASM のマクロ層はそうではない。

| 機能 | 内容 |
| :--- | :--- |
| マクロ定義 | `MACRO` / `MEND`、プロトタイプ文、入れ子の定義 |
| パラメタ | 位置パラメタ、キーワードパラメタ、サブリスト `(a,b,c)`、既定値 |
| 変数記号 | `SETA` (算術) / `SETB` (論理) / `SETC` (文字)、`GBLA/GBLB/GBLC`、`LCLA/LCLB/LCLC`、添字付き変数記号 |
| 制御 | `AIF` / `AGO` / `ANOP` / `ACTR` — **条件付きアセンブリだけで計算が書ける** |
| システム変数 | `&SYSLIST`、`&SYSNDX`、`&SYSPARM`、`&SYSDATE` ほか |
| 属性参照 | `T'` (型)、`L'` (長さ)、`K'` (数)、`N'` (要素数)、`D'` (定義済みか) |
| 診断 | `MNOTE`、`MEXIT` |

これは**それ自体が 1 つの処理系**である。そして切り落とせない。実資産で OS のサービスを要求する手段はすべてマクロだからである (`OPEN`, `CLOSE`, `GET`, `PUT`, `GETMAIN`, `FREEMAIN`, `WTO`, `LINK`, `ATTACH`, `ABEND`, `SAVE`, `RETURN`, `CALL`)。CICS の `EXEC CICS` も IMS の呼出しも、展開されればマクロである。

PL/I は「Bank-of-Z の 2 本が使う構文だけ」と切って成立した。HLASM で同じ切り方をしても、**マクロ層だけは切れない**。ここが規模の見積もりを最も大きく動かす。

### 4.3 自己書き換えと計算分岐 — ただし薄い殻の方針がここで効く

- `EX` / `EXRL` は、対象命令の 1 バイトをレジスタの下位 8 ビットで差し替えてから実行する。可変長 `MVC` の定石であり、実資産にほぼ必ず出る
- `BALR` / `BASR` / `BR 14` / `BR 15` は**レジスタの値**へ分岐する。分岐先は実行時にしか決まらない
- 分岐表 (`B *+4(R1)`) や、命令とデータが同じ領域に混在する書き方も普通である

これらは JVM バイトコードへの素直な写像を壊す。各命令を JVM のラベルへ展開する方式を採ると、計算分岐の行き先を静的に閉じられない。

**逆に言えば、PL/I で採った「薄い殻＋ランタイムが意味論を持つ」形が、HLASM では最初から正しい。**命令インタプリタであれば `EX` も計算分岐も自然に扱える。歩く対象が構文木ではなく命令の並びになるだけである。

ただし「命令インタプリタを書く」は「AST を歩く」とは別の仕事である。要るのは以下であり、`PliRuntime.Executor` の構造は流用できない。

- 命令のデコード (形式 RR / RX / RS / SI / SS / RI / RIL / RXY / RSY ほか)
- レジスタファイル、条件コード、PSW の命令アドレス
- 割込み (プログラム例外 → `S0Cx` の ABEND へ)

### 4.4 OS インタフェース — ここは既存ポートに着地する

ここは**良い知らせ**である。新規に要るのはポートそのものではなく、「マクロ展開の結果として現れる呼出しを、既存ポートへ振り分ける表」である。

| HLASM 側 | 着地先 |
| :--- | :--- |
| 標準リンケージ (R1=parmlist, R13=save area 連鎖, R14=戻り番地, R15=入口/戻り値) | 決定 0002 のバイト志向の呼出し契約。R1 が指す番地の並びが `DataView[]` に対応する |
| `SAVE` / `RETURN`、72 バイトのセーブエリア | `ProgramContext` の呼出しスタック (覚え書き・異常終了時の表示は FR-142 で既にある) |
| `WTO` | `ProgramContext` の出力 |
| `OPEN` / `GET` / `PUT` / `CLOSE`、`DCB` / `DCBD` | `cobol-runtime` の `DataSet` / `OpenMode` と JCL の DD |
| `GETMAIN` / `FREEMAIN` | 4.1 の番地体系の上の確保 |
| `ABEND` | 既存の ABEND 機構 |
| `ASMTDLI` | `cobol-ims` の DL/I コア (`PLITDLI` と同じ足し方) |
| `DFHEIENT` / `DFHECALL` | `cobol-cics` |

R1 の parmlist と `DataView[]` が対応するという点は、**COBOL から呼ばれるアセンブラ副プログラム**という最も現実的な用途に直結する。

## 5. 外の基準 — ここだけは PL/I より強い

CLAUDE.md の §1 と §3 が言っていることがそのまま効く。

PL/I は**この処理系で最も外の基準が弱い言語**である。設計 26 §1 に書いたとおり、ANSI X3.53-1976 / ISO 6160:1979 はあるが、NBS は 1984 年に「包括的な検証テストは利用できない」と報告している。だから期待値を自分で作るしかなく、「**自分で書いた規則は、自分のテストでは破れない**」状態に最も近い。

HLASM は逆である。

| | PL/I | HLASM |
| :--- | :--- | :--- |
| 公開仕様 | ISO 6160:1979 + IBM 拡張。両者を同じ数で扱えない | **z/Architecture Principles of Operation** |
| 適合性検査スイート | **存在しない** | 存在しない |
| 実行オラクル | IBM Enterprise PL/I (手元に無い) | **Hercules。既にこのリポジトリに配線済み** |
| 期待値の作り方 | 規格を読んで自分で書く | **命令を Hercules で実行して採る** |

既にあるものは次のとおりである。

- `HerculesRunner` — 所在を `HERCULES` で指定。**バージョン番号ではなく `-r` の有無という能力で検査する**。使えない理由を握りつぶさない (`Detection.Unavailable`)
- `HerculesCase` — `sysclear` / `archlvl` / `r <addr>=<hex>` / `runtest` / `r <addr>.<len>` の `.tst` スクリプトを組む。**プログラム割込みは待機 PSW の命令アドレス `0xDEAD` で検出できる**ので、異常終了まで突き合わせられる
- `StorageDump` — 読み出した記憶域の解釈
- `Insn` — 機械語の組み立て。**外部アセンブラに依存しない** (要件 FR-211、決定 D-11)。SS 形式の 10 進命令を中心に既に組める

要件 D-11 が「機械語の組み立ては本プロジェクト内で行い、外部アセンブラに依存しない」と決めているのは、HLASM 対応にとって**偶然ではない前提**である。`Insn` は既に小さなアセンブラであり、HLASM 対応はその一般化でもある。

### 5.1 守るべき 2 つの線

1. **V2 は「Hercules と一致」であって「実機と一致」ではない** (決定 D-11b、リスク R-8)。HLASM 対応でも同じ言い方を守る。Hercules 自身が、実機を持たない場合の期待値の妥当性確認は最も困難であり PoP に曖昧さが残りうると述べている
2. **Hercules は QPL であり Apache-2.0 と両立しない。外から呼ぶだけで、ソースを読んで写さない。**命令エミュレータを書くということは Hercules と同じ仕事をするということであり、**この線引きは PL/I のときより遥かに重い**。根拠は PoP と、Hercules を外から走らせて観測した出力だけに限る。IBM 製品のソースを参照しないという決めごとも同じく効く

### 5.2 ただし測る対象が 2 つに増える

COBOL と PL/I では「翻訳できたか」「実行結果が合うか」の 2 つだった。HLASM では**測る対象が 2 段になる**。

1. **アセンブルの正しさ** — 原文 → 機械語とアドレス。Hercules に載せる前に決まる
2. **実行の正しさ** — その機械語を自分のインタプリタが実行した結果

ここに落とし穴がある。**自分のアセンブラが誤った機械語を作ると、Hercules も自分のインタプリタも同じ誤った機械語を実行し、結果が一致してしまう。**測定が緑になるが、原文の意味は再現できていない。これは CLAUDE.md §6「検査の道具が、処理系の失敗を作ってはならない」の裏返しであり、**道具が処理系の成功を作ってしまう**形である。

対策は 2 つ。

- アセンブル結果そのもの (オブジェクトコードの 16 進とアドレス、`USING` の解決結果) を、PoP の命令形式から作った期待値と**別に**突き合わせる。実行の一致と同じ数に混ぜない
- 状態の数え方に `WRONG_OBJECT` を足し、`WRONG_OUTPUT` と区別する

## 6. 規模の見当

| 層 | PL/I の実績 | HLASM の見込み |
| :--- | ---: | :--- |
| プリプロセッサ / マクロ | 63 行 | マクロと条件付きアセンブリの処理系。**`PliSyntax` + `PliRuntime` を合わせたより大きい** |
| 構文解析 | 890 行 | アセンブラ指示・機械命令・マクロ呼出しの 3 種。`DC` / `DS` の型文字と修飾子、`USING` の解決、リテラルプール / `LTORG` / `ORG` だけで相当量 |
| 意味実行 | 993 行 | 命令のデコードと実行。中心となる 100〜150 本に絞っても `PliRuntime` 級 |
| クラス生成 (殻) | 119 行 | **ほぼそのままで済む** |
| 入口・診断 | 228 行 | 同程度 |
| 測定 | 329 行 | 同形 + Hercules 突き合わせ + オブジェクトコードの照合 |

PL/I は Bank-of-Z の 2 本を無修正で通すために約 1,900 行だった。**「同じ手法」ではあるが「同じ規模」ではない。**

## 7. 進め方の提案

CLAUDE.md の増分の型に従い、**測る道具を先に置く**。

| 増分 | 内容 | 終わりの判定 |
| :--- | :--- | :--- |
| **0** | 測る道具。`hlasm-corpus` の実行器を `cobol-verify` に置き、Hercules と突き合わせる。状態は 6 つ (`ASSEMBLED` / `PASSED` / `REJECTED` / `WRONG_OBJECT` / `WRONG_OUTPUT` / `CRASHED`)。時間の限りを置く。コーパスは同梱しない | 数が出る。**実装より先** |
| **1** | COBOL から `CALL` される副プログラム 1 本。`CSECT` 1 本、標準リンケージ、`DC` / `DS` の主要型、マクロ無し。命令は転記・比較・分岐・2 進算術・10 進算術に限る | ここで**番地体系と `DataView` の境界**を決める。最も設計が要る増分 |
| **2** | マクロと条件付きアセンブリ | これが入るまで実資産は 1 本も通らない |
| **3** | OS サービス (`WTO` / `GETMAIN` / `OPEN` / `GET` / `PUT` / `DCB`) と ABEND | JCL の DD に着地する |
| **4** | CICS / IMS のスタブ (`DFHEIENT` / `DFHECALL`、`ASMTDLI`) | 既存ポートへ振り分ける |
| **5** | 主プログラムとしての実行 (`EXEC PGM=`) | 配備カタログに載る |

増分 1 を「COBOL から呼ばれる副プログラム」にするのは、実資産における HLASM の使われ方がそこに偏っているからである (日付変換、表探索、ビット操作といった小さな部品)。主プログラムより先に呼出し境界を固めたほうが、得られるものが大きい。

## 8. 最初から「書けない」と断ると決めるもの

「近い値を黙って返すくらいなら、書けないと断る」。以下は最初から断ると決めておく。あとで必要になったときに、断っている位置から判断し直せる。

| 範囲 | 理由 |
| :--- | :--- |
| 浮動小数点 (HFP / BFP / DFP) | 桁の規則を突き合わせていない。COBOL 側でも同じ理由で慎重に扱っている |
| 権限命令、PSW の直接操作、割込みハンドラ | 実行環境の前提そのものが違う |
| クロスメモリ (`PC` / `SSAR`)、SRB、データスペース | OS の構造を持たない |
| ベクトル命令 | 用途が資産にない |
| チャネルプログラム (`EXCP`)、実記憶への依存 | ファイルは既存のデータセット層に着地させる |
| 時刻の値そのものに依存する資産 (`STCK`) | FR-204 の固定できる値に載らない限り断る |
| 命令境界をまたぐ自己書き換え | `EX` による 1 バイト差し替えは扱うが、それ以上は断る |

---

## 9. 未決の問い

**最大の未決事項は「対象資産が無い」ことである。**

PL/I には `BNKSTMT.pli` と `IBLOGIN.pli` という具体があり、**その 2 本が subset の境界を決めた**。設計 26 の機能表も、Bank-of-Z が使う範囲を基準に優先順位が付いている。HLASM には現時点でそれが無い。

- **どの資産を通すのかを先に決めないと、subset の切り方が決まらない。**HLASM は言語の全体が大きく、「全部」は現実的でない。境界を決めるのは資産である
- AMODE 24 / 31 / 64 のどれを既定にするか。番地体系の幅が変わる
- オブジェクトモジュール (ESD / RLD / TXT) を経由するか、原文から直接実行するか。経由すれば外部参照の解決を既存のプログラム解決に載せられる一方、別の層が増える
- アセンブラ単独で動く主プログラムを目標にするか、COBOL からの呼出し専用に絞るか
- 既存の `MacroReader` / `BmsMacroReader` を一般の HLASM マクロ処理系へ置き換えるか、別に持つか

---

## 10. まとめ

問い「PL/I と同じ手法で対応できるか」への答え。

**骨格は同じでよい。**新モジュール 1 つ、薄い殻、`CobolProgram` ABI、意味論はランタイムが持つ、`cobol-verify` で外から測る、合格率を門にしない — これらはそのまま成り立つ。しかも「原文をバイトコードへ素直に落とさず、ランタイムが意味論を持つ」という方針は、自己書き換えと計算分岐を持つ HLASM では**PL/I のとき以上に必然**である。

**足りない部品が 2 つある。**レジスタと線形アドレス空間を持つ機械の層 (`Storage` / `DataView` の下) と、マクロ・条件付きアセンブリの処理系である。後者は PL/I に対応物がなく、しかも実資産のために切り落とせない。規模は PL/I の数倍を見込む。

**そして 1 つだけ PL/I より恵まれている。**外の基準である。PL/I で最も弱かった層 (適合性検査スイートが存在せず、期待値を自分で書くしかない) が、HLASM では最も強い。Principles of Operation が公開仕様としてあり、Hercules が命令単位のオラクルとして既に配線されている。CLAUDE.md §3 が警告する「自分で書いた規則は、自分のテストでは破れない」という失敗の型から、HLASM は最も遠い位置にある。

**次にやること**は、通すべき資産を 1 本決めること、そして増分 0 の測る道具を実装より先に作ることである。
