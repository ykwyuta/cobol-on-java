## 1. なぜ IMS DB を RDB 化するとロック競合が起きやすいのか？

メインフレームの IMS は **IRLM (Internal Resource Lock Manager)** という専用のロックマネージャを備え、セグメントレベルまたはブロックレベルで細かい粒度のロックを行う。

一方、汎用 RDB 上に [ims-rdb-storage-engine-report.md](ims-rdb-storage-engine-report.md) の非正規化スキーマを構築した場合、以下の理由でロック競合・デッドロックが発生しやすくなる。

1. **インデックスの局所集中**: すべてのセグメントが同一テーブルに集約され、主キーが `(DBD_NAME, ROOT_KEY_RAW, HIERARCHY_PATH)` となるため、同一 DBD への並行 INSERT がインデックスの同一ページで競合しやすい。
2. **階層ツリー更新時のロック順序の不一致**: ジョブ A が「ルート → 子 A → 子 B」の順で処理している裏で、ジョブ B が「子 B → 子 A」の順で処理すると、行ロックが交差してデッドロックする（PostgreSQL: 40P01 / Db2: -911, 40001）。
3. **カスケード削除 (`DLET`) による広範な範囲ロック**: `DLET` は配下の子孫すべてを削除するため、広範囲にロックがかかる。
4. **バッチとオンラインの衝突**: 大量更新の夜間バッチ中に MPP オンラインが同じ DBD にアクセスするとロック待ちタイムアウトが発生する。

## 2. ロック競合を回避するための対策

```
+-----------------------------------------------------------------------------------+
| IMS DB ロック競合回避アーキテクチャ                                               |
|                                                                                   |
|  [ 対策 1: ルートアンカーロック ]                                                |
|    - 木の更新前にルート行を排他ロックし、獲得順序を (DBD, ROOT_KEY) 昇順に統一   |
|                                                                                   |
|  [ 対策 2: MVCC。読み取りは書き込みをブロックしない ]                            |
|    - GU/GN は FOR UPDATE をかけず Snapshot Read。GHU/GHN のみ排他ロック          |
|                                                                                   |
|  [ 対策 3: 撤回 ]  <-- DML 遅延バッファリングは DL/I の意味論を壊すため撤回      |
|                                                                                   |
|  [ 対策 4: DBD 単位の物理テーブル分離 ]                                          |
|    - 競合ドメインを局所化。PROCOPT=E を採るなら必須                              |
|                                                                                   |
|  [ 対策 5: PROCOPT に基づく制御。ただし G と GO は分ける ]                       |
+-----------------------------------------------------------------------------------+
```

---

### 対策 1: ルートアンカーロック（Root-Level Coarse Locking）

階層型 DB において木構造の内部で細かく行ロックを獲り合うと、獲得順序の違いからデッドロックが発生する。これを防ぐため、**「あるルートキー（木全体）を更新するトランザクションは、まず最初にルート行を排他ロックする」**というルールを徹底する。

```sql
-- 子セグメントを更新・挿入・削除する前に、必ず木全体の代表行をロックする
SELECT ROOT_KEY_RAW
  FROM IMS_ROOT_INDEX
 WHERE DBD_NAME = :dbd AND ROOT_KEY_RAW = :root_key
   FOR UPDATE;
```

**効果**:

- 同一ルートキーに対する複数プロセスの更新が、入り口で直列化される。
- 木の内部で子セグメント同士のロック順序が交差しなくなる。
- 異なるルートキーは並行実行できるため、スループットを損なわない。

**この対策で守れないもの（改訂で追加）**:

- **新規ルートの `ISRT`（ファントム）**: ロック対象の行がまだ存在しない。同一ルートキーを同時に `ISRT` した 2 つのトランザクションは直列化されず、主キー衝突で片方が失敗する。ルート行を先行確保する手順（`INSERT ... ON CONFLICT DO NOTHING` → `SELECT ... FOR UPDATE`）を規定し、返す状態コードも決める。
- **複数ルート・複数 DBD をまたぐ更新**: 振替処理のように 2 つのルートを更新する資産は普通にある。ルートロックの獲得順序が交差すればデッドロックする。**獲得順序を `(DBD_NAME, ROOT_KEY_RAW)` 昇順に規定する。**

したがって、**「デッドロックの撲滅」は同一ルート配下に限られる。**ルート間は獲得順序の規約に依存し、規約を破る経路があれば依然としてデッドロックする。

---

### 対策 2: MVCC（多版並行性制御）の活用

1. **通常の検索（`GU`, `GN`, `GNP`）はロックを獲らない**: スナップショット参照とし、読み取りが更新をブロックしない。
2. **保持付き検索（`GHU`, `GHN`, `GHNP`）**: 対象行（またはルート行）に対して `FOR UPDATE` を発行する。

これにより、読込専用の大量参照バッチが更新トランザクションを待たせることがなくなる。

---

### 対策 3【撤回】: DML 遅延バッファリングと辞書順ソート

> **この対策は撤回した。**

改訂前の案は、ループ内の複数 `ISRT` / `REPL` を都度発行せず**コミット時までメモリにバッファリング**し、発行直前に `HIERARCHY_PATH` 昇順でソートして出す、というものだった。目的は「全トランザクションが同一の物理順序で行ロックを獲得するので循環待ちが起きない」ことである。

**撤回する理由は 2 つある。**

1. **read-your-own-writes が壊れる。**DL/I では、同一 UOW 内で `ISRT` した直後の `GU` / `GN` / `GNP` はそのセグメントを見る。`DLET` した直後の `GN` はそれを見ない。COBOL 資産は「挿入 → 読み直して検算」「削除 → 走査し直し」を普通に書く。DML を溜めたままだと後続の `SELECT` が自分の更新を見ない。改訂前の案はバッファと問い合わせ結果のマージについて何も書いていなかった。
2. **`II`（重複キー）の返却タイミングがずれる。**実機は `ISRT` のその場で `II` を返す。遅延すればコミット時まで分からない。**状態コードで分岐する COBOL の制御フローが変わる。**

**撤回してよい理由**: 対策 1（ルートアンカーロック）が入っていれば、同一ルート配下でのロック順序交差はもう起きない。遅延バッファリングの主目的は対策 1 と重複しており、費用対効果が悪い。ルート間の順序は対策 1 の獲得順序規約で揃える。

残す場合は、読み取り経路にバッファのオーバレイを噛ませ（未コミット DML を SQL 結果へマージし、`II` を発行時点で判定する）設計が必要になるが、これは実質的にミニストレージエンジンを 2 段持つことになる。**採らない。**

**したがって DML は即時発行する。**

---

### 対策 4: DBD 単位の物理テーブル分離（Table-per-DBD）

基本設計では単一の `IMS_SEGMENT_STORE` を例示したが、高負荷環境では DBD ごとにテーブルを物理分割（またはパーティショニング）する。

```sql
CREATE TABLE IMS_SEG_CUSTDBD ( ... ) PARTITION BY HASH (ROOT_KEY_RAW);
CREATE TABLE IMS_SEG_ITEMDBD ( ... );
```

**効果**: `CUSTDBD` の大量更新と `ITEMDBD` の更新が同一のインデックス木を取り合う競合がなくなる。

**注意（改訂で追加）**: これは**対策 5 の `PROCOPT=E` の前提条件でもある。**単一テーブルのままで `LOCK TABLE` を打つと無関係な全 DBD が止まる。ただし Table-per-DBD を採ると、DBD 追加のたびに DDL が要るため、[ADR-0013](../decisions/0013-ims-db-denormalized-raw-storage-engine.md) の「DDL マイグレーション不要」という利点が部分的に失われる。

---

### 対策 5: PSB の `PROCOPT` に基づく最適化（`G` と `GO` を分ける）

| `PROCOPT` | 意味 | RDB 側での対応 |
| :--- | :--- | :--- |
| **`G`** (Get) | 参照。**整合性つきの読み取り** | スナップショット参照。JDBC 接続を `readOnly = true` に設定するが、**整合性は捨てない** |
| **`GO`** (Get Only) | **整合性を問わない読み取り** | ロックを獲らないダーティリード相当。ここだけ「一切のロック抑止」を適用する |
| **`GOx`** (`GON` / `GOT`) | — | **未対応。**診断を出す |
| **`I` / `R` / `D`** | 挿入 / 置換 / 削除 | 通常の更新トランザクション。対策 1 を適用 |
| **`E`** (Exclusive) | 排他実行 | `LOCK TABLE ... IN EXCLUSIVE MODE`。**対策 4（Table-per-DBD）が前提** |

> **改訂前の誤り**: `PROCOPT=G` を「参照専用 → 一切のロックを抑止」と写像していた。しかし
> 整合性を捨てた読み取りは `G` ではなく **`GO`** の意味論である。`G` は整合性つきの読み取りで
> あり、更新中のデータを読まない。
>
> この写像は「近似を既定として黙って適用する」ものであり、FR-153 が Db2 のカーソルについて
> 定める「未分類 cursor へ近似方式を暗黙適用しない」にも、CLAUDE.md 増分の型 3 にも反する。
> **移行後だけダーティリードが起きるという、最も見つけにくい種類の差になる**
> ([P-106](../decisions/provisional.md))。

ランタイム起動時に PSB 定義を読み取り、`PROCOPT` に応じて接続プロパティやロック戦略を切り替える。`PROCOPT` が許さない操作には **`AM`** を返す。

## 3. デッドロック発生時のフェイルセーフ設計

対策を施しても、RDB 側でデッドロック検知（PostgreSQL: `40P01`, Db2: `-911 / 40001`）が発生する可能性はゼロにはならない。

### 3.1 擬似 ABEND と自動リトライ

1. **ランタイムでの捕捉**: JDBC アダプタが `SQLException` のエラーコードを検知する。
2. **自動リトライ（MPP オンライン）**: トランザクション開始時点までロールバックし、ランダムなバックオフを挟んで**設定値（既定 3 回）まで**同一メッセージの処理を再試行する。
3. **バッチジョブ**: リトライ不能なら ABEND を発生させ、ジョブステップを異常終了させる（[設計 90](../design/90-job.md) の異常終了処理機構と連携）。

> **出典について**: 改訂前は「最大 3 回（メインフレーム IMS TM の標準挙動に準拠）」「擬似 ABEND
> `U0777`」と断定していたが、**再スケジュールの回数は定義側の設定に依存し固定 3 回ではない。**
> ABEND コードの妥当性も確認していない。3 回は**本実装の既定値であって実機の規定値ではない**。
> 公開仕様で確認するまでこの位置づけとする ([P-107](../decisions/provisional.md))。

## 4. 推奨する実装構成まとめ

| 対策項目 | 推奨設定 / 実装方針 |
| :--- | :--- |
| **デッドロック防止の主軸** | **対策 1**: ルートキー単位で直列化。獲得順序は `(DBD_NAME, ROOT_KEY_RAW)` 昇順 |
| **検索スループット維持** | **対策 2**: 通常の `GU`/`GN` はノーロック検索 |
| **DML の発行** | **即時発行**（対策 3 は撤回） |
| **負荷分散** | **対策 4**: DBD 単位で物理テーブルを分離。`PROCOPT=E` を採るなら必須 |
| **PSB 定義の活用** | **対策 5**: `G` は整合性つき、`GO` のみロック抑止 |
| **例外時の救済** | **3.1**: デッドロック時は設定回数まで再試行 |

この構成により、RDB バックエンド特有のロック競合を**同一ルート配下については**抑え込める。ルート間は獲得順序の規約に依存する。

**なお、この構成の効果は測っていない。**デッドロックの発生率と再試行の妥当性は、負荷をかけて測るまで数値を主張しない ([P-099](../decisions/provisional.md))。
