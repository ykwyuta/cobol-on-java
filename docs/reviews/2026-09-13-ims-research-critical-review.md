## 重大度

- **P0**: 未解消のまま実装すると要件未達、データ不整合、誤った互換性保証、公開 API の作り直しになる。
- **P1**: 初期実装は可能でも、並行実行・運用・移行資産の実形で高確率に破綻する。
- **P2**: 品質・保守性を下げる。着手前に直せば安い。

## 総括

**良い判断**は 3 つある。いずれも本プロジェクトの既存原則から素直に導かれており、維持すべきである。

1. **セグメントを生バイトで持つ** ([ADR-0013](../decisions/0013-ims-db-denormalized-raw-storage-engine.md))。`COMP-3`・`REDEFINES`・ODO を SQL 列へ分解しないという判断は、[設計 80](../design/80-file-io.md) の原則と同じ理由で正しい。DBD にデータ部の列定義がそもそも無いという観察も正確である。
2. **RDB を業務テーブルではなくストレージエンジンとして使う**という位置づけ。CQRS で参照系を分ける退避策まで書けている。
3. **中立ポート ([ADR-0007](../decisions/0007-framework-neutral-subsystem-ports.md)) を IMS にも適用する**こと。`DliDatabasePort` / `ImsQueuePort` の切り出し自体は妥当である。

**問題は、この 3 つの妥当な判断の周りに、裏付けの無い断定と、検証していない前提が大量に積まれていることである。**

最も危険なのは次の 5 点である。

1. **要件対応が誤っている。** ADR-0013/0014/0015 と設計 78 はいずれも関連要件を「FR-150〜156」としているが、これは **Db2 / SQL の要件**である。IMS の要件は **FR-164 の 1 本だけ**で、そこには「初期リリースではインタフェース定義のみとする」と書いてある (IR-01)。
2. **oracle が無いのに「実機と寸分違わぬ」と書いている。** 要件 §4.3 は FR-150〜164 を明示的に **V1 止まり**と定めている。同じ誤りは [AR-14](2026-09-09-interop-adversarial-review.md) で CICS / Db2 / BMS について既に指摘済みであり、**IMS で再発している** (IR-02)。
3. **DBD / PSB パーサが設計に存在しない。** SSA の項目修飾も、シーケンスフィールドの切り出しも、`PROCOPT` も、可変長セグメントも、すべてこれ無しには成立しない。最大の作業項目が見積もりから抜けている (IR-06)。
4. **ロック設計 (対策 3: DML 遅延バッファリング) が read-your-own-writes を壊す。** `ISRT` の直後に `GN` が自分の挿入を見ないのは、IMS の意味論ではない (IR-17)。
5. **IMS TM 案は 2 相コミットを黙って落としている。** 同じ資料群が「RRS で原子的に同期保証」と説明した直後に、RabbitMQ (XA 非対応) で `session.commit()` と JDBC commit の 2 本立てを提案しており、電文の消失・二重処理が構造的に起こる (IR-23)。

加えて、**「IMS TM は CICS より容易」という資料の結論は、会話型トランザクション (SPA) を数に入れていないために出ている** (IR-24)。この結論が MFS とロードマップの優先順位を決めてしまっているため、影響が大きい。

## A. 前提とプロセス

<a id="ir-01"></a>
### IR-01 [P0] 要件トレーサビリティが誤っており、要件が無い範囲まで ADR を採用している

**反証:** ADR-0013 / 0014 / 0015 の「関連要件」と設計 78 の「対応要件」は、いずれも `FR-150〜156, NFR-032, ARC-4, ARC-7` である。しかし要件 §7.3 の FR-150〜156 は **Db2 のデータベース連携要件** (SQL コプロセッサ、SQLCA、ホスト変数、カーソル、`COMMIT`、方言、Db2 Spring アダプタ) であって、IMS とは無関係である。

IMS の要件は **FR-164 ただ 1 本**であり、その全文はこうである。

> **FR-164 (L1)**: IMS DL/I 呼び出し (`CBLTDLI` / `AIBTDLI`) のインタフェースを定義し、PCB マスク・SSA・状態コード (`GA`、`GB`、`GE`、`II` 等) を扱えるようにする。実際のデータベースへの写像は、差し替え可能なアダプタとして提供する。**IMS 連携はフェーズ 4 の目標とし、初期リリースではインタフェース定義のみとする。**

フェーズ表の P4 受け入れ基準にも IMS の記述は無い (「疑似会話型トランザクションと主要 BMS 属性の画面が動作」)。つまり、**RDB ストレージエンジン、ロック方式、RabbitMQ、MFS、運用ユーティリティを要求している要件は 1 つも存在しない**。にもかかわらず ADR 3 本が「採用」になっている。

**改善:**
- ADR-0013/0014/0015 と設計 78 の関連要件を `FR-164, NFR-032, ARC-4, ARC-7` へ訂正する。
- IMS DB 実体・TM・MFS・運用ツールを本当に作るなら、**先に FR を書く**。要件の無い ADR は「採用」にしない。
- FR-164 の「初期リリースではインタフェース定義のみ」を変更するのか維持するのかを、要件の改訂として決める。維持するなら、これらの資料は「フェーズ 4 以降の検討」と明示して凍結する。

### IR-02 [P0] oracle が無いまま「完全互換」を主張している (AR-14 の再発)

**反証:** 要件 §4.3 は、V2 (実行検証済) に到達できない領域として **FR-150〜164 (Db2 / CICS / IMS)** を名指ししている。Hercules は IMS の oracle にならない。CCVS85 に相当する DL/I の適合性検査スイートも存在しない。**IMS には、CLAUDE.md §1 が言う「外の基準」が現時点で 1 つも無い。**

それにもかかわらず、資料は次のように書いている。

| 箇所 | 記述 | 実際の裏付け |
| --- | --- | --- |
| `ims-dli-complex-semantics-report.md` §7 | 「メインフレーム実機と寸分違わぬ動作を JVM 上で担保できます」 | 無し (V0/V1) |
| `ims-rdb-storage-engine-report.md` §5.1 | 「COBOL 資産の無修正 100% 透過実行」「データ破壊リスクの完全排除」 | 無し |
| `ims-rdb-storage-engine-report.md` §5.2 | 「メインフレームと同等以上のスループットを達成します」 | 測定無し |
| `ims-db-locking-and-deadlock-avoidance.md` §2 | 「デッドロックが原理的に 100% 撲滅」 | ルート内に限る (IR-19) |
| `ims-mfs-...-proposal.md` §3 | 「BMS と 100% 共通の JavaScript module を再利用可能」 | 流用元が未実装 (IR-28) |
| `ims-rdb-storage-engine-report.md` §1.1 | 正規化すると「L3 互換が原理的に崩壊」 | L3 を目標として語れても、達成の裏付けは別軸 |

これは要件 §4 が冒頭で警告している誤りそのものである。

> 参照実装の実機が利用できない以上、この 2 つ (互換性レベルと検証レベル) を混同すると達成できない約束を要件として抱え込むことになる

さらに、同じ指摘は [AR-14](2026-09-09-interop-adversarial-review.md) で既に出ている。CLAUDE.md §2 の「直すたびに測る」「1 度測って終わりにしない」が、レビュー指摘そのものに適用されていない。

**改善:**
- 全 8 本に検証レベル欄 (V0/V1/V2-SUBSYSTEM) を入れ、**V0/V1 の項目を「忠実」「完全」「100%」と書かない**。上表の 6 箇所を具体的に書き換える。
- 「IMS には CCVS85 相当の外の基準が存在しない」ことを資料の冒頭に明記する。そのうえで代替を先に決める。候補は (a) 公開仕様の条文を条項単位で引用した仕様準拠テスト (V1 として明示)、(b) 振る舞いの差が出る反証テスト (CLAUDE.md 増分の型 4)、(c) 実機 IMS を持つ利用者から採取した sanitized なコール/状態コードのトレース (V2-SUBSYSTEM)。
- oracle が無い領域に着手すること自体は否定しない。**否定するのは、無いのに有るかのように書くことである。**

## B. IMS DB のスコープ欠落

<a id="ir-05"></a>
### IR-05 [P0] アクセス方式 (HDAM / HIDAM / HISAM …) の区別が無く、ルート順序の前提が 1 つに固定されている

**反証:** 資料はルートを `IMS_ROOT_INDEX` に持ち、`GN` がルートを越えるときは「次の `ROOT_KEY`」を取ると書く (`ims-rdb-storage-engine-report.md` §3.2)。これは**ルートがキー昇順に並ぶ前提**であり、HIDAM / PHIDAM / HISAM の話である。

**HDAM / PHDAM ではルートの物理順序はランダマイジングモジュールが決めるため、キー順にならない。** 無限定 `GN` でデータベース全体を舐めるバッチは、実機とまったく違う順序でセグメントを受け取る。順序に依存した集計・ブレーク処理・出力ファイルの並びは、そのまま結果が変わる。DBD の `ACCESS=` は資料に一度も現れない。

**改善:** DBD の `ACCESS=` を読み、
- HIDAM / PHIDAM / HISAM: ルートキー昇順で再現する (現設計のまま)。
- HDAM / PHDAM: **ランダマイザを再現できないことを明示する**。無限定 `GN` のルート順序が実機と一致しないことを診断として出すか、順序に依存しないと利用者が宣言した場合のみ許す。CLAUDE.md 増分の型 3 のとおり、**近い順序を黙って返すくらいなら断る。**

<a id="ir-06"></a>
### IR-06 [P0] DBD / PSB パーサが設計に存在しない

**反証:** 設計 78 §2 のモジュール一覧は `CbltdliBridge` / `SsaParser` / `PcbStateManager` / 2 つのポートだけで、**DBD パーサも PSB パーサも無い**。しかし次のすべてがこれらの定義を必要とする。

| 必要な場面 | 必要な情報 | 出典 |
| --- | --- | --- |
| SSA の項目修飾 `(FIELD = VALUE)` の評価 | フィールド名 → セグメント内オフセット・長さ・型 | DBD の `FIELD` 文 |
| `SEQ_KEY_RAW` の切り出し | シーケンスフィールドの位置と `UNIQUE` 有無 | DBD の `FIELD ... SEQ` |
| 兄弟の挿入位置 (`RULES=`) | セグメントの挿入規則 | DBD の `RULES=` |
| セグメント名の妥当性検査 (`AK` 返却) | セグメント/フィールドの一覧 | DBD |
| ロック戦略の切替 (対策 5) | `PROCOPT` | PSB の `PCB` 文 |
| PCB マスクの構築順序 | PSB 内の PCB 並び | PSB |
| 可変長セグメント | `BYTES=(max,min)` | DBD |

DBDGEN / PSBGEN はアセンブラマクロであり、BMS マクロパーサと同程度の作業量になる。**IMS 対応の最大の作業項目が、見積もりからも設計からも抜けている。**

**改善:** `cobol-ims` に `DbdParser` / `PsbParser` と中立メタモデル (`ImsDatabaseCatalog`) を第 1 級のコンポーネントとして追加し、ロードマップの第 1 増分に置く。SSA 評価・ストレージ・ロック・運用ツールはすべてこの上に載る。

<a id="ir-07"></a>
### IR-07 [P0] 二次索引・論理関係・GSAM・Fast Path が一言も無い

**反証:** 8 本のどこにも次が現れない。いずれも実資産で普通に使われる。

- **二次索引 (`XDFLD` / `PROCSEQ=`)**: 別のフィールドで階層順序そのものを差し替える機能。「`HIERARCHY_PATH` の単一順序が階層順序と一致する」という本設計の中核前提を壊す。処理順序が二次索引になると、ルートも兄弟も別の順で返る。
- **論理関係 (`LCHILD` / 論理親子 / 連結セグメント)**: データが木ではなく網になる。`HIERARCHY_PATH` は単一の親しか表現できない。
- **GSAM**: IMS バッチのシーケンシャルファイル。`CHKP` / `XRST` による再始動の対象であり、バッチ資産で頻出する。
- **Fast Path (DEDB / MSDB)**: `FLD` コールなど別の API 群を持つ。

**改善:** 対応・非対応の線を明示的に引く。非対応は **L0 として、コンパイル時または PSB ロード時に診断を出す** (要件 §4.1 の原則、および第 11 章への列挙)。特に二次索引は、対応しないなら「`PROCSEQ=` を持つ PCB は受け付けない」と宣言する。黙って主キー順で返してはならない。

<a id="ir-08"></a>
### IR-08 [P1] ステータスコード表が FR-164 の要求を満たしていない

**反証:** FR-164 は状態コードとして「`GA`、`GB`、`GE`、`II` 等」を例示している。`ims-dli-complex-semantics-report.md` §6 の表には **`GA` が無い**。

`GA` (階層のより上位レベルへ移った) と `GK` (同一レベルの別セグメントタイプへ移った) は、**無限定 `GN` のループで業務プログラムが分岐に使う中核コード**である。この 2 つが返らないと、無限定 `GN` で木を舐めるプログラムはセグメント種別の切り替わりを検出できない。

他に欠けているもの: `GP` (親境界が確立していない状態での `GNP`。§3 の Parentage 設計と直結する)、`GD`、`AD` (不正なファンクションコード)、`AI` (入出力エラー)、`AM` (`PROCOPT` が許さない操作)、`AO`、`FW`、`NI`、`TH`。`AM` は `PROCOPT` を扱う以上、対策 5 とセットで必要になる。

**改善:** FR-164 の列挙を満たす完全な表を作り、各コードに (a) 発生条件、(b) 出典、(c) 検証レベルを付ける。少なくとも `GA` / `GK` / `GP` / `AM` は MVP に入れる。

<a id="ir-09"></a>
### IR-09 [P1] SSA の文法が実資産の形を表現できていない

**反証:** 資料が扱う SSA は `SEGNAME*C(FIELD  = VALUE)` の 1 形だけである。実際には次がある。

- **無限定 SSA** (`SEGNAME  ` のみ。8 バイト + 空白)。`GN` の最頻形。
- **レベルごとの複数 SSA** (親と子に 1 つずつ)。資料は `List<ParsedSsa>` を受けるところまでは書いているが、各レベルでの位置づけ規則が無い。
- **ブール結合**: AND (`*` または `&`)、OR (`|`)、独立 AND (`#`)。
- **関係演算子 6 種**: `=`/`EQ`、`>`/`GT`、`<`/`LT`、`>=`/`GE`、`<=`/`LE`、`!=`/`NE` (記号形と英字形の両方)。資料は `=` しか示していない。
- **コマンドコード `*C`** (連結キーによる指定)。実資産で頻出するが、表 (§2) に無い。他に `-` (null)、`Q` / `O` も無い。

**改善:** SSA の文法を BNF で固定し、`SsaParser` の契約とする。非対応の形は `AJ` (構文エラー) で誤魔化さず、**「対応していない」と分かる診断**を出す。

<a id="ir-10"></a>
### IR-10 [P1] 可変長セグメントの表現が定義されていない

**反証:** 非正規化を選んだ理由の 1 つが ODO であるにもかかわらず、`SEG_DATA` が可変長セグメントの 2 バイト長フィールド (`LL`) を含むのか含まないのかが、どこにも書かれていない。`REPL` でセグメント長を変えられるのか (IMS の可変長セグメントでは変えられる)、`ISRT` 時に `LL` を誰が設定するのかも未定義。`BYTES=(max,min)` の最小長検査も無い。

**改善:** `SEG_DATA` のバイトレイアウトを (`LL` を含む / 含まない) のどちらかに確定し、可変長セグメントの `ISRT` / `REPL` / `*D` パス呼出しでの長さの扱いを明記する。

<a id="ir-11"></a>
### IR-11 [P1] `CHKP` を「JDBC commit」に単純化しており、位置の破棄が抜けている

**反証:** 設計 78 §3.1 と ロードマップ第 3 増分は `CHKP` を「JDBC トランザクションコミットとの同期」としか書いていない。実機の `CHKP` は**コミットに加えてデータベースの位置を破棄する**。`GN` ループの途中で `CHKP` を打つバッチは、`CHKP` の後に `GU` で位置を取り直さなければならない。これを再現しないと、`CHKP` を挟んだ `GN` ループは実機と違う結果を返す (実機では止まるはずのループが動き続ける、あるいはその逆)。

さらに symbolic `CHKP` (ユーザ領域の退避) と `XRST` (再始動) が未設計である。**バッチ再実行という、IMS バッチ移行で最も要求される機能がここに集中している。**

**改善:** `CHKP` の意味論を「コミット + 全 PCB の位置破棄 (+ 指定領域の退避)」として定義し、位置破棄が観測できるテスト (`CHKP` を挟んだ `GN` ループが実機同様に振る舞う) を書く。`XRST` は対応/非対応を明示する。

## C. RDB ストレージエンジン設計の内部欠陥

<a id="ir-12"></a>
### IR-12 [P0] 兄弟順序の維持方法が未設計で、提案されたギャップ採番は辞書順を壊す

**反証:** 2 つの問題が重なっている。

**(a) キー付きセグメントの兄弟順序が誰の責任か書かれていない。** シーケンスフィールドを持つ兄弟セグメントは**キー昇順**に並ぶ。しかし資料は `HIERARCHY_PATH` を「100 刻みのギャップ採番」で振るとしか書かず (§4 の注)、キー順との対応付けを書いていない。キー `C`→`A`→`B` の順に `ISRT` された場合、`HIERARCHY_PATH` は `A < B < C` になっていなければならない。ギャップは有限なので、同じ隙間への挿入が刻み幅を超えた時点で枯渇する。

**(b) 枯渇時の再採番は部分木全体の書き換えになる。** `HIERARCHY_PATH` は主キーであり、かつ全子孫の `PARENT_PATH` と自身のパスに埋め込まれている。1 ノードの再採番は部分木全体の行の主キー更新を意味する。資料は「他の全レコードのキーを更新することなく高速に挿入できます」と書いているが、これはギャップが残っている間だけ成り立つ。

**(c) 資料が枯渇の回避策として挙げる「小数点採番」は、先行順走査そのものを壊す。** `RULES=(FIRST)` の行に「既存の同キーの最小シーケンス番号より小さい番号（または小数点・ギャップ採番）」とある。実測 (C ロケール = バイト順 = B-Tree 順):

```
$ LC_ALL=C sort
/000001/01-000100
/000001/01-000100.5            <- '.' (0x2E) < '/' (0x2F)
/000001/01-000100/01-000100    <- 自分の子が、兄弟の後ろに落ちる
/000001/01-000101
```

期待する先行順は `01-000100` → **その子** → `01-000100.5` → `01-000101` である。`.` が `/` より小さいため、**`GN` が孫より先に兄弟を返す**。深さ優先・先行順が崩れる。

**改善:**
- 兄弟順序の正本を決める。素直なのは `ORDER BY PARENT_PATH, SEQ_KEY_RAW` (キー付き) / `ORDER BY PARENT_PATH, SEQ_NO` (キー無し) であり、`HIERARCHY_PATH` を順序の正本にしない。
- `HIERARCHY_PATH` を順序の正本として維持するなら、**各段を固定幅・固定文字集合に強制し、小数点採番を禁止する**。そのうえで再採番の発生条件・コスト・排他範囲を設計に書く。
- どちらにせよ、この 3 点は `verify` の検査項目にする (IR-34)。

<a id="ir-13"></a>
### IR-13 [P1] `HIERARCHY_PATH` の照合順序が固定されていない

**反証:** `ORDER BY HIERARCHY_PATH ASC` が階層順と一致するのは、**バイト値順の照合順序のとき**だけである。資料は `ROOT_KEY_HEX` については照合順序に言及している (§4 の方言表に「`C` 照合順序」「BINARY 比較」) のに、**走査順序の要である `HIERARCHY_PATH` については何も書いていない**。PostgreSQL のデータベース既定照合 (glibc / ICU) は句読点の重みが異なりうるため、既定に任せてはならない。

**改善:** DDL に `HIERARCHY_PATH VARCHAR(256) COLLATE "C"` (Db2 は相当の指定) を明記する。理由は [設計 80](../design/80-file-io.md) の「生バイトで持つ」と同じであり、コメントにそう書く (CLAUDE.md 決めごと)。索引もその照合で作られることを確認する。

<a id="ir-14"></a>
### IR-14 [P1] `VARCHAR(256)` が階層深さの上限を暗黙に決めている

**反証:** IMS の階層は 15 レベルまである。資料の採番例 (`/01-000100` = 10 文字/段) なら 15 段で 157 文字に収まるが、ギャップ採番で桁が伸びれば溢れる。溢れたときの挙動 (切り捨て = 静かなデータ破壊) が未定義である。

**改善:** 段数と 1 段あたりの最大幅から上限を計算して固定し、超過は例外にする。切り捨てを起こさない。

<a id="ir-15"></a>
### IR-15 [P1] 非キー項目の SSA 修飾に索引が無く、性能主張の根拠が無い

**反証:** SSA はシーケンスフィールド以外の任意の `FIELD` でも修飾できる。その場合 BLOB 内のオフセットを取り出して比較することになり (`SUBSTRING(SEG_DATA ...)` 相当)、索引が効かず部分木の全走査になる。資料の性能節はブロックプリフェッチの話しかしておらず、「メインフレームと同等以上のスループット」の根拠になっていない。

**改善:** 非キー修飾の実行計画を設計に書く (エンジン側でプリフェッチしたブロックをメモリで絞る、頻出フィールドを生成列 + 索引に昇格させる等)。性能の主張は測ってから書く (CLAUDE.md §7: 数は記録して並べるもの)。

<a id="ir-16"></a>
### IR-16 [P2] `IMS_ROOT_INDEX.ROOT_KEY_HEX` が冗長で、不整合の種になる

**反証:** `ROOT_KEY_HEX` は `ROOT_KEY_RAW` の関数である。バイト順照合が効くなら範囲検索は `ROOT_KEY_RAW` で足りる。同じ情報を 2 列に持つと、ずれたときにどちらが正本か決まらない。

**改善:** 削るか、生成列 (`GENERATED ALWAYS AS`) にして手で書けなくする。

## D. 並行性設計の矛盾

<a id="ir-17"></a>
### IR-17 [P0] 対策 3 (DML 遅延バッファリング) が read-your-own-writes を壊す

**反証:** 対策 3 は「コミット時まで DML 操作を内部メモリにバッファリング」し、コミット直前に `HIERARCHY_PATH` 昇順でまとめて発行する、としている。

しかし DL/I では、**同一 UOW 内で `ISRT` した直後の `GU` / `GN` / `GNP` はそのセグメントを見る**。`DLET` した直後の `GN` はそれを見ない。COBOL 資産は「挿入 → 読み直して検算」「削除 → 走査し直し」を普通に書く。DML を溜めたままだと、後続の `SELECT` は自分の更新を見ない。**資料はバッファと問い合わせ結果のマージについて一言も書いていない。**

さらに、`ISRT` を遅延すると `II` (重複キー) の返却タイミングが実機とずれる。実機は `ISRT` のその場で `II` を返すが、遅延すればコミット時まで分からない。**ステータスコードで分岐する COBOL の制御フローが変わる。**

**改善:** どちらかを選ぶ。
- **対策 3 を捨てる。** 対策 1 (ルートアンカーロック) が入っていれば、同一ルート配下でのロック順序交差はもう起きない。対策 3 の主目的 (循環待ちの防止) は対策 1 と重複しており、費用対効果が悪い。**これを推奨する。**
- 残すなら、読み取り経路にバッファのオーバレイを噛ませる設計 (未コミット DML を SQL 結果へマージし、`II` を発行時点で判定する) を明記する。これは実質的にミニストレージエンジンを 2 段持つことになり、複雑度が跳ね上がる。

<a id="ir-18"></a>
### IR-18 [P1] ルートアンカーロックは新規ルートの `ISRT` を守れない (ファントム)

**反証:** 対策 1 は `SELECT ... FROM IMS_ROOT_INDEX WHERE ... FOR UPDATE` でロックする。**その行がまだ存在しない場合 (新規ルートの `ISRT`)、ロックする対象が無い。** 同一ルートキーを同時に `ISRT` した 2 つのトランザクションは直列化されず、主キー衝突で片方が失敗する。それを `II` として返すのか、デッドロック扱いで `U0777` にするのかも未定義である。

**改善:** ルート行の先行確保 (`INSERT ... ON CONFLICT DO NOTHING` → `SELECT ... FOR UPDATE`) 等、ファントムを含む手順を明記する。返却するステータスコードも決める。

<a id="ir-19"></a>
### IR-19 [P1] 「デッドロック 100% 撲滅」はルート内に限られる

**反証:** ADR-0015 は「同一ルートキー配下の」と限定して書いているが、検討資料 §2 対策 1 は「同一ルート配下のデッドロックが原理的に 100% 撲滅」と書いた直後、§4 のまとめでは「確実に抑え込むことができます」と無条件に読める書き方をしている。設計 78 §1 も「木構造内部での循環待ちデッドロックを原理的に排除」である。

**複数ルート・複数 DBD をまたぐ更新は普通にある** (顧客 A と顧客 B を同時に更新する振替処理など)。ルートロックの獲得順序が交差すればデッドロックする。

**改善:** ルートロックの獲得順序を `(DBD_NAME, ROOT_KEY_RAW)` 昇順に規定し、対策 3 と同じ「順序を揃える」規律をルート間にも適用する。主張の範囲を「同一ルート配下」に統一して書き直す。

<a id="ir-20"></a>
### IR-20 [P1] `PROCOPT=G` を「ロック抑止」に写像しているのは近似の暗黙適用である

**反証:** 対策 5 の表は `PROCOPT=G` を「参照専用 (Read Only) → 一切のロックを抑止」と写像している。しかし整合性を捨てた読み取りは `G` ではなく **`GO` (Get Only)** の意味論である。`G` は整合性つきの読み取りであり、更新中のデータを読まない。

これは「近似を既定として黙って適用する」ものであり、FR-153 が Db2 のカーソルについて明記している方針 (「未分類 cursor へ近似方式を暗黙適用しない」) にも、CLAUDE.md 増分の型 3 にも反する。移行後だけダーティリードが起きる、という最も見つけにくい種類の差になる。

**改善:** `G` と `GO` を分ける。`GO` のみロック無し (Read Uncommitted 相当) とし、`G` は整合性を保つ。`GOx` (`GON` / `GOT`) の扱いも決める。

<a id="ir-21"></a>
### IR-21 [P2] 対策 4 と対策 5 が基本設計と両立しない

**反証:** 対策 5 は `PROCOPT=E` に対し「対象 DBD のテーブル全体に対して `LOCK TABLE ... IN EXCLUSIVE MODE`」とする。しかし基本設計 (ADR-0013、設計 78) のテーブルは**単一の `IMS_SEGMENT_STORE`** である。ここで `LOCK TABLE` を打つと、無関係な全 DBD が止まる。対策 4 (Table-per-DBD) は「本番運用や高負荷環境では」という条件付きの提案であって、既定ではない。

**改善:** Table-per-DBD を既定にするか、`PROCOPT=E` を「当該 DBD の全ルート行のロック」など単一テーブルで成立する方式に変える。前提条件を対策 5 に明記する。

<a id="ir-22"></a>
### IR-22 [P2] `U0777` と「最大 3 回」に出典が無い

**反証:** 「最大 3 回まで同一メッセージの処理を自動再試行する（メインフレーム IMS TM の標準挙動に準拠）」と断定しているが、再スケジュールの回数は定義側の設定に依存し、固定 3 回ではない。CLAUDE.md の決めごと (「公開仕様と観測できる振る舞いだけを根拠にする」) に照らして、出典の無い断定を「準拠」と書くべきではない。

**改善:** 出典を付けるか、「本実装の既定値であって実機の規定値ではない」と書く。回数は設定可能にする。

## E. IMS TM / メッセージング

<a id="ir-23"></a>
### IR-23 [P0] 2 相コミットを落としたことが明示されておらず、UOW の原子性が失われる

**反証:** これは資料群の内部矛盾である。

`ims-tm-and-mq-architecture.md` §2.2 は、実機の重要な性質としてこう書く。

> OTMA と IBM MQ は z/OS の RRS (Resource Recovery Services) 等と連携し、「MQ から電文を抜く」「IMS DB / Db2 を更新する」「MQ へ応答を返す」を一連のトランザクションとして原子的に同期保証します。

その次の資料 `ims-tm-rabbitmq-jms-proposal.md` §5.3 は、これを `session.commit()` (JMS) と JDBC コミットの **2 本立て**に置き換える。RabbitMQ は XA をサポートしない。したがって:

- JMS コミット後・JDBC コミット前に落ちる → **電文は消えたが DB は更新されていない (電文の消失)**。
- JDBC コミット後・JMS コミット前に落ちる → **DB は更新済みなのに電文が再配信される (二重処理)**。

ADR-0014 の「マイナス影響 / トレードオフ」には「AMQP と JMS の仕様差異をアダプタ層で吸収する実装が必要」としか書かれておらず、**UOW 原子性の喪失という最大のトレードオフが記録されていない**。これは「COBOL からの完全透過性」という同 ADR の主張とも両立しない。透過に見えて、障害時の意味論が違う。

**改善:** どちらかを選び、選ばなかった側の観測可能な差を書く。
- **XA 対応のブローカ (ActiveMQ Artemis 等) を既定にする。** JMS 中立という ADR-0014 の狙いはそのまま活き、ローカル/CI で閉じる要件も満たせる。
- **RabbitMQ を維持し、at-least-once + 冪等化を明示する。** メッセージ連番と処理済みキーを同一 RDB トランザクションに書く outbox / inbox 方式にし、「実機の原子性とは異なる」ことを ADR とリリースノートに書く。

いずれにせよ ADR-0014 の影響欄を書き直す。

<a id="ir-24"></a>
### IR-24 [P0] 会話型トランザクション (SPA) が丸ごと欠落しており、「CICS より容易」の結論が成立しない

**反証:** `ims-tm-and-mq-architecture.md` §4.2 と §5 は次のように結論する。

> **IMS TM の容易さ**: 単なる「バイト配列をキューから取って (`GU`)、バイト配列をキューへ返す (`ISRT`)」だけなので、プログラミングモデルとしては極めてクリーン
> CICS に比べて対話状態の管理が少なく、「純粋なメッセージ駆動」であるため（略）非常に見通しやすい領域です

しかし IMS には**会話型トランザクション**があり、その状態は **SPA (Scratch Pad Area)** で持ち回る。SPA は**メッセージの第 1 セグメントとしてプログラムへ渡され、`ISRT` で書き戻す**。つまり:

- CICS の COMMAREA と同じ課題 (永続化、サイズ、有効期限、クラッシュ回復、`/EXIT` による打ち切り) が IMS にもそのまま存在する。
- **入出力バッファのレイアウトが変わる。** 資料の MPP サンプル (`LL`/`ZZ`/`TRANCODE`/データ) は非会話型のものであり、会話型では先頭に SPA が来る。中立ポートの設計が変わる。

SPA は 8 本のどこにも現れない。「対話状態の管理が少ない」という判断は、**存在を数え落としたことによる**ものであり、これがロードマップ (MFS を後回しにしてよい、TM は簡単) の根拠になっている。

**改善:** SPA と会話型トランザクションを設計 78 に追加し、[ADR-0008](../decisions/0008-cics-on-spring-mvc-and-session.md) の会話状態ストアと共通化できるかを検討する。§4.2 / §5 の「容易」という結論を、SPA と MFS を数に入れて書き直す。

<a id="ir-25"></a>
### IR-25 [P1] 複数セグメント電文・代替 PCB が扱えないモデルになっている

**反証:** 資料のモデルは「`GU` = 1 メッセージ受信」「`ISRT` = 1 メッセージ送信」に固定されている。実際には:

- **入力の 2 セグメント目以降は I/O PCB への `GN`** で取る。資料に I/O PCB の `GN` は一度も出てこない。
- **出力は複数の `ISRT` で 1 電文を組み立て、`PURG` または次の `GU` で確定する。** `PURG` が無い。
- **代替 PCB (ALTPCB) への `ISRT`** で別の LTERM / 別トランザクションへ送れる。`CHNG` で宛先を差し替える。どちらも無い。

これらを使う資産は動かない。しかも「動かない」ではなく「1 セグメント目だけ送られる」のような**部分的に正しく見える壊れ方**をする。

**改善:** I/O PCB の `GN` / `PURG` / `CHNG` / 代替 PCB を `ImsQueuePort` の契約に含めるか、明示的に非対応として診断する。`ImsQueuePort` の現在の 4 メソッド (`poll` / `sendReply` / `commit` / `rollback`) では表現できないので、契約を凍結する前に決める。

<a id="ir-26"></a>
### IR-26 [P1] 電文順序の保証が検討されていない

**反証:** IMS はトランザクションコード単位で電文を FIFO 処理する。RabbitMQ では、複数コンシューマ、prefetch、`rollback` による requeue のいずれでも順序が変わりうる。順序に依存する資産 (同一口座への連続更新など) で結果が変わる。資料に順序の記述は無い。

**改善:** 順序保証の要否を決め、必要なら構成 (キューあたり単一コンシューマ、`prefetch=1`、requeue 時の順序) を設計に書く。並列スケジューリング (実機の複数 MPP 領域) との関係も整理する。

<a id="ir-27"></a>
### IR-27 [P2] 依存ライブラリとブローカの版が未確認である

**反証:** 次はいずれも「そう書いた」だけで、解決できることを確認していない。

- `com.rabbitmq:rabbitmq-jms:3.3.0` と `jakarta.jms:jakarta.jms-api:3.1.0` の組み合わせ。
- `rabbitmq:3.13-management`。2026 年時点では 4.x 世代であり、3.13 は保守期間の観点で新規採用に向かない。
- RabbitMQ JMS クライアントでトピックを使う場合に必要な **`rabbitmq_jms_topic_exchange` プラグイン**が `compose.yaml` で有効化されていない。キューのみなら不要だが、その前提が書かれていない。

CLAUDE.md §6 は「道具が作った失敗を処理系の失敗と読み違えると、数そのものが信用できなくなる」と言う。基盤の版はここに当たる。

**改善:** 実際に依存解決と起動を確認してから版を固定し、確認した日付を書く。`infra/db2/` と同じ扱いにする。

## F. MFS

<a id="ir-28"></a>
### IR-28 [P1] 「100% 流用」の流用元がまだ存在しない

**反証:** MFS 資料の中心的な論拠は「BMS 向けに作成する UI/CSS/JS を 100% 流用できる」である。しかし **BMS の実装はリポジトリに 1 ファイルも無い** (`bms` / `thymeleaf` を名前に含むソースは 0 件、ADR-0010 と本資料のみ)。さらに [AR-12](2026-09-09-interop-adversarial-review.md) は「BMS renderer の実現方式を prototype 前に固定している」を **P0 未解決**として挙げている。

つまり **未実装かつ方式未確定の資産に対する 100% 流用**を、MFS のフェーズ 1 の前提にしている。

**改善:** MFS フェーズ 1 の前提条件を「AR-12 の spike 合格 = `WEB_3270_STRICT` 方式の確定」と明記する。流用率の見積もりは、BMS が動いてから測る。

<a id="ir-29"></a>
### IR-29 [P1] MFS 固有機構の欠落が「BMS + パーサ」という見立てを弱める

**反証:** 資料が挙げる MFS 固有の追加実装は「マクロのパース」「MOD 名の解決」「論理ページング」の 3 つだが、他にもある。

- **`PFK=` によるリテラル置換**: PF キーの押下で、あらかじめ定義したリテラルが電文へ挿入される。BMS には無い機構で、サーバ側の入力構築規則が変わる。
- **`DPAGE` の `COND=`**: 入力内容によってデバイスページを選び分ける。
- **`MFLD` のリテラル / システムリテラル** (日付・時刻・LTERM 名等の自動埋め込み)。
- **`FILL=` / `JUST=`**: 充填文字と寄せの規則。資料は「充填文字（FILL）」に触れているが規則を定義していない。
- **`EXIT=`** (フォーマット出口ルーチン)、**MFS バイパス**、**DFS メッセージ** (システムメッセージの画面出力)。

**改善:** MFS のマクロ要素ごとに対応・非対応の表を作る。非対応は L0 として診断する。

<a id="ir-30"></a>
### IR-30 [P2] 論理ページングのキー割り当てに出典が無い

**反証:** 「ユーザーが PA2 キー（または `/FOR` コマンド）で次ページ・前ページをめくる」と断定しているが、既定のページング操作キーは出典なしに書ける事柄ではない。

**改善:** 出典を付けるか、`provisional.md` に登録する。

## G. 運用ツール

<a id="ir-31"></a>
### IR-31 [P1] DBRC・イメージコピー・リカバリが対象外で、選ばれた 2 本は RDB では価値が最も低い

**反証:** 資料が実装対象に選んだのは `DFSURGU0` (アンロード) と `DFSURGL0` (リロード) である。これは **HD 再編成**のためのユーティリティであり、**RDB バックエンドでは再編成という作業自体が消える**。つまり移行後もっとも不要になるステップを最初に作ることになる。

一方、実運用の JCL にほぼ必ずある次が 8 本のどこにも出てこない。

- **DBRC (RECON データセット)**: IMS バッチ JCL の標準構成要素。`DBRC=Y`、`//DFSRESLB`、RECON の 3 データセット。
- **イメージコピー / リカバリ / バッチバックアウト**: 障害時の運用の中心。
- **`/DIS`・`/STA`・`/STO`** 等のコマンド (資料は表に挙げるが CLI 対応表には `stat` しかない)。

**改善:** 「JCL 無修正」を目的にするなら、**まず実資産の JCL に現れるユーティリティを頻度順に洗い出す**。再編成系は認識して no-op 化する (「RDB バックエンドでは不要」と `SYSPRINT` に出して RC=0) 方が、忠実に模倣するより価値が高い可能性がある。DBRC は対応/非対応を明示する。

<a id="ir-32"></a>
### IR-32 [P1] IMS バッチの起動経路 (`DFSRRC00`) が設計されていない

**反証:** 概要資料は「A. IMS バッチ / BMP」を「**最も需要が高く、移行の第一歩になりやすい**」と自ら位置づけている。ところがその JCL 側の入口 —— `PGM=DFSRRC00,PARM='DLI,プログラム名,PSB名'` (BMP なら `BMP`)、`//IMS DD` (DBD/PSB ライブラリ)、`//DFSVSAMP DD` (バッファプール)、DBD 名の DD 割り当て —— は、運用ツール資料のユーティリティ実行例に付随して 1 行現れるだけで、**設計 78 にも `cobol-job` との接続点としても定義されていない**。

MVP として最優先のはずの経路が、設計から抜けている。

**改善:** `DFSRRC00` を `cobol-job` のユーティリティレジストリに登録し、`PARM` の解析 (`DLI` / `BMP` / `ULU`)、PSB のロード、PCB リストの構築と `PROCEDURE DIVISION USING` へのバインドまでを設計 78 に書く。第 1 増分はここである。

<a id="ir-33"></a>
### IR-33 [P2] ユーティリティ名と役割に出典が無く、少なくとも 2 件が疑わしい

**反証:**
- **`DFSNDRV0`**: 「ログや整合性検証、レコードダンプ・診断」とされているが、この名前は一般に知られた IMS 標準ユーティリティとして確認できない。
- **`DFSERA10`**: 同じ行にまとめられているが、これは**ログの選択・整形印刷**のユーティリティであって、データベースのレコードダンプではない。

CLAUDE.md の決めごとは「公開仕様と観測できる振る舞いだけを根拠にする」である。名前と役割は、資料の信頼性そのものに関わる。

**改善:** 各ユーティリティ名・役割・`PARM` 形式に出典を付ける。確認できないものは表から落とす。

<a id="ir-34"></a>
### IR-34 [P2] `verify` が、この設計で実際に壊れるものを検査しない

**反証:** `verify` の検査項目は「孤児セグメント (親が存在しない)」と「シーケンスキーの順序」である。孤児は、書き込みが必ずエンジン経由なら通常発生しない。**この設計で実際に壊れるのは IR-12 (兄弟順序とギャップ枯渇)、IR-13 (照合順序)、IR-14 (パス長超過) である。**

**改善:** `verify` に次を入れる。(a) `HIERARCHY_PATH` の各段が固定幅・許可文字であること、(b) 兄弟の `HIERARCHY_PATH` 順序が `SEQ_KEY_RAW` 順序と一致すること、(c) 残ギャップの最小値 (枯渇の予兆)、(d) パス長の最大値、(e) DB の照合順序が期待どおりであること。CLAUDE.md §6 のとおり、**道具にも検査を仕込む。**

### 判断を仰ぐ点

改訂で**あえて手を付けなかった**ことが 2 つある。いずれもスコープの決定であり、こちらで決めるべきものではない。

1. **要件定義書 (`docs/requirements.md`) は変更していない。**IMS DB 実体・TM・MFS・運用ツールを要求する FR を追加するか、FR-164 の「初期リリースではインタフェース定義のみ」を維持してこれらを凍結するかは、プロダクトのスコープの決定である。当面は ADR を**提案**に留め、[P-098](../decisions/provisional.md) の解消条件として記録した。
2. **メッセージブローカを RabbitMQ から変更していない。**UOW 原子性は at-least-once + 冪等化で代替する方式を既定として書いたが、XA（Artemis + JTA）を選ぶ余地は残してある。JTA には第三者スターターの追加が要るため、費用対効果の判断が要る ([P-104](../decisions/provisional.md))。

### ゲートの現況

第 2 表の実装開始ゲート G-IMS1〜G-IMS10 は、**いずれも未合格である。**本改訂は「何が未解決かを正しく書いた」ところまでであり、ゲートを開けたわけではない。特に G-IMS2（証拠）は、IMS の oracle をどう用意するかが決まるまで開かない。
