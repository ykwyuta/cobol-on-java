# 設計 40: 構文解析

対象: 要件 FR-001, FR-183 / 方針 ARC-8 / 決定 D-5, D-14, D-18

## 位置付け

プリプロセッサ (設計 30) が作ったトークン列を受け取り、構文木を作る。
<b>字句解析器を持たない</b>。カラムも継続行も `COPY` も指示文も「島」も、
ここへ来る前に消えている。

決定 D-5 に従い、文法は ANTLR4 で書く。手書きのプリプロセッサと宣言的な文法という
分担であり、文脈依存性はすべて前段が吸収している。

## 文法は「構文文法」である

`CobolParser.g4` は `parser grammar` であり、字句解析器を伴わない。トークンは
`tokens { ... }` で宣言し、`SourceTokenSource` が供給する。

ANTLR の字句解析器を使わないのは、<b>使えないから</b>である。`PIC 99.99.` の 2 つの
ピリオドは正規表現では分けられず、`EXEC SQL` の中身は COBOL ですらない。
これらは決定 D-14 の「島」として、前段で 1 個のトークンに畳んである。

## 予約語の表は文法から引き出す

`SourceTokenKind.WORD` は予約語と利用者定義語の両方を含む。`SourceTokenSource` が
文法の語彙を引き、当たれば予約語、当たらなければ `IDENTIFIER` とする。
<b>COBOL 語のハイフンは下線に読み替える</b> — `COMP-3` は `COMP_3` である。

表を文法から引き出しているのは、<b>表と文法がずれないようにする</b>ためである。
別に持つと、文法へ語を足したときに表の更新を忘れる。

区切り文字・島・語の種別そのものを表す名前 (`PERIOD`、`PICTURE_STRING`、`NUMBER` など) は
表から除いてある。除かないと、`NUMBER` という名前のデータ項目が数字定数になってしまう。

いま予約語として扱うのは<b>文法が実際に使っている語だけ</b>である。COBOL の予約語の
全体は約 500 語あり、そこへ到達していない (暫定判断 P-024)。

## 数字定数と利用者定義語は綴りで分ける

どちらも `WORD` として来る。`[+-]?(9+(.9+)?|.9+)(E[+-]?9+)?` の形なら数字定数、
そうでなければ利用者定義語とする。`1.5` が 1 語として届くのは、前段が
「空白が続くピリオドだけが区切り」という規則 (決定 D-18) を適用しているからである。

小数点で<b>始まってもよい</b>。COBOL の決まりは「小数点がいちばん右に来てはならない」
であって、いちばん左は許す。`PIC V99 VALUE .25` は正しい COBOL であり、NIST の検査
スイートも書いている。区切りの終止符と紛れないのは、上と同じ D-18 の規則による。
`.5` は空白が続かないので定数、`. ` は区切りである。

はじめは「小数点の前に必ず数字が要る」と書いていた。CCVS85 を流して<b>21 本が
そこで止まっている</b>ことに気付いた (暫定判断 P-062)。

## 覚え書きの句は読んで捨てる

COBOL には<b>書いてあっても処理系が何もしない</b>句がいくつかある。見出し部の注記段落
(`AUTHOR` など)、`FD` の `DATA RECORDS ARE`、`LABEL RECORDS ARE STANDARD` がそれで
ある。どれも「こう書いてある」と人へ伝えるためのものであり、意味は持たない。

読み飛ばすのではなく<b>読んで捨てる</b>。読み飛ばすと、その先の句が何であっても構文
解析器が詰まる。捨てると決めた句は文法に書いてある。

注記段落だけは文法では捨てられない。どこで終わるかを決めるのが桁だからである
(暫定判断 P-064)。詳しくは[設計 30](30-compiler-preprocessor.md) の読み取りの段にある。

## コンマとセミコロンは構文解析器へ渡さない

COBOL の決まりでは、この 2 つは<b>空白が書ける場所ならどこへでも書ける飾り</b>で
あり、意味を持たない。`01 A, REDEFINES B PIC X.` と `01 A REDEFINES B PIC X.` は
同じである。

文法の側で「ここにはコンマが来るかもしれない」を書いて回ることもできるが、
<b>書き漏らしたところだけが読めなくなる</b>。実際そうなっていて、18 本が
`extraneous input ','` で止まっていた。`SourceTokenSource` が渡さないことにすれば
漏れようがない。

`DECIMAL-POINT IS COMMA` を書くとコンマは小数点になるが、それはまだ読めない
(暫定判断 P-010)。読めるようにする段で、ここも一緒に決める。

## 診断は元のソースを指す

`OriginToken` が元の `SourceToken` を持ち回る。ANTLR の行と桁は 1 本の文字列を
前提にしているが、`COPY` を展開したトークン列は<b>複数のファイルにまたがる</b>。
`DiagnosticListener` は ANTLR が渡す行と桁を使わず、トークンが持つ出自を使う。

展開後の位置を出しても直す先が分からない。コピー句の中の誤りは、コピー句の
ファイル名と行で報告する。

### 誤りで止まらない

1 つ目の誤りで例外を投げると、移行作業では使い物にならない。誤りは
`Diagnostic` として集め、ANTLR の回復に任せて最後まで読む。

## いま解析できる範囲

| 部 | 範囲 |
| --- | --- |
| 見出し部 | `IDENTIFICATION` / `ID`、`PROGRAM-ID` (`COMMON` / `INITIAL` / `RECURSIVE`)、`END PROGRAM` |
| 環境部 | `CONFIGURATION SECTION` (`SOURCE-COMPUTER`、`OBJECT-COMPUTER`、`SPECIAL-NAMES`)、`INPUT-OUTPUT SECTION` (`FILE-CONTROL` の `SELECT`) |
| データ部 | `FILE` / `WORKING-STORAGE` / `LOCAL-STORAGE` / `LINKAGE` の各節とデータ記述項 |
| 手続き部 | `DECLARATIVES`、節、段落、文、一意名 (修飾・添字・部分参照) |

データ記述項の句は `REDEFINES`、`RENAMES`、`PICTURE`、`USAGE`、`SIGN`、`OCCURS`、
`VALUE`、`JUSTIFIED`、`BLANK WHEN ZERO`、`SYNCHRONIZED`、`GLOBAL`、`EXTERNAL`。
`VALUE` は 88 レベルのために値の並びと `THRU` の範囲も受け付ける。

### 効かない段落は丸ごと読み飛ばす

`SOURCE-COMPUTER` と `OBJECT-COMPUTER` は翻訳する機械と動かす機械の指定であり、
<b>翻訳の結果に効かない</b>。中身の綴りも処理系ごとに違う。したがって
`~PERIOD* PERIOD` で段落ごと読み飛ばす。

書式を細かく写しても、そこから得られるものがない。読み飛ばすと決めておけば、
知らない書き方で構文誤りになることもない。

## SPECIAL-NAMES はデータ部より前に読む

`SPECIAL-NAMES` で決まるのは処理系の外側との結び付けである (要件 FR-054, FR-135)。
通貨記号は PICTURE の解釈に、呼び名は `ACCEPT` と `DISPLAY` の行き先に効く。

<b>データ部より前に読まなければならない</b>。PICTURE の解釈が通貨記号に依るためである。
したがって翻訳の段は 環境部 → データ部 → 手続き部 の順になる。

## 次の増分

データ部の割り付けは[設計 50](50-data-layout.md)、手続き部は[設計 60](60-procedure.md) へ続く。

1. `EXIT PROGRAM` (9 本を止めている)。呼ばれた側から戻る文である。主プログラムでは
   何もしないという決まりがあり、`GOBACK` と同じにはできない。
2. `USAGE INDEX` (6 本、暫定判断 P-006 の残り) と `SET` の指標名 (3 本、暫定判断 P-035)。
3. `PROGRAM COLLATING SEQUENCE` (6 本、暫定判断 P-042)。
4. 66 レベルの `RENAMES`。
5. 入れ子プログラム。
6. `I-O-CONTROL` 段落と `DECLARATIVES`。
7. 通信部 (`COMMUNICATION SECTION`、3 本)。
