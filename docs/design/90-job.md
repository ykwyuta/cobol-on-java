# 設計 90: ジョブ実行

| 項目 | 内容 |
| --- | --- |
| 対応要件 | FR-130〜FR-137、FR-141〜FR-143、要件定義書 7.1 節 |
| ステータス | 内部モデル・宣言的形式・JCL・ユーティリティ 5 本・`DISP`・`SPACE`・異常終了コードと診断出力 実装済 |

## 何を決めるか

バッチの実資産は<b>プログラム 1 本では動かない</b>。JCL がステップを並べ、DD 名を実際の
データセットへ結び付け、復帰コードで後続の実行を決める。そこまで揃って初めて「ソース無修正で
動く」と言える。

## 内部モデルが先で、記述形式はあと (FR-130)

実行機構が解釈するのは<b>内部ジョブモデルだけ</b>である。JCL パーサも宣言的形式のパーサも
知らない。

```
JCL         ┐
            ├→ 内部ジョブモデル (Job / Step / DdAssignment / StepCondition) → 実行機構
宣言的形式  ┘
```

こうしておく理由は 2 つある。<b>どちらの形式で書いても結果が同じ</b>になること (要件 FR-132)。
そして、JCL の込み入った書式をパーサの中に閉じ込め、実行の側へ持ち込まないことである。

| 型 | 表すもの |
| --- | --- |
| `Job` | ジョブ 1 個。ステップの並び |
| `Step` | プログラム 1 本の実行。名前・プログラム名・`PARM`・DD 割当・条件 |
| `DdAssignment` / `DdTarget` | DD 名と行き先。実ファイル、`SYSOUT`、`DUMMY`、埋め込みデータ |
| `StepCondition` | 動かすかどうかの条件 |
| `JobState` | ここまでに起きたこと。復帰コードと異常終了の有無 |

## 条件は「真なら動かす」の向きに揃える (FR-136)

JCL の `COND` は<b>「真なら飛ばす」</b>という向きで書く。`COND=(4,LT,STEP1)` は
「STEP1 の RC が 4 より大きければ飛ばす」である。逆さまで読みにくく、誤りのもとでもある。

内部モデルでは<b>「真なら動かす」</b>の向きに揃えた。向きの反転は JCL パーサの仕事である。
宣言的形式は素直に書ける。

```
WHEN RC CHECK <= 4
```

異常終了の扱いも条件の一部として持たせている。ホストでは先行ステップが異常終了すると以降は
飛ばされるが、`COND=EVEN` と `COND=ONLY` がそれを覆す。「飛ばす／飛ばさない」を決めるものは
1 か所にあるほうがよい。

**動いていないステップの復帰コードは比べられない**。飛ばされたステップを名指す条件は
成り立たないものとして扱う。

## ステップは独立している (FR-130)

ステップごとに新しい実行時の入口を作る。作業場所も、読み込んだ副プログラムも、開いたファイルも、
復帰コードも<b>持ち越さない</b>。持ち越すのはジョブの状態だけである。

ホストではステップごとに別のアドレス空間が立つ。同じ実行時の入口を使い回すと、前のステップの
作業場所が残り、初期値から始まらないプログラムができてしまう。

## SYSOUT はスプールを通る (FR-135)

ホストでは `SYSOUT` へ書いたものがスプールに溜まり、ジョブが終わってから印字される。
ここでも作業領域のファイルへ溜め、ステップが終わったところで流し出す。

<b>プログラムから見れば普通のデータセットである</b>。行順編成のファイルを開いて書くだけであり、
`SYSOUT` のための特別な道が要らない。

`DUMMY` も同じ考え方で、空のファイルを割り当てる。読めば即座に終わり、書いたものは
捨てられる。埋め込みデータ (`SYSIN DD *` 相当) も、作業領域へ書き出して行順編成で割り当てる。

## PARM は先頭 2 バイトが長さである (FR-134)

参照実装と同じ形で渡す。受け取る側は連絡節にこう書いてある。

```cobol
LINKAGE SECTION.
01  PARM-AREA.
    05  PA-LEN  PIC S9(4) COMP.
    05  PA-TEXT PIC X(100).
PROCEDURE DIVISION USING PARM-AREA.
```

長さは 2 バイトの 2 進数であり、中身はコードページで符号化したバイト列である。
`PARM=` を書かなければ引数の並びは空になる。

## 宣言的形式 (FR-132)

内部モデルを<b>そのまま書ける</b>形式である。新しく組むジョブと、この処理系自身の試験に使う。
YAML などの外部ライブラリを使わないのは、`cobol-runtime` 以外へ依存を増やさないためである。

```
# 行頭の # は注記
JOB PAYROLL
STEP CHECK PGM=PAYCHK
  DD PAYIN DSN=data/pay.dat
  DD SYSOUT SYSOUT
STEP REPORT PGM=PAYRPT PARM=202609
  WHEN RC CHECK <= 4
  DD SYSOUT SYSOUT
  DD SYSIN DATA
    DETAIL
    TOTAL
  END
STEP CLEANUP PGM=PAYCLN
  WHEN ABEND
  DD SYSOUT SYSOUT
```

字下げに意味はない。読みやすさのためだけのものである。

条件の組み合わせは<b>1 段だけ</b>である。`AND` と `OR` を混ぜて書けない。混ぜたときの
優先順位は書いた人の思い込みと食い違いやすく、誤りとしたほうがよい。

### 知らない書き方は誤りにする

読み飛ばさない。書いたつもりの指定が効いていないことに気付けないからである。
これは JCL のフロントエンドでも同じ方針である (要件 FR-131)。

## JCL フロントエンド (FR-131)

既存の JCL 資産を<b>書き換えずに実行する</b>ためのものである。読み取った結果は内部ジョブ
モデルであり、宣言的形式で書いたものと区別がない。同じ内容を両方の形式で書くと、
組み上がるモデルが等しくなる。

### 書式の都合は読み取りで尽くす

カードを読む側でやることは 3 つある。<b>注記を落とし、継続をつなぎ、埋め込みデータを
切り出す</b>。ここまでで書式の都合は尽きており、意味を取る側は 1 文ずつ見ればよくなる。

| 決まり | 扱い |
| --- | --- |
| 1〜2 桁が `//` | 3 桁目が `*` なら注記カード |
| 73 桁目から先 | 通番であり、見ない |
| オペランドの外の空白 | そこから先は注記 |
| オペランドの末尾のコンマ | 次のカードへ続く。続きのカードは名前欄が空 |
| `DD *` | 次の文か `/*` までが埋め込みデータ |
| `DD DATA` | `/*` まで。データの中に `//` で始まる行があるときに使う |
| 名前欄の空いた `DD` | 直前の `DD` への連結 |

コンマで区切るときは<b>括弧と引用符の中を区切らない</b>。`COND=((4,LT),(8,GT,STEP1))` は
1 つのオペランドであり、`PARM='A,B'` も 1 つである。

### COND の向きを裏返す

JCL の `COND` は<b>「真なら飛ばす」</b>という向きで書く。さらに `COND=(4,LT,STEP1)` は
「4 < STEP1 の RC」と読む。左右も逆さまである。内部モデルは「RC 関係 値」で「真なら動かす」
なので、ここで<b>2 回裏返す</b>。

| JCL | 内部モデル |
| --- | --- |
| `COND=(4,LT,CHECK)` | `NOT (RC(CHECK) > 4)` |
| `COND=((4,LT,A),(8,EQ))` | `NOT (RC(A) > 4 OR 最大 RC = 8)` |
| `COND=EVEN` | 異常終了していても動かす |
| `COND=((8,LE,A),EVEN)` | 異常終了を越え、かつ `NOT (RC(A) >= 8)` |

試験が複数あれば<b>どれか 1 つでも成り立てば飛ばす</b>。裏返すと「すべて成り立たなければ
動かす」になる。

### データセット名は基点の下に置く

`DSN=PAY.MASTER` はデータセット名であり、ファイルの場所ではない。基点のディレクトリの下に
<b>その名前のまま</b>置かれているものとする。区切りの点をディレクトリに読み替えないのは、
ホストの一覧と見比べたときに同じ名前が並ぶほうが追いやすいからである。

### 手続きの展開は組み立ての前に済ませる

`PROC` / `INCLUDE` / `SET` とシンボリックパラメタは、カードを読み終えたあと、モデルを組む前に
展開する。<b>ここを抜けたカードには手続きの呼び出しもシンボリックパラメタも残っていない</b>。
組み立てる側は手続きを知らずに済む。

COBOL のプリプロセッサと構文解析の分け方と同じ考え方である。字面の置き換えを先に済ませて
おけば、意味を取る側は 1 つの形だけを見ればよい。

| 決まり | 扱い |
| --- | --- |
| `&名前` | 値へ置き換える。値のない名前は誤りとする |
| `&名前.` | 点は名前の終わりを示す。置き換えたあとに残さない |
| `&&` | 1 つの `&` を表す。一時データセットの名前で使う |
| `PROC` … `PEND` | ジョブの中に書いた手続き。呼ばれたときに動く |
| `EXEC 手続き名` | 手続きを展開する。`EXEC PROC=名前` も同じ |
| `INCLUDE MEMBER=` | メンバの本文をその場へ差し込む |
| `//手続きのステップ名.DD 名 DD` | 同じ名前があれば差し替え、なければ足す |

値の強さは<b>呼び出しでの上書き → `SET` → 手続きの既定値</b>の順である。

### 展開したステップの名前

手続きが 1 ステップなら、展開したステップの名前は<b>呼び出し側の名前</b>である。
複数ステップなら `呼び出し名.手続きの中の名前` になる。1 つのときに素直な名前が付くほうが、
`COND` で名指すときに書きやすい。

名前が変わる以上、<b>手続きの中でステップを名指す `COND` も付け替えなければならない</b>。
`COND=(4,LT,FIRST)` は `COND=(4,LT,RUN.FIRST)` になる。付け替えを忘れると、名指した先が
見つからないまま条件が「成り立たない」と判定され、`NOT` で裏返って<b>いつでも動いてしまう</b>。

呼び出しに付けた `COND` は、手続きの<b>すべてのステップ</b>に効く。ただし手続きの中に
`COND` が書いてあれば、そちらが優先する。

### IF は条件をステップへ配る

`IF` / `THEN` / `ELSE` / `ENDIF` は<b>ステップを囲む</b>。囲まれたステップの条件は、
囲んでいる条件と自分の `COND` を<b>重ねたもの</b>になる。`ELSE` の中では裏返る。
入れ子にすれば重なりが増える。

`COND` と違って `IF` は<b>「真なら動かす」</b>の向きで書く。内部モデルの向きと同じなので
裏返さない。同じことを 2 通りの向きで書けるのは JCL の分かりにくいところだが、
内部モデルが 1 つの向きに揃っているので、どちらもそこへ落ちる。

| 書ける試験 | 意味 |
| --- | --- |
| `RC 関係 値` | いちばん大きい復帰コード |
| `ステップ名.RC 関係 値` | そのステップの復帰コード |
| `ステップ名.RUN` | そのステップが動いたか。異常終了したものも動いたことになる |
| `ABEND` | どれかが異常終了したか |

結び付けは `&` (`AND`)、`|` (`OR`)、`¬` (`NOT`) と括弧である。`&` は `|` より強い。

`IF` の文だけは<b>オペランド欄の切り方が違う</b>。ほかの文は括弧の外の空白で終わるが、
`IF` は関係式の中に空白が入るので、`THEN` までを 1 つの文として取る。

### 知らない書き方は誤りにする

JCL の全機能を再現するのは目標ではない。しかし<b>読み飛ばしてはならない</b> (要件 FR-131)。
`JCLLIB` / `OUTPUT` / `ABENDCC` / `UNIT` / `SPACE` などは、いまは誤りとして報告する
(暫定判断 P-046)。

## ユーティリティは普通のプログラムである (FR-137)

`IEBGENER` や `IDCAMS` は<b>翻訳された資産ではない</b>が、ジョブから見れば同じプログラムで
ある。したがって生成コードと同じ入口 (`CobolProgram`) を実装し、DD 名でデータへ触り、
復帰コードを立てる。ジョブ実行の側に特別扱いは要らない。

名前で引くとき、ユーティリティが先に見つかる。ホストでもシステムのライブラリが先だからである。

| 名前 | 実装したこと |
| --- | --- |
| `IEFBR14` | 何もしない。`DISP` を効かせるためのものであり、いまは本当に何も起きない |
| `IEBGENER` | `SYSUT1` を `SYSUT2` へ写す。制御文は未対応 (暫定判断 P-047) |
| `IDCAMS` | `REPRO` / `DELETE` / `DEFINE CLUSTER` / `LISTCAT` |
| `SORT` | 整列と合併。`INCLUDE` / `OMIT` / `SUM` / `INREC` / `OUTREC` / `OUTFIL` (別名 `DFSORT` / `ICEMAN` / `SYNCSORT`) |
| `ICETOOL` | 操作の並び。`COPY` / `SORT` / `COUNT` / `SELECT` / `DISPLAY` / `OCCUR` / `MODE` |

### バイトのまま写す

`IEBGENER` と `IDCAMS REPRO` は、レコードへ切ってから書き直すのではなく、バイト列と属性を
そのまま写す。切って書き直せば同じ属性なら同じバイトに戻るはずだが、<b>戻るはずだという
仮定を挟まずに済む</b>。写しは写しである。

### 復帰コードはいちばん大きいものが残る

`IDCAMS` は制御文ごとに復帰コードが立ち、ステップの復帰コードは<b>そのうちいちばん大きい
もの</b>になる。1 つ失敗しても後続の制御文は動く。これがホストの決まりであり、
「消してから作る」という書き方が成り立つ理由である。消すものがなければ `8` になるが、
作るほうは通る。

### 整列の中身は COBOL の SORT と同じものを使う

バッチでいちばん重いのは整列であり、COBOL の `SORT` 動詞よりもジョブステップとして
整列ユーティリティを呼ぶ場面のほうが多い。しかし<b>並べ替えの規則は 1 つしかない</b>。
鍵の比べ方は[設計 80](80-file-io.md) の `SortWork` が持っており、ユーティリティがやるのは
制御文を鍵へ翻訳することだけである。規則が 2 か所にあれば必ず食い違う。
`SORT` 動詞で正しいものは、ここでも正しい。

#### 通り道の順は決まっている

読む → `INCLUDE` / `OMIT` でふるう → `INREC` で組み直す → 並べ替える → `SUM` でまとめる
→ `OUTREC` で組み直す → `OUTFIL` で振り分ける。この順はホストの決まりであり、順を
入れ替えると答えが変わる。たとえば `SUM` は<b>並べ替えたあと</b>にしか効かない。鍵が
等しいレコードが隣り合っていて初めて、1 つ前と比べるだけでまとめられる。

`INREC` が並べ替えの<b>前</b>にあるのが効くところである。だから `SORT FIELDS` の位置は
「組み直したあとのレコード」を指す。元の位置を指すと思って書くと、静かに違うもので
並ぶ。`OUTREC` が並べ替えの後なのも同じ理屈で、組み直したあとのレコードには元の位置が
もう無い。

#### OUTFIL は 1 回読んだものを振り分ける

条件ごとにジョブステップを分けると、そのたびに<b>入力を読み直す</b>ことになる。
実資産で重い整列を 1 回で済ませる仕掛けが `OUTFIL` である。

書き先は `FNAMES=(dd,...)` か `FILES=(01,...)` で言う。番号で言ったときの DD 名は
`SORTOFnn` である。`OUTFIL` ごとに `INCLUDE` / `OMIT` / `BUILD` を書ける。

`SAVE` は「どの `OUTFIL` にも選ばれなかったもの」を受け取る。だから<b>先に他のものを
決めてから残りを配る</b>。書いた順は関係ない。

#### 位置は 1 から数え、可変長では長さも数に入る

制御文の位置はレコードの先頭を 1 とする。可変長では<b>先頭の 4 バイトが長さ (RDW)</b>
であり、データは 5 から始まる。ここでもレコードを切り出すときに長さを付けたまま持つので、
ホストと同じ数え方になる。切り離してから数え直すと、実資産の `SORT FIELDS=(5,...)` が
1 つずつずれる。

#### 形ごとの比べ方

| 形 | 比べ方 |
| --- | --- |
| `CH` | バイトの並び。EBCDIC の照合順序はバイトの値そのものである |
| `BI` | バイトの並び。符号なし 2 進数なので、これで値の順になる |
| `ZD` | `S9(n)` DISPLAY として値で比べる |
| `PD` | `S9(2n-1)` COMP-3 として値で比べる |
| `FI` | 長さ 2 / 4 / 8 を `S9(4)` / `S9(9)` / `S9(18)` COMP として値で比べる |

`CH` と `BI` をバイトで比べるのは手抜きではない。<b>バイトの並びが値の順と一致する</b>のが
この 2 つの形の定義だからであり、10 進数へ直してから比べても答えは変わらない。

`SUM` が書き戻す `ZD` には<b>符号が付く</b>。ゾーン 10 進数の符号は最下位桁の上位 4 ビットに
あり、正なら X'C' である。読むときは X'F' でも正として読み、書くときは X'C' になる。
ホストの整列も同じものを書く。

### ICETOOL は整列を持たない

`ICETOOL` は `TOOLIN` に書いた操作を上から順に実行する道具である。整列そのものは持たず、
<b>`SORT` を呼び出す</b>。`USING(cccc)` と書けば `ccccCNTL` の制御文で通る。実装としては
DD 名を付け替えた目録を渡すだけであり、`SORT` から見れば普通に `SORTIN` を読んで
`SORTOUT` へ書いている。

こうしておけば鍵の扱いが 2 か所に分かれない。`ICETOOL` が足しているのは「同じ入力を何度も
通す」「重なりを見つける」「数える」という、<b>整列の周りの仕事</b>である。

| 操作 | すること |
| --- | --- |
| `COPY` / `SORT` | 入力を出力へ通す。`USING` があれば `SORT` の制御文で通す |
| `COUNT` | 件数を出す。`EMPTY` / `NOTEMPTY` / `HIGHER` などで復帰コードを立てる |
| `SELECT` | 重なりで選ぶ。`FIRST` / `LAST` / `ALLDUPS` / `NODUPS` / `HIGHER` |
| `DISPLAY` / `OCCUR` | 場所の値を並べる。`OCCUR` は値ごとの件数を数える |
| `MODE` | 失敗した操作のところで打ち切るか (`STOP` が既定) |

`MODE STOP` が既定なのはホストと同じである。失敗した操作の結果を次が使ってしまうと、
<b>誤りが誤りのまま先へ進む</b>。

### 場所の読み方は 1 か所に置く

`SORT` も `ICETOOL` も、位置と長さと形でレコードの中の場所を言う。読み方が 2 か所にあれば
必ず食い違うので、形の解釈と値の取り出しは `SortField` 1 つに置いた。レコードの切り方
(`Records`) も同じ理由で 1 つである。

### 覚え書きの出し先

ホストのユーティリティは `SYSPRINT` へ経過を書く。ジョブが書いていなければ出さないのが
ホストの決まりだが、それでは黙って失敗したときに手がかりが残らない。結び付けがなければ
実行時の出力へ回す。

## DISP はステップの前と後の両方を決める (FR-133)

`DISP=(状態, 正常終了時, 異常終了時)` である。3 つとも意味が違う。1 つ目は<b>ステップが
始まるときに何を期待するか</b>、あとの 2 つは<b>ステップが終わったときに何を残すか</b>で
ある。

### 前で確かめるのは、黙って動いてしまわないためである

| 状態 | 割当ての段ですること |
| --- | --- |
| `NEW` | もとからあれば誤りにする。無ければ空のデータセットを割り当てる |
| `OLD` / `SHR` | 無ければ誤りにする |
| `MOD` | 無ければ空のデータセットを割り当てる。ある場合はそのまま |

無いものを空として読ませたり、あるものを黙って作り直したりすると、<b>名前を打ち間違えた
ジョブが「0 件処理した」と言って正常終了する</b>。これはいちばん見つけにくい壊れ方であり、
ホストが割当ての段で止めるのはそのためである。

割当てに失敗したステップはプログラムを呼びもしない。これは異常終了とは別のものであり、
`COND=EVEN` でも覆せない。<b>以降のステップは実行されずに流される</b>。

### 後で決めるのは、残すか消すかである

2 つ目を書かなければ、新しく作るデータセットは `DELETE`、もとからあるものは `KEEP` で
ある。<b>作ったものは消える</b>のが既定であり、残したければ書かねばならない。3 つ目を
書かなければ 2 つ目と同じになる。ただし 2 つ目が `PASS` のときだけは、新しいものは消え、
もとからあるものは残る。

残す側のうち `KEEP` / `CATLG` / `UNCATLG` は区別していない。目録をディレクトリそのものと
しているので、載せる・外すという操作が無いからである (暫定判断 P-045)。

### 一時データセットは場所を持たない

`DSN=&&WORK` はジョブの間だけ存在するデータセットである。ステップの間で受け渡す作業
ファイルがこれであり、実資産のバッチではいちばんよく使われる形である。

<b>場所を持たないのが要点である</b>。置き場を決めるのはジョブ実行であって、ジョブの記述
ではない。だから同じジョブを同時に何本流しても、互いの作業ファイルを踏まない。

ジョブが終われば置き場ごと消える。`DISP` の前の検査はそのまま効くので、書いていない一時
データセットを `DISP=OLD` で読もうとすれば止まる。

なお `&&` が 2 つなのは<b>シンボリックパラメタと区別するため</b>である。展開の段で 1 つの
`&` になり、残った先頭の `&` が一時データセットを表す。

### PASS は次のジョブへは渡さない

`DISP=(NEW,PASS)` で残したものは、<b>このジョブの後続ステップへ</b>渡る。ジョブが終われば
消える。残したければ `CATLG` と書く。

判断はデータセットごとの<b>いちばん新しい処置</b>で決まる。あとのステップが `CATLG` と
書けば残り、`DELETE` と書けばその場で消える。

### DISP=MOD だけがプログラムの書いたことを覆す

`DISP=MOD` は「`OPEN OUTPUT` と書いてあっても末尾へ足す」という意味になる。ジョブの指定が
プログラムより強い、数少ない場所である。だからこそ<b>覆るのはこの 1 か所だけ</b>にして
ある。同じプログラムを「作り直す」使い方と「積み増す」使い方の両方へ向けられるのは、
これがあるからである。

実装では `DataSetCatalog` がその DD を覚え、`OPEN` が `OUTPUT` を `EXTEND` へ読み替える。
順編成にしか意味がないので、相対編成と索引編成では読み替えない。

### 宣言的形式は DISP を書かなくてよい

JCL では `DISP` を書かなければ「新しく作る」だが、宣言的形式では<b>何も言っていない</b>
ことになる (`Disposition.Status.ANY`)。確かめも、作りも、消しもしない。名前を書くだけで
動かせるほうが、この処理系自身の試験には都合がよい。ジョブの側で状態を決めたいときは
`DD 名 DSN=場所 DISP=(NEW,CATLG)` と書ける。

### 作業領域はステップが終われば片付ける

`SYSOUT` のスプールも埋め込みデータも連結の写しも、そのステップの間だけ要るものである。
正常に終わったところで消す。<b>異常終了したステップのものは残す</b>。何が起きたのかを
見られるほうが役に立つからであり、同じ名前で上書きされるので増え続けはしない。

## 異常終了コード (FR-141)

ホストは実行を打ち切るとき、<b>何が起きたのかを 4 桁で言う</b>。`S` で始まるものはシステムが
検出したもの、`U` で始まるものはプログラムや言語環境が自分で立てたものである。運用は
このコードを見て次にやることを決める。データの誤りなら入力を直して流し直せばよく、
ロードモジュールが無いなら組み立てから直す。<b>コードが合っていない実装は、動いても
使えない</b>。

### コードは条件そのものが持つ

どの例外がどのコードになるかを 1 か所の対応表にすると、条件を足したときに<b>表を直し
忘れる</b>。そうではなく、条件を表す例外自身が `AbendCause` としてコードを名乗る。
ジョブ実行の側は例外の種類を並べず、`Abend.codeOf` に訊くだけである。

| コード | 立てる条件 | いつ |
| --- | --- | --- |
| `S0C7` | `DataException` | 数値項目に数字でないバイトが入っていた |
| `S0CB` | `DecimalDivideException` | ゼロで割った。商が入りきらなかった |
| `S0C4` | `Ops.linkage` | 渡されていない連絡節の項目を触った |
| `S806` | `ProgramNotFoundException` | 呼び先のロードモジュールが見つからない |
| `S001` | `FileOperationException` (状態 `30`) | データセットの形が記述と合わない |
| `S001` | `DataSetIoException` | データセットの置き場へ届かない |
| `S037` | `FileOperationException` (状態 `34`) | 割り当てた領域を使い切った |
| `U4038` | `RangeCheckException` | `SSRANGE` の範囲外参照 |
| `U4038` | `FileOperationException` (そのほか) | `FILE STATUS` も宣言部分も無いファイルの異常 |

包まれた例外も辿る。ランタイムの中で `UncheckedIOException` などに包まれても、もとの条件の
コードが残る。

ファイルの異常だけは、<b>条件の中に小さな対応表がある</b>。例外の型ではなくファイル状態
コードが「何が起きたか」を持っているためである。表を外へ出すと、状態コードを足したときに
直し忘れる。

### 入出力の誤りは起こせなければ意味がない (FR-141)

`S001` と `S037` は長らく<b>立てられなかった</b>。装置を持たないこの実装では、装置の誤りを
起こす手立てが無かったからである。ジョブが `IF ABENDCC = S001` と書いた枝は決して通らず、
異常終了しても想定した後始末が動かない。コードを名乗るだけでは足りず、<b>その条件を実際に
起こせるようにして初めて</b>コードに意味が出る。

起こせるようにしたのは 2 つである。

**形が記述と合っていないこと。** 固定長のはずが長さがレコード長で割り切れない、可変長の
はずが `RDW` がつながらない、というデータセットは<b>そこから先を切り出せない</b>。以前は
半端をそのまま短いレコードとして渡していた。渡してしまえば、読めていないデータで処理が
進む。いまは切れるところまでを読めるものとし、その先でファイル状態 `30` を立てる。
読めていたレコードを捨てないのは、ホストも同じく<b>読んだ時点で</b>誤りにするからである。

**割り当てた領域を使い切ること。** ホストは `SPACE=` であらかじめ場所を取ってから書く。
取った分を使い切れば書けなくなり、二次割当があればそこで伸びる。無ければ止まる。この
指定を無視していると、<b>実機では止まるジョブがここでは通る</b>。いまは目録が DD ごとの
大きさを持ち、越えた `WRITE` がファイル状態 `34` を立てる。

### 領域の大きさは目録が持つ

`SPACE=` はデータセットの属性ではない。属性はバイト列の<b>切り方</b>を決めるものであり、
置き場をどれだけ取ったかとは別の話である。同じデータセットでも、割り当てる大きさはジョブが
決める。したがって `DISP=MOD` と同じく `DataSetCatalog` が持つ。

JCL は装置の単位 (`TRK` / `CYL` / ブロック長) で書き、宣言的形式は<b>バイトで書く</b>
(`SPACE=8000`)。宣言的形式は装置を知らないので、トラックを持ち込む理由がない。トラックと
シリンダの大きさは 3390 のものを使う (暫定判断 P-052)。

### 異常終了しても、書いたものは残る

ステップが終わったら、開いたままのファイルを実行機構が閉じる。異常終了した場合も同じで
ある。閉じずに終わったファイルは<b>書いたものがまだ置き場に届いていない</b>ため、残った
ものを見て何が起きたのかを調べられない。処置 (`DISP`) が「作りかけのものを消す」という形で
効くのも、いったん届いていることが前提である。

閉じるときの誤りは伝えない。すでに異常終了しているかもしれず、そこへ別の誤りをかぶせると
<b>最初に起きたことが分からなくなる</b>。

### 受け止め手があれば打ち切らない

`ON SIZE ERROR` を書いたゼロ除算は条件のままであり、異常終了にならない。`FILE STATUS` を
書いたファイルの異常も同じである。<b>打ち切るのは受け止め手が無いときだけ</b>という規則は
ホストと同じであり、これがあるから「異常終了した」という事実に意味がある。

### 渡されていない連絡節は必ず S0C4 にする

ホストでは連絡節の項目は呼ぶ側の領域を指す仕掛け (BLL) だけを持つ。渡されていなければ
その中身が定まらず、運が悪ければ自分の持ち場の外を指して `S0C4`、運がよければ何かが読めて
<b>誤った値のまま処理が進む</b>。

ここでは必ず `S0C4` で終わることにした。定まらない挙動を再現するより、誤りを誤りとして
見せるほうがよいという判断である (要件 FR-205 の安全側)。翻訳したコードは配列から直に
取らず `Ops.linkage` を通る。

### ABENDCC で後始末を分ける

`IF (CHECK.ABENDCC = S0C7) THEN` と書ける。比べられるのは<b>等しいか等しくないかだけ</b>で
ある。異常終了コードに大小はない。ステップを言わなければ、最後に分かったコードを見る。

宣言的形式でも `WHEN ABENDCC CHECK = S0C7` と書ける。どちらも同じ内部モデル
(`StepCondition.Abend`) へ落ちる。

### 通らなかったジョブは 0 を返さない

異常終了と JCL エラーはどちらも復帰コードを立てない。いちばん大きい復帰コードをそのまま
返すと `0` になり、<b>後続の運用が「通った」と読み違える</b>。どちらの場合も終了コードは
12 以上になる。どちらだったかはステップの結末に残る。

## 異常終了の診断出力 (FR-142, FR-143)

異常終了コードだけでは、どこで何が起きたのか分からない。ホストの言語環境は `CEEDUMP` と
して、止まった場所・呼び出し履歴・記憶域の中身を書き出す。<b>それが無ければ、本番で一度
だけ起きた事故を追えない</b>。

### 止まった場所はクラスファイルの行番号表から取る

翻訳するとき、文ごとに原文の行をクラスファイルへ埋めてある
([設計 70](70-codegen.md))。だから JVM の呼び出し履歴が<b>そのまま原文の行を指す</b>。
対応表を自分で持たないので、本体とずれる余地がない。

```
TRACEBACK:
  PROGRAM   STATEMENT  SOURCE
  PAYCHK    11         PAYCHK.cbl
  PAYRUN    8          PAYRUN.cbl
```

載せるのは翻訳したプログラムの段だけである。ランタイムの中の段は、COBOL を書いた人に
とっては自分の書いたものではない。

### 項目名で書けるのは割り付けを持ち歩いているからである

16 進を読んで変位を数えるのと、名前で探すのとでは、追える速さが違う。しかし<b>どのバイトが
どの項目かを知っているのは翻訳の側</b>であり、実行時に手元にあるのはバイト列だけである。
だから割り付けを生成クラスへ埋めて持ち歩かせる ([設計 70](70-codegen.md))。

```
STORAGE FOR PAYCHK:
  01 WS-EMPLOYEE
    05 WS-NAME = 'SMITH   '  E2D4C9E3C8404040
    05 WS-GRADE = 7  F0F7
  01 WS-N = <not numeric>  C1C1C1
```

数として読めないバイトが入っていれば、そう書いて 16 進を添える。<b>読めないバイトが
入っていること自体</b>が、たいていの場合いちばんの手がかりだからである。割り付けを
持たないプログラムでは 16 進の羅列に落ちる。

### 記憶域は積んでおかないと取り出せない

呼び出し履歴だけなら JVM の履歴で足りるが、<b>それぞれの作業場所の中身</b>は残らない。
実行時の入口が、動いているプログラムを積んでおく。

正常に戻ったときだけ積み直す。<b>異常終了で抜けたプログラムは積まれたまま残る</b>ので、
覚え書きがその中身を見られる。ステップごとに新しい入口を作るので、残ったものが次の
ステップへ漏れることはない。

```
STORAGE FOR PAYCHK:
  000000  C1C1C1F0 F0F0F0F0                    |AAA00000        |
```

16 進のほうが正であり、左の値は目で追うための添え物である。読めないバイトは点にする。

### 行き先は CEEDUMP、細かさは CEEOPTS

ホストと同じく、診断出力は `CEEDUMP` の DD へ出す。書かれていなければジョブの出力へ回す。
<b>黙って捨てない</b>のは、書き忘れたジョブで事故が起きたときに手がかりが残らないから
である。

細かさは `CEEOPTS` の DD に書いた `TERMTHDACT` が決める。

| 指定 | 覚え書き | 呼び出し履歴 | 記憶域 |
| --- | --- | --- | --- |
| `QUIET` | — | — | — |
| `MSG` | 出る | — | — |
| `TRACE` (既定) | 出る | 出る | — |
| `DUMP` | 出る | 出る | 出る |

毎回すべてを書き出すと量が多すぎて<b>肝心の 1 行が埋もれる</b>。一方で追い切れない事故が
起きたときには中身が要る。だから切り替えられるようになっている。

### 書式はホストのものではない

中身はホストの `CEEDUMP` が持つものに揃えたが、並べ方と字面は真似ていない。真似ると、
<b>本物と見分けがつかないものが出てきて、既存の解析道具が誤って読む</b> (暫定判断 P-051)。

## 起動

```
cobolj [-d クラスの置き場] [-w 作業領域] [-b データセットの基点] [-p 手続きの入れ物] ジョブ記述
```

記述形式は拡張子で見分ける。`.jcl` なら JCL、それ以外は宣言的形式である。

プロセスの終了コードは<b>ジョブの終了コード</b>である。いちばん大きいステップの復帰コードで
あり、後続のジョブがそれを見て動く。ステップの結末は標準エラーへジョブログとして書く。

## 次の増分

1. 目録をディレクトリから切り離す (暫定判断 P-045)。割当てと `OPEN` の役割が分かれ、
   `S013` を立てられるようになる (暫定判断 P-048 の残り)。
2. 領域の限りと形の検査を、相対編成・索引編成・ユーティリティへ広げる (暫定判断 P-053)。
   位置を持って読み書きする形へ改める段 (暫定判断 P-038) と同じところで決まる。
3. 残りの `ICETOOL` の操作子と `OUTFIL` の副オペランド (暫定判断 P-047)。
