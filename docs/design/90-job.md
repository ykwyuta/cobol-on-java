# 設計 90: ジョブ実行

| 項目 | 内容 |
| --- | --- |
| 対応要件 | FR-130〜FR-137、FR-141〜FR-143、要件定義書 7.1 節 |
| ステータス | 内部モデル・宣言的形式・JCL・ユーティリティ 5 本・`DISP`・`SPACE`・目録・区分データセット・異常終了コードと診断出力 実装済 |

## 何を決めるか

バッチの実資産は<b>プログラム 1 本では動かない</b>。JCL がステップを並べ、DD 名を実際の
データセットへ結び付け、復帰コードで後続の実行を決める。そこまで揃って初めて「ソース無修正で
動く」と言える。

## 内部モデルが先で、記述形式はあと (FR-130)

実行機構が解釈するのは<b>内部ジョブモデルだけ</b>である。JCL パーサも宣言的形式のパーサも
知らない。

```
JCL         ┐
            ├→ 内部ジョブモデル (Job / Step / DdAssignment / StepCondition) → 実行機構
宣言的形式  ┘
```

こうしておく理由は 2 つある。<b>どちらの形式で書いても結果が同じ</b>になること (要件 FR-132)。
そして、JCL の込み入った書式をパーサの中に閉じ込め、実行の側へ持ち込まないことである。

| 型 | 表すもの |
| --- | --- |
| `Job` | ジョブ 1 個。ステップの並び |
| `Step` | プログラム 1 本の実行。名前・プログラム名・`PARM`・DD 割当・条件 |
| `DdAssignment` / `DdTarget` | DD 名と行き先。実ファイル、`SYSOUT`、`DUMMY`、埋め込みデータ |
| `StepCondition` | 動かすかどうかの条件 |
| `JobState` | ここまでに起きたこと。復帰コードと異常終了の有無 |

## 条件は「真なら動かす」の向きに揃える (FR-136)

JCL の `COND` は<b>「真なら飛ばす」</b>という向きで書く。`COND=(4,LT,STEP1)` は
「STEP1 の RC が 4 より大きければ飛ばす」である。逆さまで読みにくく、誤りのもとでもある。

内部モデルでは<b>「真なら動かす」</b>の向きに揃えた。向きの反転は JCL パーサの仕事である。
宣言的形式は素直に書ける。

```
WHEN RC CHECK <= 4
```

異常終了の扱いも条件の一部として持たせている。ホストでは先行ステップが異常終了すると以降は
飛ばされるが、`COND=EVEN` と `COND=ONLY` がそれを覆す。「飛ばす／飛ばさない」を決めるものは
1 か所にあるほうがよい。

**動いていないステップの復帰コードは比べられない**。飛ばされたステップを名指す条件は
成り立たないものとして扱う。

## ステップは独立している (FR-130)

ステップごとに新しい実行時の入口を作る。作業場所も、読み込んだ副プログラムも、開いたファイルも、
復帰コードも<b>持ち越さない</b>。持ち越すのはジョブの状態だけである。

ホストではステップごとに別のアドレス空間が立つ。同じ実行時の入口を使い回すと、前のステップの
作業場所が残り、初期値から始まらないプログラムができてしまう。

## SYSOUT はスプールを通る (FR-135)

ホストでは `SYSOUT` へ書いたものがスプールに溜まり、ジョブが終わってから印字される。
ここでも作業領域のファイルへ溜め、ステップが終わったところで流し出す。

<b>プログラムから見れば普通のデータセットである</b>。行順編成のファイルを開いて書くだけであり、
`SYSOUT` のための特別な道が要らない。

`DUMMY` も同じ考え方で、空のファイルを割り当てる。読めば即座に終わり、書いたものは
捨てられる。埋め込みデータ (`SYSIN DD *` 相当) も、作業領域へ書き出して行順編成で割り当てる。

## PARM は先頭 2 バイトが長さである (FR-134)

参照実装と同じ形で渡す。受け取る側は連絡節にこう書いてある。

```cobol
LINKAGE SECTION.
01  PARM-AREA.
    05  PA-LEN  PIC S9(4) COMP.
    05  PA-TEXT PIC X(100).
PROCEDURE DIVISION USING PARM-AREA.
```

長さは 2 バイトの 2 進数であり、中身はコードページで符号化したバイト列である。
`PARM=` を書かなければ引数の並びは空になる。

## 宣言的形式 (FR-132)

内部モデルを<b>そのまま書ける</b>形式である。新しく組むジョブと、この処理系自身の試験に使う。
YAML などの外部ライブラリを使わないのは、`cobol-runtime` 以外へ依存を増やさないためである。

```
# 行頭の # は注記
JOB PAYROLL
STEP CHECK PGM=PAYCHK
  DD PAYIN DSN=data/pay.dat
  DD SYSOUT SYSOUT
STEP REPORT PGM=PAYRPT PARM=202609
  WHEN RC CHECK <= 4
  DD SYSOUT SYSOUT
  DD SYSIN DATA
    DETAIL
    TOTAL
  END
STEP CLEANUP PGM=PAYCLN
  WHEN ABEND
  DD SYSOUT SYSOUT
```

字下げに意味はない。読みやすさのためだけのものである。

条件の組み合わせは<b>1 段だけ</b>である。`AND` と `OR` を混ぜて書けない。混ぜたときの
優先順位は書いた人の思い込みと食い違いやすく、誤りとしたほうがよい。

### 知らない書き方は誤りにする

読み飛ばさない。書いたつもりの指定が効いていないことに気付けないからである。
これは JCL のフロントエンドでも同じ方針である (要件 FR-131)。

## JCL フロントエンド (FR-131)

既存の JCL 資産を<b>書き換えずに実行する</b>ためのものである。読み取った結果は内部ジョブ
モデルであり、宣言的形式で書いたものと区別がない。同じ内容を両方の形式で書くと、
組み上がるモデルが等しくなる。

### 書式の都合は読み取りで尽くす

カードを読む側でやることは 3 つある。<b>注記を落とし、継続をつなぎ、埋め込みデータを
切り出す</b>。ここまでで書式の都合は尽きており、意味を取る側は 1 文ずつ見ればよくなる。

| 決まり | 扱い |
| --- | --- |
| 1〜2 桁が `//` | 3 桁目が `*` なら注記カード |
| 73 桁目から先 | 通番であり、見ない |
| オペランドの外の空白 | そこから先は注記 |
| オペランドの末尾のコンマ | 次のカードへ続く。続きのカードは名前欄が空 |
| `DD *` | 次の文か `/*` までが埋め込みデータ |
| `DD DATA` | `/*` まで。データの中に `//` で始まる行があるときに使う |
| 名前欄の空いた `DD` | 直前の `DD` への連結 |

コンマで区切るときは<b>括弧と引用符の中を区切らない</b>。`COND=((4,LT),(8,GT,STEP1))` は
1 つのオペランドであり、`PARM='A,B'` も 1 つである。

### COND の向きを裏返す

JCL の `COND` は<b>「真なら飛ばす」</b>という向きで書く。さらに `COND=(4,LT,STEP1)` は
「4 < STEP1 の RC」と読む。左右も逆さまである。内部モデルは「RC 関係 値」で「真なら動かす」
なので、ここで<b>2 回裏返す</b>。

| JCL | 内部モデル |
| --- | --- |
| `COND=(4,LT,CHECK)` | `NOT (RC(CHECK) > 4)` |
| `COND=((4,LT,A),(8,EQ))` | `NOT (RC(A) > 4 OR 最大 RC = 8)` |
| `COND=EVEN` | 異常終了していても動かす |
| `COND=((8,LE,A),EVEN)` | 異常終了を越え、かつ `NOT (RC(A) >= 8)` |

試験が複数あれば<b>どれか 1 つでも成り立てば飛ばす</b>。裏返すと「すべて成り立たなければ
動かす」になる。

### JCL は場所を知らない

`DSN=PAY.MASTER` はデータセット<b>名</b>であり、ファイルの場所ではない。どこにあるかを
引くのは目録の仕事であって、JCL を読む段ではない。以前はここで基点のディレクトリの下へ
直していたが、それでは<b>名前と場所が同じもの</b>になり、目録に載せる・外すという操作が
表せなくなる (後述)。

置き場での名前は、区切りの点をディレクトリに読み替えず<b>その名前のまま</b>である。
ホストの一覧と見比べたときに同じ名前が並ぶほうが追いやすいからである。

### 手続きの展開は組み立ての前に済ませる

`PROC` / `INCLUDE` / `SET` とシンボリックパラメタは、カードを読み終えたあと、モデルを組む前に
展開する。<b>ここを抜けたカードには手続きの呼び出しもシンボリックパラメタも残っていない</b>。
組み立てる側は手続きを知らずに済む。

COBOL のプリプロセッサと構文解析の分け方と同じ考え方である。字面の置き換えを先に済ませて
おけば、意味を取る側は 1 つの形だけを見ればよい。

| 決まり | 扱い |
| --- | --- |
| `&名前` | 値へ置き換える。値のない名前は誤りとする |
| `&名前.` | 点は名前の終わりを示す。置き換えたあとに残さない |
| `&&` | 1 つの `&` を表す。一時データセットの名前で使う |
| `PROC` … `PEND` | ジョブの中に書いた手続き。呼ばれたときに動く |
| `EXEC 手続き名` | 手続きを展開する。`EXEC PROC=名前` も同じ |
| `INCLUDE MEMBER=` | メンバの本文をその場へ差し込む |
| `//手続きのステップ名.DD 名 DD` | 同じ名前があれば差し替え、なければ足す |

値の強さは<b>呼び出しでの上書き → `SET` → 手続きの既定値</b>の順である。

### 展開したステップの名前

手続きが 1 ステップなら、展開したステップの名前は<b>呼び出し側の名前</b>である。
複数ステップなら `呼び出し名.手続きの中の名前` になる。1 つのときに素直な名前が付くほうが、
`COND` で名指すときに書きやすい。

名前が変わる以上、<b>手続きの中でステップを名指す `COND` も付け替えなければならない</b>。
`COND=(4,LT,FIRST)` は `COND=(4,LT,RUN.FIRST)` になる。付け替えを忘れると、名指した先が
見つからないまま条件が「成り立たない」と判定され、`NOT` で裏返って<b>いつでも動いてしまう</b>。

呼び出しに付けた `COND` は、手続きの<b>すべてのステップ</b>に効く。ただし手続きの中に
`COND` が書いてあれば、そちらが優先する。

### IF は条件をステップへ配る

`IF` / `THEN` / `ELSE` / `ENDIF` は<b>ステップを囲む</b>。囲まれたステップの条件は、
囲んでいる条件と自分の `COND` を<b>重ねたもの</b>になる。`ELSE` の中では裏返る。
入れ子にすれば重なりが増える。

`COND` と違って `IF` は<b>「真なら動かす」</b>の向きで書く。内部モデルの向きと同じなので
裏返さない。同じことを 2 通りの向きで書けるのは JCL の分かりにくいところだが、
内部モデルが 1 つの向きに揃っているので、どちらもそこへ落ちる。

| 書ける試験 | 意味 |
| --- | --- |
| `RC 関係 値` | いちばん大きい復帰コード |
| `ステップ名.RC 関係 値` | そのステップの復帰コード |
| `ステップ名.RUN` | そのステップが動いたか。異常終了したものも動いたことになる |
| `ABEND` | どれかが異常終了したか |

結び付けは `&` (`AND`)、`|` (`OR`)、`¬` (`NOT`) と括弧である。`&` は `|` より強い。

`IF` の文だけは<b>オペランド欄の切り方が違う</b>。ほかの文は括弧の外の空白で終わるが、
`IF` は関係式の中に空白が入るので、`THEN` までを 1 つの文として取る。

### 知らない書き方は誤りにする

JCL の全機能を再現するのは目標ではない。しかし<b>読み飛ばしてはならない</b> (要件 FR-131)。
`JCLLIB` / `OUTPUT` / `ABENDCC` / `UNIT` / `SPACE` などは、いまは誤りとして報告する
(暫定判断 P-046)。

## ユーティリティは普通のプログラムである (FR-137)

`IEBGENER` や `IDCAMS` は<b>翻訳された資産ではない</b>が、ジョブから見れば同じプログラムで
ある。したがって生成コードと同じ入口 (`CobolProgram`) を実装し、DD 名でデータへ触り、
復帰コードを立てる。ジョブ実行の側に特別扱いは要らない。

名前で引くとき、ユーティリティが先に見つかる。ホストでもシステムのライブラリが先だからである。

| 名前 | 実装したこと |
| --- | --- |
| `IEFBR14` | 何もしない。`DISP` を効かせるためのものであり、いまは本当に何も起きない |
| `IEBGENER` | `SYSUT1` を `SYSUT2` へ写す。`GENERATE` / `RECORD` で組み替えながら写せる |
| `IEBCOPY` | ライブラリのメンバを写す。`COPY` / `COPYGRP` / `SELECT` / `EXCLUDE` / 名前替え / 置き換え / 圧縮 |
| `IDCAMS` | `REPRO` / `DELETE` / `DEFINE CLUSTER` / `DEFINE GDG` / `LISTCAT` |
| `SORT` | 整列と合併。`INCLUDE` / `OMIT` / `SUM` / `INREC` / `OUTREC` / `OUTFIL` (振り分け・見出し・末尾・分割。別名 `DFSORT` / `ICEMAN` / `SYNCSORT`) |
| `ICETOOL` | 操作の並び。`COPY` / `SORT` / `MERGE` / `COUNT` / `STATS` / `RANGE` / `UNIQUE` / `VERIFY` / `SELECT` / `SPLICE` / `SUBSET` / `RESIZE` / `DISPLAY` / `OCCUR` / `MODE` |
| `IKJEFT01` | バッチの TSO。`LISTDS` と、メンバへの `RENAME` (`ALIAS` を含む) / `DELETE` (暫定判断 P-058。別名 `IKJEFT1A` / `IKJEFT1B`) |

### バイトのまま写す

`IEBGENER` と `IDCAMS REPRO` は、レコードへ切ってから書き直すのではなく、バイト列と属性を
そのまま写す。切って書き直せば同じ属性なら同じバイトに戻るはずだが、<b>戻るはずだという
仮定を挟まずに済む</b>。写しは写しである。

### 組を分けるのは「終わりの目印」である (暫定判断 P-047 の解消)

`IEBGENER` に制御文を書くと、写しではなく<b>組み替え</b>になる。`RECORD` を 2 つ以上
書けば入力は組に分かれ、分かれ目を言うのが `IDENT` である。

```
  GENERATE MAXFLDS=2,MAXGPS=1
  RECORD   IDENT=(3,'HDR',1),FIELD=(3,'** ',,1),FIELD=(9,1,,4)
  RECORD   FIELD=(3,'   ',,1),FIELD=(9,1,,4)
```

`IDENT` が指すのは組の<b>最後のレコード</b>であって、次の組の始まりではない。目印の
付いたレコード自身も 1 つめの組に入り、そのあとで次の組へ移る。見出し・明細・合計という
ホストの並びをこう書けるのは、<b>区切りの行を見てから</b>切り替えるからである。始まりで
切ると、区切りの行だけが前の組の書式で出てしまう。

`FIELD=(長さ,入力の位置,変換,出力の位置)` は 1 か所の移し替えである。入力の位置のところに
定数を書けば、その定数が置かれる。置く場所は<b>前へ戻ってもよい</b>。何桁目に置くかを
言うのだから、書く順は並びの順と関わりがない。

変換に書ける `PZ` と `ZP` は、パック 10 進数とゾーン 10 進数の行き来である。ホストの
`UNPK` / `PACK` と同じ数え方で、3 バイトのパック 10 進数は 5 桁になる。

`MAXFLDS` などの数え上げは<b>約束である</b>。ホストが領域を取るための数だが、書いた数と
合わなければそこで止める。読み飛ばすと、書き足した `FIELD` が黙って効かないまま正常終了
する。

### 生バイトを読むことは、検査を省く理由にならない

ユーティリティはデータセットを開かず、バイト列をそのまま読み書きする。それでも<b>開けない
ものは読めない</b>ことに変わりはない。翻訳された資産と同じ検査を通す。

| 起きたこと | 立つもの | 翻訳された資産なら |
| --- | --- | --- |
| 区分データセットの無いメンバを読ませた | `S013` | 同じ (`OPEN` で止まる) |
| 区分データセットそのものを読ませた | `S013` | 同じ |
| 形が壊れたデータセットを読ませた | `S001` | ファイル状態 `30` から `S001` |
| 割り当てた領域に収まらない量を書いた | `S037` | ファイル状態 `34` から `S037` |

省いていた間は、無いメンバを<b>空として写して正常終了</b>していた。実資産のジョブは
`IEBGENER` と `SORT` を骨組みにしているので、そこが素通しでは<b>ジョブ全体の合い方が
変わる</b>。翻訳した資産だけを実機に合わせても意味がない。

状態コードを返す先がないので、そのまま異常終了にする。「入力が無い」(`RC=12`) とは違う —
あちらは道具の言い分だが、こちらは<b>割当ては通っているのに開けない</b>という、
アクセス法の側の話である。

領域の限りは DD に付いている。ユーティリティは DD 名をファイルへ直したあとの世界で
動くので、書き出す段では<b>どの DD だったかを失っている</b>。対応表に逆引きを持たせて
引き直す。

ライブラリでは限りが付いているのが<b>ライブラリ</b>であってメンバではない。`IEBCOPY` は
すでに入っているメンバの合計に、これから書くぶんを足して見る。書くのがメンバ 1 つずつ
なので、途中で足りなくなれば<b>そこまでに写したメンバは残る</b>。ホストと同じであり、
1 度に書き出す道具 (暫定判断 P-038) が何も残さないのとは違う。

### 復帰コードはいちばん大きいものが残る

`IDCAMS` は制御文ごとに復帰コードが立ち、ステップの復帰コードは<b>そのうちいちばん大きい
もの</b>になる。1 つ失敗しても後続の制御文は動く。これがホストの決まりであり、
「消してから作る」という書き方が成り立つ理由である。消すものがなければ `8` になるが、
作るほうは通る。

### 整列の中身は COBOL の SORT と同じものを使う

バッチでいちばん重いのは整列であり、COBOL の `SORT` 動詞よりもジョブステップとして
整列ユーティリティを呼ぶ場面のほうが多い。しかし<b>並べ替えの規則は 1 つしかない</b>。
鍵の比べ方は[設計 80](80-file-io.md) の `SortWork` が持っており、ユーティリティがやるのは
制御文を鍵へ翻訳することだけである。規則が 2 か所にあれば必ず食い違う。
`SORT` 動詞で正しいものは、ここでも正しい。

#### 通り道の順は決まっている

読む → `INCLUDE` / `OMIT` でふるう → `INREC` で組み直す → 並べ替える → `SUM` でまとめる
→ `OUTREC` で組み直す → `OUTFIL` で振り分ける。この順はホストの決まりであり、順を
入れ替えると答えが変わる。たとえば `SUM` は<b>並べ替えたあと</b>にしか効かない。鍵が
等しいレコードが隣り合っていて初めて、1 つ前と比べるだけでまとめられる。

`INREC` が並べ替えの<b>前</b>にあるのが効くところである。だから `SORT FIELDS` の位置は
「組み直したあとのレコード」を指す。元の位置を指すと思って書くと、静かに違うもので
並ぶ。`OUTREC` が並べ替えの後なのも同じ理屈で、組み直したあとのレコードには元の位置が
もう無い。

#### OUTFIL は 1 回読んだものを振り分ける

条件ごとにジョブステップを分けると、そのたびに<b>入力を読み直す</b>ことになる。
実資産で重い整列を 1 回で済ませる仕掛けが `OUTFIL` である。

書き先は `FNAMES=(dd,...)` か `FILES=(01,...)` で言う。番号で言ったときの DD 名は
`SORTOFnn` である。`OUTFIL` ごとに `INCLUDE` / `OMIT` / `BUILD` を書ける。

`SAVE` は「どの `OUTFIL` にも選ばれなかったもの」を受け取る。だから<b>先に他のものを
決めてから残りを配る</b>。書いた順は関係ない。

#### 整列の出力はそのまま報告書でもある (暫定判断 P-047 の解消)

`OUTFIL` に `HEADER1` / `TRAILER1` / `HEADER2` / `TRAILER2` を書くと、並べたレコードの
まわりに行が付く。`1` が付くものはデータセット全体を囲み、`2` が付くものは `LINES=n` で
切った頁ごとに付く。末尾には `COUNT` と `TOTAL=(p,l,fmt)` / `MIN=` / `MAX=` / `AVG=` を
書ける。

これは飾りではない。ホストのバッチでは、整列の出力が<b>そのまま印刷される</b>ことが多い。
そして末尾の合計は、その上に並んだレコードから数えたものでなければならない。合計を別の
ステップで数え直すと、間にふるいが 1 つ入っただけで合わなくなる。**同じ通り道が明細と
合計の両方を作る**から合っているのであって、たまたま合っているのではない。

だから `TRAILER1` の合計は全体、`TRAILER2` の合計はその頁の分になる。

```
-- PAGE 1 --
EAST  MIKI  0120
EAST  KATO  0300
PAGE TOTAL 420
-- PAGE 2 --
WEST  SATO  0250
WEST  ITO   0130
PAGE TOTAL 380
GRAND 4 RECS 800
```

#### 番号で切るのが先、中身でふるうのが後

`STARTREC=n` と `ENDREC=n` は<b>並びの何本目か</b>で切る。`INCLUDE` / `OMIT` は中身で
ふるう。ホストはこの順であり、逆にすると `STARTREC=2` の数え方が変わる。見出し行を
落とすつもりで `STARTREC=2` と書いたのに、`INCLUDE` が先に効いて別の行が落ちる、という
食い違いがここで出る。

`SAVE` から見ると、番号で落ちたレコードも「どこにも選ばれなかったもの」である。だから
落とした見出し行は `SAVE` の側へ回る。

`SPLIT` と `SPLITBY=n` は、同じ `OUTFIL` の書き先へ<b>順ぐりに配る</b>。中身では分け
られないものを均す仕掛けであり、後の処理を並べて走らせるために使う。

#### 知らない副オペランドは誤りとして報告する

`OUTFIL` の知らない副オペランドを読み飛ばすと、<b>切ったつもりの出力が切られないまま
出る</b>。しかも正常終了する。どこで狂ったのかを後から追うのは難しいので、知らない
副オペランドはその場で報告して止める (暫定判断 P-047)。

#### 位置は 1 から数え、可変長では長さも数に入る

制御文の位置はレコードの先頭を 1 とする。可変長では<b>先頭の 4 バイトが長さ (RDW)</b>
であり、データは 5 から始まる。ここでもレコードを切り出すときに長さを付けたまま持つので、
ホストと同じ数え方になる。切り離してから数え直すと、実資産の `SORT FIELDS=(5,...)` が
1 つずつずれる。

#### 文字で書いた数は、項目では言い表せない (暫定判断 P-047 の解消)

| 形 | 比べ方 |
| --- | --- |
| `CH` | バイトの並び。EBCDIC の照合順序はバイトの値そのものである |
| `BI` | バイトの並び。符号なし 2 進数なので、これで値の順になる |
| `ZD` | `S9(n)` DISPLAY として値で比べる |
| `PD` | `S9(2n-1)` COMP-3 として値で比べる |
| `FI` | 長さ 2 / 4 / 8 を `S9(4)` / `S9(9)` / `S9(18)` COMP として値で比べる |
| `FS` (`CSF`) | 空白・符号・数字だけでできた文字を値として読む |
| `UFF` | 数字だけを拾って値として読む。符号を持たない |
| `SFF` | 数字だけを拾い、前後の `-` を符号として読む |

後ろの 3 つは<b>文字として書かれた数</b>である。ホストの帳票や、外から来たファイルには、
10 進数の欄ではなく `  1,234` や `-  99` のように書かれた数が入っている。`ZD` として読めば
どれも壊れた数になるので、形を分けてある。

これらは `PICTURE` と `USAGE` では言い表せない。`UFF` の「数字以外は読み飛ばす」は
どんな項目の定義にも当たらないからである。それでも<b>比べ方は 1 か所</b>に置きたいので、
整列の鍵には読み方そのもの (`SortValue`) を渡す形にした。並べ替えの仕掛けは COBOL の
`SORT` と同じものが動いている。

`CH` と `BI` をバイトで比べるのは手抜きではない。<b>バイトの並びが値の順と一致する</b>のが
この 2 つの形の定義だからであり、10 進数へ直してから比べても答えは変わらない。

`SUM` が書き戻す `ZD` には<b>符号が付く</b>。ゾーン 10 進数の符号は最下位桁の上位 4 ビットに
あり、正なら X'C' である。読むときは X'F' でも正として読み、書くときは X'C' になる。
ホストの整列も同じものを書く。文字で書いた数は<b>読む形であって書く形ではない</b>ので、
`SUM` の行き先にはできない。

#### 数を書き直す道は 2 つある (暫定判断 P-047 の解消)

`OUTREC` と `OUTFIL` の末尾では、場所を写すだけでなく数を書き直せる。書き直し方は 2 つ
あり、<b>行き先が違う</b>。

| 書き方 | すること | 行き先 |
| --- | --- | --- |
| `TO=形[,LENGTH=n]` | 数の形を移し替える (`PD` から `ZD` へ、など) | 次のプログラム |
| `EDIT=(型)` | 桁区切りを入れ、頭の 0 を消す | 紙 |

`EDIT=` の型で桁を表すのは `I` と `T` である。`I` は頭の 0 を消し、`T` は消さない。
だから `I,III,IIT` と書けば 1234 は `    1,234` になり、0 は `        0` になる。
最後の 1 桁を `T` にするのは、<b>0 のときに何も出ないのを防ぐ</b>ためである。区切りの
コンマも、意味のある数字が出るまでは空白になる。`0,001,234` と印字したい人はいない。

これを 1 か所 (`SortEdit`) に置いてあるのは、`OUTREC` でも末尾の合計でも<b>同じ綴りで同じ
ことが書ける</b>からである。書ける場所ごとに読み方を持つと、明細にはコンマが入るのに
合計だけ入らない、という食い違いが出る。

```
  SORT FIELDS=(6,5,ZD,D)
  OUTFIL FNAMES=SORTOUT,
        OUTREC=(1,4,6:6,5,ZD,13:6,5,ZD,EDIT=(I,III,IIT)),
        TRAILER1=(C'TOTAL',13:TOTAL=(6,5,ZD,EDIT=(I,III,IIT)))
```

```
EAST 1234E     12,345
WEST 0250{      2,500
MIKI 0076{        760
TOTAL          15,605
```

6 桁目に残した `1234E` が、パック 10 進数を開いたままの姿である。最後の桁の上位 4 ビットが
符号なので、そのまま印字すると英字に見える。<b>開いた数をそのまま紙へ出してはいけない</b>
理由がここにあり、`EDIT=` が要るのもそのためである。

### ICETOOL は整列を持たない

`ICETOOL` は `TOOLIN` に書いた操作を上から順に実行する道具である。整列そのものは持たず、
<b>`SORT` を呼び出す</b>。`USING(cccc)` と書けば `ccccCNTL` の制御文で通る。実装としては
DD 名を付け替えた目録を渡すだけであり、`SORT` から見れば普通に `SORTIN` を読んで
`SORTOUT` へ書いている。

こうしておけば鍵の扱いが 2 か所に分かれない。`ICETOOL` が足しているのは「同じ入力を何度も
通す」「重なりを見つける」「数える」という、<b>整列の周りの仕事</b>である。

| 操作 | すること |
| --- | --- |
| `COPY` / `SORT` | 入力を出力へ通す。`USING` があれば `SORT` の制御文で通す |
| `MERGE` | 整列済みの入力を突き合わせる。`SORTINnn` へ結び付けて `SORT` を呼ぶ |
| `COUNT` | 件数を出す。`EMPTY` / `NOTEMPTY` / `HIGHER` などで復帰コードを立てる |
| `STATS` | 場所ごとに最小・最大・平均・合計を出す |
| `RANGE` | 範囲に入っている値を数える。復帰コードは立てない |
| `UNIQUE` | 違う値がいくつあるかを出す |
| `VERIFY` | 10 進数の欄が数として読めるかを確かめる。読めなければ復帰コード 12 |
| `SELECT` | 重なりで選ぶ。`FIRST` / `LAST` / `ALLDUPS` / `NODUPS` / `HIGHER` |
| `SPLICE` | 鍵が同じレコードを 1 本につなぐ。`WITH(p,l)` の場所を重ね書きする |
| `SUBSET` | 順番で選ぶ。`FIRST` / `LAST` / `RRN` と `KEEP` / `REMOVE` / `DISCARD` |
| `RESIZE` | レコードの長さを変える。`TOLEN(n)` で数え直す |
| `DISPLAY` / `OCCUR` | 場所の値を並べる。`OCCUR` は値ごとの件数を数える |
| `MODE` | 失敗した操作のところで打ち切るか (`STOP` が既定) |

`MODE STOP` が既定なのはホストと同じである。失敗した操作の結果を次が使ってしまうと、
<b>誤りが誤りのまま先へ進む</b>。

#### 数を答える操作と、形を変える操作 (暫定判断 P-047 の解消)

`COUNT` / `STATS` / `RANGE` / `UNIQUE` / `VERIFY` は<b>データセットを作らない</b>。
答えは覚え書きの行と復帰コードだけである。だから `TO` を持たない。`MODE CONTINUE` と
組み合わせて「入力が空なら後を飛ばす」「数が合わなければ止める」という並びを組むための
道具であり、ジョブの流れを決めているのはこちらである。

`VERIFY` がとくにそうである。10 進数として読めない欄をそのまま計算へ渡せば、ホストでは
`S0C7` で落ちる。落ちてから探すより<b>流す前に見つける</b>ほうが早い。だから、ふるい分けが
読めないバイトを 0 とみなすのに対して、`VERIFY` だけは握り潰さない道を通る。

```
ICE612I 0 RECORD 2 HAS AN INVALID DECIMAL VALUE AT 13
ICE611I 0 INVALID DECIMAL VALUES: 1
```

`SPLICE` と `RESIZE` は<b>レコードの中身と長さを変える</b>。`SPLICE` は組の 1 本目を土台に
して、後から来たものの `WITH` の場所だけを重ね書きする。鍵が同じなら後の値が勝つ、
つまり更新レコードを当てる形である。既定では組になったものだけを出し、`KEEPNODUPS` と
書けば 1 本しかないものも出る。「両方にあるものだけ」と「片方にしかないものも」を、この
1 語で言い分ける。

### 場所の読み方は 1 か所に置く

`SORT` も `ICETOOL` も、位置と長さと形でレコードの中の場所を言う。読み方が 2 か所にあれば
必ず食い違うので、形の解釈と値の取り出しは `SortField` 1 つに置いた。レコードの切り方
(`Records`) も同じ理由で 1 つである。

### 覚え書きの出し先

ホストのユーティリティは `SYSPRINT` へ経過を書く。ジョブが書いていなければ出さないのが
ホストの決まりだが、それでは黙って失敗したときに手がかりが残らない。結び付けがなければ
実行時の出力へ回す。

## DISP はステップの前と後の両方を決める (FR-133)

`DISP=(状態, 正常終了時, 異常終了時)` である。3 つとも意味が違う。1 つ目は<b>ステップが
始まるときに何を期待するか</b>、あとの 2 つは<b>ステップが終わったときに何を残すか</b>で
ある。

### 前で確かめるのは、黙って動いてしまわないためである

| 状態 | 割当ての段ですること |
| --- | --- |
| `NEW` | もとからあれば誤りにする。無ければ空のデータセットを割り当てる |
| `OLD` / `SHR` | 無ければ誤りにする |
| `MOD` | 無ければ空のデータセットを割り当てる。ある場合はそのまま |

無いものを空として読ませたり、あるものを黙って作り直したりすると、<b>名前を打ち間違えた
ジョブが「0 件処理した」と言って正常終了する</b>。これはいちばん見つけにくい壊れ方であり、
ホストが割当ての段で止めるのはそのためである。

割当てに失敗したステップはプログラムを呼びもしない。これは異常終了とは別のものであり、
`COND=EVEN` でも覆せない。<b>以降のステップは実行されずに流される</b>。

### 後で決めるのは、残すか消すかである

2 つ目を書かなければ、新しく作るデータセットは `DELETE`、もとからあるものは `KEEP` で
ある。<b>作ったものは消える</b>のが既定であり、残したければ書かねばならない。3 つ目を
書かなければ 2 つ目と同じになる。ただし 2 つ目が `PASS` のときだけは、新しいものは消え、
もとからあるものは残る。

残す側の 3 つは<b>それぞれ違うことをする</b>。何が違うのかは、次の節の置き場と目録の
切り分けで決まる。

### 置き場と目録は別のものである (FR-131、暫定判断 P-045 の解消)

ホストではデータセットは<b>ボリュームの上にあり</b>、目録はその名前がどのボリュームに
あるかを覚えている。2 つが別だから「ボリュームにはあるが目録には載っていない」が起こる。
`KEEP` と `CATLG` が違うのはそこであり、`UNCATLG` が消すのは目録の項目だけである。

以前は目録をディレクトリそのものとしていた。ファイルがそこにあることと目録に載っている
ことが同じなので、載せる・外すという操作が無かった。いまは置き場をディレクトリ 1 つとし、
目録をその下の `.catalog` という覚え書きにしている。

| 処置 | 置き場 | 目録 |
| --- | --- | --- |
| `DELETE` | 消す | 外す |
| `KEEP` | 残す | <b>触れない</b>。`NEW` で作ったものは載らないまま |
| `CATLG` | 残す | 載せる |
| `UNCATLG` | 残す | 外す |
| `PASS` | 残す | 触れない。ジョブの終わりに片付ける |

`DISP=SHR` と `DISP=OLD` が確かめる「ある」は<b>目録から引けること</b>である。置き場に
バイト列が残っていても、目録に載っていなければ名前では届かない。`DISP=(NEW,KEEP)` で
作ったものを次のジョブが名前だけで読もうとすれば `DATA SET NOT FOUND` になる。ホストと
同じであり、実資産をそのまま動かしたときに<b>実機と同じところで止まる</b>。

`NEW` だけは目録ではなく置き場を見る。目録に載っていなくても場所は塞がっているので、
そこへ新しく作ることはできない (`DUPLICATE NAME ON DIRECT ACCESS`)。

#### 目録に届かないものへ届くのが VOL=SER である

`VOL=SER=` を書いたジョブは<b>目録を通さず置き場を直に見る</b>。目録に載っていない
データセットへ届く唯一の手であり、ホストで `KEEP` したものを次のジョブが読むときに
`VOL=SER` を書かねばならないのと同じ形である。

#### 知らない名前は載っているものとして扱う

目録が覚えるのは<b>ジョブが作ったものだけ</b>である。置き場は人がファイルを置く
ディレクトリでもあり、そこへ置いたものを目録にも書かせるのでは道具として使えない。
覚えのない名前が置き場にあれば、初めから載っていたものとして扱う。実際の運用でも、
外から持ち込まれたデータセットは目録に載っている。

そのかわり `NEW` で作ったものには<b>その場で「載っていない」と書き留める</b>。書き
留めないと、次のジョブで覚えのない名前として拾われ、`KEEP` と `CATLG` の区別がまた
消えてしまう。

#### ジョブの中では目録を通さない

同じジョブの後続ステップは、そのジョブが割り当てた名前を<b>目録を通さずに引ける</b>。
ホストもジョブが割り当てたデータセットを覚えていて、あとのステップが同じ名前を書けば
そこから引く。`DISP=(NEW,KEEP)` で作ったものを次のステップが `DISP=OLD` で使う書き方が
通るのはこれによる。通らなくなるのは<b>ジョブをまたいだとき</b>である。

### 区分データセットはディレクトリ、メンバはその下のファイル (FR-113)

`DSN=PAY.LIB(JANUARY)` の `PAY.LIB` がライブラリ、`JANUARY` がメンバである。ライブラリを
ディレクトリ、メンバをその下のファイルとして持つ。覚え書き (`.meta`) はメンバの隣に置く。
置き場の下でもライブラリの下でも<b>データセット 1 つに覚え書き 1 つ</b>という形は変わら
ない。

割り当てるのは<b>ライブラリ</b>である。目録が覚えているのもライブラリであって、メンバ
ではない。だから `DISP=(OLD,DELETE)` にメンバを書けば消えるのはメンバだけで、ライブラリは
残る。

括弧の中が `(+1)` のような相対世代のときはメンバではなく世代データグループである
(要件 FR-114、後述)。メンバ名として扱えば `(+1)` という名前のメンバを作ってしまう。

### 何が区分になるかは SPACE の 3 つ目が決める (FR-113)

メンバを名指せばライブラリなのは当たり前だが、<b>メンバを言わずにライブラリだけを作る</b>
ことがある。`IEBCOPY` の写し先がそれである。ホストでそれを決めているのは `SPACE=` の
3 つ目の数 (ディレクトリブロック) であり、ここでもそれに拠る。

```
//OUT      DD   DSN=B.LIB,DISP=(NEW,CATLG),SPACE=(TRK,(5,5,10))
```

`10` を書けば区分データセット、書かなければ順編成である。書き忘れたジョブの `IEBCOPY` が
「写し先が区分ではない」で止まるのは、ホストでもここでも同じ理由による。

### メンバの一覧と並びは 1 か所で決める (FR-053, FR-113、暫定判断 P-056 の解消)

`IEBCOPY` と `LISTDS` は<b>ディレクトリを引く</b>道具である。いままでの道具は DD が
データセット 1 つを指していたので、何を触るのかが割当ての段で決まっていた。ここでは
何を触るのかがライブラリの中身で決まる。

決めることは 2 つある。

**どこまでがメンバか。** ライブラリの下にはメンバの覚え書き (`PAYROLL.meta`) も並んで
いるので、ファイルが並んでいるだけでは一覧が言えない。決めるのは<b>メンバ名の決まり</b>
である — 8 文字まで、英大文字と数字と `@ # $`、先頭は数字でない。`.` は入らないので
覚え書きはメンバになりえない。名前の決まりを入れて初めてディレクトリが言えるようになる
ので、この 2 つは同じ増分で入れるほかない。

同じ決まりを JCL を読む段でも使う。`DSN=MY.LIB(TOOLONGNAME)` はホストではジョブを読む段で
弾かれるので、ステップは<b>動かない</b>。通せば実機で動かないジョブがここでは動く。

**どういう順に並ぶか。** ホストのディレクトリは名前の昇順である。順を決めているのは
<b>EBCDIC のバイト</b>であり、英字が数字より前に来る。Java の `String` の順は逆である。

| 名前 | EBCDIC | Java の `String` |
| --- | --- | --- |
| `PAYA` | 先 | 後 |
| `PAY1` | 後 | 先 |

これは細かい違いではない。ライブラリを丸ごと写したジョブの<b>出力そのものが実機と別の
バイト列になる</b>ということであり、写した先を読む後続のジョブまで巻き込む。並べる場所は
`IEBCOPY` だけではなく `LISTDS` と `IDCAMS LISTCAT` にもあるので、並べ方を書き分ければ
いずれ食い違う。`PartitionedDataSet` に 1 つだけ置き、3 つともそこから引く。

### ディレクトリの項目は名前だけではない (FR-113、暫定判断 P-059 の解消)

ホストのディレクトリの項目は<b>名前 8 バイト・位置 3 バイト・標識 1 バイト</b>の 12 バイト
に、利用者データが付いた大きさである。名前の並びだけを持っていると、この項目に付いてくる
3 つのことがどれも書けない。

| 事柄 | 何か | 持ち方 |
| --- | --- | --- |
| 別名 (`ALIAS`) | 同じメンバへ向けた別の名前 | 置き場のシンボリックリンク |
| ISPF の統計 | 版・更新日時・行数・直した人 (30 バイト) | メンバの隣の `名前.stats` |
| ディレクトリの大きさ | `SPACE=` の 3 つ目 | ライブラリの `.meta` の `dirblks=` |

**この 3 つはひと続きである。** 統計が付けば項目は 42 バイトになる。1 ブロックは
256 バイトで、先頭 2 バイトは使った長さだから、入るのは<b>統計なしで 21 個、統計付きで
6 個</b>である。別名も項目を 1 つ使う。つまり統計を持たずにブロックの数だけを決めることは
できない — 決めれば、統計を入れた日に<b>止まる場所が動く</b>。

**別名はシンボリックリンクである。** 覚え書きの表を別に持って「この名前は別名である」と
書く手もあるが、そうすると<b>その名前があるかどうかの拠り所が 2 つ</b>になる。ディレクトリ
の一覧を置き場から引くことにしたのと同じ理由 (暫定判断 P-056) で、リンクにする。置き場に
ファイルとして並ぶのだから一覧に出るし、開けば中身が読める — `IEBGENER` も翻訳した資産も、
別名だと知らないまま読める。

元のメンバを消したときに<b>切れたリンクが残る</b>のもホストと同じである。実機でも別名の
項目はディレクトリに残り、開こうとして初めて失敗する。メンバの名前を変えても別名は
付いてこない。

属性だけは<b>指す先から引く</b>。別名は覚え書きを持たないので、引き直さないと別名から
読んだときだけレコードの切れ目が変わる。

**統計は書いた側が作らない。** ホストでも、ISPF の編集で書いたメンバには統計が付くが、
プログラムが `OPEN OUTPUT` で書いたメンバには付かない。ISPF の一覧で統計の欄が空の
メンバが混じるのはそのためである。ここで作ってしまうと<b>実機には無いはずの統計</b>が
生える。`IEBCOPY` は持っていたものを持ち越すだけである — 写しは編集ではないので、版も
更新日時も動かない。

**ディレクトリの大きさはライブラリの覚え書きに残す。** `SPACE=` を書いたのは作ったジョブ
だけであり、あとからメンバを足すジョブは `DISP=SHR` としか書かない。DD の割当てに持たせて
渡す形も採れるが、それでは<b>DD を通らない道具</b> (TSO の `RENAME`) から見えない。
ホストでもこれはデータセットのラベルにあるものである。

使い切ったときは `S013` で止める。受け止め手がない — プログラムはライブラリの大きさを
知らないし、`FILE STATUS` を見て別のライブラリへ書き直すようなことはできない。翻訳した
資産の `OPEN OUTPUT` も `IEBCOPY` も `IEBGENER` も同じ検査を通る。片方だけで効かせると、
<b>同じライブラリが書き手によって入る数を変える</b>ことになる。止まる位置と異常終了
コードには確かめられていないところが残る (暫定判断 P-061)。

### 世代は普通のデータセットである (FR-114)

世代データグループは<b>入れ物ではない</b>。`PAY.HISTORY` という基底名を登録しておくと、
実際のデータは `PAY.HISTORY.G0001V00`、`PAY.HISTORY.G0002V00` … という普通のデータセット
として並ぶ。`PAY.HISTORY(+1)` と書けるのは JCL が相対番号をこの絶対名へ直すからであって、
括弧の中がメンバ名のように解釈されるわけではない。

だから世代の一覧も別に持たない。置き場に並んだ名前のうち `基底名.GnnnnV00` の形をして
いて、かつ<b>目録に載っている</b>ものが世代である。区分データセットのディレクトリと同じ
考え方であり (要件 FR-113)、「その世代があるか」の答えが 2 通りにならない。

覚えるのは基底の定義だけである — 何世代まで残すか (`LIMIT`)、あふれたときに 1 つだけ外す
のか全部外すのか (`NOEMPTY` / `EMPTY`)、外したものを消すのか残すのか
(`NOSCRATCH` / `SCRATCH`)。これは置き場のファイルからは引けないので、`.gdg` という
覚え書きに書く。目録と分けてあるのは<b>寿命が違う</b>からである。目録の項目はデータセットを
消せば消えるが、基底の定義は世代が 1 つも無くなっても残る。

#### 番号はジョブの初めに決まる

相対番号を絶対名へ直すのは<b>ジョブを読む段で 1 度だけ</b>である。

| 書いたもの | 指すもの |
| --- | --- |
| `(0)` | ジョブが始まった時点でいちばん新しい世代 |
| `(-1)` | その 1 つ前 |
| `(+1)` | 次に作る世代。<b>同じジョブの中では何度書いても同じ 1 つ</b> |

ステップ 1 が `(+1)` で世代を作っても、ステップ 2 の `(0)` は動かない。ステップ 2 の
`(+1)` はステップ 1 が作ったのと同じデータセットである。ホストの JCL がそう解釈するから
である。

ここを譲るとどうなるかがはっきりしている。ステップごとに引き直せば、実機では 1 つの
ファイルへ 2 度書くジョブがここでは<b>世代を 2 つ作り</b>、後続が読むのは片方だけになる。
差が復帰コードではなく<b>データの欠落</b>として出るので、あとから気付けない。

同じ理由で、`DEFINE GDG` をしたジョブの中でその基底を相対番号では指せない。ジョブが
始まった時点で基底が無いからである。ホストにも同じ制限がある。登録していない名前を
`(+1)` と書けば JCL エラーになる — 黙って絶対名を組み立てると、`DEFINE GDG` を忘れた
ジョブが<b>世代のようで世代でないデータセット</b>を作って正常終了してしまう。

#### 組み入れは目録へ載った時である

`(+1)` で作っただけの世代はまだ群れの一員ではない。`DISP=CATLG` が効いて初めて数に入る。
だから `DISP=(NEW,CATLG,DELETE)` のステップが異常終了すれば、その世代は消えて群れは元の
ままである。ホストが新しい世代をロールインまで数えないのはこの形である。

あふれたぶんは古いほうから外れる。外れるのは<b>目録から</b>であって、置き場からではない。
`SCRATCH` と書いたときだけ実体も消える。外れた世代は名前で引けなくなるので `(0)` も
`(-1)` も届かない — バイト列は残っているが、指すには `VOL=SER=` が要る。`KEEP` で残した
データセットと同じ位置に落ちる。

そのため `DELETE 基底 GDG FORCE` が消すのも<b>まだ群れにいる世代だけ</b>である。先に
あふれて外れた世代は残る。もう群れの一員ではないからであり、ホストでも同じである。

### 一時データセットは場所を持たない

`DSN=&&WORK` はジョブの間だけ存在するデータセットである。ステップの間で受け渡す作業
ファイルがこれであり、実資産のバッチではいちばんよく使われる形である。

<b>場所を持たないのが要点である</b>。置き場を決めるのはジョブ実行であって、ジョブの記述
ではない。だから同じジョブを同時に何本流しても、互いの作業ファイルを踏まない。

ジョブが終われば置き場ごと消える。`DISP` の前の検査はそのまま効くので、書いていない一時
データセットを `DISP=OLD` で読もうとすれば止まる。

なお `&&` が 2 つなのは<b>シンボリックパラメタと区別するため</b>である。展開の段で 1 つの
`&` になり、残った先頭の `&` が一時データセットを表す。

### PASS は次のジョブへは渡さない

`DISP=(NEW,PASS)` で残したものは、<b>このジョブの後続ステップへ</b>渡る。ジョブが終われば
消える。残したければ `CATLG` と書く。

判断はデータセットごとの<b>いちばん新しい処置</b>で決まる。あとのステップが `CATLG` と
書けば残り、`DELETE` と書けばその場で消える。

### DISP=MOD だけがプログラムの書いたことを覆す

`DISP=MOD` は「`OPEN OUTPUT` と書いてあっても末尾へ足す」という意味になる。ジョブの指定が
プログラムより強い、数少ない場所である。だからこそ<b>覆るのはこの 1 か所だけ</b>にして
ある。同じプログラムを「作り直す」使い方と「積み増す」使い方の両方へ向けられるのは、
これがあるからである。

実装では `DataSetCatalog` がその DD を覚え、`OPEN` が `OUTPUT` を `EXTEND` へ読み替える。
順編成にしか意味がないので、相対編成と索引編成では読み替えない。

### 宣言的形式は DISP を書かなくてよい

JCL では `DISP` を書かなければ「新しく作る」だが、宣言的形式では<b>何も言っていない</b>
ことになる (`Disposition.Status.ANY`)。確かめも、作りも、消しもしない。名前を書くだけで
動かせるほうが、この処理系自身の試験には都合がよい。ジョブの側で状態を決めたいときは
`DD 名 DSN=場所 DISP=(NEW,CATLG)` と書ける。

### 作業領域はステップが終われば片付ける

`SYSOUT` のスプールも埋め込みデータも連結の写しも、そのステップの間だけ要るものである。
正常に終わったところで消す。<b>異常終了したステップのものは残す</b>。何が起きたのかを
見られるほうが役に立つからであり、同じ名前で上書きされるので増え続けはしない。

## 異常終了コード (FR-141)

ホストは実行を打ち切るとき、<b>何が起きたのかを 4 桁で言う</b>。`S` で始まるものはシステムが
検出したもの、`U` で始まるものはプログラムや言語環境が自分で立てたものである。運用は
このコードを見て次にやることを決める。データの誤りなら入力を直して流し直せばよく、
ロードモジュールが無いなら組み立てから直す。<b>コードが合っていない実装は、動いても
使えない</b>。

### コードは条件そのものが持つ

どの例外がどのコードになるかを 1 か所の対応表にすると、条件を足したときに<b>表を直し
忘れる</b>。そうではなく、条件を表す例外自身が `AbendCause` としてコードを名乗る。
ジョブ実行の側は例外の種類を並べず、`Abend.codeOf` に訊くだけである。

| コード | 立てる条件 | いつ |
| --- | --- | --- |
| `S0C7` | `DataException` | 数値項目に数字でないバイトが入っていた |
| `S0CB` | `DecimalDivideException` | ゼロで割った。商が入りきらなかった |
| `S0C4` | `Ops.linkage` | 渡されていない連絡節の項目を触った |
| `S806` | `ProgramNotFoundException` | 呼び先のロードモジュールが見つからない |
| `S001` | `FileOperationException` (状態 `30`) | データセットの形が記述と合わない |
| `S001` | `DataSetIoException` | データセットの置き場へ届かない |
| `S037` | `FileOperationException` (状態 `34`) | 割り当てた領域を使い切った |
| `U4038` | `RangeCheckException` | `SSRANGE` の範囲外参照 |
| `U4038` | `FileOperationException` (そのほか) | `FILE STATUS` も宣言部分も無いファイルの異常 |

包まれた例外も辿る。ランタイムの中で `UncheckedIOException` などに包まれても、もとの条件の
コードが残る。

ファイルの異常だけは、<b>条件の中に小さな対応表がある</b>。例外の型ではなくファイル状態
コードが「何が起きたか」を持っているためである。表を外へ出すと、状態コードを足したときに
直し忘れる。

### 入出力の誤りは起こせなければ意味がない (FR-141)

`S001` と `S037` は長らく<b>立てられなかった</b>。装置を持たないこの実装では、装置の誤りを
起こす手立てが無かったからである。ジョブが `IF ABENDCC = S001` と書いた枝は決して通らず、
異常終了しても想定した後始末が動かない。コードを名乗るだけでは足りず、<b>その条件を実際に
起こせるようにして初めて</b>コードに意味が出る。

起こせるようにしたのは 2 つである。

**形が記述と合っていないこと。** 固定長のはずが長さがレコード長で割り切れない、可変長の
はずが `RDW` がつながらない、というデータセットは<b>そこから先を切り出せない</b>。以前は
半端をそのまま短いレコードとして渡していた。渡してしまえば、読めていないデータで処理が
進む。いまは切れるところまでを読めるものとし、その先でファイル状態 `30` を立てる。
読めていたレコードを捨てないのは、ホストも同じく<b>読んだ時点で</b>誤りにするからである。

**割り当てた領域を使い切ること。** ホストは `SPACE=` であらかじめ場所を取ってから書く。
取った分を使い切れば書けなくなり、二次割当があればそこで伸びる。無ければ止まる。この
指定を無視していると、<b>実機では止まるジョブがここでは通る</b>。いまは目録が DD ごとの
大きさを持ち、越えた `WRITE` がファイル状態 `34` を立てる。

### 領域の大きさは目録が持つ

`SPACE=` はデータセットの属性ではない。属性はバイト列の<b>切り方</b>を決めるものであり、
置き場をどれだけ取ったかとは別の話である。同じデータセットでも、割り当てる大きさはジョブが
決める。したがって `DISP=MOD` と同じく `DataSetCatalog` が持つ。

JCL は装置の単位 (`TRK` / `CYL` / ブロック長) で書き、宣言的形式は<b>バイトで書く</b>
(`SPACE=8000`)。宣言的形式は装置を知らないので、トラックを持ち込む理由がない。トラックと
シリンダの大きさは 3390 のものを使う (暫定判断 P-052)。

### 異常終了しても、書いたものは残る

ステップが終わったら、開いたままのファイルを実行機構が閉じる。異常終了した場合も同じで
ある。閉じずに終わったファイルは<b>書いたものがまだ置き場に届いていない</b>ため、残った
ものを見て何が起きたのかを調べられない。処置 (`DISP`) が「作りかけのものを消す」という形で
効くのも、いったん届いていることが前提である。

閉じるときの誤りは伝えない。すでに異常終了しているかもしれず、そこへ別の誤りをかぶせると
<b>最初に起きたことが分からなくなる</b>。

### 割当てと OPEN は役割が違う (FR-113、暫定判断 P-048 の解消)

`S013` も長らく立てられなかった。割当ての段ですべてを確かめていたので、開く段に残る
仕事が無かったからである。区分データセットを入れて初めて両者が分かれた。

- **ライブラリがあるか** — 割当ての段で分かる。無ければ JCL エラーであり、ステップは
  <b>動かない</b>。プログラムは呼ばれてすらいない
- **メンバがあるか** — 開く段まで分からない。ホストも同じで、割当ては通り、`OPEN` で
  `S013` になる

違いは重い。割当てに失敗すれば以降のステップまで流されるが、開けずに止まったステップは
<b>動いてから止まっている</b>。そこまでに書いたものが残り、`IF (STEP.ABENDCC = S013)` で
受けられる。

無いメンバが<b>ファイル状態 `35` にならない</b>のもここである。`35` は「この `OPEN` 文が
失敗した」であり、プログラムは `FILE STATUS` で受け止めて先へ進める。メンバが無いのは
データセットが無いことではない — 割当ては通っている — ので、受け止め手のある誤りとして
渡してしまうと、ジョブが<b>綴りを間違えたメンバ名で 0 件処理して正常終了する</b>。

メンバを言わずに区分データセットを開こうとしたときも同じく `S013` である。どのメンバの
バイト列を読むのかが決まっていない。

### 受け止め手があれば打ち切らない

`ON SIZE ERROR` を書いたゼロ除算は条件のままであり、異常終了にならない。`FILE STATUS` を
書いたファイルの異常も同じである。<b>打ち切るのは受け止め手が無いときだけ</b>という規則は
ホストと同じであり、これがあるから「異常終了した」という事実に意味がある。

### 渡されていない連絡節は必ず S0C4 にする

ホストでは連絡節の項目は呼ぶ側の領域を指す仕掛け (BLL) だけを持つ。渡されていなければ
その中身が定まらず、運が悪ければ自分の持ち場の外を指して `S0C4`、運がよければ何かが読めて
<b>誤った値のまま処理が進む</b>。

ここでは必ず `S0C4` で終わることにした。定まらない挙動を再現するより、誤りを誤りとして
見せるほうがよいという判断である (要件 FR-205 の安全側)。翻訳したコードは配列から直に
取らず `Ops.linkage` を通る。

### ABENDCC で後始末を分ける

`IF (CHECK.ABENDCC = S0C7) THEN` と書ける。比べられるのは<b>等しいか等しくないかだけ</b>で
ある。異常終了コードに大小はない。ステップを言わなければ、最後に分かったコードを見る。

宣言的形式でも `WHEN ABENDCC CHECK = S0C7` と書ける。どちらも同じ内部モデル
(`StepCondition.Abend`) へ落ちる。

### 通らなかったジョブは 0 を返さない

異常終了と JCL エラーはどちらも復帰コードを立てない。いちばん大きい復帰コードをそのまま
返すと `0` になり、<b>後続の運用が「通った」と読み違える</b>。どちらの場合も終了コードは
12 以上になる。どちらだったかはステップの結末に残る。

## 異常終了の診断出力 (FR-142, FR-143)

異常終了コードだけでは、どこで何が起きたのか分からない。ホストの言語環境は `CEEDUMP` と
して、止まった場所・呼び出し履歴・記憶域の中身を書き出す。<b>それが無ければ、本番で一度
だけ起きた事故を追えない</b>。

### 止まった場所はクラスファイルの行番号表から取る

翻訳するとき、文ごとに原文の行をクラスファイルへ埋めてある
([設計 70](70-codegen.md))。だから JVM の呼び出し履歴が<b>そのまま原文の行を指す</b>。
対応表を自分で持たないので、本体とずれる余地がない。

```
TRACEBACK:
  PROGRAM   STATEMENT  SOURCE
  PAYCHK    11         PAYCHK.cbl
  PAYRUN    8          PAYRUN.cbl
```

載せるのは翻訳したプログラムの段だけである。ランタイムの中の段は、COBOL を書いた人に
とっては自分の書いたものではない。

### 項目名で書けるのは割り付けを持ち歩いているからである

16 進を読んで変位を数えるのと、名前で探すのとでは、追える速さが違う。しかし<b>どのバイトが
どの項目かを知っているのは翻訳の側</b>であり、実行時に手元にあるのはバイト列だけである。
だから割り付けを生成クラスへ埋めて持ち歩かせる ([設計 70](70-codegen.md))。

```
STORAGE FOR PAYCHK:
  01 WS-EMPLOYEE
    05 WS-NAME = 'SMITH   '  E2D4C9E3C8404040
    05 WS-GRADE = 7  F0F7
  01 WS-N = <not numeric>  C1C1C1
```

数として読めないバイトが入っていれば、そう書いて 16 進を添える。<b>読めないバイトが
入っていること自体</b>が、たいていの場合いちばんの手がかりだからである。割り付けを
持たないプログラムでは 16 進の羅列に落ちる。

### 記憶域は積んでおかないと取り出せない

呼び出し履歴だけなら JVM の履歴で足りるが、<b>それぞれの作業場所の中身</b>は残らない。
実行時の入口が、動いているプログラムを積んでおく。

正常に戻ったときだけ積み直す。<b>異常終了で抜けたプログラムは積まれたまま残る</b>ので、
覚え書きがその中身を見られる。ステップごとに新しい入口を作るので、残ったものが次の
ステップへ漏れることはない。

```
STORAGE FOR PAYCHK:
  000000  C1C1C1F0 F0F0F0F0                    |AAA00000        |
```

16 進のほうが正であり、左の値は目で追うための添え物である。読めないバイトは点にする。

### 行き先は CEEDUMP、細かさは CEEOPTS

ホストと同じく、診断出力は `CEEDUMP` の DD へ出す。書かれていなければジョブの出力へ回す。
<b>黙って捨てない</b>のは、書き忘れたジョブで事故が起きたときに手がかりが残らないから
である。

細かさは `CEEOPTS` の DD に書いた `TERMTHDACT` が決める。

| 指定 | 覚え書き | 呼び出し履歴 | 記憶域 |
| --- | --- | --- | --- |
| `QUIET` | — | — | — |
| `MSG` | 出る | — | — |
| `TRACE` (既定) | 出る | 出る | — |
| `DUMP` | 出る | 出る | 出る |

毎回すべてを書き出すと量が多すぎて<b>肝心の 1 行が埋もれる</b>。一方で追い切れない事故が
起きたときには中身が要る。だから切り替えられるようになっている。

### 書式はホストのものではない

中身はホストの `CEEDUMP` が持つものに揃えたが、並べ方と字面は真似ていない。真似ると、
<b>本物と見分けがつかないものが出てきて、既存の解析道具が誤って読む</b> (暫定判断 P-051)。

## 起動

```
cobolj [-d クラスの置き場] [-w 作業領域] [-b データセットの基点] [-p 手続きの入れ物] ジョブ記述
```

記述形式は拡張子で見分ける。`.jcl` なら JCL、それ以外は宣言的形式である。

プロセスの終了コードは<b>ジョブの終了コード</b>である。いちばん大きいステップの復帰コードで
あり、後続のジョブがそれを見て動く。ステップの結末は標準エラーへジョブログとして書く。

## 次の増分

1. 報告書の見た目を揃える (暫定判断 P-047)。あらかじめ決まった編集の型 (`M0` から `M26`)、
   `SIGNS=`、`ICETOOL` の `DISPLAY` と `OCCUR` の桁揃え。制御文の骨組みも欄の書式も
   揃ったので、残っているのは<b>印字した見た目</b>だけである。型の中身は推し量らず、
   実機の出力と突き合わせて決める。
2. 領域不足の異常終了コードを `B37` / `D37` / `E37` へ分ける (暫定判断 P-052)。
   ディレクトリ満杯の異常終了コード (暫定判断 P-061) も同じ族なので、一緒に決める。
   どちらも実機で確かめないと決められない。
3. `IEBCOPY` のアンロード形式と、統計を出す一覧 (暫定判断 P-061)。資産を機械の間で運ぶ
   形であり、実資産に現れた数で決める。
4. 世代の版と番号の折り返し (暫定判断 P-060)。版を使う資産が見つかった段でよい。
