# 設計 90: ジョブ実行

| 項目 | 内容 |
| --- | --- |
| 対応要件 | FR-130〜FR-137、要件定義書 7.1 節 |
| ステータス | 内部モデル・宣言的形式・JCL・ユーティリティ 4 本 実装済 |

## 何を決めるか

バッチの実資産は<b>プログラム 1 本では動かない</b>。JCL がステップを並べ、DD 名を実際の
データセットへ結び付け、復帰コードで後続の実行を決める。そこまで揃って初めて「ソース無修正で
動く」と言える。

## 内部モデルが先で、記述形式はあと (FR-130)

実行機構が解釈するのは<b>内部ジョブモデルだけ</b>である。JCL パーサも宣言的形式のパーサも
知らない。

```
JCL         ┐
            ├→ 内部ジョブモデル (Job / Step / DdAssignment / StepCondition) → 実行機構
宣言的形式  ┘
```

こうしておく理由は 2 つある。<b>どちらの形式で書いても結果が同じ</b>になること (要件 FR-132)。
そして、JCL の込み入った書式をパーサの中に閉じ込め、実行の側へ持ち込まないことである。

| 型 | 表すもの |
| --- | --- |
| `Job` | ジョブ 1 個。ステップの並び |
| `Step` | プログラム 1 本の実行。名前・プログラム名・`PARM`・DD 割当・条件 |
| `DdAssignment` / `DdTarget` | DD 名と行き先。実ファイル、`SYSOUT`、`DUMMY`、埋め込みデータ |
| `StepCondition` | 動かすかどうかの条件 |
| `JobState` | ここまでに起きたこと。復帰コードと異常終了の有無 |

## 条件は「真なら動かす」の向きに揃える (FR-136)

JCL の `COND` は<b>「真なら飛ばす」</b>という向きで書く。`COND=(4,LT,STEP1)` は
「STEP1 の RC が 4 より大きければ飛ばす」である。逆さまで読みにくく、誤りのもとでもある。

内部モデルでは<b>「真なら動かす」</b>の向きに揃えた。向きの反転は JCL パーサの仕事である。
宣言的形式は素直に書ける。

```
WHEN RC CHECK <= 4
```

異常終了の扱いも条件の一部として持たせている。ホストでは先行ステップが異常終了すると以降は
飛ばされるが、`COND=EVEN` と `COND=ONLY` がそれを覆す。「飛ばす／飛ばさない」を決めるものは
1 か所にあるほうがよい。

**動いていないステップの復帰コードは比べられない**。飛ばされたステップを名指す条件は
成り立たないものとして扱う。

## ステップは独立している (FR-130)

ステップごとに新しい実行時の入口を作る。作業場所も、読み込んだ副プログラムも、開いたファイルも、
復帰コードも<b>持ち越さない</b>。持ち越すのはジョブの状態だけである。

ホストではステップごとに別のアドレス空間が立つ。同じ実行時の入口を使い回すと、前のステップの
作業場所が残り、初期値から始まらないプログラムができてしまう。

## SYSOUT はスプールを通る (FR-135)

ホストでは `SYSOUT` へ書いたものがスプールに溜まり、ジョブが終わってから印字される。
ここでも作業領域のファイルへ溜め、ステップが終わったところで流し出す。

<b>プログラムから見れば普通のデータセットである</b>。行順編成のファイルを開いて書くだけであり、
`SYSOUT` のための特別な道が要らない。

`DUMMY` も同じ考え方で、空のファイルを割り当てる。読めば即座に終わり、書いたものは
捨てられる。埋め込みデータ (`SYSIN DD *` 相当) も、作業領域へ書き出して行順編成で割り当てる。

## PARM は先頭 2 バイトが長さである (FR-134)

参照実装と同じ形で渡す。受け取る側は連絡節にこう書いてある。

```cobol
LINKAGE SECTION.
01  PARM-AREA.
    05  PA-LEN  PIC S9(4) COMP.
    05  PA-TEXT PIC X(100).
PROCEDURE DIVISION USING PARM-AREA.
```

長さは 2 バイトの 2 進数であり、中身はコードページで符号化したバイト列である。
`PARM=` を書かなければ引数の並びは空になる。

## 宣言的形式 (FR-132)

内部モデルを<b>そのまま書ける</b>形式である。新しく組むジョブと、この処理系自身の試験に使う。
YAML などの外部ライブラリを使わないのは、`cobol-runtime` 以外へ依存を増やさないためである。

```
# 行頭の # は注記
JOB PAYROLL
STEP CHECK PGM=PAYCHK
  DD PAYIN DSN=data/pay.dat
  DD SYSOUT SYSOUT
STEP REPORT PGM=PAYRPT PARM=202609
  WHEN RC CHECK <= 4
  DD SYSOUT SYSOUT
  DD SYSIN DATA
    DETAIL
    TOTAL
  END
STEP CLEANUP PGM=PAYCLN
  WHEN ABEND
  DD SYSOUT SYSOUT
```

字下げに意味はない。読みやすさのためだけのものである。

条件の組み合わせは<b>1 段だけ</b>である。`AND` と `OR` を混ぜて書けない。混ぜたときの
優先順位は書いた人の思い込みと食い違いやすく、誤りとしたほうがよい。

### 知らない書き方は誤りにする

読み飛ばさない。書いたつもりの指定が効いていないことに気付けないからである。
これは JCL のフロントエンドでも同じ方針である (要件 FR-131)。

## JCL フロントエンド (FR-131)

既存の JCL 資産を<b>書き換えずに実行する</b>ためのものである。読み取った結果は内部ジョブ
モデルであり、宣言的形式で書いたものと区別がない。同じ内容を両方の形式で書くと、
組み上がるモデルが等しくなる。

### 書式の都合は読み取りで尽くす

カードを読む側でやることは 3 つある。<b>注記を落とし、継続をつなぎ、埋め込みデータを
切り出す</b>。ここまでで書式の都合は尽きており、意味を取る側は 1 文ずつ見ればよくなる。

| 決まり | 扱い |
| --- | --- |
| 1〜2 桁が `//` | 3 桁目が `*` なら注記カード |
| 73 桁目から先 | 通番であり、見ない |
| オペランドの外の空白 | そこから先は注記 |
| オペランドの末尾のコンマ | 次のカードへ続く。続きのカードは名前欄が空 |
| `DD *` | 次の文か `/*` までが埋め込みデータ |
| `DD DATA` | `/*` まで。データの中に `//` で始まる行があるときに使う |
| 名前欄の空いた `DD` | 直前の `DD` への連結 |

コンマで区切るときは<b>括弧と引用符の中を区切らない</b>。`COND=((4,LT),(8,GT,STEP1))` は
1 つのオペランドであり、`PARM='A,B'` も 1 つである。

### COND の向きを裏返す

JCL の `COND` は<b>「真なら飛ばす」</b>という向きで書く。さらに `COND=(4,LT,STEP1)` は
「4 < STEP1 の RC」と読む。左右も逆さまである。内部モデルは「RC 関係 値」で「真なら動かす」
なので、ここで<b>2 回裏返す</b>。

| JCL | 内部モデル |
| --- | --- |
| `COND=(4,LT,CHECK)` | `NOT (RC(CHECK) > 4)` |
| `COND=((4,LT,A),(8,EQ))` | `NOT (RC(A) > 4 OR 最大 RC = 8)` |
| `COND=EVEN` | 異常終了していても動かす |
| `COND=((8,LE,A),EVEN)` | 異常終了を越え、かつ `NOT (RC(A) >= 8)` |

試験が複数あれば<b>どれか 1 つでも成り立てば飛ばす</b>。裏返すと「すべて成り立たなければ
動かす」になる。

### データセット名は基点の下に置く

`DSN=PAY.MASTER` はデータセット名であり、ファイルの場所ではない。基点のディレクトリの下に
<b>その名前のまま</b>置かれているものとする。区切りの点をディレクトリに読み替えないのは、
ホストの一覧と見比べたときに同じ名前が並ぶほうが追いやすいからである。

### 手続きの展開は組み立ての前に済ませる

`PROC` / `INCLUDE` / `SET` とシンボリックパラメタは、カードを読み終えたあと、モデルを組む前に
展開する。<b>ここを抜けたカードには手続きの呼び出しもシンボリックパラメタも残っていない</b>。
組み立てる側は手続きを知らずに済む。

COBOL のプリプロセッサと構文解析の分け方と同じ考え方である。字面の置き換えを先に済ませて
おけば、意味を取る側は 1 つの形だけを見ればよい。

| 決まり | 扱い |
| --- | --- |
| `&名前` | 値へ置き換える。値のない名前は誤りとする |
| `&名前.` | 点は名前の終わりを示す。置き換えたあとに残さない |
| `&&` | 1 つの `&` を表す。一時データセットの名前で使う |
| `PROC` … `PEND` | ジョブの中に書いた手続き。呼ばれたときに動く |
| `EXEC 手続き名` | 手続きを展開する。`EXEC PROC=名前` も同じ |
| `INCLUDE MEMBER=` | メンバの本文をその場へ差し込む |
| `//手続きのステップ名.DD 名 DD` | 同じ名前があれば差し替え、なければ足す |

値の強さは<b>呼び出しでの上書き → `SET` → 手続きの既定値</b>の順である。

### 展開したステップの名前

手続きが 1 ステップなら、展開したステップの名前は<b>呼び出し側の名前</b>である。
複数ステップなら `呼び出し名.手続きの中の名前` になる。1 つのときに素直な名前が付くほうが、
`COND` で名指すときに書きやすい。

名前が変わる以上、<b>手続きの中でステップを名指す `COND` も付け替えなければならない</b>。
`COND=(4,LT,FIRST)` は `COND=(4,LT,RUN.FIRST)` になる。付け替えを忘れると、名指した先が
見つからないまま条件が「成り立たない」と判定され、`NOT` で裏返って<b>いつでも動いてしまう</b>。

呼び出しに付けた `COND` は、手続きの<b>すべてのステップ</b>に効く。ただし手続きの中に
`COND` が書いてあれば、そちらが優先する。

### IF は条件をステップへ配る

`IF` / `THEN` / `ELSE` / `ENDIF` は<b>ステップを囲む</b>。囲まれたステップの条件は、
囲んでいる条件と自分の `COND` を<b>重ねたもの</b>になる。`ELSE` の中では裏返る。
入れ子にすれば重なりが増える。

`COND` と違って `IF` は<b>「真なら動かす」</b>の向きで書く。内部モデルの向きと同じなので
裏返さない。同じことを 2 通りの向きで書けるのは JCL の分かりにくいところだが、
内部モデルが 1 つの向きに揃っているので、どちらもそこへ落ちる。

| 書ける試験 | 意味 |
| --- | --- |
| `RC 関係 値` | いちばん大きい復帰コード |
| `ステップ名.RC 関係 値` | そのステップの復帰コード |
| `ステップ名.RUN` | そのステップが動いたか。異常終了したものも動いたことになる |
| `ABEND` | どれかが異常終了したか |

結び付けは `&` (`AND`)、`|` (`OR`)、`¬` (`NOT`) と括弧である。`&` は `|` より強い。

`IF` の文だけは<b>オペランド欄の切り方が違う</b>。ほかの文は括弧の外の空白で終わるが、
`IF` は関係式の中に空白が入るので、`THEN` までを 1 つの文として取る。

### 知らない書き方は誤りにする

JCL の全機能を再現するのは目標ではない。しかし<b>読み飛ばしてはならない</b> (要件 FR-131)。
`JCLLIB` / `OUTPUT` / `ABENDCC` / `UNIT` / `SPACE` などは、いまは誤りとして報告する
(暫定判断 P-046)。

## ユーティリティは普通のプログラムである (FR-137)

`IEBGENER` や `IDCAMS` は<b>翻訳された資産ではない</b>が、ジョブから見れば同じプログラムで
ある。したがって生成コードと同じ入口 (`CobolProgram`) を実装し、DD 名でデータへ触り、
復帰コードを立てる。ジョブ実行の側に特別扱いは要らない。

名前で引くとき、ユーティリティが先に見つかる。ホストでもシステムのライブラリが先だからである。

| 名前 | 実装したこと |
| --- | --- |
| `IEFBR14` | 何もしない。`DISP` を効かせるためのものであり、いまは本当に何も起きない |
| `IEBGENER` | `SYSUT1` を `SYSUT2` へ写す。制御文は未対応 (暫定判断 P-047) |
| `IDCAMS` | `REPRO` / `DELETE` / `DEFINE CLUSTER` / `LISTCAT` |
| `SORT` | 整列と合併。`INCLUDE` / `OMIT` / `SUM` / `OUTREC` (別名 `DFSORT` / `ICEMAN` / `SYNCSORT`) |
| `ICETOOL` | 未対応であることを報告する (暫定判断 P-047) |

### バイトのまま写す

`IEBGENER` と `IDCAMS REPRO` は、レコードへ切ってから書き直すのではなく、バイト列と属性を
そのまま写す。切って書き直せば同じ属性なら同じバイトに戻るはずだが、<b>戻るはずだという
仮定を挟まずに済む</b>。写しは写しである。

### 復帰コードはいちばん大きいものが残る

`IDCAMS` は制御文ごとに復帰コードが立ち、ステップの復帰コードは<b>そのうちいちばん大きい
もの</b>になる。1 つ失敗しても後続の制御文は動く。これがホストの決まりであり、
「消してから作る」という書き方が成り立つ理由である。消すものがなければ `8` になるが、
作るほうは通る。

### 整列の中身は COBOL の SORT と同じものを使う

バッチでいちばん重いのは整列であり、COBOL の `SORT` 動詞よりもジョブステップとして
整列ユーティリティを呼ぶ場面のほうが多い。しかし<b>並べ替えの規則は 1 つしかない</b>。
鍵の比べ方は[設計 80](80-file-io.md) の `SortWork` が持っており、ユーティリティがやるのは
制御文を鍵へ翻訳することだけである。規則が 2 か所にあれば必ず食い違う。
`SORT` 動詞で正しいものは、ここでも正しい。

#### 通り道の順は決まっている

読む → `INCLUDE` / `OMIT` でふるう → 並べ替える → `SUM` でまとめる → `OUTREC` で組み直す
→ 書く。この順はホストの決まりであり、順を入れ替えると答えが変わる。たとえば `SUM` は
<b>並べ替えたあと</b>にしか効かない。鍵が等しいレコードが隣り合っていて初めて、
1 つ前と比べるだけでまとめられる。`OUTREC` が最後なのも同じ理由で、組み直したあとの
レコードには元の位置がもう無い。

#### 位置は 1 から数え、可変長では長さも数に入る

制御文の位置はレコードの先頭を 1 とする。可変長では<b>先頭の 4 バイトが長さ (RDW)</b>
であり、データは 5 から始まる。ここでもレコードを切り出すときに長さを付けたまま持つので、
ホストと同じ数え方になる。切り離してから数え直すと、実資産の `SORT FIELDS=(5,...)` が
1 つずつずれる。

#### 形ごとの比べ方

| 形 | 比べ方 |
| --- | --- |
| `CH` | バイトの並び。EBCDIC の照合順序はバイトの値そのものである |
| `BI` | バイトの並び。符号なし 2 進数なので、これで値の順になる |
| `ZD` | `S9(n)` DISPLAY として値で比べる |
| `PD` | `S9(2n-1)` COMP-3 として値で比べる |
| `FI` | 長さ 2 / 4 / 8 を `S9(4)` / `S9(9)` / `S9(18)` COMP として値で比べる |

`CH` と `BI` をバイトで比べるのは手抜きではない。<b>バイトの並びが値の順と一致する</b>のが
この 2 つの形の定義だからであり、10 進数へ直してから比べても答えは変わらない。

`SUM` が書き戻す `ZD` には<b>符号が付く</b>。ゾーン 10 進数の符号は最下位桁の上位 4 ビットに
あり、正なら X'C' である。読むときは X'F' でも正として読み、書くときは X'C' になる。
ホストの整列も同じものを書く。

### 覚え書きの出し先

ホストのユーティリティは `SYSPRINT` へ経過を書く。ジョブが書いていなければ出さないのが
ホストの決まりだが、それでは黙って失敗したときに手がかりが残らない。結び付けがなければ
実行時の出力へ回す。

## 起動

```
cobolj [-d クラスの置き場] [-w 作業領域] [-b データセットの基点] [-p 手続きの入れ物] ジョブ記述
```

記述形式は拡張子で見分ける。`.jcl` なら JCL、それ以外は宣言的形式である。

プロセスの終了コードは<b>ジョブの終了コード</b>である。いちばん大きいステップの復帰コードで
あり、後続のジョブがそれを見て動く。ステップの結末は標準エラーへジョブログとして書く。

## 次の増分

1. `DISP` を実行へ効かせる (暫定判断 P-045)。データセットの後始末も同じ段で決める。
2. 異常終了コード (要件 FR-141) と `ABENDCC` (暫定判断 P-046)。
3. `ICETOOL` と `OUTFIL` (暫定判断 P-047)。
