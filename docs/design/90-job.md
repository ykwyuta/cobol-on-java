# 設計 90: ジョブ実行

| 項目 | 内容 |
| --- | --- |
| 対応要件 | FR-130〜FR-137、要件定義書 7.1 節 |
| ステータス | 内部ジョブモデルと宣言的フロントエンド 実装済。JCL フロントエンドは次 |

## 何を決めるか

バッチの実資産は<b>プログラム 1 本では動かない</b>。JCL がステップを並べ、DD 名を実際の
データセットへ結び付け、復帰コードで後続の実行を決める。そこまで揃って初めて「ソース無修正で
動く」と言える。

## 内部モデルが先で、記述形式はあと (FR-130)

実行機構が解釈するのは<b>内部ジョブモデルだけ</b>である。JCL パーサも宣言的形式のパーサも
知らない。

```
JCL         ┐
            ├→ 内部ジョブモデル (Job / Step / DdAssignment / StepCondition) → 実行機構
宣言的形式  ┘
```

こうしておく理由は 2 つある。<b>どちらの形式で書いても結果が同じ</b>になること (要件 FR-132)。
そして、JCL の込み入った書式をパーサの中に閉じ込め、実行の側へ持ち込まないことである。

| 型 | 表すもの |
| --- | --- |
| `Job` | ジョブ 1 個。ステップの並び |
| `Step` | プログラム 1 本の実行。名前・プログラム名・`PARM`・DD 割当・条件 |
| `DdAssignment` / `DdTarget` | DD 名と行き先。実ファイル、`SYSOUT`、`DUMMY`、埋め込みデータ |
| `StepCondition` | 動かすかどうかの条件 |
| `JobState` | ここまでに起きたこと。復帰コードと異常終了の有無 |

## 条件は「真なら動かす」の向きに揃える (FR-136)

JCL の `COND` は<b>「真なら飛ばす」</b>という向きで書く。`COND=(4,LT,STEP1)` は
「STEP1 の RC が 4 より大きければ飛ばす」である。逆さまで読みにくく、誤りのもとでもある。

内部モデルでは<b>「真なら動かす」</b>の向きに揃えた。向きの反転は JCL パーサの仕事である。
宣言的形式は素直に書ける。

```
WHEN RC CHECK <= 4
```

異常終了の扱いも条件の一部として持たせている。ホストでは先行ステップが異常終了すると以降は
飛ばされるが、`COND=EVEN` と `COND=ONLY` がそれを覆す。「飛ばす／飛ばさない」を決めるものは
1 か所にあるほうがよい。

**動いていないステップの復帰コードは比べられない**。飛ばされたステップを名指す条件は
成り立たないものとして扱う。

## ステップは独立している (FR-130)

ステップごとに新しい実行時の入口を作る。作業場所も、読み込んだ副プログラムも、開いたファイルも、
復帰コードも<b>持ち越さない</b>。持ち越すのはジョブの状態だけである。

ホストではステップごとに別のアドレス空間が立つ。同じ実行時の入口を使い回すと、前のステップの
作業場所が残り、初期値から始まらないプログラムができてしまう。

## SYSOUT はスプールを通る (FR-135)

ホストでは `SYSOUT` へ書いたものがスプールに溜まり、ジョブが終わってから印字される。
ここでも作業領域のファイルへ溜め、ステップが終わったところで流し出す。

<b>プログラムから見れば普通のデータセットである</b>。行順編成のファイルを開いて書くだけであり、
`SYSOUT` のための特別な道が要らない。

`DUMMY` も同じ考え方で、空のファイルを割り当てる。読めば即座に終わり、書いたものは
捨てられる。埋め込みデータ (`SYSIN DD *` 相当) も、作業領域へ書き出して行順編成で割り当てる。

## PARM は先頭 2 バイトが長さである (FR-134)

参照実装と同じ形で渡す。受け取る側は連絡節にこう書いてある。

```cobol
LINKAGE SECTION.
01  PARM-AREA.
    05  PA-LEN  PIC S9(4) COMP.
    05  PA-TEXT PIC X(100).
PROCEDURE DIVISION USING PARM-AREA.
```

長さは 2 バイトの 2 進数であり、中身はコードページで符号化したバイト列である。
`PARM=` を書かなければ引数の並びは空になる。

## 宣言的形式 (FR-132)

内部モデルを<b>そのまま書ける</b>形式である。新しく組むジョブと、この処理系自身の試験に使う。
YAML などの外部ライブラリを使わないのは、`cobol-runtime` 以外へ依存を増やさないためである。

```
# 行頭の # は注記
JOB PAYROLL
STEP CHECK PGM=PAYCHK
  DD PAYIN DSN=data/pay.dat
  DD SYSOUT SYSOUT
STEP REPORT PGM=PAYRPT PARM=202609
  WHEN RC CHECK <= 4
  DD SYSOUT SYSOUT
  DD SYSIN DATA
    DETAIL
    TOTAL
  END
STEP CLEANUP PGM=PAYCLN
  WHEN ABEND
  DD SYSOUT SYSOUT
```

字下げに意味はない。読みやすさのためだけのものである。

条件の組み合わせは<b>1 段だけ</b>である。`AND` と `OR` を混ぜて書けない。混ぜたときの
優先順位は書いた人の思い込みと食い違いやすく、誤りとしたほうがよい。

### 知らない書き方は誤りにする

読み飛ばさない。書いたつもりの指定が効いていないことに気付けないからである。
これは JCL のフロントエンドでも同じ方針である (要件 FR-131)。

## 起動

```
cobolj [-d クラスの置き場] [-w 作業領域] ジョブ記述
```

プロセスの終了コードは<b>ジョブの終了コード</b>である。いちばん大きいステップの復帰コードで
あり、後続のジョブがそれを見て動く。ステップの結末は標準エラーへジョブログとして書く。

## 次の増分

1. JCL フロントエンド (要件 FR-131)。`JOB` / `EXEC` / `DD` / `COND` / `PROC` / `INCLUDE`。
2. DD の連結 (`CONCATENATION`)。
3. ユーティリティの互換実装 (要件 FR-137)。`IEFBR14` / `IEBGENER` から始める。
