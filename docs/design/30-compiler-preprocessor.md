# 設計文書 30: cobol-compiler のプリプロセッサ (P0-b 第 1 増分)

| 項目 | 内容 |
| --- | --- |
| 対応要件 | FR-002, FR-003, FR-094, FR-193, ARC-8 |
| ステータス | 固定形式の読み取り・継続処理・`COPY` / `REPLACING`・`REPLACE` を実装済 |

## 位置付け

ARC-8 の方針は「手書きのプリプロセッサが文脈依存性をすべて吸収し、
正規化済みトークン列を ANTLR4 の構文解析器へ渡す」である。この増分はその手書き側の土台にあたる。

後段の構文解析器には<b>カラムも継続行も注釈行も見せない</b>。見せてしまえば、
宣言的に書けるはずの文法にカラム処理が染み出す。

## 出力: 1 文字ごとに出自を持つ正規化済みソース

プリプロセッサは固定形式のカラムを取り除き、継続行を連結し、注釈行を落とす。
その結果、正規化後のテキストは元のソースとは似ても似つかない形になる。

したがって `NormalizedSource` は<b>1 文字ごとに元のファイル・行・桁を保持する</b>。
位置情報を「行単位」ではなく「文字単位」で持つのは、継続行と (これから実装する) `COPY` 展開が
あるためである。正規化後の 1 行が元の複数行・複数ファイルにまたがるので、行単位では戻せない。

これがなければ、要件 FR-183 が求める「該当行・桁を指す診断メッセージ」は成立しない。

## 継続の規則が中心である

継続行 (7 桁目が `-`) の扱いは 2 通りあり、<b>直前の行が文字定数の途中で終わっているかどうか</b>で
変わる。

| 直前の行の状態 | 扱い |
| --- | --- |
| 文字定数が閉じていない | 直前の行は**72 桁まで定数の一部**とみなす (物理行が短くても空白で埋める)。継続行の B 領域の最初の非空白は引用符でなければならず、それを読み飛ばして続きを連結する |
| 定数の外 | 語の途中で切れているとみなし、継続行の最初の非空白から**区切りを入れずに**連結する |

### 72 桁までの空白補完を落としてはならない

1 番目の規則は見落としやすい。次のソースを考える。

```
      *    12345678901234567890 (桁)
           MOVE 'AB
      -    'CD' TO X.
```

`'AB` は 17〜19 桁にある。定数が閉じていないため、<b>20〜72 桁の 53 個の空白も定数の一部</b>に
なる。したがって定数の中身は `AB` + 53 個の空白 + `CD` の 57 文字である。

この規則を落とすと、<b>行末の空白を削ったソースと削っていないソースで定数の長さが変わる</b>。
実務のソースは行末が削られていることが多いため、物理行が短くても 72 桁まで補う実装にしている。

### 引用符 2 個は定数を閉じない

`'IT''S'` の途中の `''` は定数の中の引用符 1 個を表す。開閉の判定でここを取り違えると、
定数の終わりを誤検出して継続の分岐そのものが狂う。

### 行内注釈は定数の中と外を見分ける

`*>` 以降は行の終わりまで注釈である。ただし<b>文字定数の中の `*>` は注釈ではない</b>。
引用符を追いながら切る。`MOVE '*>' TO X` を注釈として落とすと、黙って別のソースになる。
固定形式でも自由形式でも同じ扱いであるため、`SourceText` に置いて共有している。

## 自由形式

`FreeFormatReader` が担う (要件 FR-002)。カラムの区分がなく、行の全体が本文である。
出力の形は固定形式とまったく同じ `NormalizedSource` であるため、
<b>後段はどちらの形式で書かれたかを知らない</b>。両者は `SourceReader` として抽象化している。

### 行の区切りは語の区切りである

文の途中で行を変えるのに継続の印は要らない。継続が本当に要るのは、
<b>文字定数を途中で切るとき</b>だけである。

### 定数の継続は行末のハイフンで示す

行末の非空白文字が `-` のとき、その直前までが定数の内容になる。ハイフンが要るのは
<b>末尾の空白を定数に含められるようにする</b>ためである。ハイフンがなければ、
行末の空白が定数の一部かどうかをソースの見た目から決められない。

定数の外での行末ハイフンは継続とみなさない。`COMPUTE A = B -` で行を変える書き方が
`B -C` に変わるほうが害が大きいためである (暫定判断 P-022)。

## 誤りは黙って飲み込まない

- 標識領域に妥当でない文字があれば、ファイル名と行番号を添えて誤りとする
- 定数が閉じないまま継続行以外が続けば誤りとする
- 継続行が引用符で再開しなければ誤りとする

いずれも「なんとなく続ける」ことができてしまう場面である。要件 FR-181 の
「未対応のものは無視せず診断する」と同じ考え方で、静かに誤った解釈をしないことを優先する。

## COPY と REPLACING

### 照合は語単位である

`REPLACING` の照合は文字列ではなく<b>語の列</b>に対して行われる。語と語の間の空白の数は
照合に影響しない。したがってプリプロセッサは、正規化済みソースをいったん
`TextWord` の列へ分けてから処理する。

擬似テキスト `==...==` は語の列を書くための記法であり、任意の語の並びを指定できる。
`==VALUE SPACE== BY ==VALUE ZERO==` のように複数の語にまたがる置換も書ける。

置換の指定は<b>書かれた順に試され、最初に一致したものが使われる</b>。
`==A B== BY ==X==` と `==A== BY ==Y==` を書く順を入れ替えると結果が変わる。

### 空白の有無を保たないと PICTURE が壊れる

語に分けて再構成する以上、語の間に空白を入れるかどうかを決めなければならない。
一律に空白で区切ると <b>`PIC 9(5)` が `PIC 9 ( 5 )` になってしまう</b>。
そこで `TextWord` は「直前に空白があったか」を保持し、再構成のときに復元する。

### 出自は 2 つのファイルに分かれる

展開結果の中で、

- コピー句から来た語は<b>コピー句のファイルと行</b>を指す
- 置換で差し込まれた語は<b>`COPY` 文を書いた側のファイルと行</b>を指す

置換で差し込まれる語は実際にそこに書かれているのだから、これが正しい。
同じ展開結果の中に 2 つのファイルの位置が混在するが、診断が
「置換をどこで指定したか」を指せるようになる。文字単位で出自を持つ設計が、ここで効く。

### SUPPRESS はリストにだけ効く

`COPY ... SUPPRESS` は<b>展開結果を変えない</b>。変わるのはリスト出力だけで、
そのコピー句から来た行が印字されなくなる。入れ子のコピー句も一緒に抑止される。
`CopyExpander` が展開したファイル名を集めておき、`SourceListing` へ渡す。

### 循環は必ず検出する

コピー句の中の `COPY` も展開する。展開中のコピー句名を積んでおき、同じ名前が再び現れたら
誤りとする。深さにも上限を設けている。<b>循環を検出せずに展開すると、記憶域が尽きるまで
止まらない</b>。プリプロセッサが黙って固まるのは、誤りを報告するより悪い。

## REPLACE

### COPY との違いは「効く範囲」である

| | 効く範囲 | 被演算子 |
| --- | --- | --- |
| `COPY ... REPLACING` | そのコピー句の中だけ | 擬似テキストでも 1 語でもよい |
| `REPLACE` | その文より後ろのソース全体。次の `REPLACE` または `REPLACE OFF` まで | **擬似テキストのみ** |

照合と差し替えの規則そのものは同じであるため、`TextReplacements` として共有している。
違うのは適用の対象だけである。

### COPY のあとに適用する

COBOL は `COPY` をすべて処理してから `REPLACE` を適用すると定めている。
つまり <b>`REPLACE` はコピー句から展開された語にも効く</b>。順序を逆にすると、
コピー句の中身が置換の対象から漏れる。`Preprocessor` はこの順序を固定している。

### 差し込んだ語は再走査しない

置換で差し込んだ語は、そのまま出力へ送る。再び置換の対象にはしない。
再走査すると `==A== BY ==A B==` のような指定で<b>終わらなくなる</b>。

## コンパイラ指示文

`DirectiveProcessor` が担う (要件 FR-092)。条件付き翻訳、すなわち
<b>どのソースが生きているか</b>を決める処理である。

### 指示文は行で終わる

指示文に終止符はない。行が終われば指示文も終わる。正規化後のテキストには行の区切りが
残っていないため、語が持つ出自 (ファイルと行) の変わり目を行の終わりとみなす。
ここでも文字単位の出自が効いている。

### 死んでいる枝の中は評価しない

偽の枝の中身は翻訳されないのだから、<b>そこに書かれた条件も評価してはならない</b>。
`>>IF` の条件評価は、親の枝が生きているときだけ行う。`>>DEFINE` も同様で、
死んでいる枝の中では定数を定義しない。

### 未定義の定数との比較は誤りとする

`>>IF X = 1` の `X` が未定義のとき、これを黙って偽とすると<b>定数名の打ち間違いが
条件の書き間違いとして通ってしまう</b>。条件付き翻訳は「どちらのソースが生きているか」を
決めるものであり、黙って落とすのは最も避けたい誤りである。定義の有無を問いたいときは
`>>IF X DEFINED` を使う。

同じ理由で、`OVERRIDE` のない再定義も誤りとする。どちらの定義が効いているか
追えなくなるためである。

### 数字と文字列は比較の規則が違う

`>>DEFINE LEVEL AS 10` の値を文字列として比較すると `"10" < "9"` になってしまう。
値は数字定数と文字定数を区別して保持し、数どうしは数として比較する。
種別の違うものを比較しようとしたら誤りとする。

### COPY と REPLACE のあとに処理する

コピー句の中に書かれた `>>IF` を処理でき、かつ主ソースの `>>DEFINE` がそこへ届く。
`>>IF` で囲まれた `COPY` は偽の枝であっても一度展開されてから捨てられるが、
結果は同じである。差が出るのは捨てられる側のコピー句が存在しないときだけで、
この順序は暫定判断 P-020 として記録した。

## 「島」の切り出しとトークン化

`Tokenizer` が担う (方針 ARC-8、決定 D-14 / D-18)。プリプロセッサの最後の段であり、
ここで文脈依存性を構文解析器から締め出す。

### 区切りピリオドは「空白が続くピリオド」である

COBOL のピリオドは、<b>直後に空白が来るときだけ</b>区切り文字になる。そうでなければ
数字定数の小数点である。読点と semicolon も同じ規則に従う。括弧はつねに区切り文字である。

この規則ひとつで `1.5` と `MOVE A TO B.` の終止符が分かれる。参照実装の分離符の定義
そのものであり、推測ではない。

### PICTURE 句の文字列は丸ごと切り出す

`PIC 99.99.` の 2 つのピリオドは、字面では区別できない。`PICTURE` / `PIC` (と省略可能な
`IS`) を見たら、続く 1 個の文字列を<b>空白または区切り文字が来るまで</b>読み、
`PICTURE_STRING` という 1 個の不透明トークンとする。中身は PICTURE 専用のパーサ
(`PictureParser`) が解析する。

上の区切り規則により、末尾の `.` は区切りピリオドになり文字列には入らない。
副作用として<b>小数点で終わる PICTURE は書けない</b>が、これも参照実装と同じである。

### EXEC ブロックは中身を見ない

`EXEC SQL ... END-EXEC` の中身は COBOL ではない。丸ごと 1 個の `EXEC_BLOCK` とし、
専用のトランスレータへ渡す (要件 FR-150, FR-160)。

終端は<b>語として現れる `END-EXEC`</b> である。文字定数は読み飛ばすので、
`WHERE C = 'END-EXEC'` はブロックを閉じない。`WS-END-EXEC` のように語の一部に
なっているものも閉じない。<b>SQL や CICS の構文を一切知らずに閉じられる</b>点が重要で、
これが「島」という設計の値打ちである。

### トークンも文字ごとの出自を保つ

`SourceToken` は `TextWord` と同じく文字ごとの `Origin` を持つ。島の中身は専用の
小さなパーサが解析するため、そのパーサが報告する誤りも元の位置へ戻せる必要がある。
先頭の位置だけでは `PIC S9(5)V99` の `V` を指せない。

### 予約語の判別はここでは行わない

語と数字定数はどちらも `WORD` として出す。どれが予約語かは構文解析器の仕事である。
プリプロセッサが予約語表を持つと、`COPY` / `REPLACE` の照合規則 (語の綴りだけで照合する)
と食い違う。

## 処理の順序

`Preprocessor` が全体の入口である。`process` は正規化済みソースを、
`tokenize` は構文解析器へ渡すトークン列を返す。

1. 固定形式のカラム分解と継続行の連結
2. `COPY` の展開と `REPLACING` の適用
3. `REPLACE` の適用
4. コンパイラ指示文の処理
5. 「島」の切り出しとトークン化

## 展開後ソースのリスト出力

`SourceListing` が担う (要件 FR-094, FR-182)。

### 折り返しの位置は出自の変わり目である

プリプロセッサの出力は改行を持たない 1 本の文字列である。そのまま見ても何が起きたか
分からない。正規化後のテキストには行の区切りが残っていないため、<b>文字の出自
(ファイルと行) が変わったところ</b>を折り返しの位置とする。文字単位で出自を持つ設計が
ここでも効いている。行単位の情報しか持たなければ、この折り返しは作れない。

結果として、コピー句から来た部分はコピー句の行の並びとして現れ、注釈行はそもそも
現れない。`REPLACING` で差し込まれた語は `COPY` を書いた行から来ているので、
<b>コピー句の 1 行が複数の出力行に割れる</b>。見た目は不揃いだが、それが実際の出自である。

### 両端の空白は落とす

語と語の区切りに置かれた空白は、元のソース上の特定の文字に対応しない。
どちらの行に寄せられるかは経路によって変わる (行の連結の直後か、字句の再構成を経たあとか)。
両端の空白を落として、この揺れを消している。元の桁は `Origin` が保っている。

### 主ソースの名前は呼び出し側から受け取る

コピー句から来た行には印 (`C`) を付ける。どれが主ソースかは正規化済みソースからは
決められない — 1 行目が `COPY` であれば、先頭の出力行はコピー句から来ているためである。
したがって `render` は主ソースの名前を引数で受け取る。
