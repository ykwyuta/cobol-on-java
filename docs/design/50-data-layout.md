# 設計 50: データ部の記憶域割り付け

対象: 要件 FR-013, FR-020, FR-030, FR-031, FR-032, FR-033 / 方針 ARC-4, ARC-7

## 位置付け

構文木 (設計 40) のデータ部から、<b>どのバイトがどの項目か</b>を決める。
`DataDivisionBuilder` が作り、`DataLayout` が持つ。

ここで初めて<b>コンパイラがランタイムの意味論を使う</b>。両モジュールがつながる最初の点である。


## 可変長の表を含む群の長さは、送るときだけ変わる (FR-020)

`OCCURS ... DEPENDING ON` の表を含む群は、長さが実行時に決まる。記憶域は<b>最大の
回数</b>で取ってあるので、割り付けた長さから使っていない分を引けばよい。

```
長さ = 割り付けた長さ - Σ (最大回数 - いまの回数) × 1 個分の長さ
```

<b>送るときと受け取るときで違う。</b>規格はこう分けている。

| 側 | 使う長さ |
| --- | --- |
| 送り出す (転記の元、比較、`INSPECT`、`STRING`、`UNSTRING`) | いまの回数で決まる長さ |
| 受け取る (転記の先) | <b>いちばん大きい形</b> |

分けないと、受取側の<b>古い個数</b>で切ってしまう。`MOVE 送 TO 受` で受取側の回数が
3 のままなら、9 個ぶん送っても 3 個ぶんしか入らない (NC247A の `MOV-TEST-F1-6`)。

<b>添字を書けば 1 個分</b>である。表そのものを添字なしで指したときだけ、いまの回数で
長さが決まる。ここを分けないと `SEARCH` の中の `表 (指標)` が表の全長になり、
記憶域の外を読む。

## 長さはランタイムに尋ねる

項目のバイト長は `NumericItem.byteLength()` と `Picture.size()` にそのまま任せる。
コンパイラが桁数から独自にバイト数を求めてはならない。

理由は 2 つある。ひとつは<b>ずれる余地を作らない</b>ため。もうひとつは、
V2 で Hercules と突き合わせて裏付けを取ったのは<b>ランタイムのほう</b>だからである。
コンパイラが別計算を持てば、裏付けのない数がひとつ増える。

| 項目 | 長さの出どころ |
| --- | --- |
| 数値 (`DISPLAY` / `COMP-3` / `COMP` / `COMP-5`) | `NumericItem.byteLength()` |
| 数値編集・英数字・英字 | `Picture.size()` |
| `COMP-1` / `COMP-2` | 4 / 8 (PICTURE を持たない) |
| 群項目 | 下位の項目から計算する |

## レベル番号は入れ子の深さではない

COBOL のレベル番号は「大きいほうが下位」という順序だけを表す。`01` の次が `05` でも
`02` でもよく、`05` の下に `10` が来ても `07` が来てもよい。深さとして扱うと、
現場のソースはたいてい通らない。

したがって<b>開いているレベルを積んで、番号の大小で閉じる</b>。新しい項目の番号以上の
レベルを積みから外し、残ったいちばん上が親になる。

`01` と独立項目 `77` は積みを空にして、それ自身の記憶域の先頭から始まる。

## REDEFINES は位置を巻き戻す

`REDEFINES` は記憶域を進めない。重ねる先と同じ位置から始め、次の項目は
<b>重ねる前の位置から</b>続く。

群項目の長さは「下位の項目の合計」ではなく<b>いちばん遠くまで届いた項目</b>で決める。
重ねた側のほうが長い場合があるためである (`01` レベルでは規格上も許される)。

重ねる先は<b>同じ親を持つ、自分より前の項目</b>から探す。見つからなければ誤りとする。
黙って位置を進めると、以降のすべての項目がずれる。

### 01 レベルの REDEFINES は、長ければ記憶域を広げる (FR-021)

重ねる先より<b>長い</b>再定義は、01 レベルでファイル節の外なら規格が許している。

```
01  REDEF10.  *> 46 バイト
    ...
01  REDEF12 REDEFINES REDEF10.  *> 120 バイト
    ...
01  REDEF13.  *> 次の 01 レベル
```

このとき記憶域は<b>いちばん長い形</b>で取らなければならない。46 バイトしか取らないと
`REDEF13` が `REDEF12` の後半に重なり、`MOVE SPACE TO REDEF12` が `REDEF13` を
<b>黙って潰す</b>。CCVS85 の NC107A がここを見ている —— 潰れた `REDEF13` を送り出し側に
使う検査が、そのあとに置いてある。

`FD` のレコード領域が同じ扱いなのは前からできていた。01 レベルの再定義だけが
記憶域を進めずに素通ししていた。

## OCCURS は 1 回分を繰り返す

下位を含めた 1 回分の長さを求め、回数だけ繰り返す。`DataItem` は 1 回分の
`length()` と反復を含めた `totalLength()` の両方を持つ。

`OCCURS m TO n DEPENDING ON` の可変長は、記憶域としては<b>最大の n</b> を確保する。
実際に使われる長さは実行時に決まるが、割り付けは最大で取る。

### 添字には相対指定を書ける (FR-025)

`WS-E (WS-I + 1)` と書ける。参照の中に足し算があるように見えるが、そうではない。
<b>添字にずれが付いている</b>だけであり、ずれは翻訳時に決まる整数である。
`DataReference.Subscript.Variable` がずれを持ち、コード生成はそれを足してから
範囲を確かめる。確かめるのは<b>足したあとの値</b>である。

`WS-E (WS-I + 1)` と `WS-E (WS-I +1)` はどちらも書ける。COBOL では 2 項の演算子は
前後に空白を置き、単項の符号は後ろに空白を置かないので、字句の切れ目が変わるだけで
意味は同じである。

## SIGN は群項目に書ける (FR-031)

`SIGN` 句は群項目にも書ける。書けば<b>配下の、符号つきで `USAGE DISPLAY` の基本項目
すべて</b>に効く。内側の群項目や基本項目が自分の `SIGN` を持っていれば、そちらが勝つ
(85 規格 5.12.4 GR2)。

```
01 TEST-17-DATA  SIGN TRAILING.
  03 TEST-17-GROUP SIGN LEADING SEPARATE.
    05 TEST-17-C   PIC S9(4).
```

`TEST-17-C` は 5 バイトであり、先頭が符号の文字である。外側だけを見ると 4 バイトに
なり、<b>長さから違う</b> (NC116A SIG-TEST-GF-17)。

`USAGE` と同じく、割り付けの前に配る (`inheritSign`)。`USAGE` が決まってからでないと
「`SIGN` が効く項目かどうか」を判じられないので、`inheritUsage` のあとに置いてある。

## 88 レベルは記憶域を占めない

条件名は直前の項目に付く。`ConditionName` として項目が持ち、値は `THRU` の範囲も
書けるようにしてある。66 レベル (`RENAMES`) は割り付けの規則が別物なので、
いまは誤りとして報告する。

## 未対応は黙って通さない

`USAGE POINTER` / `NATIONAL` / `DISPLAY-1` はランタイムが未対応である
(暫定判断 P-006)。長さを勝手に決めると、以降の項目がすべてずれたうえで
<b>誤りが出ない</b>。したがって診断として報告する。

PICTURE のない基本項目、PICTURE を持つ `COMP-1` / `COMP-2` も同様である。

## 通貨記号は環境部から来る

PICTURE の通貨記号は `SPECIAL-NAMES` の `CURRENCY SIGN IS` で差し替えられる (要件 FR-054)。
したがってデータ部を読むより<b>前に環境部を読む</b>。

差し替えると<b>既定の `$` は通貨記号でなくなる</b>。`PIC $$$9.99` は構文誤りになる。
これは参照実装と同じであり、記号が 2 つになるわけではない。

翻訳時に決まる文字だが、生成コードが `<clinit>` で PICTURE を組み立てるときにも渡している。
コンパイラとランタイムで別の記号を使うと、<b>実行時に PICTURE が解析できない</b>。

## FD のレコード領域は重なる

`FILE SECTION` の `FD` の下に書いた 01 レベルは、その `FD` の<b>レコード領域</b>である。
同じ `FD` に 01 レベルを複数書けば、それらは<b>同じ位置から始まる</b>。1 つのバッファに
別の切り方で名前を付けたものだからである。`FD` が占める長さはいちばん長いレコード記述で
決まる。

いまは作業場所の一部として割り付け、位置を揃えているだけである。ファイルごとの記憶域を
持たせるのは次の段である (暫定判断 P-037)。

`WRITE` に書くのは<b>レコード名</b>であってファイル名ではない。どのファイルへ書くのかは
そのレコードがどの `FD` の下にあるかで決まるので、項目にファイル名を持たせている。

## EXTERNAL は実行単位で 1 つの領域である (FR-014)

```
01  SHARED-DATA IS EXTERNAL.
    03 SH-TEXT PIC X(2).
```

`EXTERNAL` と書いた 01 レベルの領域は<b>実行単位で 1 つ</b>である。同じ名前で
`EXTERNAL` と書いたどのプログラムからも同じ中身が見える。引数を渡していなくても、
呼ぶ側が書いた値が呼ばれた側から見え、呼ばれた側が書いた値が呼ぶ側から見える。

`FD ... IS EXTERNAL` も同じで、こちらはファイル結合子と<b>レコード領域</b>が
実行単位で 1 つになる。ファイル結合子のほうは DD 名で引く目録が既に 1 つなので、
足りないのはレコード領域だけだった。分け合う名前は<b>ファイル名</b>にする —
規格が結び付けているのはファイル結合子であって、レコード記述ではない。両側で
レコードの名前が違っていてもよい。

### `GLOBAL` も同じ仕組みで分け合う (FR-091)

入れ子のプログラムでは、囲む側が `GLOBAL` と書いた 01 レベルが<b>囲まれた側から
見える</b>。囲まれた側の原文には書かれていないので、記述項をそのまま持ってきて
囲まれた側の割り付けにも並べる。実体を分け合う仕組みは `EXTERNAL` と同じである。

違うのは<b>分け合う名前</b>だけである。`EXTERNAL` はデータ名で分け合うが、`GLOBAL` は
<b>囲む側のプログラム名とデータ名</b>で分け合う。別のプログラムが同じ名前の `GLOBAL`
項目を持っていても、別の領域だからである。

入れ子の木は<b>意味解析で組み立てる</b>。文法は並んだプログラムとして読み、
`END PROGRAM` の名前を積み下ろしすれば木はあとから作れる (暫定判断 P-070)。

```
PROGRAM-ID. A.        → 積む [A]
PROGRAM-ID. A-1.      → 積む [A, A-1]   … A-1 は A に囲まれている
END PROGRAM A-1.      → 下ろす [A]
END PROGRAM A.        → 下ろす []
```

同じ名前を囲まれた側でも宣言していれば<b>そちらが勝つ</b>。規格がそう決めている——
内側の宣言が外側を隠す。

`FD ... GLOBAL` も同じである。ファイル節は `SELECT` と `FD` の 2 か所に分かれているので
両方を持ってくる。ファイル結合子そのものは DD 名で引く目録が実行単位で 1 つなので、
足りないのは<b>レコード領域</b>だけである。

### `USE GLOBAL` は囲む側の記憶域で動く (FR-091, FR-105)

`USE GLOBAL AFTER ERROR PROCEDURE` は、囲まれたプログラムで起きた入出力の異常でも
動く。動かすのは<b>囲む側の宣言節</b>であり、節の中身は囲む側の段落と項目を指して
いるので、<b>囲む側の記憶域で</b>動かさなければならない。

生成クラスは `performGlobalRange(最初, 最後, 記憶域, 文脈)` という入口を出す。
実行時に積まれた枠から持ち主を探し、その記憶域で段落の範囲を動かす。

受け持ちの決め方は自分の節と同じで、ファイル名が先、次に開き方である。<b>自分に
受け持つ節が無いときだけ</b>囲む側を見る——内側の宣言が外側を隠す。

分け合っているものは、この呼び出しの前後で<b>入って出るのと同じ形</b>に合わせる。
そうしないと、戻ったところで呼んだ側の古い写しが書き戻され、節の書いた値が消える。
CCVS85 の IC234A がここを見ている——3 段の入れ子の<b>いちばん外側</b>の節が動き、
その節が書いた値をいちばん外側で読む。

### 持ち方: 割り付けは変えず、境目で突き合わせる

生成コードは項目を<b>ふつうに自分の記憶域へ割り付ける</b>。参照 1 つずつを実行単位の
領域へ振り分けると、添字も部分参照も二重に持たなければならなくなる。

代わりに、実行単位の写しと突き合わせるのは<b>プログラムの境目</b>だけである。

| いつ | すること |
| --- | --- |
| プログラムへ入る | いま動いている側を写しへ書き戻し、入る側へ読み込む |
| プログラムから戻る | 抜ける側を写しへ書き戻し、呼んだ側へ読み込む |

`CALL` は呼ぶ側が書いた値を呼ばれた側が見なければならないので、<b>書き戻してから
読み込む</b>順でなければならない。1 度に動くプログラムは 1 つなので、これで
「実体が 1 つある」のと<b>見分けが付かない</b> (暫定判断 P-082)。

生成クラスは `externalRegions()` で「データ名と、自分の記憶域での位置」を返す。
突き合わせるのは実行時の `ProgramContext` である。

写しがまだ無ければ読み込みは何もしない。<b>そのプログラムの持っている中身が最初の
値</b>になる。規格は `EXTERNAL` に `VALUE` を書くことを許していないので、どの
プログラムから見ても同じ初期状態から始まる。

CCVS85 の IC226A (4 件) と IC227A (3 件) がここを見ている。それまでは
`EXTERNAL` を<b>読んで捨てて</b>いた。1 本のプログラムだけを動かすなら害が出ない
ので、落ちるまで気付かなかった。

## 特殊レジスタは 3 つ目の記憶域にある

`RETURN-CODE` は<b>実行の全体で 1 つ</b>である (要件 FR-084)。呼ぶ側と呼ばれる側が同じものを
見るため、プログラムごとの記憶域には置けない。実行時の入口 (`ProgramContext`) が持つ置き場を
指す。

```
作業場所:      記憶域 = 自分のもの          位置 = 変位
連絡節:        記憶域 = 引数[k] のもの      位置 = 引数[k] の位置 + 変位
特殊レジスタ:  記憶域 = 実行時の入口のもの  位置 = 決まった変位
```

連絡節のために作った「記憶域が項目ごとに違いうる」仕組み (`planAddress`) がそのまま効いた。
<b>写し取る仕組みは要らない</b>。同じ `Storage` を指しているので、呼び出しをまたいでも
そのまま見える。

置き場の中の位置はコンパイラとランタイムの<b>両方が知っている必要がある</b>ため、
`SpecialRegisterArea` の 1 か所に置いてある。別々に持つとずれる。

データ部に同じ名前を書けば、そちらが勝つ。特殊レジスタを探すのは<b>データ項目が
見つからなかったときだけ</b>である。

## 指標名は隠しデータ項目にする

`INDEXED BY` で書かれた指標名は COBOL のデータ項目ではない。しかし<b>反復の番号を持つ
入れ物</b>であることに変わりはないので、2 進 4 バイトの項目として記憶域の後ろへ足している
(要件 FR-025)。

データ項目にしてしまえば、添字も `SET` も比較も<b>普通の項目と同じ道を通る</b>。
参照実装は変位 (バイト数) を持つが、観測できるのは「何番目か」だけである。

名前には `$` を入れてある。COBOL 語に使えない文字なので、ソースから名前で引き当てられない。
指標名は専用の表 (`DataLayout.findIndex`) からしか引けない。

これで作業場所が指標の分だけ長くなる。記憶域の中身を外から見る手立てを実装した時点で
差が出るため、暫定判断 P-035 に記録した。

`USAGE IS INDEX` と書かれた項目 (指標データ項目) も<b>同じ持ち方</b>にした。こちらは
はじめから書く人が名前を付けた項目なので、`$` の印は付かない。したがって
<b>印を切り落とす側は、印が無い場合を必ず考えなければならない</b>。無条件に切り落として
いたところで壊れていた (設計 25 を参照)。指標データ項目に `PICTURE` は書けない。
長さは処理系が決めてよいと規格が言っており、実機と突き合わせていないので P-035 に記録した。

## 連絡節は記憶域を持たない

`LINKAGE SECTION` の 01 レベルは<b>記憶域を占めない</b> (要件 FR-027)。実体は呼ぶ側に
あり、こちらはその領域への窓である。したがって割り付けでは位置を進めず、
プログラムの記憶域の全体の長さにも数えない。決めるのは<b>その中での位置</b>だけである。

どの領域に対応するかは `PROCEDURE DIVISION USING` が決める。並べた順が、実行時に
渡される領域の並びの順である。生成コードから見ると、作業場所の項目が
「記憶域は決まった 1 つ、位置は翻訳時に決まる定数」であるのに対し、連絡節の項目は
<b>記憶域も位置も渡された領域から取る</b>。

```
作業場所:  記憶域 = 自分のもの        位置 = 変位
連絡節:    記憶域 = 引数[k] のもの    位置 = 引数[k] の位置 + 変位
```

この 2 つを 1 つの組 (`planAddress`) として扱うので、ランタイムの入口はどちらでも同じである。

`VALUE` は書けない。初期化する先がないためであり、規格も禁じている。書かれていれば
誤りとして報告する。

## VALUE 句の初期イメージ

`InitialImage` が担う (要件 FR-013)。符号化はここでもランタイムに任せる —
数値は `NumericItem.encode`、浮動小数点は `FloatingItem.encode`、文字は `CodePage` である。
コンパイラが独自にバイトを組み立てると、<b>実行時に同じ値を入れたときとずれる</b>。

### 図形定数は「ある文字で埋める」に正規化する

`SPACE` も `HIGH-VALUE` も `ALL '*'` も、意味は「項目いっぱいまで埋める」である。
`LiteralValue` で文字定数・数字定数・図形定数・`ALL 定数` の 4 つに落とし、
埋める文字はコードページから引く。`ZERO` だけは数値項目では 0 という値になる。

### 群項目の VALUE は下位を書いたあとに上書きする

群に `VALUE` を書いたなら、下位に `VALUE` を書くことは許されない。
先に群を埋めてから下位を書くと、下位の充填で消えてしまう。順序を逆にしてある。

### REDEFINES で重ねた項目は初期化しない

COBOL は `REDEFINES` の中に `VALUE` を書くことを禁じている。重ねた項目を素通しで
書くと、<b>重ねる先の初期値を空白で塗り潰してしまう</b>。したがって重ねた側は飛ばし、
そこに `VALUE` があれば誤りとして報告する。

### 桁に収まらない VALUE は誤りとする

黙って上位桁を落とすと、宣言と初期値が食い違ったまま動き出す。
`NumericItem.fits` で判定して報告する。

### 指定のない場所は空白で埋める

規格は `VALUE` のない作業場所の初期値を未定義としている。空白を既定とした理由と、
差し替えられるようにした経緯は暫定判断 P-025 に記録した。
