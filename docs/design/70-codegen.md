# 設計 70: コード生成

対象: 要件 FR-013, FR-024, FR-026, FR-060 / 方針 ARC-3, ARC-7

## 位置付け

文の並び (設計 60) と記憶域の割り付け (設計 50) から、JVM のクラスファイルを作る。
`ProgramGenerator` が ASM で直接バイトコードを書き出し、`CobolCompiler` が
ソース 1 本から通しで動かす。

ここで<b>翻訳したものが実際に動く</b>ようになった。

## 生成コードは位置を決めて動詞を呼ぶだけである

生成したクラスは `CobolProgram` を実装し、記憶域の位置を決めて `Ops` を呼ぶ。
意味論そのものは持たない。

```
Ops.moveAlphanumeric(Ops.read(storage, 0, 3), storage, 3, 3, false, CP);
```

この分け方には理由がある。<b>V2 で Hercules と突き合わせて裏付けを取ったのは
ランタイムのほう</b>である。生成コードがその経路をそのまま通れば、裏付けは
生成コードにも及ぶ。逆に生成コードが独自にバイトを組み立てると、
そこだけ裏付けのない実装がひとつ増える。

障害が出たときに「意味論の誤りか、コード生成の誤りか」を切り分けられる点も同じ理由による
(方針 ARC-7)。

`Ops` はランタイム側に置いた薄い層で、記憶域の位置と動詞をつなぐだけである。
生成するバイトコードを短く保ち、バイトコードの誤りが入り込む余地を減らすために置いている。

## 翻訳時に決まるものは定数フィールドに置く

PICTURE の解析、`NumericItem` の組み立て、文字定数の符号化は<b>いずれも翻訳時に決まる</b>。
静的初期化子で 1 度だけ作り、手続きの中では参照するだけにする。

バイト列はクラスファイルの文字列定数から `ProgramSupport.bytes` で復元する。
ISO-8859-1 は 0〜255 をそのまま 1 バイトへ写すので、<b>任意のバイト列を文字列定数 1 個で
運べる</b>。初期イメージをバイトごとに組み立てるバイトコードを吐かずに済む。

## 初期イメージは複製して返す

`initialStorage()` は定数フィールドの複製を返す。実行のたびに書き換えられるため、
そのまま渡すと 2 回目の実行が 1 回目の結果から始まってしまう。

## 誤りが出たらクラスファイルを作らない

生成は 2 段になっている。まず文をたどって命令の並びと必要な定数を決め、
そこで誤りが出たら<b>クラスファイルを書き出さない</b>。半端なクラスを返すと、
呼び出し側が誤りを見落としたときに実行時まで問題が残る。

`CobolCompiler` も同じ考えで、構文解析 → 割り付け → 初期イメージ → 手続き部 →
コード生成の順に進み、誤りが出た段でそこから先へ進まない。割り付けが決まっていない
状態で手続き部を解いても、意味のない誤りが山のように出るだけである。

## 除算の商の桁数は受取項目に合わせる

加減乗の結果の桁数は被演算子から決まるが、<b>除算だけは決まらない</b>。
したがって受取項目の小数部を見て決めるほかない。

このため、算術文の計算は<b>受取項目ごとにまるごと出す</b>。受取項目が複数あって
小数部が違えば、計算そのものが変わりうるからである。`ROUNDED` も受取項目ごとに
書けるので、丸めモードも受取項目ごとに決まる。

## 条件は「真のとき飛ぶ」と「偽のとき飛ぶ」の両方を出す

条件のコード生成は `emitCondition(条件, 飛び先, 真のときに飛ぶか)` の形にした。
向きを 2 つ持つのは<b>`AND` と `OR` の短絡</b>のためである。

| | 偽のときに飛ぶ | 真のときに飛ぶ |
| --- | --- | --- |
| `A AND B` | A で飛ぶ、B で飛ぶ | A が偽なら下へ抜ける印へ、B で飛ぶ |
| `A OR B` | A が真なら下へ抜ける印へ、B で飛ぶ | A で飛ぶ、B で飛ぶ |

片方の向きしか持たないと、どちらかで必ず余計な分岐と反転が要る。
`NOT` は向きを反転して内側へ渡すだけで済む。

`IF` は「条件が成り立てば下へ抜け、成り立たなければ `ELSE` へ飛ぶ」形に出す。

## 段落は「次の行き先」を返すメソッドにする

段落をそれぞれ別のメソッドとして出す。ただし戻り値を持たせる。<b>次にどこへ行くか</b>で
あり、最後まで流れたら `-1`、`GO TO` で飛ぶならその段落の番号である。

呼ぶ側は「段落の範囲を実行する」1 つのメソッド `performRange(最初, 最後)` にまとめてある。

```
pc = 最初
繰り返し:
    next = dispatch(pc)          // 段落を 1 つ実行する
    next < 0 ならば:              // 最後まで流れた
        pc == 最後 ならば 戻る     // 範囲の終わりに来た
        pc = pc + 1
    そうでなければ:
        pc = next                // GO TO で飛んだ
    pc が段落の数以上ならば 暗黙の STOP RUN
```

素直に流れる実行は「全段落を 1 つの範囲として実行する」ことであり、`PERFORM A THRU B` と
同じ機構で書ける。違いは<b>範囲の終わりがどこか</b>だけである。

飛び先は実行時にしか分からないので、番号から段落のメソッドへ振り分ける表引きの分岐
(`dispatch`) を挟んでいる。

この形にすると次の 3 つが同時に出る。

- <b>「`PERFORM` は次の段落へ流れ込まない」</b> — 範囲の終わりで戻るからである
- <b>`GO TO` は素直な `return`</b> — 段落の途中でも、入れ子の `IF` や `PERFORM` の中でも、
  その場で抜けられる
- <b>`PERFORM` が戻るのは範囲の最後の段落を流れきったときだけ</b> — `GO TO` で範囲の外へ
  出ても戻ってはこない。参照実装が範囲の終わりに戻り口を置くのと同じである

戻り先を JVM の呼び出し規約に預けているのが効いている。番号を振る必要があるのは飛び先だけで
あり、飛び先は段落の先頭しかないので段落の番号がそのまま使える。戻り先まで番号で表そうと
すると、`PERFORM` 文のところで段落を区切り直すことになり、状態機械が要る (暫定判断 P-029)。

### 繰り返しの指定と中身は独立に決まる

`PERFORM` の中身は<b>段落の呼び出しか、その場に書いた文か</b>のどちらかで、
繰り返しの指定は 1 回・回数・条件のいずれかである。両者は直交するので、
中身を 1 回分の命令として作り、指定に応じて包む形にした。

`UNTIL` の条件は<b>やめる条件</b>である。`WITH TEST AFTER` なら中身を 1 度
実行してから条件を見る。

### VARYING は「初期値を入れる」と「1 回分足す」の組み合わせ

`PERFORM VARYING` … `AFTER` … は入れ子の繰り返しである。段ごとに
<b>初期値を入れる命令</b>と<b>1 回分足す命令</b>の 2 つを作り、それを組み合わせて出す。
どちらも数値項目への書き込みであり、ランタイムの `Ops.store` を呼ぶだけである。

`TEST BEFORE` では、段の数だけ判定を縦に並べる。

```
        v1 := f1 ; v2 := f2
L1:     if c1 goto END
L2:     if c2 goto X2
        中身
        v2 := v2 + b2
        goto L2
X2:     v2 := f2
        v1 := v1 + b1
        goto L1
END:
```

内側の段が尽きたところ (`X2`) で<b>その段を初期値へ戻してから、外側を 1 進める</b>。
順序はこのとおりでなければならない。初期値にデータ項目を書いた場合、外側を先に
進めると戻す値が変わってしまうためである。IBM の流れ図もこの順である。

`TEST AFTER` では中身を先に実行し、<b>内側の条件から順に</b>見ていく。

```
        v1 := f1 ; v2 := f2
TOP:    中身
        if c2 goto X2
        v2 := v2 + b2 ; goto TOP
X2:     v2 := f2
        if c1 goto END
        v1 := v1 + b1 ; goto TOP
END:
```

どちらの形でも、抜けたときに変数へ残るのは<b>条件が成り立ったときの値</b>である。
繰り返した回数だけを見る試験では、1 回分の進めかたの誤りが見つからない。

初期値は<b>戻すたびに評価しなおす</b>。捕まえておいて使い回すのではない。
初期値にデータ項目を書き、中身がその項目を書き換えると違いが出る。

## 中間結果の桁数は翻訳時に決まる

除算は一般に有限桁で終わらない。どこで打ち切るかを決めなければ結果が定まらないため、
桁数は<b>実行前に決まっていなければならない</b>。規則は要件 5.5.1 にあり、
`IntermediateDigits` が実装している。

生成コードから見ると、加減乗は<b>正確に計算するだけ</b>でよい。結果の小数桁が規則どおりに
なるためである。手を入れるのは 2 か所しかない。

- 除算は、その節に決まった桁数を引数に渡して `Ops.divide` を呼ぶ
- 総桁数が上限 (30 桁) を超えて小数部を削ったときだけ `Ops.truncate` を挟む

ランタイムが持つのは「指定された桁数で割る」「指定された桁数へ切り捨てる」だけである。
どの桁数にするかはコンパイラが決める。方針 ARC-7 の切り分けはここでも保たれている。

## COMPUTE の式は 1 度だけ評価する

式を評価して局所変数へ取り、そこから受取項目へ配る。受取項目ごとに評価しなおすと、
<b>式の中に受取項目が現れたとき</b>に 2 つ目以降の値が変わってしまう
(`COMPUTE A B = A + 1` で B が 3 になる)。

`ON SIZE ERROR` つきの `COMPUTE` では、0 除算の扱いがほかの算術文と違う。
ほかの算術文は被演算子を局所変数へ取ってから除数を調べられるが、`COMPUTE` の 0 除算は
<b>式のどこにでも現れうる</b>。式の評価そのものを `try` で囲み、ランタイムが投げる
`DecimalDivideException` を条件へ読み替えている。

## ON SIZE ERROR は被演算子を局所変数へ取る

`ON SIZE ERROR` の指定があるかどうかで<b>桁があふれたときに受取項目に何が残るか</b>が
変わる。指定があれば受取項目は変わらず、なければ上位桁を切り捨てた値が入る。
ランタイムの `Arithmetic.store` と `storeChecked` を呼び分けるだけである。

0 除算も条件を立てる。ただしこちらは<b>割る前に除数を調べる</b>必要があり、
計算の途中で分岐すると作用対象のスタックが揃わなくなる。したがって
`ON SIZE ERROR` つきの算術文では、被演算子をいったん局所変数へ取ってから
除数を調べ、そのあとで畳む。

受取項目ごとに条件を見て、<b>収まったものだけが書き換わる</b>。
どれか 1 つでも条件が立てば、最後に `ON SIZE ERROR` の文を通る。

旗が計算の全体で 1 つであることが効いてくるのが `ADD CORRESPONDING` である。
組ごとに独立した算術文へ展開すると、あふれた組の数だけ条件文を通ってしまう。
「1 つの条件を分け合う算術文の集まり」(`Statement.ArithmeticGroup`) として出せば、
違いは<b>旗を立てる計算がいくつあるか</b>だけになる。尾部の分岐はそのまま分け合える。

## 位置は「定数の分をまとめてから変数の分を足す」

添字がすべて定数なら位置は翻訳時に決まり、定数を積むだけでよい。
データ項目で書いた添字が混ざる場合は、<b>定数の分をまとめてから、
変数の分を実行時に足す</b>。

```
位置 = 項目の変位 + Σ (添字 - 1) x その表の 1 回分の長さ
```

多次元の表でも同じ式である。定数の添字はその場で畳み込まれるので、
`WS-CELL (2, WS-J)` なら 1 つ分の足し算しか出ない。

部分参照の開始位置も同じ形で足す。ただし<b>長さは翻訳時に決まっていなければならない</b> —
図形定数を受取項目いっぱいに広げる処理が翻訳時に行われるためである (暫定判断 P-027)。

## DISPLAY は実行時の入口を引き回す

生成コードが大域の状態に触れないよう、`ProgramContext` を引数として引き回す。
`run` と段落のメソッドはどれも記憶域と実行時の入口の 2 つを取る。
試験で出力を捕まえられるのも、大域に書かないからである。

記憶域の中身は EBCDIC のバイト列なので、コードページで文字へ直してから書く。
<b>データセットへの書き出しとは扱いが違う</b> — そちらは生バイトのままであり、
変換するのは人が読む出力だけである。

`COMP` や `COMP-3` の項目はそのまま出しても読めないため、同じ桁数・同じ小数部の
`DISPLAY` 項目として符号化し直す。符号付きなら<b>符号は最後の桁に重なる</b> — 
`-12` は `01K` になる (`K` は EBCDIC の `D2`、負のゾーンを持つ 2)。
見た目は驚くが、参照実装の `DISPLAY` はこの形である。

## 生成したクラスはそのまま起動できる

生成したクラスに `main` を出す。翻訳したものを `java cobol.generated.HELLO` で
動かせるので、<b>間に何も挟まずに確かめられる</b>。

起動口は `dev.cobolonjava.compiler.Main` である。

```
cobolc [-d 出力ディレクトリ] [-I コピー句ディレクトリ] [--free] ソース...
```

## STRING と UNSTRING は結果を局所変数へ取る

どちらも<b>あふれたかどうか</b>と<b>次に書く位置</b>を実行してみないと決められない。
結果の対象を局所変数へ取り、そこから `POINTER` や `TALLYING` の項目へ書き戻し、
`ON OVERFLOW` の分岐を出す。

`ON OVERFLOW` の分岐そのものは `ON SIZE ERROR` と同じ形である。分岐の仕組みを
`IF` で作ってあるので、条件の出どころが変わるだけで済んでいる。

`STRING` は<b>受取項目の残りを埋めない</b>。書いた分だけが変わる。`MOVE` が残りを
空白で埋めるのとは違うため、生成コードも書き戻す範囲を変えている。

## いま生成できる範囲

`MOVE` の 3 種類 (英数字・数値・数字編集)、
算術文 4 つ (`GIVING`、`ROUNDED`、`DIVIDE ... REMAINDER` を含む)、
`MOVE` / `ADD` / `SUBTRACT` の `CORRESPONDING`、
`COMPUTE` (加減乗除・括弧・単項符号)、
`IF`、`EVALUATE`、`PERFORM` (`TIMES` / `UNTIL` / `VARYING` … `AFTER` …)、
`GO TO`、`DISPLAY`、`INSPECT`、`STRING`、`UNSTRING`、
`STOP RUN` / `GOBACK`、`CONTINUE` / `EXIT`、算術文の `ON SIZE ERROR` と `ON OVERFLOW`。
定数・図形定数・`ALL` の送出。
添字は定数でもデータ項目でもよく、多次元の表も扱える。部分参照の開始位置も同じ。

`SSRANGE` を指定すれば、実行時に決まる添字と部分参照の位置を実行時に検査する。

部分参照の<b>長さ</b>にデータ項目を書いた形は、まだ生成できない (暫定判断 P-027)。
べき乗 (`**`) も生成できない (暫定判断 P-028)。

## 記憶域と位置は 1 つの組で扱う

ランタイムの入口はどれも「記憶域」「位置」をこの順で取る。生成コードもこの 2 つを
1 つの組 (`planAddress`) として積む。<b>記憶域が項目ごとに違いうる</b>ためである。

```
作業場所:  ALOAD 1                    ; 変位
連絡節:    引数[k].storage()          ; 引数[k].offset() + 変位
```

連絡節の項目は記憶域を持たない (要件 FR-070)。実体は呼ぶ側にあり、`run` の 3 番目の
引数として渡される `DataView[]` の要素が指す。どの要素かは
`PROCEDURE DIVISION USING` に並べた順で決まる。

組にしてあるので、この違いを知っているのは `planAddress` だけである。`MOVE` も算術文も
`INSPECT` も、連絡節を扱うために変わったところはない。

## SSRANGE の検査は値をそのまま返す

`SSRANGE` を指定すると、実行時に決まる添字と部分参照の位置を実行時に検査する
(要件 FR-024, FR-026)。定数で書かれたものは従来どおり翻訳時に検査する。

検査は `Ops.checkSubscript(値, 個数, 名前)` のように<b>渡された値をそのまま返す</b>形に
してある。位置の計算の途中へ 1 つ挟むだけで済み、<b>指定がないときの命令列がまったく
変わらない</b>。

```
      添字を積む
      [checkSubscript]     ← SSRANGE のときだけ挟まる
      1 を引く
      1 回分の長さを掛ける
      足し込む
```

検査のために計算の形を組み替えると、指定がないときの挙動まで動いてしまう。既定は
検査しない側であり、そこは参照実装と一致していなければならない。

範囲外は `RangeCheckException` で止める。黙って続けないのは、範囲外の参照が
<b>そのあとの結果を信用できなくする</b>ためである。

## DIVIDE ... REMAINDER は書き込む前に両方を求める

1 回の計算から 2 つの値が出る唯一の算術文である。商と剰余は<b>どちらも書き込む前に</b>
求めて局所変数へ取る。割られる側が商の受取項目でもありうるためであり、商を先に書き込むと
剰余が狂う。

剰余は切り捨てた商から求める (`Ops.remainder`)。商に `ROUNDED` を書いても、剰余の計算に
使う商は丸めない。丸めた商から求めると、商と剰余を足し戻したときに元の値にならない。

`ON SIZE ERROR` では 0 除算が商と剰余のどちらの計算でも起きるため、`COMPUTE` と同じく
計算をまとめて `try` で囲む。商が収まらなければ<b>剰余も書き込まない</b>。
入らなかった商から求めた剰余に意味はない。

## 次の増分

1. `CALL` による副プログラムの呼び出し (連絡節の呼ぶ側)。
2. `GO TO ... DEPENDING ON` (暫定判断 P-029)。
3. 部分参照の長さにデータ項目を書いた形 (暫定判断 P-027)。
