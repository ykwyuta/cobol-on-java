## INSPECT は単一の走査で句を試す

`InspectScan` が担う (要件 FR-065)。1 つの `INSPECT` 文に書かれた句は、
項目を左から右へ 1 度だけ走査しながら、各位置で<b>書かれた順に試される</b>。
最初に当たった句だけが適用され、当たった長さだけ位置が進む。

句を独立に適用するのとは結果が違う。`TALLYING C1 FOR ALL "AB" C2 FOR ALL "B"` を
`"AB"` に適用すると、単一走査では C1 が 1、C2 が 0 になる。

- <b>`LEADING` はほかの句がその位置を取っても連なりが切れる</b>。
  1 つの走査で句が競合するためである
- <b>照合は元のバイト列に対して行う</b>。書き換えた結果を照合すると、
  置き換えた並びがもう一度当たることがある
- <b>`TALLYING` と `REPLACING` は走査を分ける</b>。COBOL はこれを 2 つの文を
  書いたのと同じに扱う。ひとつにまとめると、数える句が位置を取ってしまい
  置き換えが起きない

## 中心となる設計判断

### 1. バイト列 + ビュー (`storage`)

`Storage` は連続したバイト配列、`DataView` はその上の (オフセット, 長さ) である。
データ項目はすべて `DataView` として表現される。この一手で以下が同時に満たされる。

- `REDEFINES` (FR-021) — 同じ範囲に 2 つ目のビューを作るだけ。一方への書き込みが他方から即座に見える
- 集団項目 (FR-020) — 配下の基本項目のバイト範囲そのもの。集団項目への操作が英数字項目として
  無変換にバイト単位で作用するという規則が、表現から自然に導かれる
- 部分参照 (FR-026) — `DataView.subView`

データ項目を Java のオブジェクトへ写像する設計では、この 3 つがいずれも表現できない。

### 2. 負のゼロを表現できる `Decimal`

`Decimal` は絶対値・スケール・符号を独立に保持する。符号は値がゼロでも `-1` を取りうる。

これは装飾ではなく必須である。パック10進数とゾーン10進数は符号ニブルを値とは別に持つため、
「数字部がすべて 0 で符号ニブルが `D`」というバイト列 (負のゼロ) がホスト上に実在する。
`BigDecimal` はこれを表現できず、符号を落とすと `MOVE` を通しただけでバイト列が
`0x000D` から `0x000C` へ変化してしまう。要件 FR-020 が求める L3 互換はそこで崩れる。

演算結果のゼロには正号を与え、復号・再符号化の経路では元の符号を保つ。
命令ごとの正確な規則は Hercules による検証待ちである (P-001)。

### 3. 符号ニブルの読み書きの非対称性

読み取りでは `A` `C` `E` `F` を正、`B` `D` を負として広く受理し、書き込みでは
正に `C`、負に `D`、符号なし項目に `F` という優先符号を生成する (`SignNibble`)。

この非対称性は z/Architecture の規定どおりであり、ホストから移送してきたデータセットの
バイト列 (要件 FR-110 により生バイトのまま保持する) をそのまま読めるために必要である。

### 4. ゾーン10進の復号は符号位置以外のゾーンを見ない

ホストの `PACK` 命令は最右端バイト以外のゾーンニブルを無視する。したがって
`ZonedDecimal.decode` も、符号位置以外は下位 4 ビットだけを見る。
英数字項目から再定義された数字のように、ゾーンが `F` でないバイト列もホストと同じく数字として読める。

### 5. `TRUNC(OPT)` を型で解決させる

`TruncMode.OPT` は単独では挙動が決まらない。参照実装が「結果は予測できない」と規定しているためである
(要件 FR-205)。そこで `BinaryDecimal.encode` は未解決の `OPT` を受け取ると例外を投げ、
呼び出し側に `TruncMode.resolve(UndefinedBehavior)` での解決を強制する。

- `UndefinedBehavior.SAFE` (既定) → `STD` として扱う。定義された挙動を返す
- `UndefinedBehavior.MIMIC` → `BIN` として扱う。切り捨てを省く挙動を模倣する

未定義領域を「うっかり素通りさせない」ことを型で保証する設計である。

### 6. PICTURE を「バイト位置ごとの役割の列」に落とす

`Picture.cells()` は、項目が占める各バイト位置の役割を左から順に並べたものである。
`NumericEditor` はこの列を 1 回走査して出力を組み立てる。ホストではこの処理が
`ED` / `EDMK` 命令として実現されており、Hercules オラクルで V2 へ引き上げられる代表的な領域である。

小数位置の決定には、`P` (桁位置指定) を含む一般化した式を用いる。

```
scale = 最後の格納桁スロットの位置 + 1 - 小数点の位置
```

- `999V99` → 4 + 1 - 3 = 2
- `PPP999` → 5 + 1 - 0 = 6   (格納は 3 桁、値 = 数字 x 10^-6)
- `999PPP` → 2 + 1 - 6 = -3  (格納は 3 桁、値 = 数字 x 10^3)

`scale` が負になりうることを許すことで、`P` を特別扱いせずに同じ式で扱える。
`Decimal.storedDigits(totalDigits, scale)` も負のスケールを受け付ける。

## verb パッケージの設計

算術文の互換性はほぼ「結果を受取項目へ格納する際の規則」に集約される。したがって
`Arithmetic` が提供するのは演算ではなく<b>格納</b>である。演算そのものは `Decimal` が担う。

`ON SIZE ERROR` の有無で挙動が変わる点が中心である。

| 指定 | 桁があふれたとき |
| --- | --- |
| `ON SIZE ERROR` あり | **受取項目を変更せず**、SIZE ERROR 条件を立てる |
| なし | 上位桁を黙って切り捨てて格納する |

この違いは「桁あふれ後に受取項目に何が残っているか」に直結し、後続の処理結果を変える。
小数部の切り捨ては SIZE ERROR ではない。

`MOVE` は `ROUNDED` を持たないため、数値転記は常に切り捨てである。

## 文字列操作で気を付けた点 (FR-065)

意味論の取り違えが起きやすい箇所を、テストで明示的に固定した。

| 箇所 | 規則 |
| --- | --- |
| `INSPECT` の一致 | 左から右へ<b>重なりなく</b>。`"AAA"` から `"AA"` を数えると 1 |
| `INSPECT AFTER INITIAL` の区切りが見つからない | 「全体を検査する」のではなく<b>一切検査しない</b> |
| `INSPECT` する項目が符号つきの数字項目 | <b>符号を落とした像</b>を走査する。`S9(5)` の `-12345` から `"5"` は 1 個見つかり、`"-"` は 0 個である (`Ops.tallyUnsigned`) |
| `STRING` の受取項目 | <b>空白で埋めない</b>。書き込まれなかった位置は元の内容が残る |
| `UNSTRING` の受取項目 | 英数字転記の規則に従い、左詰めで空白で埋める。`STRING` と対照的 |
| `UNSTRING` の `COUNT IN` | 受取項目に収まらず切り捨てられた場合も、<b>切り捨て前</b>の文字数を受け取る |
| ポインタが範囲外 | `STRING` / `UNSTRING` とも<b>何も転記せず</b>オーバーフローになる |

## 浮動小数点項目を別の記述子にした理由

`FloatingItem` を `NumericItem` と分けているのは、<b>浮動小数点項目が PICTURE を持たない</b>
ためである。桁数も小数位置もなく、記憶域の幅だけで表現が決まる。PICTURE を前提とした
記述子に無理に載せると、桁数のない項目のために空の PICTURE を作ることになり意味論が濁る。

`NumericItem` は浮動小数点の `USAGE` を明示的に拒否する。この分離は Java の
switch 式の網羅性検査によって強制されており、`Usage` に値を足したときに
対応漏れがコンパイルエラーとして現れる。
