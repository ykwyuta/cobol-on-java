# 設計 25: 検証基盤

要件 NFR-040 (言語機能の網羅)、NFR-041 (データ意味論の網羅)、NFR-042 (構文バリエーションの
網羅)。モジュールは `cobol-verify`。

## この基盤が答える問い

これまでのテストは<b>自分で書いた期待値</b>に対して緑だった。V2 (Hercules 突き合わせ) が
33 件あるが、それは 10 進演算と編集移送という狭い面である。「動く」ことは示せていても、
<b>外の基準に照らして正しい</b>ことは示せていない。

検証基盤が答えるのは次の 3 つであり、どれも<b>自分では作れない問い</b>である。

| 層 | 問い | 出所 |
| --- | --- | --- |
| CCVS85 (NFR-040) | 言語の機能を網羅して<b>受理し、正しく動く</b>か | NIST の検証スイート |
| 合成ジェネレータ (NFR-041) | データの意味論がバイト単位で合っているか | Hercules (実装済) |
| OSS コーパス (NFR-042) | 実在する書き方を<b>受理できる</b>か | 公開されている資産 |

3 つは捉える欠陥の層が違う。CCVS85 は仕様の穴を、合成ジェネレータは表現の穴を、
コーパスは<b>仕様には書いてあるが自分では思い付かない書き方</b>の穴を見つける。

## コーパスは同梱しない

要件 NFR-042 が明示している。<b>URL とコミットハッシュで固定した取得スクリプトを置き、
取得時に SPDX 識別子を記録する。</b>Apache-2.0 の成果物へ、素性や条件の異なるソースを
取り込まないための措置である。

CCVS85 は NIST のパブリックドメインだが、こちらも同じ扱いにした。解いて 28 MB あり、
リポジトリの中身の大半がテストデータになってしまう。<b>Hercules を外から呼ぶのと同じ
考え方</b>である。

```
sh tools/verify/fetch-ccvs85.sh build/verify
CCVS85=build/verify/newcob.val mvn -B -pl cobol-verify -am test
```

無ければテストはスキップする。検査の道具の有無でビルドが壊れてはならない。

## CCVS85 はそのままでは翻訳できない

配布物 `newcob.val` は 1 つの本文ファイルであり、区切りの行を挟んで 459 本の検査
プログラムと 51 本の写し句が並んでいる。切り出したそれは<b>まだ COBOL ではない</b>。
処理系ごとに違うところが、印を付けたまま残してあるからである。

配布物には `EXEC85` という COBOL プログラムが同梱されており、これが起こしをやる。
`Population` はその決まりを実装したものである。

### 7 桁目の英字は「選べる行」の印である

```
032700S    EXIT PROGRAM.        → 選ばなければ  032700*S   EXIT PROGRAM.
```

7 桁目の英字は、その文字が指す機能を<b>使う処理系だけ</b>が通す行である。選んだ文字なら
7 桁目を空白にして活かし、選ばなければ注釈にする。何も選ばなければ<b>いちばん素直な形</b>
になる。上の例なら、副プログラムとして呼ばれる形ではなく、自分で `STOP RUN` する形である。

消さずに注釈にするのは、<b>何が落ちたのかが原文に残る</b>ようにするためである。

`D` だけは例外でそのまま通す。COBOL のデバッグ行という別の決まりが、すでに 7 桁目の `D`
を使っているからである。

### XXXXXnnn は処理系が埋める空欄である

12 桁目から `XXXX`、16 桁目が `X`、17 桁目から 3 桁の番号。そこにあるのが差し込み札
(X-card) であり、装置名やファイルの結び付けなど処理系ごとに違うものが来る。

```
003600     XXXXX082.            → 003600     COBOL-ON-JAVA.
```

20 桁目が `.` なら札の末尾に `.` を足し、空白なら逆に落とす。文の途中に置かれる札も
あるからである。

### 埋まらなかった空欄は必ず報せる

札を用意していない番号があれば、そのプログラムは<b>流さない</b>。黙って `XXXXX014` を
残して翻訳にかければ、処理系が受け付けられなかったのか、こちらが札を書き忘れたのかが
区別できなくなる。

**検査の道具が、処理系の失敗を作ってはならない。** これがこの基盤でいちばん大事な決まりで
ある。数を測る道具の数が信用できなければ、測る意味がない。

写し句も同じように起こす。7 桁目の印も差し込み札も、写し句の中に同じように入っている。

## 断ったのか、壊れたのか

翻訳にかけた結果は 3 つに分ける。

| 結末 | 意味 | 直す順 |
| --- | --- | --- |
| 通った | — | — |
| 断った | <b>読めないと言った</b>。未対応の構文であり、診断がどこで詰まったかを持っている | まだ書いていない機能の一覧 |
| 壊れた | <b>言わずに例外が外へ出た</b>。診断を出す道を通っていない | いま直すべき不具合 |

合格率だけを数えるなら分ける必要はない。分けるのは<b>直す順が違う</b>からである。混ぜて
数えると、少数の不具合が多数の未実装に埋もれる。

1 本が壊れても、そこで止めずに次へ進む。500 本流して 1 本目で止まったら、残りの 499 本に
ついて何も分からない。<b>検査の道具は、被験体の壊れ方に付き合って落ちてはならない。</b>

## 理由は「詰まった語」で数える

診断の文面には位置が混ざる。そのままでは 500 本で 500 通りの理由になり、<b>何がいちばん
詰まっているか</b>が見えない。位置を落としてから数える。

<b>詰まった語は残す。</b>ここを伏せると `no viable alternative at input '…'` だけが並び、
次に何を書けばよいのか分からなくなる。最初はこれで数えていて、112 件という数字が出た
だけで手が止まった。

ただし構文解析の道具は、詰まった規則の<b>先頭から拾えた語をぜんぶ</b>並べることがある。
長い引用は 1 本ごとに違うものになって数がばらけるので、頭の 24 文字だけ残して刈り込む。

```
   133  no viable alternative at input 'OPEN-FILES.OPENOUTPUTPRI…'
    11  extraneous input 'AUTHOR' expecting {<EOF>, IDENTIFICATION, ID}
     9  extraneous input 'PROGRAM' expecting {PERIOD, MOVE, ADD, ...}
     4  mismatched input 'RECORDS' expecting RECORD
```

これが<b>次に何を書くか</b>の一覧である。1 件を止めている構文より、100 件を止めている構文
を先に書くほうがよい。伏せるのは数えるときだけで、元の文面は残してある。直す人が見るのは
そちらだからである。

数えているのは<b>いちばん最初に詰まったところ</b>である。1 つ直すと、そのプログラムは
次の詰まりへ進む。だから数が動いても合格率が動かないことがある。上の 133 は、最初の
測定で 112 だったものが 2 つ直した結果<b>増えた</b>数である。減っていないのは、
手前で止まっていたものが同じ壁まで進んだからである。

## 合格率は門にしない

テストは<b>道具が正しく起こせているか</b>だけを確かめる。合格率に下限を課すと、処理系が
育つまでビルドが赤くなり、<b>数を取り続けられなくなる</b>。数は記録して並べるものであって、
通す・落とすの門にするものではない。

門になるのは要件 13 章の受け入れ基準 (入出力以外のモジュールで 95%) であり、それは
P0-b の完了を判定するときに人が見る数である。

### 基盤が見つけたもの

作った当日に測って直した。どれも<b>自分では思い付かなかった</b>ものである。

| 見つけたもの | 何本を止めていたか | 直し方 |
| --- | --- | --- |
| 読めない原文が例外で外へ出ていた | 2 | 入口で受け止めて診断に変えた |
| 小数点で始まる数字定数 (`VALUE .25`) を読めない | 21 | 定数の綴りに形を足した |
| コンマとセミコロンを飾りとして読み飛ばせない | 18 | 構文解析器へ渡さないことにした |
| `WRITE ... AFTER ADVANCING` を読めない | 133 | 行送りを実装した (暫定判断 P-063) |
| 見出し部の注記段落 (`AUTHOR` など) を読めない | 13 | 桁を見て落とすことにした (暫定判断 P-064) |
| `LABEL RECORDS` / `DATA RECORDS` の覚え書きの句 | 19 | 読んで捨てる句として文法へ足した |

<b>3.0% から 25.7% になった。</b>6 本が 52 本である。

いちばん効いたのは `WRITE ... AFTER ADVANCING` で、これ 1 つで 43 本が通るようになった。
CCVS85 のプログラムはどれも自分の結果を印字するので、印字の書き方が読めないと<b>検査の
中身へ入る前に</b>落ちていた。1 つの門が全体を塞いでいたことは、<b>数を並べて見なければ
分からなかった</b>。

直した順は数の大きい順ではない。`WRITE` は行送りの表し方を決める必要があり
(暫定判断 P-063)、注記段落は桁を見る層を決める必要があった (暫定判断 P-064)。
<b>数は順番を教えるが、決め方までは教えない。</b>

## 次の増分

1. **`EXIT PROGRAM`** (9 本)。呼ばれた側から戻る文である。主プログラムでは何もしない
   という決まりがあり、`GOBACK` と同じにはできない。
2. **`USAGE INDEX`** (6 本、暫定判断 P-006 の残り) と **`SET` の指標名** (3 本、
   暫定判断 P-035)。指標名を隠しデータ項目として持っている作りが、ここで表に出た。
3. **`PROGRAM COLLATING SEQUENCE`** (6 本)。暫定判断 P-042 と同じ根である。
4. **`USE ... FOR DEBUGGING`** (5 本)。デバッグ節である。
5. **CCVS85 を動かす段** (暫定判断 P-062)。いまは翻訳が通るかまでである。CCVS85 の
   プログラムは自分で `PASS` / `FAIL` を印字するので、動かして数えれば<b>正しく動くか</b>
   まで測れる。行送りが入ったので、その印字がそのまま答え合わせに使える。
   <b>ここから先は受理率ではなく合格率になる。</b>
7. **OSS コーパスの一覧を埋める** (要件 NFR-042、暫定判断 P-062)。`tools/verify/corpus.tsv`
   の仕掛けはできている。行を足すのは<b>ライセンスを確かめる作業</b>であり、確かめて
   いないものを書いてはならない。
8. **ベンチマークの回帰検査** (要件 NFR-046)。同じ枠に載る。
