# 設計 25: 検証基盤

要件 NFR-040 (言語機能の網羅)、NFR-041 (データ意味論の網羅)、NFR-042 (構文バリエーションの
網羅)。モジュールは `cobol-verify`。

## この基盤が答える問い

これまでのテストは<b>自分で書いた期待値</b>に対して緑だった。V2 (Hercules 突き合わせ) が
33 件あるが、それは 10 進演算と編集移送という狭い面である。「動く」ことは示せていても、
<b>外の基準に照らして正しい</b>ことは示せていない。

検証基盤が答えるのは次の 3 つであり、どれも<b>自分では作れない問い</b>である。

| 層 | 問い | 出所 |
| --- | --- | --- |
| CCVS85 (NFR-040) | 言語の機能を網羅して<b>受理し、正しく動く</b>か | NIST の検証スイート |
| 合成ジェネレータ (NFR-041) | データの意味論がバイト単位で合っているか | Hercules (実装済) |
| OSS コーパス (NFR-042) | 実在する書き方を<b>受理できる</b>か | 公開されている資産 |

3 つは捉える欠陥の層が違う。CCVS85 は仕様の穴を、合成ジェネレータは表現の穴を、
コーパスは<b>仕様には書いてあるが自分では思い付かない書き方</b>の穴を見つける。

## コーパスは同梱しない

要件 NFR-042 が明示している。<b>URL とコミットハッシュで固定した取得スクリプトを置き、
取得時に SPDX 識別子を記録する。</b>Apache-2.0 の成果物へ、素性や条件の異なるソースを
取り込まないための措置である。

CCVS85 は NIST のパブリックドメインだが、こちらも同じ扱いにした。解いて 28 MB あり、
リポジトリの中身の大半がテストデータになってしまう。<b>Hercules を外から呼ぶのと同じ
考え方</b>である。

```
sh tools/verify/fetch-ccvs85.sh build/verify
CCVS85=build/verify/newcob.val mvn -B -pl cobol-verify -am test
```

無ければテストはスキップする。検査の道具の有無でビルドが壊れてはならない。

## CCVS85 はそのままでは翻訳できない

配布物 `newcob.val` は 1 つの本文ファイルであり、区切りの行を挟んで 459 本の検査
プログラムと 51 本の写し句が並んでいる。切り出したそれは<b>まだ COBOL ではない</b>。
処理系ごとに違うところが、印を付けたまま残してあるからである。

配布物には `EXEC85` という COBOL プログラムが同梱されており、これが起こしをやる。
`Population` はその決まりを実装したものである。

### 7 桁目の英字は「選べる行」の印である

```
032700S    EXIT PROGRAM.        → 選ばなければ  032700*S   EXIT PROGRAM.
```

7 桁目の英字は、その文字が指す機能を<b>使う処理系だけ</b>が通す行である。選んだ文字なら
7 桁目を空白にして活かし、選ばなければ注釈にする。何も選ばなければ<b>いちばん素直な形</b>
になる。上の例なら、副プログラムとして呼ばれる形ではなく、自分で `STOP RUN` する形である。

消さずに注釈にするのは、<b>何が落ちたのかが原文に残る</b>ようにするためである。

`D` だけは例外でそのまま通す。COBOL のデバッグ行という別の決まりが、すでに 7 桁目の `D`
を使っているからである。

### XXXXXnnn は処理系が埋める空欄である

12 桁目から `XXXX`、16 桁目が `X`、17 桁目から 3 桁の番号。そこにあるのが差し込み札
(X-card) であり、装置名やファイルの結び付けなど処理系ごとに違うものが来る。

```
003600     XXXXX082.            → 003600     COBOL-ON-JAVA.
```

20 桁目が `.` なら札の末尾に `.` を足し、空白なら逆に落とす。文の途中に置かれる札も
あるからである。

### 埋まらなかった空欄は必ず報せる

札を用意していない番号があれば、そのプログラムは<b>流さない</b>。黙って `XXXXX014` を
残して翻訳にかければ、処理系が受け付けられなかったのか、こちらが札を書き忘れたのかが
区別できなくなる。

**検査の道具が、処理系の失敗を作ってはならない。** これがこの基盤でいちばん大事な決まりで
ある。数を測る道具の数が信用できなければ、測る意味がない。

写し句も同じように起こす。7 桁目の印も差し込み札も、写し句の中に同じように入っている。

## 断ったのか、壊れたのか

翻訳にかけた結果は 3 つに分ける。

| 結末 | 意味 | 直す順 |
| --- | --- | --- |
| 通った | — | — |
| 断った | <b>読めないと言った</b>。未対応の構文であり、診断がどこで詰まったかを持っている | まだ書いていない機能の一覧 |
| 壊れた | <b>言わずに例外が外へ出た</b>。診断を出す道を通っていない | いま直すべき不具合 |

合格率だけを数えるなら分ける必要はない。分けるのは<b>直す順が違う</b>からである。混ぜて
数えると、少数の不具合が多数の未実装に埋もれる。

1 本が壊れても、そこで止めずに次へ進む。500 本流して 1 本目で止まったら、残りの 499 本に
ついて何も分からない。<b>検査の道具は、被験体の壊れ方に付き合って落ちてはならない。</b>

## 理由は「詰まった語」で数える

診断の文面には位置が混ざる。そのままでは 500 本で 500 通りの理由になり、<b>何がいちばん
詰まっているか</b>が見えない。位置を落としてから数える。

<b>詰まった語は残す。</b>ここを伏せると `no viable alternative at input '…'` だけが並び、
次に何を書けばよいのか分からなくなる。最初はこれで数えていて、112 件という数字が出た
だけで手が止まった。

ただし構文解析の道具は、詰まった規則の<b>先頭から拾えた語をぜんぶ</b>並べることがある。
長い引用は 1 本ごとに違うものになって数がばらけるので、頭の 24 文字だけ残して刈り込む。

```
   133  no viable alternative at input 'OPEN-FILES.OPENOUTPUTPRI…'
    11  extraneous input 'AUTHOR' expecting {<EOF>, IDENTIFICATION, ID}
     9  extraneous input 'PROGRAM' expecting {PERIOD, MOVE, ADD, ...}
     4  mismatched input 'RECORDS' expecting RECORD
```

これが<b>次に何を書くか</b>の一覧である。1 件を止めている構文より、100 件を止めている構文
を先に書くほうがよい。伏せるのは数えるときだけで、元の文面は残してある。直す人が見るのは
そちらだからである。

### 1 件ずつの理由の中に、いちばん大きい塊があった

理由の一覧が 1 件ずつばかりになったので、<b>止まった行そのもの</b>を 1 本ずつ並べて
みた。診断は位置を持っているので、原文のその行を引けばよい。

```
IF119A  COMPUTE WS-NUM = FUNCTION MAX(IND(ALL)).
IF120A  COMPUTE WS-NUM = FUNCTION MEAN(IND(ALL)).
IF121A  COMPUTE WS-NUM = FUNCTION MEDIAN(IND(ALL)).
IF122A  COMPUTE WS-NUM = FUNCTION MIDRANGE(IND(ALL)).
...
```

<b>11 本が同じ `ALL` で止まっていた。</b>理由の文面は関数の名前だけ違うので、
数え上げでは 1 件ずつに散っていた。止まった行を見なければ塊に見えない。

理由で数えるのは「次に何を書くか」を決めるのによい。しかし<b>理由が細かくなったら、
数えるのをやめて行を見る</b>。同じことが 3 度あった (段分け、`ALTER`、そして `ALL`)。

### 刈り込むのは頭のほうである

はじめは<b>頭を残して</b>刈り込んでいた。これが間違いだった。

`no viable alternative at input '…'` の引用は、<b>詰まった語ではなく、そこまで読めた語を
ぜんぶ並べたもの</b>である。頭は段落名から始まる。頭を残すと、同じ原因で止まった 2 本が
段落名の違いで別々の理由になって散る。

```
1  no viable alternative at input 'INIT-SG203.PERFORMCCVS1…'
1  no viable alternative at input 'GO--TEST-n.ALTERGO--A…'
1  no viable alternative at input 'INS-INIT-F1-1.MOVE"INS-…'
```

尻を残すと、同じものがこうなる。

```
1  no viable alternative at input '…MCCVS1.GOTO50'
1  no viable alternative at input '…GO--TEST-n.ALTERGO--A'
1  no viable alternative at input '…LYINGWRK-DU-nnn(INDEXn+n)'
```

<b>知りたいのは詰まった側の端である。</b>段分け、`ALTER`、相対添字 — 3 つの別の原因が、
頭を残していたときには見えていなかった。

そして刈り方を直した次の測定で、<b>自分が前の増分で作った不具合</b>が 1 つの塊として
出た。相対添字を実装したとき、`ANIMAL (W-1 +1 W-3)` の `+1` を「`W-1` へのずれ」として
食ってしまい、3 つあるはずの添字が 2 つになっていた。自分のテストは<b>間違ったほうの
規則</b>を固定していた。測って直して、また測る。

## 検査スイートは要求そのものを持っている

いちばん大きかったのは<b>数を測ることではなかった</b>。

`SQRT` や `SIN` を「参照実装の桁数の規則を持っていないから書かない」と決めていた
(暫定判断 P-065)。根拠に置いたのは「COBOL の資産は計算結果を等号で比べる」という
<b>自分の思い込み</b>である。16 本がそこで止まっていた。

検査スイートの中身を読んだら、そうではなかった。

```
EVALUATE FUNCTION ANNUITY(2.9, 4)
WHEN  2.91252 THRU  2.91264   PERFORM PASS
```

<b>範囲で判定している。</b>規格そのものが精度を処理系に任せていて、適合性の検査は
有効数字 6 桁ほどを求めている。等号では比べていない。

適合性の検査スイートは、通った通らないを数える道具であるだけでなく、
<b>規格が何を求めているかを、実行できる形で書いたもの</b>である。読めばよかった。
「仕様が無いから書けない」と自分で決めたところは、まずスイートを読む。

数えているのは<b>いちばん最初に詰まったところ</b>である。1 つ直すと、そのプログラムは
次の詰まりへ進む。だから数が動いても合格率が動かないことがある。上の 133 は、最初の
測定で 112 だったものが 2 つ直した結果<b>増えた</b>数である。減っていないのは、
手前で止まっていたものが同じ壁まで進んだからである。

## 翻訳が通ることと、正しく動くことは別である

`verify ccvs85` は<b>翻訳が通るか</b>だけを見る。これは受理率であって合格率ではない。
`verify ccvs85-run` は<b>動かして</b>、検査プログラムが自分で書いた成績を読む。

```
                                            END OF TEST-  NC101A

                                            093 OF 093  TESTS WERE EXECUTED SUCCESSFULLY
                                            NO  TEST(S) FAILED
                                            NO  TEST(S) DELETED
                                            NO  TEST(S) REQUIRE INSPECTION
```

数えるのは<b>プログラム自身が書いたこの 4 行</b>である。1 行ずつの `PASS` / `FAIL` を
数えても近い値は出るが、検査スイートが自分で決めた数え方に従うほうが正しい。
行を数えると、見出しの「`FEATURE PASS PARAGRAPH-NAME`」まで数えてしまう。

`END OF TEST-` が無ければ、プログラムは<b>最後まで行かなかった</b>。途中で止まった
ものを「落ちた検査が 0 だから合格」と数えてはならない。

### 動かす段でも、道具が失敗を作った

作った日に 4 つ出た。<b>数を信じる前に、道具を疑う</b>。

| 道具の落ち度 | どう見えたか | 本数 |
| --- | --- | --- |
| 呼ぶ側と呼ばれる側を別々に動かしていた | 「呼び先が無い」「引数が渡されていない」 | 54 |
| 診断を見るための検査を動かしていた | 「報告を書かずに終わった」 | 31 |
| 検査プログラムの `DISPLAY` が道具の出力に混ざる | 数のほうが読めない | — |
| 外部スイッチを合わせずに流していた | `SWITCH-STATUS` が 8 件落ちる | 2 |

最後のものは差し込み札 (X-card) と同じ種類の支度である。NC174A は
「SWITCH-1 EXPECTED ON」と自分で書いており、`UPSI-0` が入・`UPSI-1` が切である
ことを前提にしている。<b>検査が要求している環境を用意する</b>ことであって、
答えを合わせにいくのではない。

配布物は `*HEADER,COBOL,IC101A,SUBRTN,IC102A` のように、<b>呼ぶ側の名前を頭に置いて</b>
副プログラムを別の部品にしている。最初のコンマまでが検査の名前である。同じ検査の部品は
まとめて翻訳し、同じ読み込み器へ入れて、<b>呼ぶ側 1 本として数える</b>。

診断を見るための検査は、ソースが報告の文面を持っているかで見分ける。<b>名前の形では
決めない</b>。名前の付け方は配布物の都合であって、中身の性質ではない。

### 数は 2 つ並べる

| 数え方 | 意味 |
| --- | --- |
| 本数 | 全部の検査に通ったプログラムが何本か |
| 検査の数 | プログラムの中の個々の検査が何件通ったか |

本数だけでは粗い。1 本の中に 100 件の検査があり、そのうち 1 件が落ちてもその本は
落ちたことになる。逆に検査の数だけを見ると、<b>翻訳が通らなくて 1 件も流れていない
プログラム</b>が数に出ない。両方を並べる。

## 合格率は門にしない

テストは<b>道具が正しく起こせているか</b>だけを確かめる。合格率に下限を課すと、処理系が
育つまでビルドが赤くなり、<b>数を取り続けられなくなる</b>。数は記録して並べるものであって、
通す・落とすの門にするものではない。

門になるのは要件 13 章の受け入れ基準 (入出力以外のモジュールで 95%) であり、それは
P0-b の完了を判定するときに人が見る数である。

### 基盤が見つけたもの

作った当日に測って直した。どれも<b>自分では思い付かなかった</b>ものである。

| 見つけたもの | 何本を止めていたか | 直し方 |
| --- | --- | --- |
| 読めない原文が例外で外へ出ていた | 2 | 入口で受け止めて診断に変えた |
| 小数点で始まる数字定数 (`VALUE .25`) を読めない | 21 | 定数の綴りに形を足した |
| コンマとセミコロンを飾りとして読み飛ばせない | 18 | 構文解析器へ渡さないことにした |
| `WRITE ... AFTER ADVANCING` を読めない | 133 | 行送りを実装した (暫定判断 P-063) |
| 見出し部の注記段落 (`AUTHOR` など) を読めない | 13 | 桁を見て落とすことにした (暫定判断 P-064) |
| `LABEL RECORDS` / `DATA RECORDS` の覚え書きの句 | 19 | 読んで捨てる句として文法へ足した |
| `EXIT PROGRAM` を読めない | 9 | 実装した。`GOBACK` と同じにはできない |
| 1 本のソースの 2 本目のプログラムを読めない | 4 | プログラムごとに翻訳するようにした |
| `USAGE IS INDEX` を読めない | 8 | 指標データ項目として実装した (暫定判断 P-006, P-035) |
| `SET 整数の項目 TO 指標名` を断っていた | 3 | 受取側の規則が狭すぎた。直した (暫定判断 P-035) |
| 表に付いた条件名の添字を落としていた | 2 | 親への参照へ移すようにした。<b>不具合</b>である |
| `GIVING` の受取項目に数字編集項目を書けない | 5 | 受取項目の規則が狭すぎた。<b>不具合</b>である |
| 組み込み関数 (`FUNCTION`) を読めない | 45 | 枠を作り、値が決まる 19 個を実装した (暫定判断 P-065) |
| `ALPHABET` と `PROGRAM COLLATING SEQUENCE` | 6 | 照合順序を差し替えられるようにした (暫定判断 P-042) |
| 日付と中央値の組み込み関数 | 8 | 値が決まるものを 8 個足した (暫定判断 P-065) |
| 引用の刈り込みが原因を散らしていた | — | <b>道具のほうの不具合</b>。尻を残すように直した |
| `GO TO ... DEPENDING ON` を読めない | 5 | 飛び先表として実装した |
| 添字の相対指定 (`WS-E (I + 1)`) を読めない | 4 | 添字にずれを持たせた |
| 相対指定が符号つきの添字を食っていた | 4 | <b>前の増分で作った不具合</b>。次の測定で出た |
| `NEXT SENTENCE` を読めない・空として扱っていた | 3 | 文の区切りを IR に残して実装した |
| 数字だけの手続き名 (`00 SECTION 00.`) を読めない | 6 | 手続き名に数字の語を足した (暫定判断 P-067) |
| 表の中の表を `SEARCH` できないと断っていた | 3 | 制限が広すぎた。`SEARCH ALL` だけに狭めた |
| 近似が入る組み込み関数を「書かない」と決めていた | 13 | <b>決めた根拠が間違っていた</b>。実装した (暫定判断 P-065) |
| `ALL` と書いた添字を読めない | 11 | 翻訳時に反復の数だけ広げる (暫定判断 P-068) |
| `MAX` と `MIN` が英数字の引数を取れない | 5 | 引数を見て形が決まるようにした |
| 開き括弧の前のコンマを落としていた | 1 | <b>道具のほうの不具合</b>。そこだけ残すようにした |
| `ALTER` を読めない | 7 | 飛び先の表として実装した。段分けの独立段も一緒に (暫定判断 P-066) |
| 関係条件と `EVALUATE` の目的語に式を書けない | 3 | 両辺を算術式にした |

<b>3.0% から 80.2% になった。</b>6 本が 162 本である。

いちばん効いたのは `WRITE ... AFTER ADVANCING` で、これ 1 つで 43 本が通るようになった。
CCVS85 のプログラムはどれも自分の結果を印字するので、印字の書き方が読めないと<b>検査の
中身へ入る前に</b>落ちていた。1 つの門が全体を塞いでいたことは、<b>数を並べて見なければ
分からなかった</b>。

`EXIT PROGRAM` は 20 本を動かした。止めていたのは 9 本と数えていたのに、である。
数えているのは<b>いちばん最初に詰まったところ</b>だから、後ろに控えていたものが一緒に
通った。区分で見ると `IC` (プログラム間の呼び出し) が 23.8% から 69.0% になっている。
呼ばれた側から戻る文が無ければ、そのモジュールの検査はどれも成り立たない。

11 のうち 3 つは<b>未実装ではなく不具合</b>だった。`duplicate FD for PRINT-FILE` と
いう<b>自分の診断</b>が 4 本で並んでいた。検査スイートが同じ `FD` を二重に書いていると
は考えにくいので調べたところ、`END PROGRAM` で区切って 2 本のプログラムが並んでおり、
こちらが 1 本として読んでいた。<b>数の一覧に自分の診断が並んだら、まずそれを疑う。</b>

`SET 整数の項目 TO 指標名` を断っていたのも同じ形である。<b>自分で書いた規則が狭すぎた</b>
のであって、機能が無かったのではない。しかもそれを固定するテストまで書いてあった。
検査スイートが 3 本で同じところに引っかかって、はじめて規則のほうを疑った。

`GIVING` の受取項目も同じだった。`an arithmetic statement requires a numeric receiver` は
自分の診断である。算術文の受取項目は、<b>計算に加わるかどうか</b>で規則が変わる。
`ADD A TO B` の `B` は計算に加わるので数値項目でなければならないが、
`ADD A B GIVING C` の `C` は書き込まれるだけなので<b>数字編集項目でよい</b>。
一律に数値項目へ限っていた。5 本と数えていたものが、直すと 9 本を動かした。

<b>同じ形の見落としが 3 度続いた。</b>いずれも「規格が許している書き方を、こちらが
狭く決めていた」ものであり、どれも自分のテストが<b>狭いほうを正しいこととして固定</b>
していた。自分で書いた規則は、自分のテストでは破れない。

## 区分ごとに見ると塊が出る

全体の理由の一覧は、直すたびに散らばっていく。10 本以上を止めている門が無くなった
ところで、<b>区分ごとに</b>数えてみたら別のものが見えた。

```
== IF  0/45
      6  extraneous input 'PRG-COLL-SEQ' expecting IS
      1  mismatched input 'ACOS' expecting {MOVE, ADD, ...}
      1  mismatched input 'LENGTH' expecting {MOVE, ADD, ...}
```

`IF` の 45 本が<b>全部</b>落ちていた。全体の一覧では 6 と 1 と 1 に散らばって見えたが、
1 区分がまるごと 0.0% である。原因は 1 つ、<b>組み込み関数 (`FUNCTION`) を読めない</b>
ことだった。CCVS85 の `IF` は 1 本が 1 つの関数を検査する作りなので、理由が
関数の数だけばらける。

<b>数え方を変えると別の塊が見える。</b>全体で数えるのは「次に何を書くか」を決めるのに
よいが、それだけでは<b>1 つの原因が 45 通りに散った</b>ものを見落とす。

## 直すと次が見える

`USAGE INDEX` を実装した直後の測定で、<b>壊れたものが 0 本から 2 本に増えた</b>。
それまで `USAGE INDEX` の診断で止まっていたプログラムが、その先へ進んで別のところで
落ちたからである。

| 壊れたもの | 何が起きていたか |
| --- | --- |
| `IC208A` | `IF CN1 (1)` — 表に付いた条件名の添字を、親への参照へ移していなかった |
| `NC236A` | `SEARCH ... VARYING 指標データ項目` — 指標名の印を無条件に切り落としていた |

どちらも<b>指標を実装しなければ見えなかった</b>不具合である。門を 1 つ開けると、その奥に
あったものが数に出る。だから測るのは 1 度ではなく、<b>直すたび</b>である。

2 つ目は指標の持ち方 (暫定判断 P-035) が直に出たものである。`INDEXED BY` の指標名には
`IDX$` という印を付けているが、`USAGE IS INDEX` と書かれた項目には付かない。印を無条件に
切り落とす書き方をしていたので、名前の短い項目で範囲外になった。
<b>隠しデータ項目という作りの継ぎ目が、そこにあった。</b>

直した順は数の大きい順ではない。`WRITE` は行送りの表し方を決める必要があり
(暫定判断 P-063)、注記段落は桁を見る層を決める必要があった (暫定判断 P-064)。
`EXIT PROGRAM` は<b>主プログラムでは何もしない</b>という決まりを実行時に見分ける形が
要った。<b>数は順番を教えるが、決め方までは教えない。</b>

## 落ちた検査は<b>機能ごとに</b>数える

本数で数えると「1 本が全滅」までしか分からない。検査プログラムは落ちた検査を
1 行ずつ印字しており、そこに<b>何を試した検査か</b>が書いてある。

```
 CREATE-FILE-FD1      FAIL* WRITE-TEST-GF-01     IX-41;WRONG NUMBER OF RECORDS
 └ 機能 (FEATURE)          └ 段落名 (PAR-NAME)  └ 覚え書き (REMARKS)
```

桁で切る。機能名にも段落名にも空白が入りうるので、空白で切ると 1 件が 2 件に散る。
<b>行の区切りも当てにしない</b> — 報告のデータセットは決まった長さのレコードの並びで
あり、改行を持たない。行頭に錨を打つ正規表現は 1 件も見つけられなかった。

## いまの数 (2026-09-09、動かした結果)

```
合計 390 本 (うち動かさない診断の検査 29 本):
  全部通った 340 / 落ちた 7 / 翻訳できない 14 / 壊れた 0 / 返らない 0  (合格率 94.2%)
検査は 8717 件流れて 7 件落ちた (合格率 99.9%)
このうち 127 件は<人が紙を見て決める>検査であり、道具は確かめていない
```

<b>この測定で受理率は 96.3% から 95.9% に下がった</b>。`OPEN INPUT ... REVERSED` を
黙って読み飛ばしていたのをやめ、断るようにしたためである (SQ303A と SQ401M)。
逆から読めと言われて順に読めば<b>違う答えを返す</b>。数は記録して並べるものであって
門ではない (覚え書き §7)。<b>動く本の数も、検査の数も 1 件も動いていない</b> —
2 本とも診断だけの本であり、もともと動かしていない。

<b>道具は自分の甘さを申告する</b>。CCVS85 には `REQUIRE INSPECTION` の札がある。
検査スイート自身が「これは紙を見て人が決めろ」と言っているものであり、道具は
落ちた検査に数えていない。だからそれを抱えた本も「通った」に入る。数だけ出すと、
読む側は 95.9% を額面どおりに受け取る。<b>見ていないところを一緒に出す</b>。

<b>最初の測定で 1671 件落ちていた。1 つの不具合を直して 666 件になった。</b>
01 レベルの `REDEFINES` が、重ねる先の初期値を空白で塗り潰していた。群の中の
`REDEFINES` は避けてあったのに、01 どうしの重なりだけが素通しだった。
IX215A の 409 件、IX214A の 147 件、IX211A から IX209A の 389 件が、これ 1 つだった。

<b>本数の合格率は 66.9% から 69.4% にしか動いていない</b>。1 本の中に落ちた検査が
1 件でもあればその本は落ちたままだからである。だから 2 つの数を並べる。

### 4 度目: 選ばなかった行が、鍵の位置をずらしていた

IX208A は 29 件中 23 件が落ちていた。理由の 1 件目は最初の `WRITE` の
`INVALID KEY` で、残り 22 件はその後始末である。<b>ファイルができていなければ
読む検査は全部落ちる。</b>

原因は処理系ではなかった。索引編成の検査は鍵の長さを 2 通り持っていて、7 桁目の
`T` が 10 桁、`U` が 5 桁である。原文の但し書きはこう言っている。

```
FOR CODE WITH LETTERS T OR U ONLY ONE SHOULD BE SELECTED.
EITHER THE T"S OR THE U"S SHOULD BE USED EXCLUSIVELY, NOT BOTH.
```

<b>どちらか一方を必ず選べ</b>である。どちらも選ばないという道は無い。選ばずにいた
ので、レコードが 240 バイトのはずが 230 バイトになり、副鍵の位置が 5 バイトずれた。
ずれた先は詰め物なので、どのレコードも副鍵が空白になり、2 本目の `WRITE` が
重複鍵で撥ねられていた。

`U` を選ぶ。`T` は DB105A にも印が付いていて、そちらは選ばない形でちょうど
227 件すべて通っている。<b>直したいところ以外を動かさない</b>。

これで 4 度目である。<b>道具にも検査を仕込む。</b>

### 索引はデータから導けるが、<b>並び</b>までは導けない

IX215A の 2 件は「副鍵を書き換えたレコードが、同じ値の並びのどこへ来るか」だった。
レコードを書き換えるたびに索引を丸ごと組み直していたので、同じ副鍵の並びが
<b>いつも主鍵の順</b>になっていた。ホストの副索引は入った順に並ぶので、
あとから書き換えたレコードは末尾へ来る。

索引を組み直すのは開いたときだけにして、書き足し・書き換え・消しは
索引へ直接映すようにした。書き換えでは<b>値が変わった副鍵だけ</b>を動かす。

閉じて開き直すと並びは主鍵の順に戻る。ファイルがレコードしか持っていないためで
ある。IX215A が要求しているのは開いているあいだの並びなので、そこは合っている
(暫定判断 P-087)。

### 写し句の置き場を、道具が 1 つしか持っていなかった

SM207A は `COPY ALTLB OF <X-47>` と `COPY ALTLB IN <X-48>` を並べ、
<b>同じ原本名から違う中身が来ること</b>を確かめる。道具は原本を名前だけで
覚えていたので、2 つめが 1 つめと同じ原本を引いていた。<b>道具が処理系の
失敗を作っていた</b> (覚え書き §6)。

置き場の名前を決めるのは差し込み札 047 / 048 であり、そこに何と書くかはこちらの
自由である。だから原本と置き場の結び付けも道具の側で決めるほかない。配布物の指示は
SM207A の冒頭に文章で書いてある。

```
X-47 の置き場 ← 原本 ALTLB
X-48 の置き場 ← 原本 ALTL1 を、ALTLB という名前で
```

`Ccvs85Suite.PLACEMENTS` に写した。<b>配布物が文章でしか書いていない指示は、
道具の側にコードとして置く</b>。置かなければ、読んだ人が居ないのと同じである。

### 72 桁目の引用符は、次の行を見なければ読めない

NC215A は 51 文字の照合順序を 2 行に分けて書いている。

```
004900     THE-BIG-OL-LITERAL-ALPHABET IS "A+0B-1C*2D/3E=4Fl5G,6H;7I.8J"
005000-    ""9K(L)M>N<O PQRSTUVWXYZ".
```

72 桁目の `"` を「定数を閉じた」と読んでいたので、次の行が宙に浮いて翻訳できて
いなかった。正しくは 72 桁目が「2 個 1 組」の 1 個目、継続行の B 領域の 1 個目が
<b>再開の印</b>、2 個目が組の 2 個目である。<b>3 個で 1 文字の `"` を表している</b>
(暫定判断 P-084)。原文を読む層の不具合は、黙って別のソースにしてしまうので質が悪い。

### 翻訳できない 14 本の内訳

| 本数 | 理由 | どう見るか |
| --- | --- | --- |
| 11 | 通信部 (`COMMUNICATION SECTION`) | <b>L0</b>。支えないと決めてある (制約 C-5) |
| 2 | `OPEN INPUT ... REVERSED` | 逆から読む。断っている (暫定 P-081) |
| 1 | `PICTURE P` | <b>配布物の誤り</b>である (下記) |

IX110A に `01 STATUS-TEST-10 PIC P VALUE ZERO.` と書いてある。`P` は<b>桁を 1 つも
持たない</b>ので、数字項目の PICTURE として規格が許していない。対になる IX109A の
同じ項目は `PIC 9 VALUE ZERO` であり、使い方も `IF STATUS-TEST-10 EQUAL TO 1` で
ある。一連番号も `012250` という差し込みの番号であり、<b>あとから足した行の打ち
間違い</b>と読める。断るのが正しい。

断るときは<b>何を読んだのか</b>まで書く。ランタイムの例文は数値だけを持っていて、
どの項目のどの PICTURE でそうなったかを知らない。「digits must be positive: 0」
だけでは原文のどこが悪いのか読み取れなかった。

### 卓の人が打ち込む値は、札束にして持つ

`ACCEPT` の検査は<b>卓の人が決まった値を打ち込む</b>ことを前提にしている。ホストでは
その値を `SYSIN` の札束として渡す。道具に人はいないので、同じ札束を道具の側に置いた
(`OperatorInput`)。差し込み札 (X-card) と同じく<b>道具の側の道具立て</b>である。

札の中身をこちらで考えたわけではない。検査は `ACCEPT` のすぐあとで<b>対になる項目と
比べている</b>ので、打ち込むべき値は原文に書かれている。

```
02 ACCEPT-D3 PICTURE 9(10) USAGE DISPLAY.
02 ACCEPT-D4 PICTURE 9(10) USAGE DISPLAY VALUE 0123456789.
    ACCEPT ACCEPT-D3.
    IF ACCEPT-D3 EQUAL TO ACCEPT-D4 PERFORM PASS.
```

<b>合否を決めているのはプログラムのほうであって、札ではない。</b>転記の規則を
間違えていれば、正しい値を流し込んでも落ちる。実際 NC204M の ACC-TEST-F1-13 は、
札を用意しただけでは通らなかった。

### 1 枚は 80 桁である — 検査スイートがそう言っている

NC204M の ACC-TEST-F1-13 は 200 桁の項目を 1 回の `ACCEPT` で埋める。期待する中身は
`D001*002...*050` という 4 桁ごとの並びで、`D` が来るのは<b>0 桁目・80 桁目・
160 桁目</b>である。3 枚の札の先頭にあたる。

つまり `ACCEPT` は受取項目が収まるまでレコードを読む。1 本しか読んでいなかったので、
81 桁目から先が空白になっていた。<b>「仕様が無い」と思っていたところを、検査スイートが
実行できる形で書いていた</b> (覚え書き §5)。

### 止まらない 2 本は、札を選ばなかったせいだった

SQ109M と SQ110M が 60 秒で見捨てられていた。原文はこう書いている。

```
    IF XRECORD-NUMBER (1) EQUAL TO 325
H       ADD 1 TO REELUNIT-NUMBER (1)
H       CLOSE SQ-FS1 REEL.
I  MOVE "CLOSE REEL DELETED" TO RE-MARK.
    IF XRECORD-NUMBER (1) EQUAL TO 750
        GO TO SEQ-WRITE-001.
    ADD 1 TO XRECORD-NUMBER (1).
    GO TO SEQ-TEST-001.
```

`H` は「`CLOSE ... REEL` を支えている」の印である。選ばないと外側の `IF` の本体が
<b>空になり</b>、次の `IF` がその本体になる。すると「325 であり、かつ 750 である」
ときしか抜けられず、750 本で終わるはずの書き込みが<b>止まらなくなる</b>。

`CLOSE ... REEL` を実装したので `H` と `E` を選ぶようにした。2 本とも通った。
<b>4 度目である</b> (覚え書き §6)。道具が処理系の失敗を作っていた。

### 卓に人はいないと、道具のほうで決める

`ACCEPT` の既定の送出側は標準入力である。道具を端末から起動すると<b>返ってこない</b>
一方、`< /dev/null` で起動すると流れる。測定が<b>起動の仕方に依っていた</b>。
`ProgramRunner` で「人はいない」を明示して断ち切った。

### 一覧の打ち切りを回帰と読み違えた

落ちた本の一覧は<b>上位 20 本で打ち切って</b>いる。数字定数の綴りを直した増分で
13 件が消えたとき、一覧に SQ133A / SQ144A / SQ147A の 3 本が<b>新しく現れた</b>。
入れた不具合かと思ったが、そうではない。20 本の枠が空いたので、尻に隠れていた
1 件ずつの本が繰り上がっただけである。

  54 = 一覧に出た 43 + 出なかった 11
  41 = 一覧に出た 33 + 出なかった  8

機能ごとの数え上げに<b>新しい理由が 1 つも増えていない</b>ことが決め手になった。
一覧どうしを引き算するときは、<b>打ち切られた尻がある</b>ことを忘れてはならない
(覚え書き §6 の裏返しで、道具が測定を誤読させた例である)。

組み込み関数 (IF 区分) は<b>この一覧から消えた</b>。17 本・30 件が落ちていたのは
関数そのものの精度ではなく、<b>中間結果の桁数</b>の 2 つの不具合だった。
一覧を機能ごとに数えていなければ「三角関数と対数の精度が足りない」と読み違えていた。

<b>DB105A 1 本で 227 件が落ちていた。いまは 227 件すべて通る。</b>
`USE FOR DEBUGGING` を実装したときに 6 件が残り、そのすべてが `ALTER` だった。
残った理由は 2 つあって、どちらも<b>入る道を数え落としていた</b>。

1. 書き換えられる段落は本体を出さずに飛び先を返すので、入り口ごと落ちていた
2. 規格は `ALTER` に書かれた手続き名も見張ると決めている。`ALTER` の直後に
   もう 1 度動き、`DEBUG-CONTENTS` に書き換え先が入る

<b>入る道の数だけ入り口が要る。</b>1 つ実装して「できた」と思ったところに、まだ
2 本の道が残っていた。次の測定が見つけた。

- **返ってこない 2 本** (SQ109M、SQ110M)。返らないのは断るより悪い。
- **壊れた 2 本** (NC109M、NC204M)。`empty zoned decimal field`。
- **通信部 (`COMMUNICATION SECTION`)** は L0 (制約 C-5)。9 本は翻訳できないままである。
- **OSS コーパスの一覧を埋める** (要件 NFR-042)。
- **ベンチマークの回帰検査** (要件 NFR-046)。
