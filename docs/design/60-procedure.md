# 設計 60: 手続き部と一意名の解決

対象: 要件 FR-024, FR-026, FR-060 / 方針 ARC-7, ARC-8

## 位置付け

手続き部の構文木から文の並びを作り、<b>一意名を記憶域の割り付け (設計 50) へ結び付ける</b>。
`ReferenceResolver` が名前を解き、`ProcedureBuilder` が文を組み立てる。

意味論そのものはランタイムが持つ (ARC-7)。ここが作るのは
<b>何をどれに対して行うか</b>だけであり、実際の移送や算術は行わない。

## 同じ名前は複数あってよい

COBOL は同じ名前を複数の場所に置ける。区別は `OF` / `IN` による修飾で行う。
<b>修飾は「直上」ではなく「外側のどこか」でよい</b> — 途中のレベルを飛ばして書ける。
したがって候補ごとに祖先をたどり、修飾子が外へ向かう順に現れるかを見る。

絞り込んで 1 個にならなければ誤りとする。どれか 1 個を選ぶと、
<b>書いた人の意図と違う項目を黙って使う</b>ことになる。移行作業でいちばん困る種類の誤りである。

## 添字は表の数だけ要る

`OCCURS` を持つ項目とその外側の表の数だけ添字が要る。<b>回数が 1 でも要る</b>ため、
「反復が 1 かどうか」では判別できない。`DataItem` は `OCCURS` 句の有無を別に持つ。

位置は次のように決まる。

```
位置 = 項目の変位 + Σ (添字 - 1) x その表の 1 回分の長さ
```

定数だけで書かれていれば翻訳時に決まる。データ項目で添字を書けば実行時に決まるため、
`constantOffset()` は空を返し、式のまま保つ。

範囲の外を指す定数の添字は誤りとして報告する。

## 添字と部分参照は括弧の中身で見分ける

`WS-T (2)` と `WS-A (4:3)` はどちらも括弧である。区別はコロンの有無だけであり、
文法では `subscripts? referenceModifier?` として並べてある。両方書くこともできる
(`WS-T (2) (1:2)`)。

<b>部分参照は添字の代わりにはならない</b>。表の項目には添字が要る。

長さを省いた `WS-A (4:)` は項目の終わりまでを指す。

## コロンは区切り文字である

部分参照を書くために、トークナイザの「つねに区切り文字」へ `:` を加えた。
PICTURE 文字列の切り出しは空白と区切りの句読点 (`.` `,` `;`) で終わるため、影響しない。
`EXEC SQL` の中のホスト変数 `:WS-NAME` は島の中にあるので、そもそも見えない。

## 段落の前に文を置ける

手続き部は段落を持たずに文だけを書ける。その場合の文は<b>名前のない段落</b>に入れる。
段落名は利用者定義語であり、文は予約語で始まるため、両者の区別は文法の先読みで付く。

## 分類の組み合わせは翻訳時に決める

`MOVE` は受取側の分類によって<b>ランタイムの別々の関数</b>を呼ぶ。呼ぶ先が決まって
いなければコードは生成できないので、`MoveRules` が翻訳時に決める。

| 受取側 | 呼ぶ先 |
| --- | --- |
| 数値 | `Move.numeric` — 小数点で位置を合わせる |
| 数字編集 | `Move.toNumericEdited` — 編集結果を書き込む |
| 英数字編集 | `Move.toAlphanumericEdited` — 挿入文字を置きながら詰める |
| それ以外 | `Move.alphanumeric` — バイト列として左右に詰める |

<b>英数字編集を「それ以外」に混ぜてはならない。</b>`PICTURE XX0XXBXXX` は 9 バイトで
あるが、送出データが入るのは `X` の 7 か所だけである。バイト列として 9 バイト詰めると
`0` と `B` が消えて、うしろが 2 文字ずれる。図形定数を広げる長さも、項目の長さでは
なく<b>文字位置の数</b>である。NC105A はこの違いを 12 通りで確かめている。

表を読むだけでは出てこない規則が 3 つある。

- <b>どちらかが集団項目なら、必ずバイト列の転記になる</b>。受取側が数字編集項目でも、
  送出側が集団項目なら編集は起きない。集団項目はバイト範囲そのものだからである
- <b>部分参照を書いた項目は英数字になる</b>。数字項目の一部を切り出しても、
  それは数値ではなくバイトの並びである
- <b>図形定数 `SPACE` の分類は英字である</b>。したがって数値項目へは移せない。
  `ZERO` だけが受取側に合わせて数値にも文字にもなる
- <b>符号付きの表示形式からは、符号を落として送る</b>。`PIC S9(5)` の `+60666` を
  `PIC X(5)` へ移すと `60666` である。ゾーンに埋め込んだ符号をそのまま送ると
  最後の桁が英字に見える。ただし<b>受取側が集団項目なら落とさない</b>。集団項目への
  転記はバイト範囲そのものへの写しであり、変換が一切起きないからである。SQ111A は
  符号の 1 バイトを `FILLER` で受け、うしろの 5 桁だけを数えている

書けない組み合わせ (英字項目を数値へ、数字編集項目を数値へ、小数を持つ数値を英数字へ) は
翻訳時に誤りとする。通してしまうと<b>実行時に見当違いの値になる</b>。

## 被演算子は文の実行前に 1 度だけ読む (FR-043)

受取項目が被演算子でもあることがある。

```
DIVIDE B INTO A GIVING R1 A ROUNDED R2 R3
```

2 つ目の受取項目が `A` を書き換える。そのあとで `A` を読み直すと、3 つ目からは
<b>別の計算</b>になる。規格は被演算子を文の実行前に評価すると決めている。

だから被演算子は<b>受取項目の並びに入る前に</b>局所変数へ取る。受取項目ごとに
畳み直すのは変わらない (除算の商の桁数が受取項目で決まるため) が、読むのは 1 度である。

`ON SIZE ERROR` を書いた形でも同じである。書き換えたあとの値で計算し直すと、
あふれない計算まであふれたことになる。NC172A / NC173A がこの形を 32 通り確かめている。

## 算術文は 1 つの形に落とす

`ADD` / `SUBTRACT` / `MULTIPLY` / `DIVIDE` の 4 つは、書き方こそ違うが
どれも「被演算子を左から畳んだ値を、受取項目へ入れるか、受取項目に対して演算する」形に落ちる。
文ごとの違いは<b>畳み方と、受取項目を巻き込むかどうか</b>だけである。

| 書き方 | 意味 | 畳む演算 | 受取項目を巻き込む演算 |
| --- | --- | --- | --- |
| `ADD A B TO C` | `C = C + (A + B)` | `ADD` | `ADD` |
| `ADD A B GIVING C` | `C = A + B` | `ADD` | なし |
| `SUBTRACT A B FROM C` | `C = C - (A + B)` | `ADD` | `SUBTRACT` |
| `SUBTRACT A FROM B GIVING C` | `C = B - A` | `SUBTRACT` | なし |
| `MULTIPLY A BY B` | `B = B * A` | `MULTIPLY` | `MULTIPLY` |
| `DIVIDE A INTO B` | `B = B / A` | `DIVIDE` | `DIVIDE` |
| `DIVIDE A BY B GIVING C` | `C = A / B` | `DIVIDE` | なし |

`SUBTRACT ... FROM` だけは<b>畳む演算と受取項目に対する演算が違う</b> — 引く側を
まず足し合わせ、その和を受取項目から引く。表を作らずに書くと、ここを取り違える。

`GIVING` の有無で `TO` / `FROM` / `BY` / `INTO` のあとの役割が変わる。文法では区別せず、
意味解析で振り分けている。

### 受取項目に何を書けるかは GIVING で決まる

表の右端の列が、そのまま受取項目の規則になる。

- <b>受取項目を巻き込む演算がある</b>形 (`GIVING` を書かない形) の受取項目は、
  計算に加わる。したがって<b>数値項目でなければならない</b>。編集した文字列を読み戻して
  足すことはできない
- <b>巻き込まない</b>形 (`GIVING`、`COMPUTE`、`DIVIDE ... REMAINDER`) の受取項目は
  書き込まれるだけである。したがって<b>数字編集項目でもよい</b>。転記の受取側に
  数字編集項目を書けるのと同じ理由である

丸めるのは<b>編集の前</b>である。編集は桁を絵に当てはめるだけの処理であり、どちら向きに
丸めるかを知らない。`DIVIDE ... GIVING 数字編集項目 REMAINDER ...` では、剰余を求めるのに
使う商も<b>編集項目の絵の小数桁</b>で切り捨てる。編集した結果の文字列から求めるのではない。

はじめは受取項目をすべて数値項目に限っていた。CCVS85 が 5 本でそこに止まり、
<b>自分の診断が数の一覧に並んで</b>気付いた (設計 25)。

## 関係条件の両辺は算術式である (FR-046)

`IF 1 + (TWO * 3) = 7` と書ける。被演算子 1 個では足りない。`EVALUATE` の目的語も
同じであり、`WHEN (WS-B + 1) * 2` と書ける。

ふつうの項目や定数は `Expression.Value` 1 つになるので、式にしても後段の作りは
<b>変わらない</b>。英数字の比較には式が来ない — 四則の相手は数値しかないので、
そちらは被演算子 1 個のままである。

## 条件は関係条件だけに落とす

条件の IR は関係条件と、その否定・連言・選言だけを持つ。
<b>符号条件と条件名 (88 レベル) は意味解析で関係条件へ展開する</b>。

- `IF WS-A IS POSITIVE` → `WS-A > 0`
- `88 WS-NO VALUE 'N' 'n'` に対する `IF WS-NO` → `(WS-FLAG = 'N') OR (WS-FLAG = 'n')`
- `88 WS-DIGIT VALUE '0' THRU '9'` → `(WS-FLAG >= '0') AND (WS-FLAG <= '9')`

どちらも「値を比べる」ことの言い換えでしかない。別の形として持つと、
後段 (コード生成) が同じ処理を 2 度書くことになる。

<b>添字は条件名のほうに書かれる。</b>`IF CN1 (1)` の `(1)` は条件名の添字ではなく、
条件名が付いている<b>親の表への添字</b>である。条件名は記憶域を持たないので名前では
引けず、展開するときに書かれた添字を親への参照へ移してやる必要がある。`SET 条件名 TO TRUE`
も同じである。移し忘れると、添字を取るはずの参照が添字なしのまま後段へ渡り、
コード生成で落ちる (CCVS85 の `IC208A` で見つかった)。

比較の仕方は<b>両辺の分類で決まる</b>。両辺が数値なら代数的な比較 (内部表現と桁数の
違いに影響されない)、そうでなければ照合順序による比較になる。
EBCDIC では英字が数字より小さいので、ASCII と結果が変わる。

### 数字項目を英数字として使うときは、格納した文字ではなく代数値である (FR-031, FR-060)

2 つの場面がある。<b>転記の送り出し側</b>になったときと、<b>英数字と比べる</b>とき
である。どちらも規格が「格納した文字ではなく代数値を使う」と決めている
(85 規格 5.9.4、6.15.2)。効くのは 2 つ。

**符号は落ちる。** `S9(3)` に `-123` を入れて `X(3)` へ移せば `"123"` である。
比べるときも同じで、`IF S9(3)項目 = "123"` は<b>真</b>になる。規格は比較の規則を
「数字の被演算子を同じ大きさの英数字項目へ移したものとして比べる」と書いている。

**`P` は 0 として数える。** `P` は桁を数えるが<b>記憶域は取らない</b>。

```
01  WRK PICTURE S9PP VALUE 200.
```

記憶域は 1 桁 (`2`) しか持たないが、表す値は 200 である。英数字へ移せば `"200"` に
なる。逆に `9PP` へ 123 を入れると 100 に丸められ、そこから英数字へ移せば `"100"` で
ある。CCVS85 では NC124A・NC114M・NC103A がここを見ている。

送り出し側と比較で<b>同じ道を通す</b>。片方だけ直すと、移した結果と比べた結果が
食い違う。

### 英数字の受取項目へ入れる数字定数は、綴りのまま入る (FR-061)

```
MOVE 0123456789 TO GRP-X.
```

`GRP-X` が群項目や英数字項目なら、これは<b>英数字転記</b>である。規格は数字定数を
そのとき「英数字定数として扱う」と決めている。したがって入るのは<b>原文に書かれた
綴り</b>であって、値ではない。

値に直してから書き戻すと `0123456789` が `123456789` になり、<b>1 桁ずれる</b>。
群への転記でずれると、そのあと `ADD CORRESPONDING` で桁を配ったときに<b>すべての
組がずれる</b>。CCVS85 では NC105A (3 件)、NC202A (4 件)、NC237A (3 件)、NC103A
(1 件) が、どれもこの 1 つで落ちていた。

そのため `LiteralValue.Number` は値のほかに<b>原文の綴り</b>を持つ。使い分けは
受取側で決まる。数字項目なら値 (小数点で位置が合う)、英数字項目なら綴りである。

### 照合順序は差し替えられる (FR-054)

既定の照合順序はコードページのバイト値そのものである。`SPECIAL-NAMES` の `ALPHABET` 句と
`OBJECT-COMPUTER` の `PROGRAM COLLATING SEQUENCE` で差し替えられる。

持ち方は<b>バイト値から位置への 256 個の表</b>である。比較はバイト値ではなく位置で行う。

```
ALPHABET DIGITS-FIRST IS "1" "2" "3".
```

と書けば `1` `2` `3` が 1・2・3 番目を取り、<b>書かれなかった文字はその後ろに
コードページの並びのまま</b>続く。`"A" ALSO "1"` と書けば 2 文字が同じ位置を持つので、
比べると<b>等しくなる</b>。

表は翻訳時に決まるので、生成したクラスの定数として持たせる。差し替えていないプログラムの
生成コードは<b>今までと同じ</b>である。既定と同じ並びなら表を持たせる意味がないので、
`NATIVE` と書いただけのプログラムも既定の比較を出す。

`FUNCTION CHAR` と `FUNCTION ORD` も、この並びの位置で答える。定義がそうなっており、
照合順序を差し替えれば両方の答えが変わる。

#### `HIGH-VALUE` と `LOW-VALUE` も動く

図形定数 `HIGH-VALUE` / `LOW-VALUE` は<b>バイト値 `0xFF` / `0x00` ではない</b>。規格は
「その並びで<b>いちばん後ろ / いちばん前に来る文字</b>」と決めている。差し替えていなければ
コードページの端がそのまま端なので `0xFF` / `0x00` になるが、差し替えれば別の文字になる。

```
ALPHABET COLLATING-SEQ-1 IS "F" "U" "N"
    ALSO HIGH-VALUE
    ALSO LOW-VALUE
    "Y".
```

`0xFF` と `0x00` を `ALSO` で `"N"` の位置へ動かしている。この並びで

- いちばん前に来るのは `"F"` — これが `LOW-VALUE` である
- いちばん後ろに来るのは<b>並べ残った文字のうち最大のもの</b> (`0xFE`) — これが `HIGH-VALUE`

したがって `N = HIGH-VALUE` は<b>偽</b>、`F = LOW-VALUE` は<b>真</b>になる。バイト値を
そのまま使っていると、`N` と `0xFF` が同じ位置なので前者が真になり、規格の定義が壊れる。
CCVS85 の NC219A がここを 5 件で見ている。

動くのは<b>`PROGRAM COLLATING SEQUENCE` を書いたとき</b>だけである。`ALPHABET` 句を
書いただけの並びは `SORT ... SEQUENCE` が引くためのものであって、図形定数は動かさない。

`NULL` は動かさない。「あて先を持たない」を表すものであり、照合順序とは関わらない。
`ALPHABET` 句の中に書いた `HIGH-VALUE` も動かさない — その並びを<b>これから決める</b>
ところなので、指しているのはコードページのバイト値である。

`SORT` と `MERGE` の鍵は<b>まだ差し替えられない</b>。差し替えたプログラムでそれらを
書くと誤りとして報告する。ここだけコードページの並びで並べると、同じプログラムの中で
場所によって順序が食い違うためである (暫定判断 P-042)。

## EVALUATE は IF の連なりへ展開する

`EVALUATE` は「主語と目的語を突き合わせ、最初に当たった枝を通る」ものであり、
<b>`IF` … `ELSE IF` … `ELSE` と同じ意味である</b>。別の形として持つと、
コード生成が同じ分岐を 2 度書くことになる。したがって意味解析で展開する。

突き合わせ方は主語で変わる。

| 主語 | 目的語 | 条件 |
| --- | --- | --- |
| `TRUE` / `FALSE` | 条件 | その条件 (`FALSE` なら否定) |
| 値 | 値 | 主語 = 目的語 |
| 値 | `値 THRU 値` | 主語 >= 下限 かつ 主語 <= 上限 |
| 何でも | `ANY` | つねに成り立つ |

`ALSO` で並べた主語と目的語は<b>連言</b>、同じ本体に並べた `WHEN` は<b>選言</b>になる。

### 名前だけの目的語は主語を見て読み替える

`WHEN WS-X` の `WS-X` は、主語が `TRUE` なら条件名、そうでなければ<b>比べる値</b>である。
文法だけでは見分けられないため、意味解析で読み替えている。

## CORRESPONDING は意味解析で展開する

`MOVE CORRESPONDING A TO B` は、名前の合う組の数だけの `MOVE` へ展開する
(`Statement.Sequence`)。展開をここで済ませておけば、コード生成は普通の `MOVE` を
出すだけでよい。分類の組み合わせの検査も 1 組ずつ同じ経路を通る。

組になる条件は `Correspondence` にある。名前が同じで `FILLER` でないこと、
<b>少なくとも一方が基本項目</b>であること、そして `OCCURS` や `REDEFINES` で
書かれていないことである。

両方が集団項目のときに組にせず下へ降りるのが要である。組にしてしまうと
<b>下位の対応付けが上位の一括転記に飲み込まれる</b>。`CORRESPONDING` は名前の合うものだけを
移すものであり、集団項目まるごとの転記とは違う。

`OCCURS` と `REDEFINES` を外すのは、<b>名前が同じでも指す範囲が違いうる</b>ためである。
副作用として、組になった項目の表の連なりは集団項目のものと同じになる。
集団項目に書かれた添字をそのまま引き継げるのはこのためである。

名前の合う項目が 1 つもなければ誤りとして報告する。何も移さない `MOVE` は書き間違いで
あり、黙って通すと「実行しても何も起きない」という最も気付きにくい形になる。
参照実装は警告に留めるため、この点は挙動が違う (暫定判断 P-030)。

### 算術文の CORRESPONDING は条件を分け合う

`ADD CORRESPONDING` と `SUBTRACT CORRESPONDING` は<b>数値の基本項目どうしの組だけ</b>を
選ぶ。ほかの組は計算しようがない。

`MOVE` と違って展開しきれないものが 1 つある。`ON SIZE ERROR` は組ごとではなく
<b>全体で 1 つ</b>であり、参照実装はすべての計算を終えてから条件文を 1 度だけ実行する。
組ごとに独立した算術文へ展開すると、あふれた組の数だけ条件文を通ってしまう。

そこで「1 つの `ON SIZE ERROR` を分け合う」という関係だけを `Statement.ArithmeticGroup`
で表す。中身は普通の `Statement.Arithmetic` であり、それぞれの条件は空である。

## GO TO の行き先は組み立ての最後に確かめる

段落はあとから書かれることもあるため、`GO TO` と `PERFORM` の行き先が実在するかは
<b>すべての段落を組み立てたあと</b>に見る。

このとき文の中に入れ子になっている文も辿る。`IF` や `PERFORM` の中だけでなく、
`ON SIZE ERROR` や `ON OVERFLOW` の中にも文が書ける。入れ子の数え上げを
`nestedStatements` の 1 か所へまとめたのは、新しい文を足すたびに走査の抜けが
できるのを防ぐためである。

## NEXT SENTENCE は CONTINUE ではない (FR-061)

どちらも「ここでは何もしない」に見えるが、<b>その後どこへ行くかが違う</b>。

| 文 | 意味 |
| --- | --- |
| `CONTINUE` | 何もしない。<b>次の文へ進む</b> |
| `NEXT SENTENCE` | いまの<b>文 (センテンス) の残りを飛ばして</b>、次の文の先頭へ移る |

```
IF WS-A = 1 NEXT SENTENCE ELSE MOVE 'E' TO WS-R END-IF
MOVE 'X' TO WS-S.
```

`END-IF` のあとにまだ同じ文が続いている。`CONTINUE` なら `MOVE 'X'` は通り、
`NEXT SENTENCE` なら通らない。<b>終止符の先へ飛ぶ</b>からである。

そのために、段落が持つのは<b>文の並び</b>である (`Statement.Sentence`)。区切りを IR に
残しているのは飛び先を決めるためだけであり、並べて出すぶんには区切りは要らない。
コード生成は文の終わりに印を打ち、`NEXT SENTENCE` はそこへ飛ぶ。

はじめは `NEXT SENTENCE` を<b>空の文の並び</b>として扱っていた。囲んでいる `IF` が
文の最後にあれば結果は同じなので、それで通っていた。<b>違いが出る形をテストに
書いていなかった</b>のが穴である。

## GO TO ... DEPENDING ON は飛び先表である (FR-063)

値が 1 なら 1 つ目、2 なら 2 つ目へ飛ぶ。<b>並びの外なら飛ばない</b>。誤りにはならず、
次の文へ進む。規格がそう決めている。

段落は「次にどこへ行くか」を返すメソッドとして生成されるので、飛び先表はそのまま
`tableswitch` になる。外れ道 (`default`) は<b>何も返さずに下へ抜ける</b>だけである。
飛ばないことが「何もしない」と一致するので、外れ道に特別な処理が要らない。

## 手続き名は数字だけでもよい (FR-061)

データ名と違うところである。`00 SECTION 00.` も `GO TO 50` も書ける。段分けの章は
たいていこの形で書かれる。

### 段分けで観測できる違いは ALTER だけである (FR-061)

段番号 (`SECTION 50.` の `50`) のうち 0〜49 は<b>常駐段</b>で、ふつうの章と振る舞いが
変わらない。50〜99 は<b>独立段</b>であり、別の段から制御が移るたびに初期状態へ戻る。

「初期状態」とは <b>`ALTER` で書き換えた飛び先が元へ戻る</b>ことである。記憶域の
中身は戻らない。だから観測できる違いは `ALTER` だけであり、<b>段を入れ替える必要は
ない</b>。記憶域はすべて常駐しており、入れ替えるものが無い。

戻す場所は段落へ入る 1 か所 (`dispatch`) である。段番号が変わって独立段へ入ったら、
その段の飛び先を書かれたままへ戻す。

<b>いま動いている段の番号は、`PERFORM` から戻るときに元へ戻す。</b>戻さないと、
同じ段落から独立段を 2 度呼んだときに 2 度目が「同じ段の中にいる」と見えて、初期状態
へ戻らない。`PERFORM` が返るということは<b>呼んだ側の段へ制御が戻る</b>ということで
あり、番号もそこへ戻る。

SG201A はこの形を 22 通り書いている。段の<b>中で</b> `ALTER` する形なので、
呼ぶ前に `ALTER` する形の試験では差が出ない。自分で書いた試験は呼ぶ前に書き換える
形だったので、緑のままだった。

## ALTER は飛び先の表を書き換える (FR-063)

`ALTER` が書き換えられるのは<b>`GO TO` だけを書いた段落</b>である。規格がそう限って
いるのは、行き先が 1 つでなければ書き換える先が定まらないからである。

その段落は、飛び先を定数で返すのではなく<b>表から読んで返す</b>。中身は `GO TO` 1 つ
だけなので、段落の本体をまるごとその形に置き換えてしまってよい。`ALTER` がするのは
<b>表を書き換えること</b>だけになる。

書き換えられる段落が 1 つも無ければ表そのものを出さない。ふつうのプログラムの生成
結果は今までと同じである。

## SEARCH は指標を初期化しない

`SEARCH` は表をいまの指標の位置から順に見る (要件 FR-066)。<b>指標を初期化しない</b>のが
要である。どこから見はじめるかは直前の `SET` が決める。すでに範囲の外なら一度も見ずに
`AT END` へ行く。

抜けたあとも指標はそのままなので、当たった位置から表を引ける。これが `SEARCH` の使い道の
半分である。

`VARYING` に<b>その表の指標名</b>を書いたなら、それが進める指標になる。ほかの項目を書いたなら、
指標と一緒に進む。同じ語で 2 つの意味があるので、意味解析で見分けている。

#### 表の中の表も探せる

`SEARCH` が動かすのは<b>いちばん内側の指標だけ</b>である。外側の何番目を見るかは、
外側の指標のいまの値が決める。`WHEN` の条件は書いた人が添字をぜんぶ書くので、
`SEARCH` 自身は外側を知らなくてよい。

```
SET WS-R TO 2
SET WS-I TO 1
SEARCH WS-E
    WHEN WS-KEY (WS-R, WS-I) = 'bbb' ...
```

`SEARCH ALL` は違う。2 分探索は<b>鍵の位置を自分で計算する</b>ので、外側の添字を
受け取る道が要る。まだ無いので、表の中の表に対する `SEARCH ALL` は断る。

## SEARCH ALL は向きを知らなければ書けない

`SEARCH ALL` は 2 分探索であり、逐次の `SEARCH` とは別物である。<b>指標を用意しなくてよい</b> —
探索そのものが範囲を狭めながら指標を決める。

`OCCURS ... ASCENDING KEY` / `DESCENDING KEY` が要るのは、<b>捨てる半分が逆になる</b>ためである。
昇順なら鍵が小さいときに奥半分を、降順なら手前半分を見る。

書ける条件は<b>鍵と値の等号だけ</b>である。大きいか小さいかで半分を捨てる仕組みだからであり、
任意の条件は書けない。鍵は書かれた順に、先頭から欠かさず照合しなければならない。
2 番目の鍵だけを指定しても、1 番目で並んでいる表は絞り込めない。

探索の指標以外で鍵を引いていないかも見ている。絞り込みにならない書き方を黙って通すと、
<b>当たらないことに気付けない</b>。

## ACCEPT の送出側はどれも符号なし整数の表示形式

`ACCEPT` は日付と時刻の特殊レジスタか、端末から読んだ 1 行を受け取る (要件 FR-060)。
どちらも<b>符号なし整数の表示形式のバイト列</b>として扱う。違うのは値を作る呼び出しだけで
あり、受け取る項目への詰め方は普通の転記と同じ規則で決まる。

| 指定 | 形 | 桁 |
| --- | --- | --- |
| `DATE` | YYMMDD | 6 |
| `DATE YYYYMMDD` | YYYYMMDD | 8 |
| `DAY` | YYDDD | 5 |
| `DAY YYYYDDD` | YYYYDDD | 7 |
| `DAY-OF-WEEK` | D (月曜が 1) | 1 |
| `TIME` | HHMMSSss | 8 |

英数字項目なら数字がそのまま並び、数値項目なら整数として読まれる。受取項目が短ければ
切り捨てられ、長ければ埋められる。<b>切り捨てられる側が違う</b>のがここの見どころで、
英数字なら左から詰めるので下位が落ち、数値なら小数点で合わせるので上位が落ちる。

### 呼び名は環境部が決める

`ACCEPT ... FROM 呼び名` と `DISPLAY ... UPON 呼び名` の行き先は、環境部の `SPECIAL-NAMES` で
機能名と結び付ける (要件 FR-135)。

読み取る側の呼び名を `DISPLAY` に書いた場合と、その逆は誤りとして報告する。
機能名の綴りには別名があるので (`SYSOUT` / `SYSLIST` / `SYSPRINT` など)、まとめて 1 つへ寄せている。

`SYSERR` へ出すものは<b>標準エラー出力へ回す</b>。捕まえる先が違うためであり、
標準出力と混ざらない。

### 時計は外から渡す

日付と時刻は実行のたびに変わる。そのままでは試験に書けないので、時計を
`ProgramContext` が持ち、外から差し替えられるようにした (要件 FR-204)。端末からの入力も同じ
理由で差し替えられる。

## INITIALIZE は書き込むバイト列を先に決める

`INITIALIZE` は配下の基本項目それぞれへの転記の集まりである (要件 FR-060)。素直に展開すると
<b>表の反復の数だけ転記が並ぶ</b>。`OCCURS 1000` の表なら 1000 個である。

入る値が翻訳時に決まるなら、書き込まれるバイト列も決まる。であればまとめて 1 回で書けばよい。
`InitializeImage` がその並びを組み立てる。

ただし<b>一括で塗り潰すことはできない</b>。`FILLER` は初期化の対象外であり
(`WITH FILLER` を書いた場合を除く)、`REDEFINES` で重ねた項目も対象外である。
書き込む場所を印で覚えておき、連続する部分ごとに分けて書く。印が付くのは基本項目の
バイトだけなので、`FILLER` の前後で自然に分かれる。

符号化はランタイムに任せる。ゼロを詰めるといっても、パック 10 進なら `000C`、数字編集項目なら
編集した結果になる。コンパイラが独自に組み立てると<b>実行時に同じ値を転記したときとずれる</b>。
実際に `Ops` を呼んで書かせている。

値が実行時に決まる形 (`REPLACING ... BY データ項目`) はこの手が使えないため、まだ書けない
(暫定判断 P-033)。

## SET 条件名 TO TRUE は MOVE である

条件名を成り立たせるとは、<b>親の項目にその条件名の値を入れる</b>ことである (要件 FR-068)。
値が複数書かれていれば最初のものを入れる。したがって普通の `MOVE` へ展開できる。

条件名を<b>読む</b>ほう (`IF WS-DONE`) はすでに関係条件へ展開してある。書くほうと読むほうが
同じ 88 レベルの値を見ているので、`SET` してから `IF` で見れば必ず成り立つ。

## CALL は「引数の並びを作って渡す」だけ

`CALL` が意味解析でやるのは、呼び先の名前と引数の並びを取り出すことだけである
(要件 FR-080)。呼び先を探すのも、作業場所を呼び出しをまたいで持ち続けるのも、
`GOBACK` を受け止めるのもランタイムの仕事である (方針 ARC-7)。

`BY REFERENCE` と `BY CONTENT` は<b>次の指定が現れるまで</b>後ろの引数すべてに効く。
引数ごとに書き直す必要はない、という参照実装の規則である。したがって意味解析では
指定を持ち回りながら畳み、引数ごとに「写しかどうか」へ落とす。

定数の引数は<b>つねに写し</b>になる。渡す先の領域を持たないためである。
図形定数は「項目いっぱいまで埋める」ものであり渡す先の長さが決まらないので、
書けば誤りとして報告する。

## STOP RUN と GOBACK はどこまで抜けるかが違う

どちらも例外で抜ける。段落が別々のメソッドとして生成される (設計 70) ため、単に戻るだけでは
呼び出し元の段落へ制御が返ってしまうからである。

違うのは<b>どこまで抜けるか</b>である。

| 文 | 例外 | 受け止める場所 |
| --- | --- | --- |
| `STOP RUN` | `ProgramStop` | いちばん外側 (`runFresh`) |
| `GOBACK` | `ProgramReturn` | 呼んだ側 (`Ops.call`) |

手続き部の終わりまで流れたときは<b>暗黙の `GOBACK`</b> である。副プログラムなら呼んだ側へ
戻り、主プログラムなら実行の終わりになる。主プログラムでは 2 つの違いが表に出ないので、
`runFresh` はどちらも受け止める。

## STOP RUN は例外で抜ける

段落は別々のメソッドとして生成される (設計 70) ため、単に戻るだけでは呼び出し元へ
制御が返ってしまう。`ProgramStop` を投げて<b>一気に抜ける</b>。誤りではないので、
積みの記録は取らない。

## 節は段落をまとめたものである (FR-061)

節見出しを<b>その名前の段落として置き</b>、どこからどこまでかを別に覚えておく。すると
`PERFORM 節名` は段落の範囲の実行になり、`GO TO 節名` はその先頭の段落への移動になる。
段落の番号付けと飛び先の仕組みをそのまま使える。

節を別の仕組みで表すと、飛び先が段落と節の 2 種類になる。飛び先が 1 種類なら、
飛び先の表も分岐も 1 つで済む。

## 宣言部分はいちばん前に置く (FR-105)

`DECLARATIVES` は手続き部の先頭にある。宣言節は<b>入出力で異常が起きたときにだけ</b>
呼ばれるものであり、通常の流れで通ってはならない。

段落の並びでも<b>いちばん前に置く</b>。通常の流れはそのうしろから始めれば、落ちて入って
しまうことがない。うしろに置くと、最後の通常段落から落ちて入る道ができてしまう。

`USE AFTER STANDARD ERROR PROCEDURE` は文ではない。その節が<b>いつ動くか</b>の宣言であり、
文の並びには入れない。受け持ちの決め方は 2 つあり、ファイル名で指定するか、開き方で指定する。
同じファイルや同じ開き方を 2 つの節が受け持てば、どちらが動くか決まらないので誤りとする。

## USE FOR DEBUGGING は「入る前に呼ばれる節」である (FR-193)

`USE FOR DEBUGGING` も宣言節であるが、動く条件が入出力の異常ではない。見張られた
手続きへ<b>制御が移るたび</b>に動く。呼ばれる側からは「誰が入ってきたか」が分からない
ので、<b>入る側に持たせる</b>。

段落ごとに、書かれた文とは<b>別の並び</b>としてデバッグの入り口を持つ。

```
MOVE SPACES        TO DEBUG-ITEM      … 使わない欄を空白にする
MOVE "段落名"      TO DEBUG-NAME
MOVE DBG-LINE$     TO DEBUG-LINE      … 移した側が控えた行番号
PERFORM 節の先頭 THRU 節の終わり
```

`DBG-LINE$` は意味解析が置く見えない項目である。`DEBUG-LINE` は<b>制御を移した文</b>の
行番号であって、入られた段落の行番号ではない。だから `PERFORM` / `GO TO` /
`GO TO ... DEPENDING ON` / `ALTER` を組み立てるときに、その文の行番号をここへ書いておく。
デバッグを書いていないプログラムには置き場が無く、命令はまったく出ない。

書かれた文と別に持つ理由は 2 つある。

- `ALTER` で書き換えられる段落かどうかは「`GO TO` だけを書いた段落か」で決まる。
  入り口を混ぜると、その判定が狂う
- 書き換えられる段落は本体を出さずに飛び先を返す。混ぜると入り口ごと落ちる

出すときは<b>飛び先を返す前に</b>入り口を出す。これで書き換えられる段落でも動く。

### ALTER も見張られる

規格は、見張られた手続き名が `ALTER` に書かれたときも節を動かすと決めている。動くのは
`ALTER` を実行した<b>直後</b>であり、`DEBUG-CONTENTS` には書き換え先の手続き名が入る。
`ALTER` の文を組み立てるときに、書き換えの数だけ入り口を後ろへ並べる。

CCVS85 の DB105A は、動いた順に `DEBUG-NAME` を積んで期待表と突き合わせる。`ALTER` の
分を出さないと 3 本が合わない。<b>入る道の数だけ入り口が要る</b>ことが、ここで数に出た。

### ファイル名も見張れる

`USE FOR DEBUGGING ON ファイル名` は、そのファイルを名指した入出力文
(`OPEN` `CLOSE` `READ` `WRITE` `REWRITE` `DELETE` `START`) の<b>直後</b>に節を動かす。
`DEBUG-NAME` にはファイルの名前が入る。

置き場所が 2 つの点で手続き名と違う。

- <b>`INVALID KEY` で飛ぶ前</b>に出す。飛んだ先で `DEBUG-ITEM` を読む試験がある
  (DB203A の `REWRITE-TEST-2`)
- <b>`READ` だけは成功した道にしか出さない。</b>`AT END` や `INVALID KEY` では
  レコードが渡っていないので、節は動かない (DB203A の `READ-TEST-2`)。ほかの文は
  成否によらず動く

`DEBUG-CONTENTS` には、成功した `READ` なら<b>読んだレコード</b>が入る。それ以外は
空白である。桁数は規格が決めていないので、<b>そこへ入りうるいちばん大きいもの</b>が
入る幅にする (暫定 P-080)。

`DEBUG-LINE` はその入出力文の行である。手続き名の見張りと違って「移した側」が別に
いるわけではないので、組み立てるときに<b>文字にして埋める</b>。

### DEBUG-CONTENTS は「なぜ来たか」である

手続き名の見張りでは、`DEBUG-CONTENTS` に<b>その手続きへ来た理由</b>が入る。
規格が文字まで決めている。

| 入り方 | `DEBUG-CONTENTS` |
| --- | --- |
| 実行の最初の手続き | `START PROGRAM` |
| 前の段落から落ちて入った | `FALL THROUGH` |
| `PERFORM` で入った | `PERFORM LOOP` |
| 宣言節 (`USE`) として呼ばれた | `USE PROCEDURE` |
| 整列の手続き | `SORT INPUT` / `SORT OUTPUT` / `MERGE OUTPUT` |
| `GO TO` で入った | 空白 |

来た理由を知っているのは<b>移す側</b>だけである。`DEBUG-LINE` と同じで、意味解析が
置いた見えない項目 `DBG-WHY$` (13 桁) へ移す側が控える。落ち込みは `performRange` が、
実行の最初は `run` が、宣言節と整列の手続きはそれを呼ぶところが控える。

`PERFORM LOOP` は<b>繰り返しの 2 周目から</b>ではない。1 周目からそうである。
`PERFORM 段落名` と 1 行だけ書いても `PERFORM LOOP` になる。DB101A の
`SIMPLE-PERFORM-TEST` がそこだけを見ている。

<b>書き換えられる段落は本体を出さない</b>ので、その中の `GO TO` も出ない。行番号と
理由をそこで控え損ねると、1 つ前の落ち込みの理由が残る。飛び先を返す前に控える。

### 切り替えは 2 つある

`WITH DEBUGGING MODE` は<b>翻訳のとき</b>の切り替えである。書かなければ宣言節も
7 桁目の `D` の行も注釈と同じになる。

もう 1 つ、<b>実行のとき</b>の切り替えがある。切ると `D` の行は動いたまま
<b>デバッグの節だけが動かなくなる</b>。参照実装ではジョブの指定で切る。

節を動かす文はまとめて `Statement.DebugEntry` に包んであり、生成した符号は
その手前で実行時の切り替えを見る。包む場所が 1 つなので、手続き名でもファイル名でも
`ALTER` でも同じように止まる。デバッグを書いていないプログラムには
<b>命令がまったく出ない</b>。

CCVS85 の DB102A がこの形である。自分の説明文で「流す前にジョブで切り替えを
切っておくこと」と書いている。切らずに流すと、道具のほうが処理系の失敗を作る。

### 一意名も見張れる

`USE FOR DEBUGGING ON 一意名` は、その名前を書いた文のあとで節を動かす。
`ALL REFERENCES OF` を書くかどうかで<b>どの文が数に入るか</b>が変わる。

| 書き方 | 動く文 |
| --- | --- |
| `ALL REFERENCES OF 一意名` | その名前を書いた文すべて |
| `一意名` | その名前の<b>中身が書き換わる</b>文だけ |

どの名前を書いたかを知っているのは<b>名前を引き当てるところ</b>だけなので、
`ReferenceResolver` に控え帳を持たせ、文 1 つを組み立てる間に引き当てた名前を集める。
入れ子の文は自分の控え帳を積むので、`IF` の条件はその `IF` のものになる。

数え方に落とし穴が 4 つあった。どれも CCVS85 が教えてくれた。

- <b>指した回数ではなく、指された名前の数だけ動く。</b>
  `ADD ID-2 ID-2 ID-2 ID-2 TO ID-3` で動くのは 1 度である
- <b>繰り返す `PERFORM` は別</b>である。`VARYING` の段は「変える項目を置くたび」と
  「条件を見るたび」の<b>両方</b>で動く。`VARYING ID-1 ... UNTIL ID-1 > 5` は
  6 + 6 = 12 度である。`AFTER` の内側は 31 度になる
- <b>`PERFORM` の `VARYING` / `UNTIL` に書いた名前は、条件に書いただけでも動く。</b>
  ほかの文では「書き換わる側」に限られるのに、ここだけ違う
- <b>制御を移す文は移す前に動かす。</b>`GO TO ... DEPENDING ON` の飛び先で
  `DEBUG-ITEM` を読む試験がある。入出力の文も同じで、`INVALID KEY` の枝へ飛ぶ前に出す

`DEBUG-NAME` には<b>書いたとおりの名前</b>が入る。修飾を書けば `WS-X OF G-TWO` である。
添字を書けば `DEBUG-SUB-1` から `-3` に入る。`DEBUG-CONTENTS` は<b>文が終わったあとの
中身</b>である。

### デバッグでない宣言節は見張れる

`USE AFTER STANDARD ERROR PROCEDURE` の節は手続き名で見張れる。見張れないのは
<b>デバッグの節そのもの</b>だけである。見張ると際限なく自分を呼ぶことになる。

### 章へ入ると 2 度動く

節見出しはその名前の段落として置いてある。章へ入ると、章の名前で 1 度、最初の段落の
名前で 1 度、あわせて 2 度動く。これは規格の求めるとおりである。

## いま組み立てられる文

`MOVE`、算術文 4 つ (`DIVIDE ... REMAINDER` を含む)、`COMPUTE`、`IF`、`EVALUATE`、
`PERFORM` (`TIMES` / `UNTIL` / `VARYING` … `AFTER` …)、`GO TO`、`DISPLAY`、`INSPECT`、
`STRING`、`UNSTRING`、`INITIALIZE`、`SET`、`SEARCH` / `SEARCH ALL`、`ACCEPT`、
`CALL` / `CANCEL`、
`STOP RUN` / `GOBACK`、`CONTINUE` / `EXIT` である。
`MOVE` / `ADD` / `SUBTRACT` には `CORRESPONDING` を書ける。
算術文には `ON SIZE ERROR` / `NOT ON SIZE ERROR` を書ける。
べき乗 (`**`) は文法が受け付けるが、まだ生成できないと報告する (暫定判断 P-028)。

## COMPUTE だけが式を取る

ほかの算術文は被演算子の並びであり、畳み方が文の種類で決まっている。`COMPUTE` だけが
木を取る。違いはそこだけなので、受取項目と `ON SIZE ERROR` は `Statement.Arithmetic` の
ものをそのまま使う。

式の木には<b>桁数を持たせない</b>。中間結果の桁数は文全体から決まる (要件 5.5.1) ため、
節ごとに持つと決めた場所が分かれる。`IntermediateDigits` が文を 1 度見て `dmax` を決め、
節を渡されるたびに桁数を答える形にした。

優先順位と結合は文法が決めている。ANTLR の左再帰では<b>先に書いた選択肢ほど優先順位が
高い</b>ので、単項符号・べき乗・乗除・加減の順に並べてある。

## 組み込み関数は被演算子である (FR-070)

`FUNCTION LENGTH(WS-X)` は<b>被演算子の 1 つ</b>として持つ (`Operand.Function`)。
参照や定数と並べる。

そうしたのは、関数が書ける場所が<b>被演算子の書ける場所そのもの</b>だからである。
算術式にも、条件にも、`MOVE` の送出側にも、`DISPLAY` にも書ける。被演算子として
持てば、<b>送出側を作る道 1 本</b>を直すだけで全部に効く。文ごとに関数を扱う枝を
足していく形にすると、書き忘れたところだけが通らない。

関数は「数値を返すもの」と「バイト列を返すもの」に分かれる。どちらを返すかは
関数ごとに決まっているので、`planSourceDecimal` と `planSourceBytes` のどちらへ
落ちるかも決まる。バイト列を返すものの<b>長さは翻訳時に決まる</b> — `UPPER-CASE` と
`REVERSE` は引数と同じ長さ、`CHAR` は 1 である。決まらなければ転記も比較も組み立て
られない。

### ALL と書いた添字は翻訳時に広げる

`FUNCTION SUM(表 (ALL))` の `ALL` は「その次元のすべての反復」である。組み込み関数の
引数にだけ書ける。<b>翻訳時に反復の数だけ引数へ広げる</b>ので、この形が後段へ届く
ことはない。次元が 2 つ以上あれば組み合わせすべてになる。

`OCCURS ... DEPENDING ON` の表では、規格が言う「すべての反復」は実行時の個数である。
こちらは宣言した最大で広げる (暫定判断 P-068)。

### MAX と MIN は引数を見て形が決まる

引数がぜんぶ数値なら数値を返し、ぜんぶ英数字なら<b>引数そのもの</b>を返す。
比べ方も照合順序になる。したがって戻り値の分類は関数ではなく<b>呼び出しのほう</b>が
持つ (`Operand.Function.returns`)。規格は引数の種別をそろえることを求めているので、
混ぜて書かれたら断る。

EBCDIC では英小文字が英大文字より小さいので、`FUNCTION MAX("R", "I", "a")` は
`"R"` になる。ASCII なら `"a"` である。<b>照合順序を差し替えれば答えが変わる。</b>

### 引数を分けているのは空白である

引数の区切りのコンマは飾りであり、字句の段で落としている。分けているのは<b>空白の
ほう</b>である。COBOL では 2 項の演算子は前後に空白を置き、単項の符号は後ろに空白を
置かない。したがって字句の切れ目に差が残る。

| 書き方 | 字句 | 引数 |
| --- | --- | --- |
| `FUNCTION MAX(11 - 5)` | `11` `-` `5` | 1 個 (値は 6) |
| `FUNCTION MAX(11, -5)` | `11` `-5` | 2 個 (値は 11) |

コンマを落としても区別が残るのは、`-5` が<b>1 つの語</b>として切り出されるからである。

ただし 1 か所だけ、コンマを落とすと<b>意味が変わる</b>ところがある。

| 書き方 | 意味 |
| --- | --- |
| `FUNCTION MAX(A * B, (C + 1) / 2)` | 引数 2 個 |
| `FUNCTION MAX(A * B  (C + 1) / 2)` | `B` を `(C + 1)` で添字付けした 1 個 |

データ名のうしろに括弧が来れば添字である。分けているのはコンマだけなので、
<b>次が開き括弧のコンマは落とさない</b>ことにした。それ以外の場所に `, (` と書ける
ところは COBOL に無いので、残しても他の読みには効かない。

### 日付は 1601 年から数える

`INTEGER-OF-DATE` と `DATE-OF-INTEGER` が使う通日は、<b>1601 年 1 月 1 日を 1</b> として
数える。規格がそう決めている。暦はグレゴリオ暦であり、暦に無い日 (2 月 31 日など) と
1601 年より前は<b>0 を返す</b>。誤りとして止めるのではない。規格がそう決めている。

`CURRENT-DATE` は 21 文字を返す。`YYYYMMDDhhmmsscc` に、協定世界時からのずれ 5 文字
(`±hhmm`) が続く。時計は `ProgramContext` が持っているので、試験では固定できる
(要件 FR-204)。`WHEN-COMPILED` は<b>翻訳時に決まる</b>ので、生成したクラスの定数として
持たせる。実行時に読むものは何も無い。

### どこまで合っていればよいかは、検査スイートが決めている

`SQRT` や `SIN` の精度は<b>規格が処理系に任せている</b>。ではどこまで合っていれば
よいのか。適合性の検査スイート (NIST CCVS85) が答えを持っていた。

```
EVALUATE FUNCTION ANNUITY(2.9, 4)
WHEN  2.91252 THRU  2.91264   PERFORM PASS
```

<b>範囲で判定している。</b>求められているのは有効数字 6 桁ほどであり、等号ではない。

そこで `double` で計算し、結果を<b>有効数字 15 桁</b>へ丸めて返す。15 桁は `double` が
確かに持てる桁数であり、それより下は 2 進から 10 進へ写したときの屑である。屑を
そのまま返さないことが、要件 FR-071 の言う「`Math` の結果をそのまま用いない」である。
`SQRT` だけは `BigDecimal.sqrt` で 10 進のまま正しく丸められる。

値域の外の引数 (`SQRT(-1)`、`LOG(0)`、`ASIN(2)`) は 0 を返す。詳しくは暫定判断 P-065。

はじめは<b>これらを実装しないと決めていた</b>。「COBOL の資産は計算結果を等号で比べる」
という思い込みを根拠にしていたからである。<b>規格が何を求めているかを、規格ではなく
自分の思い込みから決めていた。</b>

## EXIT PROGRAM は GOBACK と同じではない (FR-067)

どちらも「呼んだ側へ戻る」だが、<b>主プログラムで書いたときの意味が違う</b>。

| 文 | 呼ばれているとき | 主プログラムのとき |
| --- | --- | --- |
| `GOBACK` | 呼んだ側へ戻る | 実行を終える |
| `EXIT PROGRAM` | 呼んだ側へ戻る | <b>何もしない</b>。次の文へ進む |

同じプログラムが呼ばれることも主として動くこともある。したがって<b>どちらの意味に
なるかは実行時にしか分からない</b>。翻訳時に決められない。

実行時に見るのは<b>積まれているプログラムの数</b>である。`CALL` は積むので、呼ばれて
いれば 2 つ以上ある。1 つなら主である。

`EXIT` だけなら何もしない。`PERFORM ... THRU` の範囲の終わりに置く段落のためにある
別の文であり、`EXIT PROGRAM` とは語が続くかどうかで分かれる。

2. 指標名を本物の指標として持つ形 (暫定判断 P-035)。

4. 66 レベルの `RENAMES` と入れ子プログラム。
