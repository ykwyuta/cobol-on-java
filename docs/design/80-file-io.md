# 設計文書 80: ファイル入出力

| 項目 | 内容 |
| --- | --- |
| 対応要件 | FR-100〜FR-115、要件定義書 6.1〜6.2 節 |
| ステータス | 第 4 段まで実装済 |

## 何を決めるか

ファイル入出力は<b>要件の分量がいちばん大きい</b>領域である。編成が 4 つ、アクセス様式が 3 つ、
入出力文が 7 つ、ファイル状態コードが 25 種類以上ある。まとめて実装することはできないので、
段を分ける。

この文書は全体の形を決め、段ごとに何を実装したかを記録する。

## 段

| 段 | 範囲 |
| --- | --- |
| 第 1 段 | 順編成 (固定長) と行順編成。`OPEN` / `READ` / `WRITE` / `CLOSE`、`FILE STATUS` |
| 第 2 段 | 可変長レコード (RDW)、`REWRITE`、`OPEN I-O`、`EXTEND`、`SELECT OPTIONAL` |
| 第 3 段 | 相対編成と索引編成、`START`、`READ NEXT`、`DELETE`、`ACCESS MODE` |
| 第 4 段 | `DECLARATIVES` の `USE AFTER STANDARD ERROR PROCEDURE`、`SORT` / `MERGE` |

## 生バイトで持つ (FR-110)

既定の格納形式は<b>EBCDIC の生バイト</b>である。ホストのデータセットを移行したバイト列を、
変換せずそのまま保持する。

変換して保存すると L3 互換が<b>原理的に成立しない</b>。往復変換で情報が欠落し、照合順序が
食い違い、パック 10 進などのバイナリ項目が壊れる。データセットの中身は「文字」ではなく
「バイト」だからである。

### 属性はサイドカーに持つ

レコード様式 (RECFM)、レコード長 (LRECL)、コードページは<b>データ本体とは別のファイル</b>に
持つ。ホストではデータセットのラベルにある情報であり、バイト列の中にはない。

```
CUSTOMER.DAT       ← 生バイト
CUSTOMER.DAT.meta  ← recfm=F, lrecl=80, codepage=IBM-1047
```

サイドカーがなければ既定 (固定長 80 バイト、IBM-1047) を使う。

## レコードの切り出し方は様式で決まる

| 様式 | 切り出し方 |
| --- | --- |
| 固定長 (F/FB) | LRECL バイトずつ。ファイルの長さが割り切れなければ最後は短い |
| 可変長 (V/VB) | 4 バイトの RDW が先頭に付く。最初の 2 バイトが RDW を含む長さ |
| 行順 | 改行までが 1 レコード。書くときは<b>末尾の空白を落とす</b> |

行順編成の改行は<b>コードページの改行</b>である。EBCDIC なら `0x15` であり、
`0x0A` ではない。生バイトで持つと決めた以上、区切りもそのコードページのものになる。

## ファイル状態コードは文ごとに立てる (FR-103)

入出力文のたびに 2 バイトのコードを `FILE STATUS` の項目へ書き込む。

| コード | 意味 |
| --- | --- |
| `00` | 成功 |
| `04` | レコード長が合わない (読んだ長さが記述と違う、書く長さが範囲外) |
| `05` | `OPTIONAL` のファイルがなかったので空として開いた |
| `10` | ファイルの終わり (`AT END`) |
| `35` | 開こうとしたファイルがない (`OUTPUT` 以外) |
| `37` | 開き方が編成に合わない |
| `41` | すでに開いている |
| `42` | 開いていない |
| `43` | 読んでいないのに書き換えようとした |
| `44` | 固定長で長さの違うレコードへ書き換えようとした |
| `46` | 読める位置にない (`AT END` のあとの `READ`) |
| `47` | 読み取りが許されていない開き方である |
| `48` | 書き込みが許されていない開き方である |
| `49` | 書き換えが許されていない開き方である (`REWRITE` は `I-O` だけ) |

`FILE STATUS` を書いていないファイルで異常が起きたら<b>異常終了する</b> (要件 FR-104)。
黙って続けると、読めていないデータで処理が進む。

## 記憶域の 4 つ目

`FD` のレコード領域は、作業場所とも連絡節とも違う<b>4 つ目の記憶域</b>である。
`READ` が書き込み、`WRITE` が読み出す。

```
作業場所:      記憶域 = 自分のもの          位置 = 変位
連絡節:        記憶域 = 引数[k] のもの      位置 = 引数[k] の位置 + 変位
特殊レジスタ:  記憶域 = 実行時の入口のもの  位置 = 決まった変位
ファイル:      記憶域 = 開いたファイルのもの 位置 = 変位
```

同じ `FD` に複数の 01 レベルを書けば、それらは<b>同じ場所に重なる</b>。
`REDEFINES` と同じであり、レコードの形が 2 つ以上ある場合に使う。

いまの段では、レコード領域を<b>作業場所の一部として割り付ける</b>。ファイルごとに
別の記憶域を持たせるのは、入出力バッファを別に持つ形へ移すときに行う。
この暫定の扱いは P-037 に記録した。

重なりのほうは先に入れた。同じ `FD` の 01 レベルは<b>同じ位置から始まり</b>、
その `FD` が占める長さは<b>いちばん長いレコード記述</b>で決まる。
`WRITE` に書くのはレコード名であってファイル名ではないので、どのファイルへ書くのかは
「そのレコードがどの `FD` の下にあるか」で決まる。項目にファイル名を持たせて引いている。

## `READ` は 3 つに分かれる

状態コードで分岐する。

| 状態 | 通る道 |
| --- | --- |
| 成功 (`0` で始まる) | `INTO` の転記 → `NOT AT END` |
| ファイルの終わり (`10`) | `AT END` |
| それ以外の誤り | <b>どちらも通らない</b> |

誤りのときにレコード領域の中身は決まっていない。読めたことにして先へ進めるわけには
いかないので、`INTO` の転記も起こさない。`FILE STATUS` を書いていなければ、そもそも
ここへ来る前に異常終了する。

`INTO` と `FROM` は<b>ただの転記</b>である。読み込みはレコード領域までで、そこから先は
`MOVE` と変わらない。意味解析で `MOVE` へ展開しておけば、分類の検査も編集も
そのまま効く。

## 可変長では長さそのものがデータである (FR-106)

`RECORD IS VARYING IN SIZE FROM n TO m DEPENDING ON 項目`。書くときは項目の値が
レコード長になり、読んだときは実際の長さが項目へ入る。

**受取領域の余りには触らない**。規格上そこの中身は決まっていないので、`READ` は読めた分だけを
入れる。固定長と行順は空白で埋めるが、可変長は埋めない。短いレコードを読んだあとに前の
レコードの残りが見えるのは、参照実装でもそうなる。

**範囲外の長さは収める**。`DEPENDING ON` の項目に上限を超える値が入っていることはありうる。
そのまま使えば<b>レコード領域の外を読み書きする</b>ので、範囲へ収めたうえで `04` を立てる。
上限そのものがレコード領域より長い指定は、翻訳時に誤りとして報告する。読めば必ずはみ出すからである。

`DEPENDING ON` を書かなければ、`WRITE` に書いたレコード記述の長さがそのままレコード長になる。
1 つの `FD` に長さの違うレコード記述を並べる書き方がこれで効く。

## 行送りは空行で表す (FR-102、暫定判断 P-063)

`WRITE ... AFTER ADVANCING 2 LINES` は「2 行送ってから印字する」である。2 行送っても
文字が乗るのは<b>最後の 1 行だけ</b>なので、間に空くのは 1 行である。`BEFORE` なら
先に書いてから送る。

```
WRITE REC AFTER  ADVANCING 2 LINES.   → 空行, REC
WRITE REC BEFORE ADVANCING 3 LINES.   → REC, 空行, 空行
```

空行は様式で決まる。行の並びなら<b>長さ 0</b> が空行であり、決まった長さのレコードなら
空白で埋める。行の切れ目を決めているのはデータセットの様式だからである。

ホストの印字ファイルはレコードの先頭に<b>紙送りの制御文字</b>を持つ。その形を真似れば
バイト列まで合うが、桁の取り方を実機で確かめていない。確かめないまま 1 バイト増やすと
<b>レコードの長さが全部ずれる</b>ので、いまは空行で表すほうを採った (暫定判断 P-063)。

行送りは印字するファイルのものである。鍵で引くファイルには行がないので、書けば誤りと
して報告する。

## REWRITE は直前に読んだレコードを書き換える

書き換える相手は<b>文に書かれていない</b>。「いま指しているレコード」であり、それを覚えているのは
開いているファイルのほうである。したがって

- 読んでいなければ `43`。読まなければ何も指していない
- 書き換えたあとにもう一度書き換えても `43`。指していたものは書き換えで解ける
- 開き方が `I-O` でなければ `49`。読みながら書き戻す使い方だけが意味を持つ
- 固定長で長さが違えば `44`。あとのレコードの位置がずれてしまう

可変長なら長さを変えてよい。RDW を書き直せば済むからである。

## ないファイルを開く

`OUTPUT` 以外は<b>ファイルがあることを前提とする</b>。ないなら `35` である。
`SELECT OPTIONAL` と書いてあるときだけ、空のファイルとして開いて `05` を返す。

黙って空のファイルを作ってはならない。入力を取り違えたジョブが「0 件処理した」と言って
正常終了してしまう。

### 区分データセットのメンバだけは状態コードにならない (FR-113)

無いメンバは `35` ではなく `S013` である (設計 90 を見よ)。`35` は「この `OPEN` 文が失敗
した」であり、プログラムは `FILE STATUS` で受け止めて先へ進める。メンバが無いのは
<b>データセットが無いことではない</b> — ライブラリはあり、割当ては通っている。受け止め
手のある誤りとして渡すと、綴りを間違えたメンバ名で「0 件処理した」と言って正常終了して
しまう。

そのため<b>開くという操作そのものが成り立たなかった</b>ものとして扱い、プログラムへ制御を
戻さない。区分データセットをメンバを言わずに開こうとしたときも同じである。

これがメンバだと知っているのは<b>割当てだけ</b>である。パスを見ても分からない — メンバは
ディレクトリの下のファイルだが、順編成のデータセットも置き場の下のファイルだからである。
だから DD 名の対応表がそれを覚えて、開くときに渡す。書くつもり (`OUTPUT` / `EXTEND`) の
ときは無くてよい。そこで作るからである。

区分データセットそのものかどうかはパスから分かる。ディレクトリだからである。したがって
そちらの検査には対応表が要らない。

編成は問わない。相対編成のファイルをメンバへ割り当てても、無ければ同じく `S013` である。

### メンバの一覧は 1 か所で決める (FR-053, FR-113)

翻訳された資産はメンバを 1 つ名指して開くので一覧を要らないが、ジョブの道具 (`IEBCOPY`、
`LISTDS`、`IDCAMS LISTCAT`) は要る。決めるのは<b>どこまでがメンバか</b>と<b>どういう順に
並ぶか</b>の 2 つであり、どちらも `PartitionedDataSet` に置く。

メンバ名の決まり (8 文字まで、英大文字と数字と `@ # $`、先頭は数字でない) が、ライブラリの
下に並ぶファイルのどれがメンバかを決める。`.` は入らないので、覚え書きのサイドカー
(`PAYROLL.meta`) はメンバになりえない。

並びは<b>コードページのバイト順</b>である。EBCDIC では英字が数字より前に来るので、`PAYA`
が `PAY1` より先である。Java の `String` の順は逆であり、そちらで並べるとライブラリを
丸ごと写したジョブの出力が実機と別のバイト列になる。詳しくは設計 90 を見よ。

## 相対編成は番号が住所である (FR-100, FR-101)

レコードを<b>番号で引く</b>。1 起点の相対レコード番号 (RRN) が住所であり、中身とは関わりが
ない。ホストの VSAM RRDS にあたる。

番号が住所である以上、<b>消してもあとのレコードは動かない</b>。3 番を消しても 4 番は 4 番の
ままである。したがって消したところは<b>空きスロット</b>として残り、順次読みはそこを飛ばす。

空きスロットが<b>バイト列から分からない</b>のが難しいところである。消したスロットと空白だけの
レコードは同じバイトになる。VSAM は制御情報として持っており、レコードのバイト列の外にある。
ここではサイドカーの `empty=` 行に持つ (暫定判断 P-039)。データ本体は移行したままの
固定長スロットの並びである。

| 状態 | 意味 |
| --- | --- |
| `22` | すでに使われている番号へ書こうとした |
| `23` | その番号にレコードがない |
| `24` | 書ける範囲の外である (番号が 1 より小さい) |

## 索引編成は鍵が中身の一部である (FR-100, FR-101)

レコードを<b>中身の一部で引く</b>。鍵はレコードの中にあり、住所ではなく<b>持ち物</b>である。
ホストの VSAM KSDS にあたる。

鍵が中にある以上、<b>索引はデータから導ける</b>。したがってファイルに持つのはレコードだけで、
開いたときに組み直す。索引を別に保存すると、本体と食い違う余地ができる。

鍵の場所はファイルではなく<b>プログラムが決める</b>。`RECORD KEY` に書いた項目の位置と長さで
あり、開くときに渡す。だから鍵はその `FD` のレコードの中になければならない。外にある項目を
鍵と言われても、書き出したバイト列のどこを見ればよいのか決まらない。

書き出す並びは主鍵の順である。移行してきた KSDS の抽出も鍵順なので、読み書きを往復しても
並びが変わらない。

| 状態 | 意味 |
| --- | --- |
| `21` | 主鍵の昇順でない (`ACCESS SEQUENTIAL` の `WRITE`)、または書き換えで主鍵を変えた |
| `22` | 同じ主鍵、または `DUPLICATES` を書いていない副鍵が重なった |
| `23` | その鍵のレコードがない |

### 副鍵は同じ値を許せる

`ALTERNATE RECORD KEY IS 項目 WITH DUPLICATES` と書けば、同じ副鍵のレコードを複数持てる。
`READ ... KEY IS 副鍵` はそのうち<b>主鍵の小さいもの</b>を返し、そのあとの `READ NEXT` が
残りをたどる。副鍵を読み切れば次の副鍵へ移る。

`DUPLICATES` を書いていない副鍵は、主鍵と同じく 1 つの値に 1 つのレコードである。
2 つ目を書こうとすれば `22` になる。

### 主鍵は書き換えられない

`REWRITE` でレコードの主鍵を変えることはできない。書き換えではなく<b>別のレコード</b>に
なってしまうからである。変えようとすれば `21` である。

## START は読まずに位置を決める (FR-101)

`START` は<b>レコードを読まない</b>。指定した鍵との関係を満たす最初のレコードへ位置を合わせ、
そのあとの順次読み出しがそこから始まる。満たすレコードがなければ `23` である。

関係は 5 つある。`=`、`>`、`>=`、`<`、`<=`。小さいほうを探す関係 (`<` と `<=`) では、
条件を満たす<b>最後の</b>レコードが位置になる。そこから順に読めば、指定した鍵の手前までを
たどれるからである。

## アクセス様式が文の意味を決める (FR-101)

同じ `READ` でも、`ACCESS MODE` によって意味が変わる。

| 様式 | `READ` | `WRITE` | `REWRITE` / `DELETE` |
| --- | --- | --- | --- |
| `SEQUENTIAL` | 次のレコード | 次のスロットへ / 昇順に追加 | 直前に読んだもの |
| `RANDOM` | 鍵で引く | 鍵の場所へ | 鍵で引いたもの |
| `DYNAMIC` | `NEXT` なら次、なければ鍵で引く | 鍵の場所へ | 鍵で引いたもの |

相対編成では鍵は `RELATIVE KEY` の項目にあり、索引編成では<b>レコードの中</b>にある。
したがって索引編成の `WRITE` と `REWRITE` は、順アクセスと乱アクセスで渡すものが変わらない。
違うのは主鍵の昇順を求めるかどうかだけである。

翻訳時に様式が分かっているので、<b>どちらを呼ぶかは生成時に決まる</b>。実行時に分岐しない。

## 属性は開くたびに読み直す

サイドカーは<b>閉じるたびに書き換わる</b>。相対編成の空きスロットの一覧がそうである。
1 度読んだきりにすると、同じ実行の中で書いてから開き直したときに古い一覧を使ってしまい、
書いていないスロットが空白のレコードとして見える。

したがって開くたびに読み直す。<b>ディスクにあるバイト列を切り分けた属性が正</b>である。
空きスロットの一覧だけは白紙に戻してから読む。書かれていなければ空きがないという意味であり、
前に覚えていたものを引き継いではならない。

## 宣言は 2 か所に分かれている

`SELECT` (環境部) と `FD` (データ部) の両方が要る。<b>どちらが欠けてもファイルは
使えない</b> — 場所を知らなければ開けず、レコードの形を知らなければ読み書きできない。
片方だけ書けば誤りとして報告する。

レコード様式は `SELECT` の `ORGANIZATION` と `RECORDING MODE`、`FD` の `RECORDING MODE`
から決まる。あとに読む `FD` 側が勝つ。

新しく作るファイルにはサイドカーがない。そのとき<b>レコードの切れ目を決められるのは
プログラムの宣言だけ</b>である。逆にサイドカーがあればそちらが勝つ。そこに置かれている
バイト列を実際に切り分けたのはその属性であり、宣言と食い違っていてもバイト列の事実は
変わらない。

## DD 名でファイルを探す

`SELECT ... ASSIGN TO 名前` の名前は<b>DD 名</b>であり、ファイルの場所そのものではない。
ホストでは JCL が DD 名と実際のデータセットを結び付ける。

実行時の入口 (`ProgramContext`) が対応表を持ち、書かれていなければ既定のディレクトリの
下から同じ名前で探す。ジョブ実行 ([設計 90](90-job.md)) が JCL からこの表を埋める。

### ジョブがプログラムの開き方を覆すのは 1 か所だけである

`DISP=MOD` と書かれた DD は、プログラムが `OPEN OUTPUT` と書いていても<b>末尾への
書き足し</b> (`EXTEND`) になる。対応表がその DD を覚えており、`OPEN` が読み替える。

覆るのはここだけである。開き方はプログラムが決めるもの、という原則を崩すと、どちらが
勝つのか場所によって変わってしまう。`DISP=MOD` だけを例外にしたのは、同じプログラムを
「作り直す」使い方と「積み増す」使い方の両方へ向ける道が、ホストでもこれしかないから
である。順編成にしか意味がないので、相対編成と索引編成では読み替えない。

### 割り当てた領域を越えたら書けない

`SPACE=` と書かれた DD は、書ける大きさに限りを持つ。越えた `WRITE` はファイル状態 `34` に
なり、受け止め手がなければ `S037` で終わる (設計 90 を見よ)。これも対応表が覚えている。
<b>置き場をどれだけ取ったかはジョブが決めること</b>であり、レコードの切り方を決める属性
とは別の話だからである。

立つコードは編成で違う。順編成は `34`、相対編成と索引編成は `24` である。<b>ホストで
仕組みが違う</b>ためで、順編成 (QSAM) はアクセス法が場所を取りにいって失敗するので
プログラムがコードを見る前に異常終了するが、相対編成・索引編成 (VSAM) は
コードをプログラムへ返す。受け止め手がないときの終わり方も、それに従って
`S037` と `U4038` に分かれる。

相対編成では<b>空けた番号のぶんも場所を取る</b>。番号が住所である以上、10 番へ書けば
1 番から 10 番までの場所が要るからである。

## 割当てが決めることは編成によらない (FR-113, FR-141)

ジョブが割当てで決めてプログラムが知らないことは 2 つある — 取った領域の大きさと、
指しているのが区分データセットのメンバかどうかである。どちらもレコードの探し方とは
関わりがない。したがって<b>編成ごとに書き分けない</b>。1 つ置いて、3 つの編成から使う。

書き分けていた間は、順編成のジョブだけが実機と同じところで止まり、相対編成のジョブは
素通しになっていた。<b>どの編成かで実機との合い方が変わる</b>のがいちばん困る形である。
移行してきた資産のどれが信用できてどれができないのか、編成を数えなければ言えなくなる。

同じことがジョブのユーティリティにも要る。あれらはデータセットを開かずに生バイトを読むが、
<b>開けないものは読めない</b>ことに変わりはない。`IEBGENER` に無いメンバを読ませれば
`S013`、形が壊れたデータセットを写させれば `S001`、割り当てた領域に収まらなければ `S037`
である (設計 90 を見よ)。

## 形が壊れたデータセットは、そこで読むのをやめる (FR-103)

バイト列をレコードへ切るのは属性だが、<b>切り終えられないことがある</b>。固定長なのに
長さがレコード長で割り切れない、可変長なのに `RDW` が残りより長い長さを名乗る、という
形である。書いている途中で落ちたか、レコード長の違うデータセットを取り違えたときに起きる。

半端をそのまま短いレコードとして渡してはならない。渡せば<b>読めていないデータで処理が
進む</b>。切れるところまでを読めるものとし、その先の `READ` でファイル状態 `30` を返す。

読めたレコードを捨てないのは、ホストが<b>読んだ時点で</b>誤りにするからである。開いた
時点で誤りにすると、先頭の 1 件だけを見て終わるジョブが動かなくなる。壊れているのは
そこであって、手前ではない。

相対編成も同じである。番号が住所である以上、<b>位置とバイト列の並びは対応している</b>ので、
半端の残るスロットを指したときに `30` を返せる。順次に読んでも番号で読んでも同じで、
「そのスロットが無い」(`23`) ではない — あるのに読めないのである。

索引編成だけは違う。読む順序が<b>鍵の順</b>であり、バイト列の位置と対応しない。どこまで
読めるとは言えないので、開いた時点で `30` を返して開かない。切り方が同じでも、
そこから何をするかは編成が決める。

切り方そのものは 1 か所に置く。切り方を編成ごとに書けば、<b>形が壊れているの意味も
編成ごとに分かれる</b>からである。実際そうなっていて、順編成だけが半端に気付き、
相対編成・索引編成・ジョブのユーティリティは黙って短いレコードを渡していた。

## 整列は溜めて、並べ替えて、配る (FR-120, FR-121)

`SD` が表すのは<b>データセットではなく作業場所</b>である。開くことも閉じることもなく、
`SORT` の間だけ存在する。したがって編成もアクセス様式もファイル状態も持たない。

入口と出口はそれぞれファイルか手続きのどちらかであり、組み合わせは 4 通りある。

| | 入口 | 出口 |
| --- | --- | --- |
| ファイル | `USING`。開いて全部読んで閉じる | `GIVING`。開いて全部書いて閉じる |
| 手続き | `INPUT PROCEDURE`。中で `RELEASE` する | `OUTPUT PROCEDURE`。中で `RETURN` する |

`USING` と `GIVING` のファイルは<b>プログラムが開いてはならない</b>。開け閉めは整列の仕事で
ある。手続きのほうは段落の範囲の実行であり、宣言節と同じ仕組みで出せる。

### 並べ替えは安定でなければならない

鍵が等しいレコードの順は<b>入れた順のまま</b>である。`WITH DUPLICATES IN ORDER` が求めるのは
これであり、指定がなくても崩す理由がない。

### 合併も同じ道を通る

`MERGE` は整列済みの入力を突き合わせる。すべてを溜めてから安定に並べ替えれば、鍵が等しい
ところは<b>先に読んだファイルのものが先</b>になる。これは合併の規則そのものであり、
結果は同じになる。だから道を分けていない。

### 鍵は項目の種類で比べ方が変わる

数値項目なら<b>値として</b>比べる。`010` と `9` はバイトで比べれば `010` が小さいが、
値としては `9` が小さい。英数字項目ならバイトで比べる。EBCDIC の照合順序はバイトの値そのもの
である。

## 異常を受け止める道は 3 つある (FR-103, FR-104, FR-105)

| 書いたもの | 起きること |
| --- | --- |
| `AT END` / `INVALID KEY` | その句へ分岐する。異常として扱わない |
| `FILE STATUS` | 2 バイトのコードが項目に入る。流れは変わらない |
| `USE AFTER STANDARD ERROR PROCEDURE` | 宣言節が動き、終われば入出力文の次へ戻る |
| どれもない | 異常終了する |

`FILE STATUS` と宣言節は<b>両方書ける</b>。コードが入ったうえで節が動く。節の中から
状態コードを見て振る舞いを分けられる。

## 次の増分

設計 80 の 4 つの段はここまでで実装済である。残っているのは次のものである。

1. 位置を持って読み書きする形へ改める (暫定判断 P-038)。整列の外部マージも同じ段で決める。
2. データセットの物理表現を選べるようにする (要件 FR-111、暫定判断 P-039)。
3. `COLLATING SEQUENCE` と `ALPHABET` (暫定判断 P-042)。
