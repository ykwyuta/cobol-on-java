# 設計文書 80: ファイル入出力

| 項目 | 内容 |
| --- | --- |
| 対応要件 | FR-100〜FR-115、要件定義書 6.1〜6.2 節 |
| ステータス | 第 1 段 (順編成と行順編成の読み書き) 実装済 |

## 何を決めるか

ファイル入出力は<b>要件の分量がいちばん大きい</b>領域である。編成が 4 つ、アクセス様式が 3 つ、
入出力文が 7 つ、ファイル状態コードが 25 種類以上ある。まとめて実装することはできないので、
段を分ける。

この文書は全体の形を決め、段ごとに何を実装したかを記録する。

## 段

| 段 | 範囲 |
| --- | --- |
| 第 1 段 | 順編成 (固定長) と行順編成。`OPEN` / `READ` / `WRITE` / `CLOSE`、`FILE STATUS` |
| 第 2 段 | 可変長レコード (RDW)、`REWRITE`、`OPEN I-O`、`EXTEND` |
| 第 3 段 | 相対編成と索引編成、`START`、`READ NEXT`、`DELETE` |
| 第 4 段 | `DECLARATIVES` の `USE AFTER STANDARD ERROR PROCEDURE`、`SORT` / `MERGE` |

## 生バイトで持つ (FR-110)

既定の格納形式は<b>EBCDIC の生バイト</b>である。ホストのデータセットを移行したバイト列を、
変換せずそのまま保持する。

変換して保存すると L3 互換が<b>原理的に成立しない</b>。往復変換で情報が欠落し、照合順序が
食い違い、パック 10 進などのバイナリ項目が壊れる。データセットの中身は「文字」ではなく
「バイト」だからである。

### 属性はサイドカーに持つ

レコード様式 (RECFM)、レコード長 (LRECL)、コードページは<b>データ本体とは別のファイル</b>に
持つ。ホストではデータセットのラベルにある情報であり、バイト列の中にはない。

```
CUSTOMER.DAT       ← 生バイト
CUSTOMER.DAT.meta  ← recfm=F, lrecl=80, codepage=IBM-1047
```

サイドカーがなければ既定 (固定長 80 バイト、IBM-1047) を使う。

## レコードの切り出し方は様式で決まる

| 様式 | 切り出し方 |
| --- | --- |
| 固定長 (F/FB) | LRECL バイトずつ。ファイルの長さが割り切れなければ最後は短い |
| 可変長 (V/VB) | 4 バイトの RDW が先頭に付く。最初の 2 バイトが RDW を含む長さ |
| 行順 | 改行までが 1 レコード。書くときは<b>末尾の空白を落とす</b> |

行順編成の改行は<b>コードページの改行</b>である。EBCDIC なら `0x15` であり、
`0x0A` ではない。生バイトで持つと決めた以上、区切りもそのコードページのものになる。

## ファイル状態コードは文ごとに立てる (FR-103)

入出力文のたびに 2 バイトのコードを `FILE STATUS` の項目へ書き込む。

| コード | 意味 |
| --- | --- |
| `00` | 成功 |
| `04` | レコード長が合わない (読んだ長さが記述と違う) |
| `10` | ファイルの終わり (`AT END`) |
| `35` | 開こうとしたファイルがない (`OPEN INPUT`) |
| `37` | 開き方が編成に合わない |
| `41` | すでに開いている |
| `42` | 開いていないのに閉じようとした |
| `43` | 読んでいないのに書き換えようとした |
| `46` | 読める位置にない (`AT END` のあとの `READ`) |
| `48` | 読み取り専用で開いたのに書こうとした |
| `49` | 書き込み専用で開いたのに読もうとした |

`FILE STATUS` を書いていないファイルで異常が起きたら<b>異常終了する</b> (要件 FR-104)。
黙って続けると、読めていないデータで処理が進む。

## 記憶域の 4 つ目

`FD` のレコード領域は、作業場所とも連絡節とも違う<b>4 つ目の記憶域</b>である。
`READ` が書き込み、`WRITE` が読み出す。

```
作業場所:      記憶域 = 自分のもの          位置 = 変位
連絡節:        記憶域 = 引数[k] のもの      位置 = 引数[k] の位置 + 変位
特殊レジスタ:  記憶域 = 実行時の入口のもの  位置 = 決まった変位
ファイル:      記憶域 = 開いたファイルのもの 位置 = 変位
```

同じ `FD` に複数の 01 レベルを書けば、それらは<b>同じ場所に重なる</b>。
`REDEFINES` と同じであり、レコードの形が 2 つ以上ある場合に使う。

いまの段では、レコード領域を<b>作業場所の一部として割り付ける</b>。ファイルごとに
別の記憶域を持たせるのは、入出力バッファを別に持つ形へ移すときに行う。
この暫定の扱いは P-037 に記録した。

重なりのほうは先に入れた。同じ `FD` の 01 レベルは<b>同じ位置から始まり</b>、
その `FD` が占める長さは<b>いちばん長いレコード記述</b>で決まる。
`WRITE` に書くのはレコード名であってファイル名ではないので、どのファイルへ書くのかは
「そのレコードがどの `FD` の下にあるか」で決まる。項目にファイル名を持たせて引いている。

## `READ` は 3 つに分かれる

状態コードで分岐する。

| 状態 | 通る道 |
| --- | --- |
| 成功 (`0` で始まる) | `INTO` の転記 → `NOT AT END` |
| ファイルの終わり (`10`) | `AT END` |
| それ以外の誤り | <b>どちらも通らない</b> |

誤りのときにレコード領域の中身は決まっていない。読めたことにして先へ進めるわけには
いかないので、`INTO` の転記も起こさない。`FILE STATUS` を書いていなければ、そもそも
ここへ来る前に異常終了する。

`INTO` と `FROM` は<b>ただの転記</b>である。読み込みはレコード領域までで、そこから先は
`MOVE` と変わらない。意味解析で `MOVE` へ展開しておけば、分類の検査も編集も
そのまま効く。

## 宣言は 2 か所に分かれている

`SELECT` (環境部) と `FD` (データ部) の両方が要る。<b>どちらが欠けてもファイルは
使えない</b> — 場所を知らなければ開けず、レコードの形を知らなければ読み書きできない。
片方だけ書けば誤りとして報告する。

レコード様式は `SELECT` の `ORGANIZATION` と `RECORDING MODE`、`FD` の `RECORDING MODE`
から決まる。あとに読む `FD` 側が勝つ。

新しく作るファイルにはサイドカーがない。そのとき<b>レコードの切れ目を決められるのは
プログラムの宣言だけ</b>である。逆にサイドカーがあればそちらが勝つ。そこに置かれている
バイト列を実際に切り分けたのはその属性であり、宣言と食い違っていてもバイト列の事実は
変わらない。

## DD 名でファイルを探す

`SELECT ... ASSIGN TO 名前` の名前は<b>DD 名</b>であり、ファイルの場所そのものではない。
ホストでは JCL が DD 名と実際のデータセットを結び付ける。

実行時の入口 (`ProgramContext`) が対応表を持ち、書かれていなければ既定のディレクトリの
下から同じ名前で探す。ジョブ実行 (要件 FR-130 台) を実装するときに、JCL からこの表を
埋めることになる。
