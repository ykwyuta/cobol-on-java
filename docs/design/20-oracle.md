# 設計文書 20: cobol-oracle (V2 期待値の採取)

| 項目 | 内容 |
| --- | --- |
| 対応要件 | FR-210〜213、要件定義書 4.2〜4.4 節 |
| ステータス | 実装済 (第 1 増分)。**V2 検証が実際に稼働している** |

## 何ができるようになったか

Hercules を実行オラクルとして、cobol-runtime の出力を
**z/Architecture の機械語命令の実行結果とバイト列で突き合わせられる**ようになった。
これにより、要件 4.3 節が V2 到達可能としていた領域の検証が実際に始まっている。

期待値は仕様書の解釈ではなく、命令を実行した結果そのものである。

## 動かし方

Hercules (SDL Hyperion 4.x) が必要である。ビルド後、実行ファイルの場所を
環境変数で指定する。

```
HERCULES=/path/to/hercules mvn test
```

指定がなければ `PATH` 上の `hercules` を使う。見つからない場合、V2 テストは
**失敗ではなくスキップ**される。オラクルの有無でビルドが壊れないようにするためである。

## 構成

| パッケージ | 責務 |
| --- | --- |
| `machine` | z/Architecture 機械語の組み立て。SS 形式の 10 進命令が中心 |
| `script` | Hercules の `.tst` スクリプトの生成 |
| `run` | Hercules の起動と、コンソール出力の解析 |

## 生成されるスクリプトの構造

```
*Testcase <name>
sysclear
archlvl z/Arch
r 1A0=00000001800000000000000000000200   # 再始動新 PSW: 実行は 0x200 から
r 1D0=0002000180000000000000000000DEAD   # プログラム割込み新 PSW
r 200=<命令列>
r 380=00020001800000000000000000000000   # 正常終了用の待機 PSW
r 400=<データ>
runtest 1
*Compare
r 400.3
*Done
```

**正常終了と割込みの区別**: 命令列の末尾に `LPSWE` を置き、命令アドレス 0 の待機 PSW を
ロードして終了する。プログラム割込みが起きた場合は割込み新 PSW によって命令アドレス
`0xDEAD` の待機状態へ入る。停止時の待機 PSW を見ればどちらか判別できる。
これは将来、データ例外 (COBOL から見た `S0C7`、要件 FR-141) の検証にそのまま使える。

## 実装上で分かった要点

### 外部アセンブラは不要 (要件 FR-211)

必要な命令は SS 形式の 10 進命令が中心であり、いずれも固定長・固定レイアウトである。

| 形式 | 構成 | 命令 |
| --- | --- | --- |
| SS-b | 命令コード / L1L2 ニブル / B1D1 / B2D2 | `AP` `SP` `MP` `DP` `ZAP` `CP` `PACK` `UNPK` `MVO` |
| SS-a | 命令コード / 長さ 1 バイト / B1D1 / B2D2 | `MVC` `CLC` `ED` `EDMK` |
| SS-c | 命令コード / L1 と丸め桁のニブル / B1D1 / B2D2 | `SRP` |

ベースレジスタには 0 を用いる。ベースレジスタ 0 は「ベースなし」を意味し、実効アドレスが
変位そのものになるため、アドレスは 0〜4095 に限られる。テストは小さな領域で完結するため十分である。

### Hercules の起動には `-t` が要る

`runtest` コマンドはテストモードでのみ有効になる。`-t` オプションを付けないと
「Unknown command runtest」となる。あわせて `-n` (パネルを使わない) を指定し、
スクリプト末尾に `exit` を置かないとプロセスが終了しない。

### オラクルの適格性はバージョンではなく能力で判定する

これは実装中に踏んだ落とし穴であり、記録しておく価値がある。

Ubuntu の `hercules` パッケージは 3.13 を提供する。3.13 は `-r` (スクリプト実行) を持たない。
`PATH` 上に 3.13 があると、起動には成功しながらスクリプトが一切実行されず、
**記憶域を読み出せないまま「検証した」ことになってしまう**。実際、最初の実装では
V2 テストが理由不明の失敗を起こし、原因が「間違ったオラクルを黙って使っていた」ことだった。

対策として、`HerculesRunner.detect` は使う前に `--help` の出力を読み、
`-r` に対応していることを確かめる。バージョン番号ではなく**必要な能力そのもの**を
検査するのは、そのほうが判定の意図が明確で、将来の版でも壊れないためである。

適格な Hercules が見つからない場合は、理由を伴ってテストをスキップする。
「オラクルがないので検証をスキップした」と「間違ったオラクルで検証したつもりになった」を
取り違えないために、理由を握りつぶさない。

### 記憶域表示のアドレスは行頭ではなく桁位置で決まる

`r <addr>.<len>` の出力はこう見える。

```
HHC02290I R:0000000000000400  00123C                               ...
HHC02290I R:0000000000000400                    00456C                     ..%
```

2 行目は行頭アドレスが `0x400` でありながら、実際のデータ `00456C` は `0x408` の内容である。
表示行は常に 16 バイト境界に揃えられ、要求範囲の外は空白で埋められるためである。

したがって解析器は、行頭アドレスをそのまま使ってはならない。16 進表示部は 4 バイトずつ 4 組
(組の間は空白 1 個、計 35 桁) で、桁位置 `i` のバイトのアドレスは
`行頭 + (i / 9) * 4 + (i % 9) / 2` である。ここを取り違えると、
静かに間違った期待値を採取してしまう。

### プロセス起動が支配的なので、1 回の実行に複数の演算をまとめる

Hercules の起動は約 0.1 秒、10 進命令の実行はその数桁下である。したがって
テストケースは「1 命令 1 実行」ではなく、**多数の演算を 1 つのスクリプトにまとめて
一度に流し、結果をまとめて読み出す**構造にしている。

## 最初の成果: P-001 の決着

暫定対応 P-001 (演算結果がゼロのときの符号) を実測で決着させた。
**ゼロ結果の符号は命令ごとに規則が異なる**という、仕様書からは読み取れなかった事実が判明した。

| 命令 | ゼロ結果の符号 |
| --- | --- |
| `AP` / `SP` | 常に正。オペランドが両方とも負のゼロでも正 |
| `ZAP` | ゼロは正へ正規化。非ゼロは元の符号を保つ |
| `MP` | 代数の規則どおり。負のゼロが生じる |
| `DP` | 代数の規則どおり。商・剰余ともに負のゼロが生じる |

これを受けて `Decimal.multiply` / `divide` / `remainder` を修正した。
暫定のままであれば、乗除算の結果がゼロになる場合に誤ったバイト列を生成していた。

副産物として、`ZAP` が負のゼロを正規化することが分かった。COBOL の `MOVE` が
負のゼロを保つかどうかはコンパイラの命令選択で決まるという論点が生まれ、
P-013 として記録している。

あわせて、符号ニブル `A` `B` `F` の受理規則も実機で裏付けられた。

## 第 2 の成果: 数値編集の V2 化

ホストの数値編集は文字どおり `ED` 命令である。PICTURE から `ED` の編集マスクを生成する
`EditMask` を実装し、`NumericEditor` の出力を実機の `ED` の結果とバイト列で突き合わせた。
ゼロ抑制・小切手保護・CR/DB・単純挿入の 20 ケースが一致している。

マスクの生成は本来コンパイラ側の処理であり、P0-b でそちらへ移す。

### ED の意味論 (実測により確定)

| マスクのバイト | 役割 |
| --- | --- |
| 先頭バイト | **充填文字**。COBOL の編集項目には含まれない |
| `0x20` | 桁選択子。数字を 1 桁取り出す。有意性が立っておらず数字が 0 なら充填文字 |
| `0x21` | 有意性開始子。桁選択子と同じだが、処理後に必ず有意性を立てる |
| その他 | メッセージ文字。有意性が立っていればそのまま、いなければ充填文字 |

数字の符号が正であれば末尾で有意性が落ちる。これにより `CR` / `DB` が
正数のときだけ充填文字に置き換わるという COBOL の規則がそのまま実現される。

### 実装中に踏んだ落とし穴 (さらに 3 つ)

**1. 有意性開始子を「常に表示する桁」に置いてはならない。**
`0x21` は「数字が 0 かつ有意性が立っていなければ充填文字を出す」ため、
`ZZ9.99` の `9` の位置に置くと値 0.45 が `"    .45"` になってしまう。
正しくは<b>常に表示する最初の位置のひとつ手前の抑制位置</b>、つまり 2 番目の `Z` に置く。
マスクは `40 20 21 20 4B 20 20` であって `40 20 20 21 4B 20 20` ではない。

**2. `ED` の結果は COBOL の編集項目より 1 バイト長い。**
マスクの先頭が充填文字であるためで、項目の内容はオフセット 1 以降である。
参照実装も作業域に対して `ED` を実行し、作業域 + 1 から転記している。

**3. マスクの桁位置の数とソースの数字ニブル数は一致していなければならない。**
`ED` はソースの符号ニブルに達した時点で処理を止める。数が合わないと、
残りのマスクバイトが未処理のまま出力に残り、静かに壊れた結果になる。
パック10進項目の数字ニブル数は `2 x バイト長 - 1` であるため、
現在の検証は桁数が奇数の PICTURE を対象にしている。

## 第 3 の成果: ゾーン10進の変換とデータ例外の V2 化

`PACK` / `UNPK` 命令、およびデータ例外 (COBOL から見た `S0C7`) を実機で検証した。

**`UNPK` はランタイムの `ZonedDecimal.encode` と完全に一致する。**
ゾーンを `F` に、最右端バイトのゾーンを符号にする挙動が同一である。

**`PACK` は符号位置以外のゾーンニブルを見ない。** ゾーンが `00` でも `A1B2C3D4` でも、
数字ニブルさえ同じなら結果は変わらない。`ZonedDecimal.decode` を
「符号位置以外のゾーンを検査しない」実装にしていた前提が、実機で裏付けられた。

**`PACK` は符号ニブルをそのまま移す。** `F` は `F` のまま、`A` は `A` のままであり、
優先符号への正規化は行われない。ランタイムは常に正規化するため、この点でバイト列が異なる。
どちらが正しいかは `NUMPROC` の指定とコンパイラの生成コードで決まるため、
P-015 として記録した。

**データ例外は割込みコード `0x0007` である。** 不正な数字ニブル (`1A345C`) でも
不正な符号ニブル (`123453`) でも、実機はプログラム割込みを起こし、実アドレス `0x8E` に
`0007` を格納する。ランタイムが `DataException` を投げる条件がこれと一致していることを確認した。
要件 FR-141 の `S0C7` 再現は、これで実機の裏付けを得た。

## 第 4 の成果: 合成テストジェネレータ (NFR-041, D-15)

手で選んだ代表値ではなく、機械的に導いた組み合わせで V2 を広げる仕組みを実装した。

### 縮約の方針

| 因子 | 水準 |
| --- | --- |
| 項目のバイト長 | 1, 2, 3, 4, 8, 16 — 数字ニブル数 1, 3, 5, 7, 15, 31 に対応。`ARITH(COMPAT)` の 18 桁と `ARITH(EXTEND)` の 31 桁の境界を含む |
| 第 1 オペランドの値 | 11 分類 — 正負のゼロ、±1、最大値、最大値 -1、桁ごとに異なる値、符号ニブル `F` / `A` / `B` |
| 第 2 オペランドの値 | 同上 |
| 演算 | `AP` / `SP` / `ZAP` |

完全列挙は 6 x 11 x 11 x 3 = 2178 件になる。2-way カバリングアレイによる縮約で
**121 件**まで減った。これは最大 2 因子の積 (11 x 11) と一致しており、pairwise の理論下限である。

**121 件すべてが初回の実行でホストと一致した。** 桁あふれ (最大値どうしの加算) を含む。
プログラムマスクで 10 進オーバーフローが抑止されているため実機は割込みを起こさず結果を
切り捨てる。これはランタイムの「`ON SIZE ERROR` を指定しない場合は上位桁を切り捨てる」
という挙動 (要件 FR-043) と一致した。

### 実装中に踏んだ落とし穴: 貪欲法で最初の因子が固定される

素朴な貪欲法は「すでに決めた因子との間で新たに覆える組の数」だけを見る。すると
**最初の因子は決めた因子がないため全水準が同点になり、常に水準 0 が選ばれる**。
その結果、最初の因子の他の水準を含む組が永久に覆われず、生成が終わらない。

対策として、同点の打開に「まだ決めていない因子との間に残っている、覆われていない組の数」を
使う。あわせて、1 行で 1 つも覆えなかった場合に例外を投げる保険を入れた。
無限ループは静かに時間を溶かすだけで原因が見えにくいため、明示的に止める。

## 第 5 の成果: MP / DP と 10 進除算例外

`MP` と `DP` はオペランドの長さに制約を持つため、加減算とは別の生成が必要である。

| 命令 | 制約 |
| --- | --- |
| 共通 | 第 2 オペランドは 8 バイト以下で、第 1 オペランドより短い |
| `MP` | 第 1 オペランドの上位 {@code l2} バイトがゼロでなければならない。違反するとデータ例外 |
| `DP` | 商が上位 {@code l1 - l2} バイトに収まらなければならない。収まらないと 10 進除算例外。**これは抑止できない** |

制約を満たす長さの組を 1 個の因子として扱うことで pairwise の枠組みに載せた。
被除数の有効桁数を商の格納領域の桁数に抑えれば、商は必ず収まる (商は被除数以下であるため)。

**`MP` 121 件、`DP` 99 件が一致した。** `DP` は商と剰余を 1 つの項目に並べて格納する
(上位 `l1 - l2` バイトが商、下位 `l2` バイトが剰余) 点も含めて一致している。
COBOL の `DIVIDE ... REMAINDER` はこの形に対応する。

**ゼロ除算の割込みコードは `0x000B`** である。COBOL から見た `S0CB` にあたる。
`DP` の除数をゼロにすると実機は割込みを起こし、ランタイムも同じ入力で
`DecimalDivideException` を投げることを確認した。これで要件 FR-141 の ABEND のうち
`S0C7` と `S0CB` の 2 つが実機の裏付けを得た。

## 次の増分

1. **浮動挿入・固定符号・全桁抑制の検証** — 平の `ED` では表現できないため未着手 (P-014)。
   参照実装が `EDMK` + 後処理で実現しているのか、`UNPK` + 挿入なのかを確定させる必要がある。
2. **編集マスクの合成ジェネレータ** — PICTURE の組み合わせを機械的に列挙して `ED` と突き合わせる。
3. **浮動挿入・固定符号の検証** — 平の `ED` では表現できない (P-014)。
