## 文脈

IMS TM (Transaction Manager) は、メッセージキュー駆動のオンライントランザクションモニタである。メインフレーム実機環境では、オープン系システムとメインフレーム間の通信に **IBM MQ + OTMA (Open Transaction Manager Access)** を組み合わせ、ホスト内 MPP (Message Processing Program) が `CALL 'CBLTDLI' USING 'GU  ', IO-PCB` で電文を取得・処理する構成が主流である。

開発・テスト環境や OSS CI 環境において商用 IBM MQ の実機やライセンスを調達することは困難であり、軽量・コンテナ環境で完結するオープンソースのメッセージングバックエンドが求められる。また、特定のメッセージング製品にランタイムが密結合することを避けなければならない。

### 実機の原子性という制約

実機では、OTMA と IBM MQ が z/OS の RRS 等と連携し、**「電文をデキューする」「IMS DB / Db2 を更新する」「応答を返す」を 1 つのトランザクションとして原子的に確定する**。オープン環境でこれをそのまま再現するには XA (2 相コミット) が要る。当初案はこの点を検討せずに JMS コミットと JDBC コミットの 2 本立てを採っており、電文の消失と二重処理が構造的に起きる状態だった。

## 決定

1. **JMS 3.0 (Jakarta Messaging) による抽象化**:
   - `cobol-ims` コアは中立ポート `ImsQueuePort` を定義し、アダプタ層は `jakarta.jms.*` API でメッセージを送受信する。ブローカ製品を差し替えられる状態を保つ。
   - `jakarta.jms.BytesMessage` を用い、EBCDIC 生バイト列と `LLZZ` プレフィックスを透過的に変換・転記する。
2. **原子性は at-least-once + 冪等化 (inbox 方式) で代替する**:
   - 処理済み電文のキー（メッセージ ID とトランザクション連番）を、IMS DB の更新と**同一 JDBC トランザクション**へ書く。
   - JMS は手動 ACK とし、**JDBC コミットが成功してから ACK する**。
   - 再配信された電文は inbox のキーで検出して捨てる。
   - これにより電文の消失は起きない。残る差は「障害と再配信のタイミングによっては業務ロジックが 2 度呼ばれうる」ことであり、これを**実機との差として明記する**。
   - XA（XA 対応ブローカ + JTA トランザクションマネージャ）を選べば原子性を保てるが、Spring Boot は 3.x で Atomikos / Bitronix の自動構成を落としており、第三者スターターの追加が要る。この費用を払うかは利用者の判断とする ([P-104](provisional.md))。
3. **順序保証**:
   - IMS はトランザクションコード単位で電文を FIFO 処理する。第 1 増分は**キューあたり単一コンシューマ・`prefetch=1`** を既定とし、順序を保つ。実機の複数 MPP 領域による並列スケジューリングは再現しない ([P-105](provisional.md))。
     - <b>2026-09-16 の実測による訂正</b>: `prefetch=1` は実装されておらず (既定は無制限)、設定しても消費者どうしの配分は変わらなかった。順序を守っているのは**消費者が 1 つであること**だけであり、それも処理系は強制していない ([P-105](provisional.md))。
4. **ローカル環境**:
   - `infra/rabbitmq/compose.yaml` にコンテナ構成を置き、ローカル開発・テストおよび管理 UI によるキュー監視を提供する。**依存ライブラリとブローカの版は、実際に依存解決と起動を確認してから固定する** ([IR-27](../reviews/2026-09-13-ims-research-critical-review.md))。
5. **電文モデルの範囲**:
   - `ImsQueuePort` の契約は、1 電文 1 メッセージの往復だけでは足りない。次を契約に含めるか、明示的に L0 として診断する。
     - 入力の 2 セグメント目以降を取る I/O PCB への **`GN`**
     - 出力を複数 `ISRT` で組み立てて確定する **`PURG`**
     - 宛先を差し替える **`CHNG`** と、代替 PCB (ALTPCB) への `ISRT`
     - 会話型トランザクションの **SPA (Scratch Pad Area)**。SPA はメッセージの第 1 セグメントとして渡され、`ISRT` で書き戻す
   - これらが無いと、該当する資産は「動かない」ではなく**「1 セグメント目だけ送られる」のような部分的に正しく見える壊れ方**をする。契約を凍結する前に決める。

## 影響

- **プラス影響**:
  - 商用ライセンス不要で、ローカル PC や CI 上で閉じた自動テストが可能。
  - JMS 規格に準拠しているため、クラウド環境や別製品へのポータビリティが確保される。
- **マイナス影響 / トレードオフ**:
  - **実機の UOW 原子性は再現しない。**at-least-once であり、業務ロジックが 2 度呼ばれうる。冪等でない業務（採番、加算、外部送信）は影響を受ける。これは「COBOL からの透過性」が成り立たない領域であり、リリースノートに明記する ([P-104](provisional.md))。
  - inbox テーブルの保持期間と刈り取りが運用項目として増える。2026-09-16 に、置き場を開くときに既定 7 日で刈る形を入れた ([P-163](provisional.md))。刈ったあとに再配信されると業務は 2 度動くので、日数はブローカの設定に合わせて決める。
  - 単一コンシューマ前提のため、実機の並列スケジューリング相当のスループットは出ない。消費者を増やせば出るが、取引コードの中の順序が崩れることを実測した ([P-105](provisional.md))。
  - AMQP と JMS の仕様差異（ヘッダの扱い、トランザクションセマンティクス）をアダプタ層で吸収する実装が必要。

## 会話型トランザクションについて

当初の検討資料は「IMS TM は CICS に比べて対話状態の管理が少なく、Java/Spring 環境への置き換えが容易」と結論していた。これは**会話型トランザクションと SPA を数え落とした結論である**。SPA は CICS の COMMAREA と同じ課題（永続化、サイズ、有効期限、クラッシュ回復、打ち切り）を持ち込み、入出力バッファのレイアウトも変える。[ADR-0008](0008-cics-on-spring-mvc-and-session.md) の会話状態ストアと共通化できるかを検討する。
