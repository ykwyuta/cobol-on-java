# ADR-0002: 呼び出し ABI は DataView、Java 向け API は生成した型付きビューを使う

## 文脈

COBOL の引数は、Java の値の並びではなく、呼ぶ側の連続した記憶域への参照である。
`REDEFINES`、集団項目、部分参照、EBCDIC、固定小数点、パック10進、同一領域を複数引数へ
渡すエイリアシングを保たなければならない。一方、Java 利用者へオフセットと生バイトだけを
公開すると、文字コード、桁、符号、長さの誤りが呼び出すたびに再発する。

Java のレコードや POJO へ自動変換すると扱いやすく見えるが、複数のデータ記述が同じバイトを
指す COBOL の意味を1個のオブジェクトグラフへ一意に写せない。呼び出し前後の自動コピーでは、
引数間のエイリアシングと呼び出し中に Java コールバックが見る値も失われる。

## 決定

ランタイム内部の呼び出し ABI は、現行と同じく `DataView[]` とする。`BY REFERENCE` は元の
`DataView`、`BY CONTENT` は同じバイト列の独立した写しを渡す。受け手は渡し方を知らなくてよく、
見えている領域へ同じ規則で読み書きする。

Java 向けには、COBOL の01レベルまたは copybook から次の成果物を生成する。

- `Storage` 上の項目位置と COBOL の符号化規則を知る型付きレコードビュー
- プログラム名、引数順、最小バイト長、入出力意図を持つ `ProgramSignature`
- 引数を正しい順序で組み立てるプログラム別のファサード
- 生成元のレイアウトを識別する安定した `layoutHash`

型付きビューは POJO ではなく記憶域のビューであり、`String`、`BigDecimal` 等との変換は getter /
setter の時点だけで行う。元の `Storage` は呼び出しのあいだ保持し、戻ったあと同じビューから
更新値を読む。低レベル API は手書き連携と段階移行のために公開するが、型付きファサードを
標準の利用方法とする。

呼び出し時に、引数の個数と各 `DataView` の長さを `ProgramSignature` に対して検査する。
未知の動的 COBOL 呼び先は署名なしでも呼べる互換モードを持てるが、Java アダプタは必ず署名を
登録する。`layoutHash` を持つファサードと配備先マニフェストが不一致なら、プログラムを動かす
前に契約不一致として失敗させる。

`BY VALUE` は ABI の別種類として、対応する COBOL の利用法と大きさを明示した不変の
`CobolValue` を追加する。`DataView` を Java のプリミティブへ暗黙変換して先行実装しない。

## 影響

- 既存の生成コードとランタイムのバイト指向モデルを保ったまま Java API を型安全にできる。
- copybook 変更時は Java 成果物も再生成が必要になる。ハッシュ検査により古い成果物の混在は
  呼び出し前に検出できる。
- Java アダプタは `DataView` を呼び出し中だけ使用する。ビューや内部 `byte[]` を非同期処理へ
  保持してはならない。
- 文字コードは `CobolSession` の `CodePage` を唯一の基準とし、プラットフォーム既定文字コードを
  データ変換に使用しない。

## 却下した案

### 全引数を POJO / Java record へ自動マッピングする

エイリアシング、`REDEFINES`、未使用バイト、項目変更の順序を保存できない。値オブジェクトが
必要なアプリケーションは、生成ビューの外側で明示的に変換する。

### JSON、MessagePack 等を共通 ABI にする

プロセス間連携には適するが、同一 JVM 内で COBOL の記憶像を一度構造化して戻す費用が増え、
バイト単位の互換性も失う。別プロセス化する場合はこの ABI の外側の輸送層として扱う。

### Java のプリミティブ配列を引数ごとに渡す

同じ `byte[]` の範囲を重ねる情報と、ビューの境界を表現しにくい。既存の `DataView` より意味が
弱いため採用しない。
