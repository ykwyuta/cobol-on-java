## 文脈

メインフレームの IMS は専用の超高速ロック機構（IRLM: Internal Resource Lock Manager）を持ち、細かい粒度（セグメント/ブロック単位）での並行排他制御を行っている。

一方、汎用 RDB（PostgreSQL / Db2）をストレージエンジンとした場合、木構造（親・子・孫セグメント）の複数行に対する更新が並行して走ると、トランザクション間で行ロックの獲得順序が交差し、循環待ちデッドロック（PostgreSQL: 40P01, Db2: -911 / 40001）が頻発する危険がある。また、大量更新バッチとオンライン参照が衝突すると、インデックスページの競合やロック待ちタイムアウトが発生する。

## 決定

RDB 上でのロック競合・デッドロックを防止するため、以下の多層防御アーキテクチャを採用する。

1. **ルートアンカーロック (Root-Level Coarse Locking)**:
   - 木構造の内部（子セグメント・孫セグメント）を更新・挿入・削除する前に、トランザクションは必ずその木の頂点であるルート行（`IMS_ROOT_INDEX` の該当行）に対して `SELECT ... FOR UPDATE` を発行し、排他ロックを獲得する。
   - これにより、同一ルートキー配下の並行更新は入り口で直列化され、**木内部の行ロック順序交差によるデッドロックが原理的に 100% 排除** される（異なるルートキー同士は完全並行に動作可能）。
2. **MVCC スナップショット参照**:
   - 通常の検索（`GU`, `GN`, `GNP`）は一切ロックを獲得せず、スナップショット参照（Read Committed）とする。読込処理は更新をブロックせず、更新処理も読込をブロックしない。
   - `GHU` / `GHN`（Get Hold: 更新前提の読込）が呼ばれた場合のみ、排他ロックを予約する。
3. **DML 遅延ソート発行**:
   - トランザクション内の複数 `ISRT` / `REPL` は即時発行せずバッファリングし、コミット直前に `HIERARCHY_PATH ASC`（階層パスの辞書順）で整流化して発行する。
4. **DBD 単位の物理テーブル分離**:
   - 競合ドメインを局所化するため、DBD ごとにテーブルを物理分割（必要に応じてハッシュパーティショニング併用）する。
5. **メインフレーム互換 `U0777` 自動リトライ**:
   - 万一のデッドロック検知時は、メインフレームの擬似 ABEND `U0777` 意味論に準拠し、MPP オンライン処理であれば自動ロールバックと指数バックオフを挟んで最大 3 回まで同一電文の処理を自動再試行する。

## 影響

- **プラス影響**:
  - RDB 特有のデッドロック頻発を根本から抑止し、高い並行スループットを維持できる。
  - 同一ルート配下のデータ整合性が確実に保証される。
- **マイナス影響 / トレードオフ**:
  - 同一ルート配下に対する並行更新は直列化されるため、同一顧客に対する高頻度の同時書き込みではロック待ち時間が発生する（ただしメインフレームの業務設計自体がキー単位の直列性を前提としているため実害は極小）。
