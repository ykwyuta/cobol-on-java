## 文脈

メインフレームの IMS は専用のロック機構 (IRLM) を持ち、細かい粒度での並行排他制御を行っている。

一方、汎用 RDB（PostgreSQL / Db2）をストレージエンジンとした場合、木構造（親・子・孫セグメント）の複数行に対する更新が並行して走ると、トランザクション間で行ロックの獲得順序が交差し、循環待ちデッドロック（PostgreSQL: 40P01, Db2: -911 / 40001）が発生する危険がある。また、大量更新バッチとオンライン参照が衝突すると、インデックスページの競合やロック待ちタイムアウトが発生する。

## 決定

1. **ルートアンカーロック (Root-Level Coarse Locking)**:
   - 木構造の内部（子セグメント・孫セグメント）を更新・挿入・削除する前に、トランザクションは必ずその木の頂点であるルート行（`IMS_ROOT_INDEX` の該当行）に対して `SELECT ... FOR UPDATE` を発行し、排他ロックを獲得する。
   - これにより、**同一ルートキー配下**の並行更新は入り口で直列化され、木内部の行ロック順序交差によるデッドロックが起きなくなる。異なるルートキー同士は並行に動作できる。
   - **新規ルートの `ISRT` はこの方式で守れない（ファントム）。**ロック対象の行がまだ存在しないためである。ルート行を先行確保する手順（`INSERT ... ON CONFLICT DO NOTHING` → `SELECT ... FOR UPDATE`）を規定し、同一ルートキーの同時 `ISRT` に対して返す状態コードも決める ([IR-18](../reviews/2026-09-13-ims-research-critical-review.md))。
   - **複数ルート・複数 DBD をまたぐ更新は、これでは直列化されない。**振替処理のように 2 つのルートを更新する資産は普通にある。ルートロックの獲得順序を **`(DBD_NAME, ROOT_KEY_RAW)` 昇順**に規定し、ルート間でも順序を揃える。
2. **MVCC スナップショット参照**:
   - 通常の検索（`GU`, `GN`, `GNP`）はロックを獲得せず、スナップショット参照とする。読込処理は更新をブロックせず、更新処理も読込をブロックしない。
   - `GHU` / `GHN` / `GHNP`（Get Hold: 更新前提の読込）が呼ばれた場合のみ、排他ロックを獲得する。
3. **DML は即時発行する（当初案の「遅延ソート発行」は撤回）**:
   - 当初案は、トランザクション内の複数 `ISRT` / `REPL` をバッファリングし、コミット直前に `HIERARCHY_PATH` 昇順で整流化して発行するとしていた。**これは撤回する。**
   - 理由は 2 つある。第 1 に、DL/I では**同一 UOW 内で `ISRT` した直後の `GU` / `GN` / `GNP` はそのセグメントを見る**。DML を溜めると後続の `SELECT` が自分の更新を見ず、「挿入 → 読み直して検算」「削除 → 走査し直し」という普通の COBOL の書き方が壊れる。第 2 に、`ISRT` を遅延すると `II`（重複キー）の返却がコミット時までずれ、**ステータスコードで分岐する制御フローが変わる**。
   - 撤回してよい理由は、対策 1 のルートアンカーロックが入っていれば同一ルート配下でのロック順序交差はもう起きないためである。遅延バッファリングの主目的は対策 1 と重複していた ([IR-17](../reviews/2026-09-13-ims-research-critical-review.md))。
4. **DBD 単位の物理テーブル分離**:
   - 競合ドメインを局所化するため、DBD ごとにテーブルを物理分割（必要に応じてハッシュパーティショニング併用）する。
   - **これは `PROCOPT=E` の前提条件でもある。**単一の `IMS_SEGMENT_STORE` に対して `LOCK TABLE` を打つと無関係な全 DBD が止まるため、`PROCOPT=E` を採るなら Table-per-DBD を既定にする必要がある ([IR-21](../reviews/2026-09-13-ims-research-critical-review.md))。
5. **`PROCOPT` に基づく最適化は `G` と `GO` を分ける**:
   - 整合性を捨てた読み取りは `G` ではなく **`GO` (Get Only)** の意味論である。`G` は整合性つきの読み取りであり、更新中のデータを読まない。
   - したがってロック抑止は `GO` にのみ適用し、`G` はスナップショット参照で整合性を保つ。`GOx` (`GON` / `GOT`) は未対応として診断する。
   - 当初案は `G` を「一切のロックを抑止」と写像していた。これは「近似を既定として黙って適用する」ものであり、FR-153 が Db2 のカーソルについて定める「未分類 cursor へ近似方式を暗黙適用しない」に反する。移行後だけダーティリードが起きる、最も見つけにくい種類の差になる ([P-106](provisional.md))。
6. **デッドロック検知時の再試行**:
   - RDB 側でデッドロックを検知した場合、MPP トランザクションを自動ロールバックし、指数バックオフを挟んで再試行する。
   - **再試行回数は設定値（既定 3）とする。**実機の再スケジュール回数は定義側の設定に依存し、固定値ではない。ABEND コード `U0777` の妥当性も含め、実機の規定とは突き合わせていない ([P-107](provisional.md))。

### 実装メモ (2026-09-16)

最初の実装は、決定 1 のルートアンカーロックを**同期点の確定の時点で**押さえる形で始めた ([P-161](provisional.md))。
領域がデータベースをメモリで動かし、同期点で置き場へ確定する形 ([P-160](provisional.md)) だからである。
獲得順序は決定 1 のとおり `(DBD_NAME, ROOT_KEY_RAW)` 昇順とし、ファントムは排他の行 `IMS_ROOT_LOCK` の一意制約で検出する。
押さえた版が読んだときと違えば、上書きせずに競合として止める。決定 2 (GH の時点の排他) と決定 6 (自動の再試行) はまだ無い。

## 影響

- **プラス影響**:
  - 同一ルート配下でのロック順序交差によるデッドロックを抑止できる。
  - 同一ルート配下のデータ整合性が保証される。
  - 読み取りが更新をブロックしない。
- **マイナス影響 / トレードオフ**:
  - 同一ルート配下に対する並行更新は直列化されるため、同一キーへの高頻度の同時書き込みではロック待ちが発生する。
  - **「デッドロックの撲滅」は同一ルート配下に限られる。**ルート間・DBD 間は獲得順序の規約に依存し、規約を破る経路があれば依然としてデッドロックする。
  - ルート行の先行確保が、新規ルート挿入のたびに 1 往復増える。
  - `PROCOPT=E` を採るなら Table-per-DBD が必須になり、DBD 追加のたびに DDL が要る（[ADR-0013](0013-ims-db-denormalized-raw-storage-engine.md) の「DDL マイグレーション不要」という利点が部分的に失われる）。

## 検証について

本 ADR の内容は実行による裏取りが無い ([P-099](provisional.md))。特にデッドロックの発生率と再試行の妥当性は、負荷をかけて測るまで数値を主張しない。
