## 文脈

メインフレームの COBOL 資産における階層型データベース（IMS DB）をオープン環境（Java/JVM）へ移行するにあたり、バックエンドストレージとしてオープンソースの PostgreSQL または IBM Db2 を採用したいという要件がある。

従来のリホスト・マイグレーション手法では「IMS の DBD を解析し、各セグメントを RDB の正規化された親子テーブルへ分解・マッピングする」アプローチが取られることが多い。しかしこの方式には以下の致命的な問題がある：

1. **COBOL データ表現との非互換**: セグメント内には `COMP-3`（パック10進数）、バイナリ、`OCCURS DEPENDING ON`（可変長配列）、同一領域の多重 `REDEFINES` が含まれ、SQL の列型へ分解すると情報欠落やエンコーディング変換破損が起き、L3 互換（生バイト完全互換）が成立しない。
2. **階層走査（Hierarchical Sequence）の破綻**: DL/I の `GN`（次走査）や `GNP`（親配下走査）は深さ優先・先行順（Pre-order Traversal）で走査される。正規化テーブルの多数の外部キー結合や UNION でこの順序を毎度エミュレートするのは性能的・論理的に維持困難である。
3. **未定義フィールド**: DBD にはシーケンスフィールド（検索キー）のみ定義され、データ部は単なる `BYTES=500` の連続バイト塊としてしか定義されていないものが多く、業務テーブル定義がそもそも存在しない。

## 決定

RDB を業務テーブルとしてではなく、**「トランザクション対応の階層ストレージエンジン」** として利用する非正規化・生バイト格納モデルを採用する。

1. **汎用スキーマ設計**:
   - `IMS_SEGMENT_STORE`: `(DBD_NAME, ROOT_KEY_RAW, HIERARCHY_PATH)` を主キーとし、セグメント生データは `BLOB` / `BYTEA`（EBCDIC生バイト列）でそのまま保持する。
   - `IMS_ROOT_INDEX`: 高速なルートキー（`GU`）検索用のインデックス。
2. **階層パス（`HIERARCHY_PATH`）による順序保証**:
   - 階層位置を `/000001/01-000100/02-000100` のような文字列パスで採番・保持する。
   - これにより、RDB の B-Tree インデックス順序（`ORDER BY HIERARCHY_PATH ASC`）がそのまま DL/I の階層順序と完全一致し、`GN` や `GNP` を単純な単一テーブルのレンジスキャンで高速実行できる。
3. **完全透過な `CALL 'CBLTDLI'` 実行**:
   - COBOL プログラムからは中立モジュール `cobol-ims` 経由で実行され、背後の PostgreSQL / Db2 の存在を完全に隠蔽する。

## 影響

- **プラス影響**:
  - COBOL 側のコード修正が一切不要（100% 透過実行）。
  - パック10進数や `REDEFINES` のデータ破損リスクが完全にゼロになる。
  - DBD に新しいセグメントやフィールドが追加されても、RDB 側の DDL マイグレーションが不要。
- **マイナス影響 / トレードオフ**:
  - 外部の BI ツール等から直接 SQL で業務データを集計できない（必要に応じて CQRS パターンによる非同期の参照用 RDB テーブル展開で対処）。
  - 大量連続 `GN` 時のクエリ往復オーバーヘッドを防ぐため、ランタイム層でのブロックプリフェッチ機構が必要となる。
