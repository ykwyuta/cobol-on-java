## 文脈

メインフレームの COBOL 資産における階層型データベース（IMS DB）をオープン環境（Java/JVM）へ移行するにあたり、バックエンドストレージとしてオープンソースの PostgreSQL または IBM Db2 を採用したいという要望がある。

従来のリホスト・マイグレーション手法では「IMS の DBD を解析し、各セグメントを RDB の正規化された親子テーブルへ分解・マッピングする」アプローチが取られることが多い。しかしこの方式には以下の問題がある：

1. **COBOL データ表現との非互換**: セグメント内には `COMP-3`（パック10進数）、バイナリ、`OCCURS DEPENDING ON`（可変長配列）、同一領域の多重 `REDEFINES` が含まれ、SQL の列型へ分解すると情報欠落やエンコーディング変換破損が起きる。L3 (バイト忠実) を目標として掲げること自体ができなくなる。
2. **階層走査（Hierarchical Sequence）の破綻**: DL/I の `GN`（次走査）や `GNP`（親配下走査）は深さ優先・先行順（Pre-order Traversal）で走査される。正規化テーブルの多数の外部キー結合や UNION でこの順序を毎度エミュレートするのは性能的・論理的に維持困難である。
3. **未定義フィールド**: DBD にはシーケンスフィールド（検索キー）のみ定義され、データ部は単なる `BYTES=500` の連続バイト塊としてしか定義されていないものが多く、業務テーブル定義がそもそも存在しない。

### この ADR が要件に先行していること

**IMS を要求している要件は FR-164 の 1 本だけである。**その FR-164 は「IMS 連携はフェーズ 4 の目標とし、初期リリースではインタフェース定義のみとする」と定めており、RDB ストレージエンジンを要求してはいない。本 ADR は要件が書かれるまで**提案**であり、採用ではない ([P-098](provisional.md))。

## 決定

RDB を業務テーブルとしてではなく、**「トランザクション対応の階層ストレージエンジン」** として利用する非正規化・生バイト格納モデルを提案する。

1. **汎用スキーマ設計**:
   - `IMS_SEGMENT_STORE`: `(DBD_NAME, ROOT_KEY_RAW, HIERARCHY_PATH)` を主キーとし、セグメント生データは `BLOB` / `BYTEA`（EBCDIC生バイト列）でそのまま保持する。
   - `IMS_ROOT_INDEX`: ルートキー（`GU`）検索および `GN` のルート跨ぎ用。
2. **階層パス（`HIERARCHY_PATH`）による順序保証**:
   - 階層位置を `/000001/01-000100/02-000100` のような文字列パスで採番・保持する。
   - **各段は固定幅・固定文字集合（数字と `-` のみ）とする。**小数点採番は禁止する。`.` (0x2E) は `/` (0x2F) より小さく、混ぜると自分の子より兄弟が先に並び、先行順走査が壊れるためである ([P-101](provisional.md) に実測を記録)。
   - **列に `COLLATE "C"`（Db2 は相当の指定）を明記する。**`ORDER BY HIERARCHY_PATH` が階層順と一致するのはバイト値順の照合のときだけであり、データベース既定の照合順序に任せてはならない。理由は [設計 80](../design/80-file-io.md) の「生バイトで持つ」と同じである。
   - **兄弟順序の正本は `HIERARCHY_PATH` ではない。**キー付きセグメントの兄弟はシーケンスフィールド昇順でなければならず、正本は `SEQ_KEY_RAW` である。`HIERARCHY_PATH` はその写像として維持する。
3. **アクセス方式によるルート順序の切り分け**:
   - HIDAM / PHIDAM / HISAM はルートキー昇順で再現する。
   - **HDAM / PHDAM はランダマイジングモジュールがルートの物理順序を決めるため、キー順にならない。**再現できないので、無限定 `GN` のルート順序が実機と一致しないことを診断として出す ([P-102](provisional.md))。近い順序を黙って返さない。
4. **対象外の明示**:
   - 二次索引 (`PROCSEQ=`)、論理関係、GSAM、Fast Path (DEDB / MSDB) は **L0 (未対応)** とし、DBD / PSB のロード時に診断を出す ([P-103](provisional.md))。特に二次索引は「`HIERARCHY_PATH` の単一順序が階層順序と一致する」という本方式の中核前提を壊すため、黙って主キー順で返してはならない。
5. **DBD / PSB メタデータの前提**:
   - 本方式は DBD の `FIELD` 定義（オフセット・長さ・`SEQ` の有無）、`RULES=`、`ACCESS=`、PSB の `PROCOPT` を必要とする。`DbdParser` / `PsbParser` / `ImsDatabaseCatalog` は本方式の**前提コンポーネント**であり、第 1 増分に置く。

## 影響

- **プラス影響**:
  - COBOL 側のソース修正を必要としない（`CALL 'CBLTDLI'` の呼出し形をそのまま受ける）。
  - パック10進数や `REDEFINES` を SQL 列型へ分解しないため、型変換に起因するデータ破損の経路が無い。
  - DBD に新しいセグメントやフィールドが追加されても、RDB 側の DDL マイグレーションが不要。
- **マイナス影響 / トレードオフ**:
  - 外部の BI ツール等から直接 SQL で業務データを集計できない（必要に応じて CQRS パターンによる非同期の参照用 RDB テーブル展開で対処）。
  - 大量連続 `GN` 時のクエリ往復オーバーヘッドを防ぐため、ランタイム層でのブロックプリフェッチ機構が必要となる。
  - **中間挿入でギャップが枯渇すると、部分木全体の主キー再採番が発生する。**`HIERARCHY_PATH` は全子孫の `PARENT_PATH` に埋め込まれているためである。刻み幅と再採番コストは実測して決める ([P-101](provisional.md))。
  - **非キー項目で修飾された SSA は索引が効かず、部分木の走査になる。**性能はプリフェッチ前提であり、測るまで数値を主張しない。
  - **HDAM の全件走査順序は再現しない** ([P-102](provisional.md))。
  - **二次索引を使う資産は動かない** ([P-103](provisional.md))。頻出するなら本方式そのものの見直しが必要になる。

## 検証について

DL/I には CCVS85 や Hercules に相当する外の基準が無い。要件 §4.3 は FR-150〜164 を V1 止まりと定めている。本 ADR の内容は**実行による裏取りが無い** ([P-099](provisional.md))。「忠実」「完全」「100%」といった表現は用いない。
