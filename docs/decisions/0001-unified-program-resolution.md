# ADR-0001: COBOL と Java の呼び先を明示的なプログラムカタログで解決する

| 項目 | 内容 |
| --- | --- |
| 状態 | 採用 |
| 日付 | 2026-09-09 |
| 関連要件 | FR-080, FR-082, FR-083, FR-086, NFR-050 |
| 関連設計 | [設計 75](../design/75-java-interop.md) |

## 文脈

現在の `ProgramContext.resolve` は、COBOL のプログラム名を `ProgramSupport.classNameOf` で
Java クラス名へ変換し、呼ぶ側のクラスローダから反射で生成する。この方法は翻訳済み
COBOL 同士の呼び出しには小さくて有効だが、次の要件を同時には満たせない。

- COBOL の `CALL` から Java 実装を呼ぶための明示的な登録先
- Java から COBOL を呼ぶ際の同じ名前解決規則
- `DYNAM` / `NODYNAM` の解決時期と `CANCEL` 後の再生成
- ロードできるクラスの範囲を運用側が制限する NFR-050
- 同じプログラム名が複数の提供元にある場合の決定的な診断

`CALL` の文字列を Java の完全修飾クラス名やメソッド名として直接解釈すると、業務データから
任意のクラスを初期化できる。パッケージ名の文字列検査だけでは、クラスローダや依存 JAR が
変わったときの境界にもならない。

## 決定

実行時に不変な `ProgramCatalog` を構築し、すべての呼び先をそこから解決する。
カタログは次の2種類の提供元を同じ `ProgramId` 名前空間へ載せる。

- 翻訳済み COBOL を、許可したパッケージまたは生成物のマニフェストから供給する
  `CobolProgramResolver`
- アプリケーションが名前とファクトリを明示登録する `JavaProgramResolver`

カタログが返す値は、インスタンスそのものではなく `ProgramFactory` と `ProgramSignature` を
持つ `ProgramDefinition` とする。インスタンスと `WORKING-STORAGE` は実行セッションが生成して
保持し、`CANCEL` で破棄する。Java 実装もファクトリからセッションごとに生成するため、状態の
有無によって COBOL と違うライフサイクルにならない。

プログラム名は、末尾空白を除去して英大文字へ正規化した `ProgramId` を唯一のキーとする。
異なる提供元が同じキーを宣言したカタログは構築時に失敗させ、検索順による上書きは許さない。

静的な文字定数への `NODYNAM` 呼び出しは、生成物のリンク情報を用いてセッション開始時に
定義を検証して束縛する。`DYNAM` とデータ項目による動的 `CALL` は実行時にカタログを引く。
どちらもプログラムのインスタンスはセッション内でキャッシュし、`CANCEL` 後はファクトリから
作り直す。

既存のクラス名規則は互換用の `CobolProgramResolver` の内部に閉じ込める。既定では
`cobol.generated` だけを許可し、追加パッケージとクラスローダは Java ホストが明示する。
任意クラスパスを走査するフォールバックや、完全修飾クラス名による `CALL` は提供しない。

## 影響

- Java→COBOL と COBOL→Java が、名前の正規化、重複検査、キャッシュ、`CANCEL` を共有する。
- Java アダプタの追加はカタログ構築時のコードまたは構成変更になり、COBOL の入力値だけで
  呼び出し権限を広げられない。
- `ProgramContext` は反射による探索を直接行わず、セッションから渡されたカタログを使う形へ
  移行する必要がある。
- NFR-050 の境界は「JVM の完全なサンドボックス」ではない。登録済み Java 実装自身の権限は
  ホストアプリケーションと同じであり、その監査はアプリケーション側の責務である。

## 却下した案

### `CALL` 名を Java のクラス名または静的メソッド名として扱う

設定なしで呼べる反面、公開範囲がクラスパス全体へ広がり、リファクタリングで COBOL の ABI も
変わる。引数検査、インスタンス寿命、監査情報も呼び先ごとにばらつくため採用しない。

### Java 用と COBOL 用に別々のレジストリを作り、優先順位で選ぶ

同名衝突が配備順で変わる。`CANCEL` と呼び出し履歴も二重実装になるため採用しない。

### Java の `ServiceLoader` だけで自動発見する

ライブラリ追加だけで公開呼び先が増え、ホストが許可対象を一覧で確定できない。明示登録を作る
補助手段としては利用できるが、登録前の許可検査を省略してはならない。
