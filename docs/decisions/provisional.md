# 暫定対応の記録

実装を進めるうえで、正式な解決を先送りして暫定の扱いを採った箇所を記録する。
コード中のコメントからこの表の番号 (P-nnn) を参照している。

各項目には**解消条件**を明記する。「いつ直すのか分からないもの」を暫定対応として残さないためである。

| 状態 | 意味 |
| --- | --- |
| 未解決 | 暫定の扱いのまま。解消条件が満たされていない |
| 解消済 | 正式な実装に置き換わった |

## P-001 演算結果がゼロのときの符号

| 項目 | 内容 |
| --- | --- |
| 状態 | **解消済** (2026-09-03、Hercules による V2 検証で決着) |
| 場所 | `Decimal.fromBigDecimal`, `Decimal.withAlgebraicSign` |
| 関連要件 | FR-040, FR-042, 検証レベル V2 |

**当初の暫定の扱い**: すべての演算でゼロ結果に正号を与えていた。

**実測で判明したこと**: Hercules 上で各命令を実行した結果、**ゼロ結果の符号は命令ごとに規則が異なる**。
これは Principles of Operation の記述からは読み取れなかった点であり、暫定のままでは
乗除算で誤ったバイト列を生成していた。

| 命令 | ゼロ結果の符号 | 実測例 |
| --- | --- | --- |
| `AP` / `SP` | **常に正**。オペランドが両方とも負のゼロでも正になる | `000D` + `000D` → `000C` |
| `ZAP` | ゼロは**正へ正規化**。非ゼロは元の符号を保つ | `000D` → `000C`、`005D` → `005D` |
| `MP` | **代数の規則どおり**。負のゼロが生じる | `0000000C` x `5D` → `0000000D` |
| `DP` | **代数の規則どおり**。商・剰余ともに負のゼロが生じる | `0000000D` ÷ `5C` → 商 `00000D`、剰余 `0D` |

**行った修正**: `Decimal.multiply` / `divide` / `remainder` を、結果がゼロでも代数の符号を
保つように変更した (`withAlgebraicSign`)。加減算は従来どおりゼロ結果に正号を与える。
剰余の符号は被除数に従う。

**裏付け**: `DecimalArithmeticOracleTest` (検証レベル V2)。
Hercules 上での実行結果とランタイムの出力をバイト列で突き合わせている。

## P-003 NUMPROC(PFD) における不正ニブルの解釈

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `PackedDecimal.decode`, `ZonedDecimal.decode` |
| 関連要件 | FR-033, FR-205 |

**暫定の扱い**: `NUMPROC(PFD)` では妥当性検査を行わない。数字として妥当でないニブル
(0xA〜0xF) に出会った場合は、その値を 10 で割った余りを数字とみなす。

**なぜ暫定か**: これは仕様上の未定義領域であり、参照実装でも結果は保証されない。
ホストの実際の挙動は、コンパイラが生成した命令列に依存する
(例えば `PACK` を経由するか `CVB` を経由するかで異なりうる)。
現在の「10 で割った余り」という解釈には何の裏付けもない。

**解消条件**: 要件 FR-205 の 2 モード方式に組み込む。
既定 (`UndefinedBehavior.SAFE`) では検査して `DataException` を投げ、
互換モード (`MIMIC`) では Hercules から採取した実際の挙動を再現する。
現在の実装は `SAFE` / `MIMIC` の区別を持たないまま `MIMIC` 相当の動作をしており、この点が要件と乖離している。

## P-007 内部演算に BigDecimal を用いている

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `Decimal` |
| 関連要件 | NFR-002, NFR-005 |

**暫定の扱い**: 10 進演算の内部実装に `java.math.BigDecimal` を用いている。
負のゼロを表現できないという `BigDecimal` の制約は、符号を独立したフィールドとして
保持することで回避している。

**なぜ暫定か**: 要件 NFR-002 は「`BigDecimal` への変換をホットパスで避け、バイト列上で直接演算する
実装を優先する」としている。現在の実装はこれを満たしていない。

**なぜ今はこれでよいか**: 要件 NFR-005 は「性能のためであっても互換性を犠牲にする最適化は行わない」
としている。正しい意味論を先に確定させ、その振る舞いを固定するテストを揃えてから最適化するほうが、
逆順よりも安全である。丸めモードが `java.math.RoundingMode` の 8 モードと 1 対 1 で対応するため、
初期実装としては素性がよい。

**解消条件**: ベンチマークを整備し (NFR-001)、10 進演算がホットパスであることを実測で確認したうえで、
パック10進バイト列上の直接演算へ置き換える。置き換えの前後で全テストが同一結果になることを条件とする。

## P-008 英数字編集 (ALPHANUMERIC_EDITED) の編集処理が未実装

| 項目 | 内容 |
| --- | --- |
| 状態 | **解消済** (2026-09-03) |
| 場所 | `AlphanumericEditor` |
| 関連要件 | FR-030, FR-060 |

`AlphanumericEditor` を実装した。送出データを `A` / `X` の文字位置へ左から順に詰め、
挿入文字 (`B` は空白、`0` はゼロ、`/` は斜線) をその位置へ置く。

(設計文書 20 の「V2 にできない領域について」を参照)。

## P-009 中間結果の桁数規則が未実装

## P-013 COBOL の MOVE がパック10進の負のゼロを保つかどうか

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `NumericItem.encode` / `decode` (ランタイム側)、コンパイラ側は未着手 |
| 関連要件 | FR-020, FR-060 |

**判明したこと**: P-001 の検証の副産物として、`ZAP` 命令が**負のゼロを正のゼロへ正規化する**ことが
分かった (`000D` → `000C`)。一方 `MVC` は単なるバイト転記なので符号ニブルをそのまま保つ。

したがって COBOL の `MOVE` がパック10進の負のゼロを保つかどうかは、
**コンパイラがどちらの命令を生成するかで決まる**。参照実装は、送出側と受取側の PICTURE が
同一なら `MVC`、異なるなら `ZAP` を生成すると考えられるが、未確認である。

**現在のランタイムの扱い**: `NumericItem` の復号・再符号化は符号を保つ (`MVC` 相当)。

**なぜ重要か**: 負のゼロを含むバイト列が `MOVE` を通ったときに変化するかどうかは、
出力ファイルのバイト列に直接現れる。要件 FR-020 の L3 互換の対象である。

**解消条件**: 参照実装が `MOVE` に対してどの命令を生成するかを、PICTURE と USAGE の
組み合わせごとに確定させる。実機のコンパイラリストが得られないため、
仕様書の記述と、生成コードとして自然な選択の両面から決め、
コンパイラ (P0-b) の実装時に方針を固定する。ランタイム側は両方の意味論を提供できるよう、
`MVC` 相当 (符号保持) と `ZAP` 相当 (ゼロを正規化) を別の関数として用意する。

## P-014 数値編集の一部が V2 の裏付けを持たない

| 項目 | 内容 |
| --- | --- |
| 状態 | **一部解消** (2026-09-03、浮動挿入を `EDMK` で検証)。固定符号と全桁抑制は未解決 |
| 場所 | `NumericEditor` / `EditMask` |
| 関連要件 | FR-030、検証レベル V2 |

**解消した部分: 浮動挿入**

平の `ED` では浮動挿入を表現できない。記号を置く位置が値によって変わるためである。
`EDMK` は `ED` と同じ編集を行ったうえで<b>最初の有効数字の位置</b>を汎用レジスタ 1 に残す。
そこから 1 を引いた位置へ記号を書き込めば浮動挿入になる。

```
LA   1,<有意性開始子の 1 つ後ろ>   値がゼロで EDMK がレジスタを更新しない場合に備える
EDMK マスク,ソース                 編集し、最初の有効数字の位置をレジスタ 1 へ
BCTR 1,0                          1 つ手前へ
MVI  0(1),記号                     そこへ記号を書き込む
```

この命令列で `$$$,$$9.99`、`$$$9.99`、`$$$$9`、`----9`、`---9.99`、`+++9.99` の
6 種 x 値 9 種の 54 件が `NumericEditor` と一致した。

記号そのものの選択 (`+` なら符号に応じて `+` / `-`、`-` なら負のときだけ `-`) は
検証では Java 側で決めている。実機側で分岐させるには条件分岐命令が必要であり、
検証の焦点である<b>記号を置く位置</b>とは別の話であるためである。位置は完全に実機が決めている。

**残っている部分**

| 機能 | なぜまだ V2 にできないか |
| --- | --- |
| 固定符号 (`+9(4)`、`-9(4)`) | 符号の位置は固定なので `ED` の後に `MVI` で書けばよいが、抑制位置を持たない PICTURE は `ED` 自体が使えない (参照実装は `UNPK` と挿入で処理していると考えられる) |
| 全桁が抑制対象の PICTURE (`ZZZZ`、`****`、`***.**`) | 「値がゼロなら項目全体を抑制する」という COBOL 固有の規則を持ち、`ED` 単独では実現されていないと考えられる |
| `BLANK WHEN ZERO` | 同上 |

**なぜ重要か**: 特に全桁抑制の PICTURE については、`***.**` に値ゼロを編集した結果が
`"***.**"` なのか `"***.00"` なのか `"******"` なのかが仕様の読み方で分かれる。
現在の実装は `"***.**"` を返すが、裏付けがない。

**解消条件**: 参照実装がこれらの PICTURE に対してどの命令列を生成するかを確定させる。
確定できれば同じ命令列を `cobol-oracle` で組み立てて実行し、V2 へ引き上げる。

## P-015 符号ニブルの正規化のタイミング

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `PackedDecimal.encode`, `ZonedDecimal.encode` |
| 関連要件 | FR-031, FR-033 |

**実測で判明したこと**: `PACK` 命令は**符号ニブルをそのまま移す**。ゾーン10進の最右端バイトの
ゾーンが `F` なら、パック10進の符号ニブルも `F` になる。`A` なら `A`、`B` なら `B` のままである。
優先符号 (`C` / `D`) への正規化は行われない。

**現在のランタイムの扱い**: `PackedDecimal.encode` は符号を解釈したうえで、常に優先符号
(`C` / `D`、符号なし項目は `F`) を書き出す。したがって `F` / `A` / `B` の符号を持つ入力に対して、
`PACK` の結果とはバイト列が一致しない。

**どちらが正しいか**: これは命令の挙動ではなく<b>コンパイラが何を生成するか</b>で決まる。
`NUMPROC(NOPFD)` では参照実装は符号を正規化するコードを生成し、`NUMPROC(PFD)` では
正規化を省くとされている。つまり `MOVE` の結果のバイト列は `NUMPROC` の指定に依存する。

現在の実装は常に正規化する (`NOPFD` 相当) が、`NUMPROC(PFD)` を指定した場合に
正規化を省くべきかどうかを実装に反映していない。

**なぜ重要か**: 正規化の有無は出力ファイルのバイト列に直接現れる。要件 FR-020 の L3 互換の対象である。

**解消条件**: `NumericItem` の符号化に `NumProcMode` を反映させ、`PFD` では入力の符号ニブルを
温存する経路を設ける。そのうえで、参照実装が `NUMPROC` の各指定でどちらを生成するかを確定させる。
P-013 (`MOVE` が `MVC` か `ZAP` か) と同じ問題圏にあり、コンパイラ (P0-b) と一体で決める。

## P-029 PERFORM を段落のメソッド呼び出しで実装している

| 項目 | 内容 |
| --- | --- |
| 状態 | **解消済** (2026-09-04、段落が「次の行き先」を返す形にして `GO TO` を実装) |
| 場所 | `ProgramGenerator.emitParagraph` / `emitDispatch` / `emitPerformMethod` |
| 関連要件 | FR-061 |

**当初の暫定の扱い**: 段落をそれぞれ別のメソッドとして出し、素直に流れる実行は上から順に
呼び、`PERFORM P` は P のメソッドだけを呼ぶ形にしていた。この形なら「`PERFORM` は次の
段落へ流れ込まない」という規則が自然に出るが、<b>`GO TO` が書けない</b>のが難点であった。
段落の並び全体を 1 つのメソッドにして分岐で書くか、状態機械へ変えるしかないと考えていた。

**実際に採った形**: メソッドのままでよかった。変えたのは 1 点だけである。

<b>段落のメソッドが「次にどこへ行くか」を返す</b>ようにした。最後まで流れたら `-1`、
`GO TO` で飛ぶならその段落の番号である。`GO TO` は素直な `return` になり、段落の途中でも
入れ子の `IF` や `PERFORM` の中でも、その場で抜けられる。

呼ぶ側は「段落の範囲を実行する」1 つのメソッド (`performRange`) にまとめた。素直に流れる
実行は「全段落を 1 つの範囲として実行する」ことであり、`PERFORM A THRU B` と同じ機構で書ける。
違いは範囲の終わりがどこかだけである。飛び先は実行時にしか分からないため、番号から段落の
メソッドへ振り分ける表引きの分岐 (`dispatch`) を挟んでいる。

**なぜ状態機械にしなくて済んだか**: 状態機械が要ると考えたのは、`PERFORM` の戻り先が
<b>段落の途中</b>にあるためであった。段落を区切り直して番号を振る話になり、大掛かりになる。
しかし戻り先を JVM の呼び出し規約に預けてしまえば、番号を振る必要があるのは
<b>飛び先だけ</b>である。飛び先は段落の先頭しかないので、段落の番号がそのまま使える。

**参照実装との差**: 参照実装は範囲ごとに戻り口を 1 つ持つため、同じ範囲を入れ子に
`PERFORM` すると戻り口が壊れる。こちらは JVM の呼び出しスタックを使うので壊れない。
仕様が結果を保証しない領域であり、こちらのほうが安全側である (要件 FR-205 の考え方)。

`EXIT` も実装した (何もしない文である)。
`PERFORM VARYING` … `AFTER` … は先に実装してあった。段の増減は繰り返しの<b>指定</b>の
話であり、中身をどう呼ぶかとは独立なので、この暫定の扱いに縛られなかった。

**残っている形**: `GO TO ... DEPENDING ON` と `ALTER` は文法が受け付けない。

**どこがずれているか**: `READ` の前と `CLOSE` のあとにレコード領域の中身が保証されない
(規格上は未定義) 点を再現していない。いまは作業場所の一部なので、初期イメージのまま残る。
記憶域の中身を外から見る手立てを実装すると、作業場所の長さがレコード領域の分だけ長いことも
差として出る。

**解消条件**: ファイルごとの記憶域を `planAddress` の 4 つ目として足す。位置を揃える処理は
そのとき不要になり、`FD` 配下の 01 はすべて位置 0 から始まる。連絡節と特殊レジスタで作った
仕組みがそのまま使える。

## P-042 照合順序を差し替えられない

| 項目 | 内容 |
| --- | --- |
| 状態 | **一部解消** (2026-09-08、条件と `SEARCH ALL` と `CHAR` / `ORD` で差し替えられる) |
| 場所 | `Alphabet` / `CollatingSequence` / `SortWork.compare` / `IndexedDataSet.ByteKey` |
| 関連要件 | FR-054, FR-100, FR-120 |

**解消した部分**: `SPECIAL-NAMES` の `ALPHABET` 句 (`STANDARD-1` / `STANDARD-2` /
`NATIVE` / `EBCDIC` と、定数を並べる形。`ALSO` と `THRU` を含む) と、`OBJECT-COMPUTER` の
`PROGRAM COLLATING SEQUENCE` を実装した。

持ち方は<b>バイト値から位置への 256 個の表</b>である。比較はバイト値ではなく位置で行う。
`ALSO` で並べた文字は同じ位置を持つので、比べると等しくなる。表は翻訳時に決まるので、
生成したクラスの定数として持たせている。

`FUNCTION CHAR` と `FUNCTION ORD` も、この並びの位置で答える。定義がそうなっており、
照合順序を差し替えれば<b>両方の答えが変わる</b>。

**残っている部分**: `SORT` と `MERGE` の鍵、索引編成の索引、`SORT ... COLLATING SEQUENCE IS`。

`PROGRAM COLLATING SEQUENCE` が書かれたプログラムで `SORT` / `MERGE` を書くと、
<b>誤りとして報告する</b>。ここだけコードページの並びで並べると、同じプログラムの中で
場所によって順序が食い違うためである。黙って違う順に並べるより、書けないと言うほうがよい。

**どこがずれているか**:

- `SORT` / `MERGE` を含み、かつ照合順序を差し替えたプログラムは翻訳できない
- 索引編成のファイルの索引は、いまもコードページの並びで並ぶ
- `STANDARD-1` と `STANDARD-2` を同じ並び (ISO/IEC 646、いわゆる ASCII の順) として
  扱っている。規格上は別物だが、どちらも 128 文字の集合であり、EBCDIC のコードページ
  から見た並びは変わらない
- ASCII に無い文字 (EBCDIC の 128 個以上の文字) の位置を規格は決めていない。
  こちらでは<b>ASCII に写る文字をすべて並べたあと、コードページの並びのまま</b>続ける

**解消条件**: `SortWork` と `IndexedDataSet` が照合順序を受け取る形にする。
`SORT ... COLLATING SEQUENCE IS` はその上に載る。

どれもファイルをそのまま置くだけだった。目録をディレクトリそのものとしていたので、

| 処置 | 置き場 | 目録 |
| --- | --- | --- |
| `DELETE` | 消す | 外す |
| `KEEP` | 残す | 触れない。`NEW` で作ったものは載らないまま |
| `CATLG` | 残す | 載せる |

**残したこと**: 覚えのない名前が置き場にあれば、目録に載っているものとして扱う。置き場は
人がファイルを置くディレクトリでもあり、そこへ置いたものを目録にも書かせるのでは道具と
して使えないからである。`NEW` で作ったものにはその場で「載っていない」と書き留めるので、
`KEEP` と `CATLG` の区別はこの既定に流されない。

ボリュームが 1 つしかないことは暫定判断 P-055 へ、`DISP` を書かない割当が目録を見ない

- `OUTFIL` の `HEADER2` / `TRAILER2` を `LINES=n` なしで書くと<b>全体が 1 頁</b>になる。
  ホストは導入時の既定 (ふつう 60 行) で切る。既定の値を勝手に決めると、頁の切れ目が
  実機と違う場所に入るので、書かれていないうちは切らないほうを採った
- `&DATE` は `mm/dd/yy`、`&TIME` は `hh:mm:ss` で出す。ホストにはほかの形もあるが、
  接尾辞 (`&DATE1` など) は読めない
- `OUTFIL` の見出しと末尾からレコードの場所 (`p,l`) は参照できない。参照できる範囲が

- `ICETOOL` の `SPLICE` は、鍵が同じものが 3 本以上あるとき<b>後のものを順に重ねる</b>。
  ホストの既定 (`WITHALL` を書かないとき) は組ごとの扱いが違う。2 本の組ではどちらも
  同じ答えになるので、実資産に 3 本以上の組が現れた段で決める。`KEEPBASE` と `USING` は
  誤りとして報告する
- `ICETOOL` の `RESIZE` は入力を<b>一続きのバイト列として</b>数え直す。`TOLEN` が元の
  長さで割り切れるときはホストと同じ答えになるが、割り切れないときの端の扱い
  (ここでは空白で埋める) は実機で確かめていない
- `ICETOOL` の `SUBSET` に `USING` は書けない。`INPUT` と `OUTPUT` は、`USING` が無ければ
  同じことなので区別していない
- `ICETOOL` の `VERIFY` は `ZD` / `PD` / `FI` / `FS` / `UFF` / `SFF` を受ける。`FI` と
  `UFF` と `SFF` はどんなバイトでも数として読めるので必ず通る。ホストがこれらを受けるか
  どうかは確かめていない
- `STATS` と `AVG=` の平均は 0 の位で切り捨てる。負の数をどちらへ丸めるかは実機で
  確かめていない
- `ICETOOL` の覚え書きの番号と文面 (`ICE607I` / `ICE608I` / `ICE609I` / `ICE610I` /
  `ICE611I` / `ICE612I`) は実機で確かめていない。桁揃えもしていない
- `SORT` の覚え書きはホストの書式に似せていない。`ICE143I` / `ICE054I` / `ICE052I` /
  `ICE224I` の 4 種だけであり、行数や統計は合わない
- `ICETOOL` の `DISPLAY` と `OCCUR` の報告書もホストの書式に似せていない。見出しと値が
  並ぶだけで、桁揃え・改頁・小計・`HEADER` / `BLANK` / `TOTAL` は無い。同じ仕掛けは
  `OUTFIL` の側に入ったので、揃えるならそちらを呼ぶ形になる
- `ICETOOL` の `SELECT` は `ON` に書いた場所で並べ替えてから組にする。ホストは入力の順を
  保つ形も選べるが、ここでは並べ替えた順で出る
- `FS` (`CSF`) は空白と 1 つの符号と数字だけを受ける。全部空白の欄は 0 として通す。
  `UFF` と `SFF` は<b>数字だけを拾い</b>、ほかの文字は読み飛ばす。`SFF` の符号は前の
  `-` か、後ろの `-` か `CR` で見る。ホストがどこまでを許すかは実機で確かめていない
- `TO=` に `LENGTH=` を書かないときの大きさは、元の場所が持てる桁数から決める
  (`ZD` は桁数、`PD` は桁数の半分と 1、`FI` と `BI` は 2 / 4 / 8 のいちばん小さいもの)。
  ホストの既定の表とは突き合わせていない
- `TO=ZD` は符号を最後の桁の上位 4 ビットへ置く。正の数は `C` になるので、印字すると
  最後の桁が英字に見える。ホストの `UNPK` と同じだが、`TO=` がいつも符号を付けるか
  どうかは確かめていない
- `EDIT=` の型で桁を表すのは `I` (頭の 0 を消す) と `T` (消さない) と `S` (符号) だけで
  ある。ほかの文字はそのまま入るが、意味のある数字が出る前にあるものは空白になる。
  通貨記号を数の直前まで寄せる形 (浮動する `$`) にはならない
- `EDIT=` の型より桁が多い数は<b>上の桁が落ちる</b>。ホストが誤りとして報せるかどうかは
  確かめていない
- `IEBGENER` の `MAXFLDS` / `MAXGPS` / `MAXLITS` は、書いた数がそれを超えていれば止める。
  復帰コード 12 と文面は実機で確かめていない。`MAXNAME` は `MEMBER` を読めないので数え
  ない
- `IEBGENER` の組は、目印の付いたレコードを<b>組に入れてから</b>次へ移る。組を使い切った
  あとのレコードは最後の組のままである。ホストがそこで何をするかは確かめていない
- `IEBGENER` の `PZ` は入力 n バイトから 2n-1 桁を、`ZP` は入力 n 桁から n/2+1 バイトを
  作る。ホストの `UNPK` / `PACK` と同じ数え方だが、`FIELD` の長さがどちらの側を指すかは
  実機で確かめていない
- `IEBGENER` の可変長レコードは、制御文を書くと<b>編集できない</b>と報せる。RDW を組み
  直す道が要る (`SORT` の `INREC` / `OUTREC` と同じ理由である)

**解消条件**: 制御文の骨組みと欄の書式は揃った。残っているのは<b>報告書の見た目</b>で
ある。あらかじめ決まった編集の型 (`M0` から `M26`)、`SIGNS=`、覚え書きの番号と桁揃えは、
ホストの出力を読む道具が実際に使われていることが分かった段で、実機の出力と突き合わせて
決める。

## P-050 COPY で取り込んだ文の行番号が入らない

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `ProgramGenerator.planLine` |
| 関連要件 | FR-142 |

**暫定の扱い**: クラスファイルの行番号表へ入れるのは、<b>そのプログラム自身のファイルから
来た文だけ</b>である。`COPY` で取り込んだ文には行番号を付けない。

**なぜこうしたか**: クラスファイルの `SourceFile` は 1 つしか書けない。取り込んだ文の

**どこがずれているか**: 写本の中の文で止まると、呼び出し履歴の行番号は<b>その手前にある

止まった文そのものではない。

**解消条件**: JSR-45 (`SourceDebugExtension`) で複数のファイルを結び付けられる。
写本を多用する実資産を動かす段で、必要になったら入れる。

## P-051 診断出力の書式がホストのものではない

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `Diagnosis` / `DumpLevel.of` |
| 関連要件 | FR-142, FR-143 |

**暫定の扱い**: 診断出力の<b>中身</b>はホストの `CEEDUMP` に揃えたが、並べ方と字面は

細かさへ読み替えるだけである。

**解消条件**: 実資産の運用でホストの書式を前提とした道具が使われていることが分かったら、

## P-052 領域不足の異常終了コードを 1 つにまとめている

| 項目 | 内容 |

| 状態 | 未解決 |
| 場所 | `FileOperationException.abendCode` / `Jcl` の `SPACE=` |
| 関連要件 | FR-141 |

**暫定の扱い**: 書ける領域を使い切ったことを、順編成では `S037` にまとめている。

## P-053 領域の限り・形・開く段の検査が順編成にしか効かない

| 項目 | 内容 |
| --- | --- |
| 状態 | **解消済 (2026-09-07)** |
| 場所 | `DataSetAllocation` / `RecordFraming` / `UtilityProgram` |
| 関連要件 | FR-113, FR-141 |

**何が問題だったか**: 「割り当てた領域を使い切ったら書けない」「形が壊れていたら読めない」
「無いメンバは開けない」の 3 つを、順編成にだけ実装していた。相対編成と索引編成は
`SPACE=` を無視し、半端なバイトが残っていても気付かず、区分データセットのメンバも
見分けなかった。ジョブのユーティリティ (`IEBGENER` / `SORT` / `ICETOOL` / `IDCAMS`) は
生バイトをそのまま読むので、どの検査も通らなかった。

**どう解消したか**: 3 つとも<b>レコードの探し方とは関わりがない</b>ので、編成ごとに
書き分ける理由がない。割当てが決めること (領域の限り・メンバかどうか) を
`DataSetAllocation` へ、バイト列の切り方と「形が壊れている」の意味を `RecordFraming` へ
1 つずつ置き、3 つの編成とユーティリティがそこを通るようにした。

| 起きたこと | 順編成 | 相対編成 | 索引編成 | ユーティリティ |
| --- | --- | --- | --- | --- |
| 割り当てた領域を越えた | `34` | `24` | `24` | `S037` |
| 形が壊れている | 読んだ位置で `30` | 読んだ位置で `30` | 開いた時点で `30` | `S001` |
| 無いメンバを開いた | `S013` | `S013` | `S013` | `S013` |
| 区分データセットそのものを開いた | `S013` | `S013` | `S013` | `S013` |

決めたことが 3 つある。

1. <b>領域を越えたときのコードは編成で違う</b>。順編成 (QSAM) は `34`、鍵で引く編成
   (VSAM) は `24` である。ホストで仕組みが違い、QSAM はアクセス法が場所を取りにいって
   失敗するのでプログラムがコードを見る前に異常終了するが、VSAM はコードを返す。
   受け止め手がないときの終わり方も `S037` と `U4038` に分かれる。
2. <b>索引編成だけは開いた時点で `30`</b> になる。順編成と相対編成は位置とバイト列の
   並びが対応しているので「壊れた場所まで読める」と言えるが、索引編成は読む順序が鍵の順
   であり、どこまで読めるとは言えない。
3. <b>ユーティリティも同じ検査を通す</b>。状態コードを返す先がないので、そのまま
   異常終了にする。「入力が無い」(`RC=12`) は道具の言い分だが、こちらは割当てが通って
   いるのに開けないという、アクセス法の側の話である。

相対編成では空けた番号のぶんも場所を取る。番号が住所である以上、10 番へ書けば 1 番から
10 番までの場所が要るからである。

**残っていること**: 領域不足の異常終了コードを分けていないこと (暫定判断 P-052) と、
いちどに読み込んでいること (暫定判断 P-038) はそのままである。後者のため、
ユーティリティが領域を越えたときに<b>途中まで書いたものが残らない</b> —
ホストは書けなくなったところまでを残す。`IEBCOPY` だけは書く単位がメンバなので、
足りなくなるまでに写したメンバは残る。

## P-054 DISP を書かない割当は目録を見ない

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `JobRunner.allocateDataSet` / `Disposition.Status.ANY` |
| 関連要件 | FR-131, FR-132, FR-133 |

**暫定の扱い**: 宣言的形式で `DISP=` を書かなかった DD は状態 `ANY` になり、何も確かめず、
何も作らず、<b>目録も見ない</b>。置き場の場所をそのまま使う。目録に載っていない
データセットでも `VOL=` を書かずに届く。

データセットの範囲が違う。2 つのフロントエンドは同じ内部モデルへ落ちるという原則から
外れている唯一の場所である。

**解消条件**: 宣言的形式に「読む/書く」を言う書き方を入れる段で決める。それが入れば
`ANY` は要らなくなる。

## P-055 ボリュームが 1 つしかない

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `SystemCatalog` / `Jcl.serialOf` |
| 関連要件 | FR-112, FR-131 |

**暫定の扱い**: 置き場はディレクトリ 1 つであり、ボリュームという入れ物は無い。
`VOL=SER=通し番号` は<b>「目録を通さず置き場を直に見る」という合図としてだけ</b>効き、
通し番号そのものは何とも照合しない。どんな綴りを書いても同じである。複数ボリュームに

- 通し番号を間違えたジョブが通ってしまう。ホストでは見つからない
- 目録は名前が<b>載っているかどうか</b>しか覚えていない。どのボリュームにあるかは

- 同じ名前のデータセットを別のボリュームに置けない

**解消条件**: 物理格納先を差し替えられるようにする段 (要件 FR-112、暫定判断 P-039) で

## P-056 区分データセットにディレクトリがない

| 項目 | 内容 |
| --- | --- |
| 状態 | **解消済 (2026-09-07)** |
| 場所 | `PartitionedDataSet` / `Iebcopy` / `Ikjeft01` / `Jcl.memberOf` |
| 関連要件 | FR-053, FR-113 |

**何が問題だったか**: ライブラリをディレクトリ、メンバをその下のファイルとして持っていた
だけで、ホストの<b>ディレクトリ (メンバの一覧)</b> にあたるものが無かった。メンバを 1 つ

**どう解消したか**: 一覧を別に持たず、置かれているファイルから引くことにした。持たせれば
`OPEN OUTPUT` と削除のたびに合わせ込む手間が要り、<b>メンバがあるかどうかの拠り所が
2 つになる</b>。合わなくなったときにどちらが正しいとも言えない。移行の途中で手で置いた
ファイルがそのまま見えるのも、引くほうの利点である。

決めたことが 3 つある。

1. <b>メンバ名の決まりが、ディレクトリの中身を決める</b>。ライブラリの下には覚え書きの
   サイドカー (`PAYROLL.meta`) も並ぶので、ファイルが並んでいるだけでは一覧が言えない。
   ホストのメンバ名は 8 文字まで、英大文字と数字と `@ # $`、先頭は数字でない。`.` は
   入らないので覚え書きはメンバになりえない。名前の決まりを入れて初めて一覧が言えるので、
   この 2 つは同じ増分でしか入れられなかった。同じ決まりを JCL を読む段でも使う —
   `DSN=MY.LIB(TOOLONGNAME)` は実機ではジョブを読む段で弾かれ、ステップは動かない。
2. <b>並びはコードページのバイト順である</b> (要件 FR-053)。ホストのディレクトリは名前の
   昇順であり、EBCDIC では英字が数字より前に来る。Java の `String` の順は逆であり、
   `PAYA` と `PAY1` が入れ替わる。ライブラリを丸ごと写したジョブの<b>出力そのものが実機と
   別のバイト列になる</b>ので、細かい違いでは済まない。並べる場所は `IEBCOPY` だけでなく
   `LISTDS` と `IDCAMS LISTCAT` にもあるため、`PartitionedDataSet` に 1 つだけ置いた。
3. <b>新しく作るデータセットが区分になるかは `SPACE=` の 3 つ目が決める</b>。メンバを
   名指せば当然そうだが、メンバを言わずにライブラリだけを作ることがあり (`IEBCOPY` の
   写し先)、そのときに拠れるのはディレクトリブロックの数しかない。

**残っていること**: 別名 (`ALIAS`)、ISPF の統計、ディレクトリブロックの使い切りは無い
(暫定判断 P-059)。いずれもメンバの外に持つ覚え書きを要るので、引くだけでは足りない。
`IEBCOPY` のアンロード形式 (区分データセットを順編成の 1 本へ落とす) も無い。

## P-057 SELECT OPTIONAL は無いメンバの検査に勝つ

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `DataSetAllocation.opening` |
| 関連要件 | FR-103, FR-113 |

**暫定の扱い**: 区分データセットのメンバが無いとき `S013` で止める (要件 FR-113) が、
プログラムが `SELECT OPTIONAL` と書いていればそちらを優先し、空のファイルとして開いて
`05` を返す。

**なぜこうしたか**: `SELECT OPTIONAL` は<b>プログラムが明示的に「無いこともある」と
言っている</b>ものである。無いときの手当てが書いてあるのだから、書き手の言い分を
覆すよりは通すほうがよい。逆にすると、月次だけ作られるメンバを `OPTIONAL` で受けている
資産が動かなくなる。

**いま危ないこと**: ホストで確かめていない。実機の `S013` はアクセス法が出すもので、
`SELECT OPTIONAL` は言語処理系が持つ概念だから、<b>ホストでは `OPTIONAL` が効かずに
`S013` になる</b>可能性がある。そうだとすれば、`OPTIONAL` で受けたメンバの綴りを間違えた
ジョブが、実機では止まりここでは 0 件処理して正常終了する。

**解消条件**: `SELECT OPTIONAL` を書いた区分データセットのメンバを、無い状態で
`OPEN INPUT` する COBOL を実機で走らせて確かめる。外部の振る舞い基準 (Hercules) を
使う段で確かめられる。

## P-058 IKJEFT01 は LISTDS しか分からない

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `Ikjeft01` |
| 関連要件 | FR-137 |

**暫定の扱い**: バッチの TSO (`IKJEFT01`) は `SYSTSIN` の行を上から読むが、分かるのは
`LISTDS` と、区分データセットのメンバに対する `RENAME` / `DELETE` だけである
(`RENAME ... ALIAS` を含む。暫定判断 P-059 の解消で足した)。ほかのコマンドは
`IKJ56500I` を出して復帰コード 12 で終わる。
引用符で囲まない名前には TSO の接頭辞 (利用者 ID) が付くはずだが、接頭辞を持たないので
囲んでも囲まなくても同じに扱う。

**どこがずれているか**:

- 実資産の `IKJEFT01` は DB2 の `DSN` とプログラムの `CALL` に使われていることが多い。
  どちらも動かない
- `ALLOCATE` / `FREE` / `LISTALC` が無い。`DELETE` と `RENAME` は<b>メンバにしか</b>
  効かない — データセットそのものを消す・名前を変えるのは `IDCAMS` の `DELETE` /
  `ALTER` と重なるので、そちらから先に入れる
- `RENAME` / `DELETE` が出す覚え書きの文言 (`IKJ58012I` / `IKJ58013I` / `IKJ56712I`) は
  実機で確かめていない。復帰コードは合っていても、文言を拾っている運用があれば外れる
- CLIST と REXX (`%名前`、`EXEC`) が無い
- `LISTDS` の `BLKSIZE` は分からないので `**NONE**` と書く。ライブラリ自体の `RECFM` /
  `LRECL` も同じである — 覚え書きを持っているのはメンバのほうである
- 接頭辞が無いので、`LISTDS PAY.LIB` と `LISTDS 'PAY.LIB'` を区別できない。実機では
  前者が `利用者ID.PAY.LIB` を指す

**なぜこうしたか**: 一覧を出す道具が要るのは<b>ディレクトリを入れた増分</b>である。TSO を
広く実装するのは別の話であり、いま入れても確かめようがない。知らないコマンドを読み飛ばして
0 で終わらせないのは、それをすると<b>何もしていないステップが成功したことになる</b>から
である。実機では動いていた `DSN` のステップが、黙って何もせず後続へ流れる。

**解消条件**: 実資産に現れた TSO コマンドを数えて決める。`ALLOCATE` と `DELETE` は
`IDCAMS` と重なるので、そこから先に入れる。接頭辞は利用者 ID を持つ段で決める。

## P-059 ディレクトリに別名と統計がない

| 項目 | 内容 |
| --- | --- |
| 状態 | **解消済 (2026-09-07)** |
| 場所 | `PartitionedDataSet` / `MemberStatistics` / `DataSetAllocation` / `Iebcopy` / `Ikjeft01` |
| 関連要件 | FR-113, FR-141 |

**何が問題だったか**: ディレクトリを名前の並びとしてしか持っていなかった。<b>項目そのもの</b>
が無いので、次の 3 つがどれも書けなかった。

- 別名 (`ALIAS`) — 同じメンバへ向けた別の名前。版を上げたモジュールに古い名前を残すのに
  使われている
- ISPF の統計 — 版・更新日時・行数・直した人。実資産の運用がこれを見ていることがある
- ディレクトリブロックを使い切って止まること。`SPACE=` の 3 つ目は読んでいたが、
  <b>いくつ入るか</b>を決めていなかった

**なぜひと続きなのか**: ホストのディレクトリの項目は、名前 8 バイト・位置 3 バイト・
標識 1 バイトの<b>12 バイトに利用者データが付いた</b>大きさである。ISPF の統計はその
利用者データ 30 バイトであり、付けば項目は 42 バイトになる。1 ブロック (256 バイト、
うち先頭 2 バイトは使った長さ) に入る数が<b>21 と 6 で変わる</b>。統計を持たずに数だけ
決めれば、統計を入れた日に<b>止まる場所が動く</b>。別名も項目を 1 つ使うので同じ話である。

**どう解消したか**: どれも<b>置き場から引ける形</b>で持たせた。覚え書きの表を別に持って
「この名前は別名である」と書く手もあるが、そうすると名前があるかどうかの拠り所が 2 つに
なる — 暫定判断 P-056 で退けたのと同じ形である。

| 事柄 | 持ち方 | 拠り所 |
| --- | --- | --- |
| 別名 | 置き場のシンボリックリンク | 置き場を見れば分かる |
| 統計 | メンバの隣の `名前.stats` | 無ければ<b>統計を持たないメンバ</b> |
| ディレクトリの大きさ | ライブラリの `.meta` の `dirblks=` | ホストでもデータセットのラベルにある |

決めたことが 5 つある。

1. <b>別名はシンボリックリンクである</b>。ファイルとして置くのだから一覧に出るし、開けば
   中身が読める。`IEBGENER` も翻訳した資産も、別名だと知らないまま読める — ホストの別名が
   そう見えるのと同じである。元のメンバを消したときに<b>切れたリンクが残る</b>のも同じで、
   実機でも別名の項目はディレクトリに残り、開こうとして初めて失敗する。
2. <b>統計は書いた側が作らない</b>。ホストでも、ISPF の編集で書いたメンバには統計が付くが、
   プログラムが `OPEN OUTPUT` で書いたメンバには付かない。作ってしまうと<b>実機には
   無いはずの統計</b>が生える。`IEBCOPY` は持っていたものを持ち越すだけである — 写しは
   編集ではないので、版も更新日時も動かない。
3. <b>属性は別名の指す先から引く</b>。別名は覚え書きを持たない。引き直さないと、
   別名から読んだときだけレコードの切れ目が変わる。
4. <b>ディレクトリの大きさはライブラリの覚え書きに残す</b>。`SPACE=` を書いたのは作った
   ジョブだけで、あとからメンバを足すジョブは `DISP=SHR` としか書かない。DD の割当てに
   持たせる形も採れるが、それでは DD を通らない道具 (TSO の `RENAME`) から見えない。
5. <b>道具も同じ数で止まる</b>。翻訳した資産の `OPEN OUTPUT` だけで効かせると、同じ
   ライブラリが<b>書き手によって入る数を変える</b>ことになる。

そのついでに、ユーティリティが<b>新しいメンバを作れる</b>ようにした。`IEBGENER` /
`SORT` / `ICETOOL` / `IDCAMS REPRO` の書き先を読む側と同じ検査に通していたので、
無いメンバへ書こうとすると `S013` になっていた。書き先は無くてよい — これから作るのだから。

**残っていること**: 暫定判断 P-061 へ移した。

## P-060 世代データグループに版と自動作成がない

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `GenerationDataGroup`、`JobRunner.withGenerations`、`Idcams` |
| 関連要件 | FR-114, FR-137 |

**暫定の扱い**: 世代を `基底名.GnnnnV00` という普通のデータセットとして持ち、相対番号は
<b>ジョブの初めに 1 度だけ</b>絶対名へ直す。群れの一員かどうかは名前の形と目録で決まる。
基底の登録 (`LIMIT`、`EMPTY` / `NOEMPTY`、`SCRATCH` / `NOSCRATCH`) だけを置き場の
`.gdg` という覚え書きに書く。

**どこがずれているか**:

- 版 (`V00` の部分) が常に `00` である。ホストは同じ世代を作り直すと版が上がる。
  実資産で版を意識したジョブは多くないが、名前そのものは変わる
- 世代番号が 9999 を越えたときホストは 1 へ戻る。ここでは戻さず桁が増える。
  戻すと<b>古い世代を上書きする</b>ことになり、桁の増えた名前のほうがまだ気付ける
- SMS の属性 (`DATACLAS`、`STORCLAS`、`MGMTCLAS`)、`GDG` の `LIFO` / `FIFO`、
  `EXTENDED` (255 世代) を読まない
- `LISTCAT` が基底を 1 行で出すだけであり、`GDG BASE` の属性 (`LIMIT`、いま何世代か) を
  並べない
- `IDCAMS` の出す番号のうち、`IDC3211I` (世代が残る基底を `FORCE` なしで消した) は
  実機で確かめていない。ほかの番号も含め、字面は暫定判断 P-047 と同じ扱いである
- ロールインの時期を<b>ステップの終わり</b>に置いている。ホストの SMS 管理の世代には
  ジョブの終わりまで遅らせる指定 (`DEFERRED ROLL-IN`) があり、そこは合わない

**なぜこうしたか**: 世代の一覧を別に持たない、というのが芯である。持たせると「その世代が
あるか」の答えが<b>ファイルがある</b>と<b>覚え書きに載っている</b>の 2 つになる
(区分データセットのディレクトリと同じ理由、暫定判断 P-056 の解消)。名前の形と目録から
引けるので、版と番号の折り返しはそのぶん後回しにできる。

相対番号をジョブの初めに固定するのは<b>譲れない</b>。ステップごとに引き直すと、実機では
1 つのファイルへ 2 度書くジョブがここでは世代を 2 つ作り、しかも後続が読むのは片方だけに
なる。差が復帰コードではなく<b>データの欠落</b>として出るので、あとから気付けない。

**解消条件**: 版を使う資産か、9999 を越える運用が見つかった段で決める。SMS の属性は
記憶域の管理を持つ段 (要件 FR-112) と一緒でよい。

## P-061 ディレクトリの項目に足りないもの

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `PartitionedDataSet` / `MemberStatistics` / `DataSetAllocation.directory` |
| 関連要件 | FR-113, FR-137, FR-141 |

**暫定の扱い**: 別名と統計とディレクトリの使い切りは持たせた (暫定判断 P-059 の解消)。
そのうえで残っているものを 1 つにまとめる。

**どこがずれているか**:

- <b>止まる場所が早い</b>。ホストがディレクトリの空きを見るのは書き終えた `CLOSE`
  (`STOW`) のときであり、そこまでに書いたレコードは領域に残る。ここでは `OPEN` の段で
  止めるので、<b>入りきらなかったメンバのバイト列が残らない</b>。異常終了することは
  同じだが、後始末のジョブが半端なメンバを見つけるかどうかが変わる
- <b>異常終了コードが確かめられていない</b>。ここでは `S013` にしている。実機の
  ディレクトリ満杯は `S013` の理由コードか `SE37` かのどちらかであり、公開資料からは
  決められなかった。`IF (STEP.ABENDCC = SE37)` で受けている資産があれば取り違える
  (暫定判断 P-052 と同じ族の話である)
- <b>別名の項目に利用者データを持たない</b>。ホストの別名の項目は、指す先と同じ利用者
  データを持てる。ここでは別名の項目をいつも 12 バイトと数えるので、統計を持つメンバの
  別名が多いライブラリで<b>入る数を多めに見積もる</b>
- <b>統計を作るものが無い</b>。ISPF 相当の編集を持たないので、統計は移行で持ち込むか
  写しで持ち越すかのどちらかでしか生まれない。統計を出す一覧 (ISPF 3.4 相当、
  `IEHLIST LISTPDS`) も無い
- <b>`IEBCOPY` のアンロード形式が無い</b>。区分データセットを順編成の 1 本へ落とし、
  また戻す形である。資産を機械の間で運ぶのに使われている
- <b>シンボリックリンクを要る</b>。別名は置き場のシンボリックリンクなので、それを作れない
  ファイルシステム (権限のない Windows) では別名が作れない。開発と実行が Linux である
  うちは表に出ない
- <b>ディレクトリを詰め直さない</b>。ホストはメンバを消しても項目の跡が残り、圧縮
  (`IEBCOPY` の `COPY INDD=A,OUTDD=A`) で詰め直す。ここでは消せばすぐ空くので、
  <b>実機なら満杯のライブラリがここでは空いている</b>

**なぜこうしたか**: 止まる場所と異常終了コードは、どちらも<b>実機で確かめないと決められ
ない</b>。当てずっぽうで `SE37` にしても `S013` にしても、外れていれば同じだけ困る。
いま `S013` にしてあるのは、ディレクトリに入らないのが<b>開くという操作の失敗</b>であり、
無いメンバを開いたときと同じ位置付けだからである。

別名の利用者データと統計を作る道具は、どちらも<b>それを見る操作</b>が無いうちは形を
決められない。作っておいて後から出し方を変えるより、出す側と一緒に決めるほうがよい。

**解消条件**: 止まる場所と異常終了コードは、外部の振る舞い基準 (Hercules) を使う段で
確かめる。統計を出す一覧と `IEBCOPY` のアンロードは、実資産に現れた数で決める。
圧縮は、ライブラリを消しては足す運用が実資産に見つかった段でよい。

## P-062 検証基盤が翻訳までしか測っていない

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 (2026-09-07 に基盤を作った。測っているのは翻訳が通るかまで。同日、基盤が見つけた 3 つを直した) |
| 場所 | `cobol-verify` |
| 関連要件 | NFR-040, NFR-042, NFR-046、要件 13 章 (P0-b の受け入れ基準) |

**暫定の扱い**: CCVS85 と OSS コーパスを流す枠組みを作り、<b>翻訳が通るかどうか</b>を数え
ている。動かして答え合わせをする段はまだ無い。

**なぜこうしたか**: いまの合格率は 3.0% (202 本中 6 本) である。動かす段を先に作っても、
動かせるものが 6 本しかない。<b>測れるところから測る</b>ほうを採った。翻訳が通る本数が
増えれば、動かす段の値打ちも出る。

**どこがずれているか**:

- CCVS85 は<b>翻訳までしか見ていない</b>。検査プログラムは自分で `PASS` / `FAIL` を印字
  するので、動かして数えれば「正しく動くか」まで測れる。要件 NFR-040 が言う合格率は
  本来こちらである。いまの数は<b>受理率</b>であって合格率ではない
- 459 本のうち<b>202 本しか流していない</b>。入出力のモジュール (`SQ` / `RL` / `IX` /
  `ST`) が使う差し込み札を書いていないためである。書いていない札を勝手に埋めると、
  検査の道具が処理系の失敗を作ることになるので、流さないほうを採った
- 7 桁目の選べる行は<b>1 つも選んでいない</b>。いちばん素直な形になるが、選んだ形での
  検査は行っていない。ホストの処理系が何を選ぶかは実機で確かめないと決められない
- OSS コーパスの一覧 (`tools/verify/corpus.tsv`) が<b>空である</b>。仕掛けはできているが、
  行を足すのはライセンスを確かめる作業であり、確かめていないものを書いてはならない
  (要件 NFR-042)
- 合成ジェネレータ (要件 NFR-041) は加減乗除と数値編集の 4 件のみである。境界値の全列挙
  と pairwise カバリングアレイという打ち切り基準には届いていない
- ベンチマークの回帰検査 (要件 NFR-046) が無い
- 合格率に下限を課していない。数は記録して並べるものであって、通す・落とすの門には
  していない。門にすると、処理系が育つまでビルドが赤くなり<b>数を取り続けられなくなる</b>
- CCVS85 の配布元は NIST ではなく GnuCOBOL の SourceForge である。中身は NIST の
  パブリックドメインだが、元の配布は終了している。取得スクリプトは sha256 で中身を
  固定してある
- 数えているのは<b>いちばん最初に詰まったところ</b>である。1 つ直すとそのプログラムは
  次の詰まりへ進むので、理由の数が動いても合格率が動かないことがある
- 引用の中身は頭の 24 文字だけ残して刈り込む。長さは実際の出力を見て決めたものであり、
  根拠のある数ではない
- 数の一覧に<b>自分の診断</b>が並んだら、まずそれを疑う。`duplicate FD for PRINT-FILE`
  が 4 本で出たとき、検査スイートが同じ `FD` を二重に書いているとは考えにくかった。
  調べたら 2 本のプログラムが並んでおり、こちらが 1 本として読んでいた。<b>未実装の
  一覧に紛れた不具合</b>である
- 202 本を流すのに<b>10 分以上かかる</b>。構文解析が深くまで進むようになったぶん遅く
  なっており、通る本数が増えるほど延びる。要件 NFR-046 は CI で回すことを求めているので、
  どこかで速さを見る必要がある。いまは測っていない
- コンマとセミコロンを構文解析器へ渡さない扱いは、`DECIMAL-POINT IS COMMA` を
  読めるようにする段で決め直す必要がある (暫定判断 P-010)。その指定があるとコンマは
  小数点になる

**解消条件**: 翻訳が通る本数が増えたら、動かして `PASS` / `FAIL` を数える段を作る。
差し込み札は、入出力のモジュールへ手が届いた段で足す。OSS コーパスは、ライセンスを
確かめた資産から 1 件ずつ足す。ベンチマークは CI を組む段で一緒に決める。

## P-063 印字ファイルの紙送りを空行で表している

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `Ops.writeLine` |
| 関連要件 | FR-102 |

**暫定の扱い**: `WRITE ... ADVANCING` の行送りを、<b>空のレコードを足すこと</b>で表す。
`AFTER ADVANCING 2 LINES` なら空行を 1 本書いてからレコードを書く。改頁は<b>改頁の文字
だけの行</b>を置く。

**なぜこうしたか**: ホストの印字ファイルは、レコードの先頭に<b>紙送りの制御文字</b>を
持つ (RECFM の `A`)。空白なら 1 行送り、`0` なら 2 行送り、`1` なら改頁、`+` なら重ね
印字である。その形を真似ればバイト列まで合うが、<b>桁の取り方を実機で確かめていない</b>。

確かめずに 1 バイト増やすと、レコードの長さが全部ずれる。`01 PRINT-REC PIC X(120).` と
書いた資産の出力が 121 バイトになるのか 120 バイトのままなのか、宣言したレコードに制御
文字の場所が含まれるのかどうかを、当てずっぽうで決めるわけにはいかない。

空行で表す形は、<b>読んで意味が分かる</b>うえに、桁を偽らない。

**どこがずれているか**:

- 出力のバイト列がホストと合わない。行数は合うが、制御文字が無い分だけ 1 バイト短い
- `ADVANCING 0 LINES` は紙の上では<b>重ね印字</b>である。行の並びでは表せないので、
  空行を足さないだけになる。前の行が消えずに残る
- 改頁は改頁の文字 (`X'0C'`) だけの行になる。ホストは制御文字の `1` であり、行そのものは
  増えない。したがって<b>行数が 1 本多い</b>
- 頁の行数を数えていないので、`ADVANCING PAGE` を書かない限り頁は改まらない。ホストは
  紙の終わりで自動的に改頁する
- 印字ファイルかどうかを見分けていない。`ADVANCING` を書いたファイルがそうなのだと
  みなしている。ホストは `RECFM` で決まる

**解消条件**: 実機の出力データセットを 1 本採り、レコードの先頭に何が入っているか、
`LRECL` が宣言したレコードより 1 バイト長いかどうかを確かめる。そこが決まれば、制御
文字を持つ形へ移せる。移すときは、いまの空行の形を<b>読みやすさのための別の出し方</b>
として残すかどうかも決める。

## P-064 自由形式では注記段落を落とせない

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `FixedFormatReader.withoutCommentEntries` |
| 関連要件 | FR-002 |

**暫定の扱い**: 見出し部の注記段落 (`AUTHOR` / `INSTALLATION` / `DATE-WRITTEN` /
`DATE-COMPILED` / `SECURITY`) を落とすのは<b>固定形式だけ</b>である。自由形式で書けば、
いまも誤りとして報告する。

**なぜこうしたか**: 注記がどこで終わるかを決めるのは<b>桁</b>である。注記は B 領域
(12 桁目から) に書き、次に A 領域 (8〜11 桁目) から始まる行が来たら終わる。語では
決められない。実際、NIST の検査スイートの注記には `DATA` という語が入っており、
部の見出しと見分けがつかない。

```
000600 INSTALLATION.
000700     GENERAL SERVICES ADMINISTRATION
000800     AUTOMATED DATA AND TELECOMMUNICATION SERVICE.
000900 DATA DIVISION.
```

自由形式には領域が無い。COBOL 2002 以降の決まりでは<b>終止符まで</b>が注記だが、
上のように注記の中に終止符が無い行が続く書き方は移せない。書き換えの規則を決めない
まま実装すると、注記の途中で切れたものを構文解析器へ渡すことになる。

**どこがずれているか**:

- 自由形式のソースに注記段落を書くと誤りとして報告する
- 固定形式でも、注記段落の中身は<b>診断にも一覧にも残らない</b>。読んで捨てている

**解消条件**: 自由形式の資産に注記段落が現れた段で、終止符までとする規則を実装する。
実資産が固定形式ばかりであれば、そのままでよい。

## P-065 組み込み関数のうち近似が入るものを実装していない

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 (2026-09-08、値が一意に決まる 27 個を実装) |
| 場所 | `Intrinsic` / `Intrinsics` |
| 関連要件 | FR-070, FR-071 |

**実装した部分**: `LENGTH`、`UPPER-CASE`、`LOWER-CASE`、`REVERSE`、`CHAR`、`ORD`、
`MAX`、`MIN`、`SUM`、`ORD-MAX`、`ORD-MIN`、`RANGE`、`INTEGER`、`INTEGER-PART`、
`MOD`、`REM`、`FACTORIAL`、`NUMVAL`、`NUMVAL-C`、`MEDIAN`、`MIDRANGE`、
`INTEGER-OF-DATE`、`INTEGER-OF-DAY`、`DATE-OF-INTEGER`、`DAY-OF-INTEGER`、
`CURRENT-DATE`、`WHEN-COMPILED`。どれも<b>規格の定義から答えが 1 つに決まる</b>もので
ある。整数の切り方、文字の並べ替え、照合順序の位置、10 進の四則、暦の日数え。

`MEDIAN` と `MIDRANGE` が入るのは、<b>2 で割るのが 10 進では必ず割り切れる</b>から
である。小数桁が 1 つ増えるだけで近似は入らない。`MEAN` は個数で割るので入らない。

**暫定の扱い**: `SQRT`、`LOG`、`LOG10`、`EXP`、`SIN`、`COS`、`TAN`、`ASIN`、`ACOS`、
`ATAN`、`ANNUITY`、`PRESENT-VALUE`、`RANDOM`、`MEAN`、`VARIANCE`、
`STANDARD-DEVIATION` は<b>書けないと断る</b>。

**なぜこうしたか**: 要件 FR-071 が「数学関数の結果桁数・丸めは参照実装の定義に従う。
特に `SQRT` 等の中間結果桁数は、参照実装の仕様を優先し、Java の `Math` の結果を
そのまま用いない」としている。<b>その仕様をまだ持っていない</b>。

`Math.sqrt` を呼んで返せば、たいていの桁は合う。合わないのは末尾の 1 桁か 2 桁である。
そしてその 1 桁は<b>比較の結果を変える</b>。COBOL の資産は計算結果を等号で比べる。
近い値を黙って返す実装は、<b>間違いを見つけにくい形で</b>間違える。書けないと言えば、
少なくともどこで止まったかが分かる。

`MEAN` と `VARIANCE` は近似ではなく<b>結果の小数桁</b>が決まらないために入れていない。
値そのものは一意に決まるが、個数で割るときに何桁で打ち切るかは処理系の決めごとであり、
そこを決めるには同じ根拠が要る。

**どこがずれているか**:

- 上の関数を使うプログラムは翻訳できない。NIST CCVS85 の `IF` 区分 45 本のうち
  16 本がこれである
- `CURRENT-DATE` の末尾 5 文字 (協定世界時からのずれ) は時計から取っている。
  規格は「ずれが分からない処理系は `00000` を置く」としており、どちらでもよい
- 実装した関数についても、<b>結果の桁数</b>の決め方は暫定である。周りの式をどこで
  打ち切るかを決めるのに、整数を返す関数は上限の桁で数え、そうでないものは引数の
  いちばん大きいものに合わせている (`IntermediateDigits.digitsOf`)。関数が返す値
  そのものは実行時の `Decimal` が自分の小数桁を持っているので、ずれるのは
  <b>式の途中で切り捨てる位置</b>だけである
- `CHAR` と `ORD` は照合順序の位置で答える。`PROGRAM COLLATING SEQUENCE` を書けば
  答えが変わる (暫定判断 P-042)

**解消条件**: 参照実装の数学関数の仕様 (結果の桁数と丸めの規則) を公開資料から
確かめる。確かめられないうちは実装しない。
