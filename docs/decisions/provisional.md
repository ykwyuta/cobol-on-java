# 暫定対応の記録

実装を進めるうえで、正式な解決を先送りして暫定の扱いを採った箇所を記録する。
コード中のコメントからこの表の番号 (P-nnn) を参照している。

各項目には**解消条件**を明記する。「いつ直すのか分からないもの」を暫定対応として残さないためである。

| 状態 | 意味 |
| --- | --- |
| 未解決 | 暫定の扱いのまま。解消条件が満たされていない |
| 解消済 | 正式な実装に置き換わった |

---

## P-001 演算結果がゼロのときの符号

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `Decimal.fromBigDecimal` |
| 関連要件 | FR-040, FR-042, 検証レベル V1 |

**暫定の扱い**: 加減乗除の結果がゼロになった場合、符号は正 (`+1`) とする。
一方、`MOVE` 相当の経路 (`PackedDecimal.decode` → `encode`) では元の符号を保つため、
負のゼロ (`0x000D` など) はバイト列として保存される。

**なぜ暫定か**: z/Architecture の 10 進演算命令 (`AP` / `SP` / `MP` / `DP` / `ZAP`) が
ゼロ結果に与える符号の規則は命令ごとに異なる可能性があり、Principles of Operation の
記述だけでは各命令の挙動を確信をもって特定できていない。COBOL の `COMPUTE` が
どの命令列へ落ちるかによって観測結果が変わりうる。

**解消条件**: `cobol-oracle` モジュールで各命令のゼロ結果の符号ニブルを Hercules から採取し、
命令別の規則を確定させる。そのうえで演算の実装を命令単位の規則に合わせる。

## P-002 日本語コードページ IBM-1390 / IBM-1399 が未対応

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `CodePages` |
| 関連要件 | FR-051 |

**暫定の扱い**: JDK 標準のチャーセットに存在する IBM-1047 / IBM-037 / x-IBM930 / x-IBM939 のみを
提供する。IBM-1390 / IBM-1399 (JIS X 0213:2004 拡張を含む) は
`CodePages.forName` が `UnsupportedCharsetException` を投げる。
要件 FR-181 の「未実装のオプションは無視せず未対応と診断する」に従い、黙って既定へ倒すことはしない。

**なぜ暫定か**: 要件 FR-051 はこれらのコードページを対象に含めており、独自の変換表の同梱を求めている。

**解消条件**: IBM CDRA の変換表に基づく独自実装を追加し、全コードポイントの往復変換テスト
(リスク R-5 の対策) を通す。あわせて JDK の x-IBM930 / x-IBM939 と IBM の変換表の一致も検証する
(これ自体が未検証であり、P-012 として別立てで記録している)。

## P-003 NUMPROC(PFD) における不正ニブルの解釈

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `PackedDecimal.decode`, `ZonedDecimal.decode` |
| 関連要件 | FR-033, FR-205 |

**暫定の扱い**: `NUMPROC(PFD)` では妥当性検査を行わない。数字として妥当でないニブル
(0xA〜0xF) に出会った場合は、その値を 10 で割った余りを数字とみなす。

**なぜ暫定か**: これは仕様上の未定義領域であり、参照実装でも結果は保証されない。
ホストの実際の挙動は、コンパイラが生成した命令列に依存する
(例えば `PACK` を経由するか `CVB` を経由するかで異なりうる)。
現在の「10 で割った余り」という解釈には何の裏付けもない。

**解消条件**: 要件 FR-205 の 2 モード方式に組み込む。
既定 (`UndefinedBehavior.SAFE`) では検査して `DataException` を投げ、
互換モード (`MIMIC`) では Hercules から採取した実際の挙動を再現する。
現在の実装は `SAFE` / `MIMIC` の区別を持たないまま `MIMIC` 相当の動作をしており、この点が要件と乖離している。

## P-004 NUMPROC(MIG) を NOPFD と同一に扱っている

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `NumProcMode` |
| 関連要件 | FR-033 |

**暫定の扱い**: `MIG` は `NOPFD` と同じ挙動とする。

**なぜ暫定か**: 参照実装における `MIG` 固有の差異 (旧処理系との移行を目的とした符号の扱い) を
まだ調査していない。

**解消条件**: 参照実装の仕様書で `MIG` の定義を確認し、差異があれば実装を分ける。
差異がないと確認できた場合は、その根拠を記録したうえで本項目を解消済とする。

## P-005 19〜31 桁の 2 進項目 (16 バイト) が未対応

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `BinaryDecimal.byteLength` |
| 関連要件 | FR-031, FR-041 |

**暫定の扱い**: 桁数が 19 以上の 2 進項目は `UnsupportedOperationException` を投げる。
2 / 4 / 8 バイトの項目のみ対応している。

## P-006 未実装の USAGE

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `Usage` |
| 関連要件 | FR-031, FR-032 |

**暫定の扱い**: `DISPLAY` / `COMP-3` / `COMP` / `COMP-5` のみを提供する。
`COMP-1` / `COMP-2` (IBM 16 進浮動小数点)、`INDEX`、`POINTER`、`FUNCTION-POINTER`、
`NATIONAL`、`DISPLAY-1` (DBCS) は未実装。

**なぜ後回しにしたか**: P0-a の主眼は 10 進系の意味論であり、そこが最も互換性の要求水準が高く
(すべて L3)、かつ Hercules オラクルで V2 へ引き上げられる領域だからである。

**解消条件**: `COMP-1` / `COMP-2` は HFP 命令の挙動を Hercules から採取したうえで実装する
(要件 FR-032 は丸めの癖まで再現することを求めている)。その他は P0-b 以降。

## P-007 内部演算に BigDecimal を用いている

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `Decimal` |
| 関連要件 | NFR-002, NFR-005 |

**暫定の扱い**: 10 進演算の内部実装に `java.math.BigDecimal` を用いている。
負のゼロを表現できないという `BigDecimal` の制約は、符号を独立したフィールドとして
保持することで回避している。

**なぜ暫定か**: 要件 NFR-002 は「`BigDecimal` への変換をホットパスで避け、バイト列上で直接演算する
実装を優先する」としている。現在の実装はこれを満たしていない。

**なぜ今はこれでよいか**: 要件 NFR-005 は「性能のためであっても互換性を犠牲にする最適化は行わない」
としている。正しい意味論を先に確定させ、その振る舞いを固定するテストを揃えてから最適化するほうが、
逆順よりも安全である。丸めモードが `java.math.RoundingMode` の 8 モードと 1 対 1 で対応するため、
初期実装としては素性がよい。

**解消条件**: ベンチマークを整備し (NFR-001)、10 進演算がホットパスであることを実測で確認したうえで、
パック10進バイト列上の直接演算へ置き換える。置き換えの前後で全テストが同一結果になることを条件とする。

## P-009 中間結果の桁数規則が未実装

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | 該当なし (未着手) |
| 関連要件 | FR-040, FR-041 |

**暫定の扱い**: `Decimal` の演算は数学的に厳密な結果を返し、桁数の制限を課さない。
参照実装が定める「中間結果の精度」の規則 (`ARITH(COMPAT)` の 18 桁、`ARITH(EXTEND)` の 31 桁と、
式の形から中間結果の桁数を決定する規則) は実装していない。

**なぜここにないか**: 中間結果の桁数は式の構造から静的に決まるため、本来はコンパイラ側の責務である。
ランタイムは「指定された桁数で丸める」機能を提供すればよい。

**解消条件**: P0-b でコンパイラの意味解析に中間結果の桁数決定を実装する。
ランタイム側は現状のままでよいことを、その時点で再確認する。

## P-012 JDK のチャーセットと IBM の変換表の一致が未検証

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `CodePages` |
| 関連要件 | FR-051, リスク R-5 |

**暫定の扱い**: JDK の `IBM1047` / `IBM037` / `x-IBM930` / `x-IBM939` をそのまま用いており、
IBM CDRA の変換表と一致するかを検証していない。

**なぜ問題になりうるか**: リスク R-5 のとおり、変換表の微細な差異は日本語データの文字化けと
照合順序の誤りに直結する。特に混在コードページ (930 / 939) はシフトコードの扱いを含めて差異が出やすい。

**解消条件**: 全コードポイントの往復変換テストを追加し、IBM の変換表と突き合わせる。
差異があれば独自変換表へ差し替える (P-002 の作業と一体で行う)。
