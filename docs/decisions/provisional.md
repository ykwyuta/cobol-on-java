# 暫定対応の記録

実装を進めるうえで、正式な解決を先送りして暫定の扱いを採った箇所を記録する。
コード中のコメントからこの表の番号 (P-nnn) を参照している。

各項目には**解消条件**を明記する。「いつ直すのか分からないもの」を暫定対応として残さないためである。

| 状態 | 意味 |
| --- | --- |
| 未解決 | 暫定の扱いのまま。解消条件が満たされていない |
| 解消済 | 正式な実装に置き換わった |

## P-001 演算結果がゼロのときの符号

| 項目 | 内容 |
| --- | --- |
| 状態 | **解消済** (2026-09-03、Hercules による V2 検証で決着) |
| 場所 | `Decimal.fromBigDecimal`, `Decimal.withAlgebraicSign` |
| 関連要件 | FR-040, FR-042, 検証レベル V2 |

**当初の暫定の扱い**: すべての演算でゼロ結果に正号を与えていた。

**実測で判明したこと**: Hercules 上で各命令を実行した結果、**ゼロ結果の符号は命令ごとに規則が異なる**。
これは Principles of Operation の記述からは読み取れなかった点であり、暫定のままでは
乗除算で誤ったバイト列を生成していた。

| 命令 | ゼロ結果の符号 | 実測例 |
| --- | --- | --- |
| `AP` / `SP` | **常に正**。オペランドが両方とも負のゼロでも正になる | `000D` + `000D` → `000C` |
| `ZAP` | ゼロは**正へ正規化**。非ゼロは元の符号を保つ | `000D` → `000C`、`005D` → `005D` |
| `MP` | **代数の規則どおり**。負のゼロが生じる | `0000000C` x `5D` → `0000000D` |
| `DP` | **代数の規則どおり**。商・剰余ともに負のゼロが生じる | `0000000D` ÷ `5C` → 商 `00000D`、剰余 `0D` |

**行った修正**: `Decimal.multiply` / `divide` / `remainder` を、結果がゼロでも代数の符号を
保つように変更した (`withAlgebraicSign`)。加減算は従来どおりゼロ結果に正号を与える。
剰余の符号は被除数に従う。

**裏付け**: `DecimalArithmeticOracleTest` (検証レベル V2)。
Hercules 上での実行結果とランタイムの出力をバイト列で突き合わせている。

## P-003 NUMPROC(PFD) における不正ニブルの解釈

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `PackedDecimal.decode`, `ZonedDecimal.decode` |
| 関連要件 | FR-033, FR-205 |

**暫定の扱い**: `NUMPROC(PFD)` では妥当性検査を行わない。数字として妥当でないニブル
(0xA〜0xF) に出会った場合は、その値を 10 で割った余りを数字とみなす。

**なぜ暫定か**: これは仕様上の未定義領域であり、参照実装でも結果は保証されない。
ホストの実際の挙動は、コンパイラが生成した命令列に依存する
(例えば `PACK` を経由するか `CVB` を経由するかで異なりうる)。
現在の「10 で割った余り」という解釈には何の裏付けもない。

**解消条件**: 要件 FR-205 の 2 モード方式に組み込む。
既定 (`UndefinedBehavior.SAFE`) では検査して `DataException` を投げ、
互換モード (`MIMIC`) では Hercules から採取した実際の挙動を再現する。
現在の実装は `SAFE` / `MIMIC` の区別を持たないまま `MIMIC` 相当の動作をしており、この点が要件と乖離している。

## P-007 内部演算に BigDecimal を用いている

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `Decimal` |
| 関連要件 | NFR-002, NFR-005 |

**暫定の扱い**: 10 進演算の内部実装に `java.math.BigDecimal` を用いている。
負のゼロを表現できないという `BigDecimal` の制約は、符号を独立したフィールドとして
保持することで回避している。

**なぜ暫定か**: 要件 NFR-002 は「`BigDecimal` への変換をホットパスで避け、バイト列上で直接演算する
実装を優先する」としている。現在の実装はこれを満たしていない。

**なぜ今はこれでよいか**: 要件 NFR-005 は「性能のためであっても互換性を犠牲にする最適化は行わない」
としている。正しい意味論を先に確定させ、その振る舞いを固定するテストを揃えてから最適化するほうが、
逆順よりも安全である。丸めモードが `java.math.RoundingMode` の 8 モードと 1 対 1 で対応するため、
初期実装としては素性がよい。

**解消条件**: ベンチマークを整備し (NFR-001)、10 進演算がホットパスであることを実測で確認したうえで、
パック10進バイト列上の直接演算へ置き換える。置き換えの前後で全テストが同一結果になることを条件とする。

## P-008 英数字編集 (ALPHANUMERIC_EDITED) の編集処理が未実装

| --- | --- |
| 状態 | **解消済** (2026-09-03) |
| 場所 | `AlphanumericEditor` |
| 関連要件 | FR-030, FR-060 |

`AlphanumericEditor` を実装した。送出データを `A` / `X` の文字位置へ左から順に詰め、

## P-013 COBOL の MOVE がパック10進の負のゼロを保つかどうか

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `NumericItem.encode` / `decode` (ランタイム側)、コンパイラ側は未着手 |
| 関連要件 | FR-020, FR-060 |

**判明したこと**: P-001 の検証の副産物として、`ZAP` 命令が**負のゼロを正のゼロへ正規化する**ことが
分かった (`000D` → `000C`)。一方 `MVC` は単なるバイト転記なので符号ニブルをそのまま保つ。

したがって COBOL の `MOVE` がパック10進の負のゼロを保つかどうかは、
**コンパイラがどちらの命令を生成するかで決まる**。参照実装は、送出側と受取側の PICTURE が
同一なら `MVC`、異なるなら `ZAP` を生成すると考えられるが、未確認である。

**現在のランタイムの扱い**: `NumericItem` の復号・再符号化は符号を保つ (`MVC` 相当)。

**なぜ重要か**: 負のゼロを含むバイト列が `MOVE` を通ったときに変化するかどうかは、
出力ファイルのバイト列に直接現れる。要件 FR-020 の L3 互換の対象である。

**解消条件**: 参照実装が `MOVE` に対してどの命令を生成するかを、PICTURE と USAGE の
組み合わせごとに確定させる。実機のコンパイラリストが得られないため、
仕様書の記述と、生成コードとして自然な選択の両面から決め、
コンパイラ (P0-b) の実装時に方針を固定する。ランタイム側は両方の意味論を提供できるよう、
`MVC` 相当 (符号保持) と `ZAP` 相当 (ゼロを正規化) を別の関数として用意する。

## P-014 数値編集の一部が V2 の裏付けを持たない

| 項目 | 内容 |
| --- | --- |
| 状態 | **一部解消** (2026-09-03、浮動挿入を `EDMK` で検証)。固定符号と全桁抑制は未解決 |
| 場所 | `NumericEditor` / `EditMask` |
| 関連要件 | FR-030、検証レベル V2 |

**解消した部分: 浮動挿入**

平の `ED` では浮動挿入を表現できない。記号を置く位置が値によって変わるためである。
`EDMK` は `ED` と同じ編集を行ったうえで<b>最初の有効数字の位置</b>を汎用レジスタ 1 に残す。
そこから 1 を引いた位置へ記号を書き込めば浮動挿入になる。

```
LA   1,<有意性開始子の 1 つ後ろ>   値がゼロで EDMK がレジスタを更新しない場合に備える
EDMK マスク,ソース                 編集し、最初の有効数字の位置をレジスタ 1 へ
BCTR 1,0                          1 つ手前へ
MVI  0(1),記号                     そこへ記号を書き込む
```

この命令列で `$$$,$$9.99`、`$$$9.99`、`$$$$9`、`----9`、`---9.99`、`+++9.99` の
6 種 x 値 9 種の 54 件が `NumericEditor` と一致した。

記号そのものの選択 (`+` なら符号に応じて `+` / `-`、`-` なら負のときだけ `-`) は
検証では Java 側で決めている。実機側で分岐させるには条件分岐命令が必要であり、
検証の焦点である<b>記号を置く位置</b>とは別の話であるためである。位置は完全に実機が決めている。

**残っている部分**

| 機能 | なぜまだ V2 にできないか |
| --- | --- |
| 固定符号 (`+9(4)`、`-9(4)`) | 符号の位置は固定なので `ED` の後に `MVI` で書けばよいが、抑制位置を持たない PICTURE は `ED` 自体が使えない (参照実装は `UNPK` と挿入で処理していると考えられる) |
| 全桁が抑制対象の PICTURE (`ZZZZ`、`****`、`***.**`) | 「値がゼロなら項目全体を抑制する」という COBOL 固有の規則を持ち、`ED` 単独では実現されていないと考えられる |
| `BLANK WHEN ZERO` | 同上 |

**なぜ重要か**: 特に全桁抑制の PICTURE については、`***.**` に値ゼロを編集した結果が
`"***.**"` なのか `"***.00"` なのか `"******"` なのかが仕様の読み方で分かれる。
現在の実装は `"***.**"` を返すが、裏付けがない。

**解消条件**: 参照実装がこれらの PICTURE に対してどの命令列を生成するかを確定させる。
確定できれば同じ命令列を `cobol-oracle` で組み立てて実行し、V2 へ引き上げる。

## P-015 符号ニブルの正規化のタイミング

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `PackedDecimal.encode`, `ZonedDecimal.encode` |
| 関連要件 | FR-031, FR-033 |

**実測で判明したこと**: `PACK` 命令は**符号ニブルをそのまま移す**。ゾーン10進の最右端バイトの
ゾーンが `F` なら、パック10進の符号ニブルも `F` になる。`A` なら `A`、`B` なら `B` のままである。
優先符号 (`C` / `D`) への正規化は行われない。

**現在のランタイムの扱い**: `PackedDecimal.encode` は符号を解釈したうえで、常に優先符号
(`C` / `D`、符号なし項目は `F`) を書き出す。したがって `F` / `A` / `B` の符号を持つ入力に対して、
`PACK` の結果とはバイト列が一致しない。

**どちらが正しいか**: これは命令の挙動ではなく<b>コンパイラが何を生成するか</b>で決まる。
`NUMPROC(NOPFD)` では参照実装は符号を正規化するコードを生成し、`NUMPROC(PFD)` では
正規化を省くとされている。つまり `MOVE` の結果のバイト列は `NUMPROC` の指定に依存する。

現在の実装は常に正規化する (`NOPFD` 相当) が、`NUMPROC(PFD)` を指定した場合に
正規化を省くべきかどうかを実装に反映していない。

**なぜ重要か**: 正規化の有無は出力ファイルのバイト列に直接現れる。要件 FR-020 の L3 互換の対象である。

**解消条件**: 参照実装がこの PICTURE に対して生成する命令列を確定させる。

## P-029 PERFORM を段落のメソッド呼び出しで実装している

| 項目 | 内容 |
| --- | --- |
| 状態 | **解消済** (2026-09-04、段落が「次の行き先」を返す形にして `GO TO` を実装) |
| 場所 | `ProgramGenerator.emitParagraph` / `emitDispatch` / `emitPerformMethod` |
| 関連要件 | FR-061 |

**当初の暫定の扱い**: 段落をそれぞれ別のメソッドとして出し、素直に流れる実行は上から順に
呼び、`PERFORM P` は P のメソッドだけを呼ぶ形にしていた。この形なら「`PERFORM` は次の
段落へ流れ込まない」という規則が自然に出るが、<b>`GO TO` が書けない</b>のが難点であった。
段落の並び全体を 1 つのメソッドにして分岐で書くか、状態機械へ変えるしかないと考えていた。

**実際に採った形**: メソッドのままでよかった。変えたのは 1 点だけである。

<b>段落のメソッドが「次にどこへ行くか」を返す</b>ようにした。最後まで流れたら `-1`、
`GO TO` で飛ぶならその段落の番号である。`GO TO` は素直な `return` になり、段落の途中でも
入れ子の `IF` や `PERFORM` の中でも、その場で抜けられる。

呼ぶ側は「段落の範囲を実行する」1 つのメソッド (`performRange`) にまとめた。素直に流れる
実行は「全段落を 1 つの範囲として実行する」ことであり、`PERFORM A THRU B` と同じ機構で書ける。
違いは範囲の終わりがどこかだけである。飛び先は実行時にしか分からないため、番号から段落の
メソッドへ振り分ける表引きの分岐 (`dispatch`) を挟んでいる。

**なぜ状態機械にしなくて済んだか**: 状態機械が要ると考えたのは、`PERFORM` の戻り先が
<b>段落の途中</b>にあるためであった。段落を区切り直して番号を振る話になり、大掛かりになる。
しかし戻り先を JVM の呼び出し規約に預けてしまえば、番号を振る必要があるのは
<b>飛び先だけ</b>である。飛び先は段落の先頭しかないので、段落の番号がそのまま使える。

**参照実装との差**: 参照実装は範囲ごとに戻り口を 1 つ持つため、同じ範囲を入れ子に
`PERFORM` すると戻り口が壊れる。こちらは JVM の呼び出しスタックを使うので壊れない。
仕様が結果を保証しない領域であり、こちらのほうが安全側である (要件 FR-205 の考え方)。

`EXIT` も実装した (何もしない文である)。
`PERFORM VARYING` … `AFTER` … は先に実装してあった。段の増減は繰り返しの<b>指定</b>の
話であり、中身をどう呼ぶかとは独立なので、この暫定の扱いに縛られなかった。

**残っている形**: `GO TO ... DEPENDING ON` と `ALTER` は文法が受け付けない。

- VSAM の制御情報そのものは再現していない。制御区間 (CI) の大きさや空き領域の配置は

## P-042 照合順序を差し替えられない

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `SortWork.compare` / `IndexedDataSet.ByteKey` / `SpecialNames` |
| 関連要件 | FR-054, FR-100, FR-120 |

**暫定の扱い**: 英数字の比較は<b>コードページの照合順序</b>に固定している。

**なぜこうしたか**: 字面まで真似ると、<b>本物と見分けがつかないものが出てくる</b>。
ホストのダンプを読む解析道具が、この実装の出力を本物として読んで誤った結論を出しうる。
出所が分かる形にしておくほうが安全である。

`UAxxx` の 4 つは「利用者が受け止めなかった異常だけ」を区別するものだが、この実装では
受け止め手の有無で打ち切るかどうかがすでに決まっているため、区別する意味がない。

**どこがずれているか**:

- 見出し行は `CEE3250C` を借りているが、続く行の並びは違う
- 記憶域の 1 行は 16 バイトである。ホストは 32 バイトである
- スレッドやエンクレーブの情報が無い。この実装には対応するものが無い

**解消条件**: 実資産の運用でホストの書式を前提とした道具が使われていることが分かったら、
そのときに揃える。揃えるなら「これは本物ではない」と分かる印を残す。

## P-052 領域不足の異常終了コードを 1 つにまとめている

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `FileOperationException.abendCode` / `Jcl` の `SPACE=` |
| 関連要件 | FR-141 |

**暫定の扱い**: 書ける領域を使い切ったことを、すべて `S037` にしている。また
`SPACE=(TRK,...)` と `SPACE=(CYL,...)` を、3390 のトラック 56664 バイト・シリンダ 15
トラックとして数えている。

**なぜこうしたか**: ホストは領域に関する異常終了をいくつかに分けており、ボリュームに
空きが無い、一次割当を使い切って二次割当が無い、これ以上エクステントを取れない、といった
区別がある。<b>この区別を裏付ける手段が無い</b>。要件 (FR-141) が名指しているのは `S037`
だけであり、裏付けの無い区別を作るより、名指されたコード 1 つに寄せるほうが誠実である。

装置の大きさも同じで、実際の装置を持たない以上どこかで決めるほかない。3390 を採ったのは
いちばん広く使われているからである。

**いま危ないこと**: 実資産が `IF ABENDCC = B37` のように<b>領域不足の種類で分岐</b>して
いると、その枝は通らない。また `SPACE=(TRK,(1))` で止まる位置がホストと 1 レコード単位で
食い違いうる。ブロック化 (`BLKSIZE`) を見ていないためである。

**解消条件**: 領域不足の分類は、実資産で `B37` / `D37` / `E37` を見分ける必要が出た時点で
決める。装置の大きさは、データセットの物理表現を選べるようにする段 (暫定判断 P-039) で
装置の記述を持てるようになったときに、そこへ移す。

## P-053 領域の限りと形の検査が順編成にしか効かない

| 項目 | 内容 |
| --- | --- |
| 状態 | 未解決 |
| 場所 | `SequentialDataSet` / `RelativeDataSet` / `IndexedDataSet` / `Records` |
| 関連要件 | FR-141 |

**暫定の扱い**: 「割り当てた領域を使い切ったら書けない」ことと「形が壊れていたら読めない」
ことを、順編成にだけ実装した。相対編成と索引編成は `SPACE=` を無視し、半端なバイトが
残っていても気付かない。ジョブのユーティリティ (`IEBGENER` / `SORT` / `ICETOOL`) も
同じで、これらは `Records` でバイト列を切るが形を検めない。

**なぜこうしたか**: 実資産のバッチが読み書きするものの大半は順編成であり、そこから始める
のが効く。相対編成と索引編成は自前の制御情報 (空きスロット、索引) をサイドカーに持って
おり、「形が壊れている」の意味がそれぞれ違う。<b>1 つずつ決めるべきことを、まとめて
決めない</b>。

**いま危ないこと**: 相対編成や索引編成のデータセットが途中で切れていると、黙って短い
レコードを渡す。ユーティリティも同じで、壊れたデータセットを写して<b>正常終了する</b>。

**解消条件**: 位置を持って読み書きする形へ改める段 (暫定判断 P-038) で、編成ごとに
決める。ユーティリティは `Records` を順編成の実装へ寄せたときに一緒に効くようにする。
